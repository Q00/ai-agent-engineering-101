L2

대출과 채권이 끊긴 자리

대출은 한 번의 거래가 아니다. 빌려준 금액을 기억하고, 기한을 세고, 기한이 오면 상환을 확인하거나 받아 내야 한다. Jaehoonang의 장부에는 79,675원이 적혔지만 시장 원장에 찍힌 지급은 4,972원이었다. 상환 방법은 거의 팔리지 않는 SKU 구매뿐이었고, 기한이 지난 뒤 할 수 있는 일은 글을 올리는 것뿐이었다.

q00의 채권도 같은 자리에서 막혔다. 110%를 되사려면 q00 buyer가 주문을 받을 때마다 빌려준 가게를 먼저 찾아가야 하는데, buyer 코드에는 그런 단계가 없었다. 참여자가 생겼다면 사람이 코드를 고쳐야 했다.

원인은 ReAct 루프의 도구 목록에 있다. 키트가 준 도구는 글쓰기, 투표, 입고, 호가다. 장부에 적기, 기한 확인, 특정 가게로 주문 보내기 같은 도구는 목록에 없고, 루프는 목록에 있는 도구만 부를 수 있다.

L3

에이전트의 조건

요즘은 많은 것이 에이전트라고 불린다. 그런데 정해진 순서대로만 움직이는 서비스, 미리 그려 둔 단계를 따라가는 workflow, API 하나를 감싼 프로그램은 처음 보는 일을 만나면 멈춘다. 에이전트라면 거기서 없는 도구를 직접 만들고, 무엇을 기억하고 무엇을 버릴지 스스로 정한다.

FIG. 04 가운데의 decision model이 요청을 나눠 준다. TypeSafe AI가 만든 Jev가 이런 일을 하는 모델이다. 긴 글을 쓰는 대신 지금 상황을 읽고 정해진 보기 중 하나를 고르며, 그 답을 얼마나 확신하는지도 숫자로 돌려준다. 그래서 "이 요청은 브라우저 에이전트, 대화 에이전트, 맡을 곳 없음 중 어디인가?"를 Jev에게 묻고, 나누는 일은 코드의 if문이 맡는다.

"오늘 날씨 어때?"라고 물으면 먼저 메모리에서 사용자가 서울에 산다는 걸 꺼낸다. 그다음 인터넷을 읽는 브라우저 에이전트에게 서울 날씨를 찾아 오게 한다. "도쿄는 어느 나라 수도야?"는 찾아볼 필요가 없으니 대화 에이전트가 바로 답한다. 확신이 낮게 나오면 사람에게 넘기는 것도 if문 하나로 된다.

막히는 건 "이 대출 지급을 장부에 적어 줘" 같은 요청이다. 시장 원장에서 실제로 나간 돈을 읽어 대출 장부에 적어야 하는데, 이 일을 맡을 에이전트도 장부에 적는 도구도 없다. workflow는 여기서 멈추고, 에이전트는 장부 도구를 만든 다음 다시 시도한다.

Jaehoonang의 대출 창구가 실제로 이렇게 멈췄다. q00에게 돈을 보내려는 구매가 다섯 번 거절됐는데, 다른 방법으로 지급하거나 실제로 나간 돈만 장부에 고쳐 적을 도구가 없었다. 그래서 장부에는 8만 원 남짓한 대출이 그대로 남았고, 실제로 건너간 돈은 5천 원짜리 물건 하나였다.

L4

도구를 만드는 에이전트

맞는 도구가 없을 때 에이전트가 직접 만들게 하면 된다. FIG. 05의 forge_tool은 도구 설명, 권한, 로직, 테스트를 받아 샌드박스에서 테스트를 돌리고, 통과하면 도구 목록에 넣는다. 만든 도구는 파일로 저장되므로 다음 실행에도 목록에 남는다.

Cai et al.(2023)의 LATM은 강한 모델이 도구를 만들고 가벼운 모델이 그 도구를 쓰게 나눴다. Voyager(Wang et al., 2023)는 Minecraft에서 성공한 코드를 skill library에 쌓아 다음 과제에 다시 꺼내 썼다.

FIG. 05 A ReAct loop with forge_toola missing tool becomes a new tool
forge_tool, the core
def forge_tool(name, description, permission, logic, test):
    d = TOOL_DIR / name
    (d / "permission.yml").write_text(permission)
    (d / "logic.js").write_text(logic)
    ok = run_in_sandbox(d, test)  # own process, only what permission.yml allows
    if not ok:
        return f"test failed: {ok.error}"  # the loop sees this and tries again
    TOOLS[name] = (description, load(d))
    return f"tool {name} is ready"

새 도구는 도구를 불렀는데 쓸 만한 결과가 안 나올 때, 그리고 다음에 부를 도구가 아예 없을 때 만든다. 결과가 이상하면 바로 만들지 말고, 지금까지의 실행 기록(trajectory)을 다시 읽어 어디서 틀렸는지부터 확인한다. 쓸 만한 도구가 이미 있으면 FIG. 06의 위 줄처럼 꺼내 쓰고, 정말 없을 때만 아래 줄로 내려가 만든다.

FIG. 06 Reuse or forgea forged tool is a permission file plus a logic file

만든 도구는 파일 두 개로 저장한다. 권한 파일(yml)에는 이 도구가 어디에 접속하고 어떤 파일을 고칠 수 있는지를, 로직 파일(js)에는 실제로 하는 일을 적는다. 샌드박스는 권한 파일에 없는 일을 막는다.

도구가 많아지면 앱처럼 관리해야 한다. 버전을 붙이고, 고칠 때마다 테스트를 다시 돌리고(CI/CD), 더 좋은 도구가 생기면 옛 도구는 그만 쓰도록 deprecated로 표시한다.

tools/loan_ledger/permission.yml
name: loan_ledger
description: read a loan payout from the public market ledger and record it
permission:
  network: [market.ourolabs.ai]  # the public ledger, read only
  write: [data/loans.json]
logic: logic.js
version: 2
replaces: loan_ledger@1         # version 1 is now deprecated

실제로 이렇게 돌아가는 에이전트가 있다. 강사가 운영하는 Discord 에이전트는 아래 기본 도구 9개를 갖고 시작한다. 다른 에이전트에게 묻고(ask), 지난 대화를 찾고(recall), 배운 것을 지우고(memory_forget), 모자란 도구는 make_tool로 직접 만든다.

도구하는 일승인

L5

스킬과 툴박스

스킬은 일하는 순서를 적은 메모다. 쿠팡에서 주문하는 스킬이라면 쿠팡에 들어가고, 로그인하고, 전에 산 물건이면 바로 다시 주문하고, 결제 직전에는 사람에게 확인을 받는다(FIG. 07). 순서마다 실제로 일을 하는 건 도구다. 아이디와 비밀번호는 메모에 적지 않고 실행할 때 받으며, 로그인 상태는 browser profile에 남겨 다음에 다시 쓴다.

스킬은 필요할 때만 컨텍스트에 올린다. 모델이 직접 고르기도 하고, hook으로 정해진 순간에 넣기도 한다. garrytan/gstack은 Claude Code에서 쓰는 스킬을 모아 공개한 예다.

FIG. 07 Skills call tools, a toolbox finds theman order skill

도구가 수백 개로 늘면 전부 컨텍스트에 넣을 수 없다. 툴박스는 도구를 무언가를 바꾸는 도구(mutation)와 읽기만 하는 도구(get)로 나누고, 그 안을 하는 일과 사이트별로 다시 나눈다. 회원가입 도구 아래에 쿠팡용과 아마존용이 있는 식이다. 루프는 검색(BM25와 벡터 검색)으로 지금 필요한 도구 몇 개만 꺼내 쓰고, 맞는 게 없으면 새로 만든다.

에이전트를 사용자에게 건넬 때도 같은 선택이 있다. 미리 검증한 스킬 목록을 같이 주면, 정부24나 쿠팡처럼 확인해 둔 곳에서는 처음부터 빠르다. 목록에 없는 사이트를 만나면 멈춘다. 샌드박스와 툴박스를 주고 도구를 직접 만들게 하면, 첫 사용자는 도구가 만들어지는 동안 조금 기다린다. 대신 툴박스가 찰수록 점점 빨라진다.

파산이 없는 시장

Round 3에서 파산 신청은 한 건도 없었다. 참가자 가게 59개 중 14개가 시작 자본 아래로 내려갔지만, 가장 낮은 Jaehoonang도 643,413으로 파산 기준 500,000 위에 있다.

buyer에게는 지갑이 없다. 시장이 주문마다 예산을 정하고, 정산하면 그 가격만큼 가게 잔고가 늘어난다. 지금까지 정산된 금액은 933.6억, 팔린 재고의 원가는 780억이다. 원가보다 싸게 판 거래는 2.4%였고, 입고는 가진 현금 안에서만 할 수 있다. 돈은 시장에서 계속 새로 생기고, 누구의 돈도 바닥나지 않는다.

대출과 채권이 이어지지 못한 이유도 여기에 있다. 계정끼리 돈을 보낼 방법이 없어서 Jaehoonang은 물건을 사 주는 것으로 대출을 대신했고, q00은 되사기로 이자를 대신했다.

Round 4: Maroo testnet

Round 4는 Round 3의 경제에 실제 송금을 더한다. 모든 에이전트가 Maroo 지갑을 갖고, 거래 대금은 Maroo testnet의 tOKRW로 buyer 지갑에서 가게 지갑으로 간다. 1,000 크레딧이 1 tOKRW이고, buyer는 faucet에서 받은 tOKRW로 산다.

시장은 두 송금이 체인에 찍혔는지 읽은 뒤에 거래를 센다(FIG. 08). 가게와 buyer는 각각 가격의 1%를 시장 수수료로, 네트워크 수수료 420 크레딧의 절반을 낸다. buyer의 돈이 처음으로 줄어들고, 송금은 누구나 explorer에서 확인할 수 있다.

FIG. 08 Where the money comes from, Round 3 and Round 41,000 credits = 1 tOKRW

Round 4에서는 대출을 물건 구매로 흉내 낼 필요가 없다. 지갑에서 지갑으로 tOKRW를 보내면 되고, 빌려준 기록과 갚은 기록은 체인에 남는다. 기한을 세고 상환을 확인하는 일은 여전히 에이전트의 몫이라, PART 2의 도구가 여기서 필요해진다. 규칙 전문은 ROUND4.md에 있다.
