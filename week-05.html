A1

MCP의 구조: host, client, server

1주차 에이전트는 모델에게 넘기는 도구 설명과 인자 형식(TOOLS)도, 실제로 실행되는 함수(TOOLS_IMPL)도 에이전트 코드 안에 갖고 있었다. 그래서 도구를 하나 늘리려면 에이전트를 고쳐야 하고, 같은 read_file을 Claude Code나 Codex에서 쓰려면 그 애플리케이션용으로 다시 만들어야 한다. 애플리케이션이 M개, 도구가 N개면 연결 코드가 M×N개 필요하다.

Anthropic은 2024년 11월 25일 Model Context Protocol을 공개했다. 도구를 별도 프로그램인 server로 떼어 내고, 애플리케이션과 server가 주고받는 메시지의 형식을 정했다. 도구를 만드는 사람은 이 형식에 맞춰 server를 한 번 만들고, 애플리케이션을 만드는 사람은 이 형식에 맞춰 client 코드를 한 번 쓴다. 그러면 필요한 코드가 M+N개로 줄어든다.

FIG. 01 M × N adapters become M + N implementationsthe protocol sits between hosts and tools

host는 사용자가 쓰는 애플리케이션이다. Claude Code, Codex, Cursor, 그리고 실습에서 고칠 1주차 루프가 host다. host는 모델을 부르고, 모델이 도구를 쓰겠다고 하면 그 도구를 대신 실행한다. client는 host 안에서 server 하나와의 연결을 맡는 코드다. host가 server 셋을 쓰면 client도 셋이다. server는 도구와 데이터를 정해진 형식으로 내놓는 프로그램이다. 연결마다 client가 따로 있으므로, 어떤 방식으로 연결하는지, 어떤 API 키를 쓰는지, 오류가 났는지도 연결마다 따로 관리된다.

FIG. 02 Host, client, serverthe host runs the model; each client talks to one server

server가 내놓는 것(primitive)은 tools, resources, prompts다. 규격은 이것들을 누가 쓰기로 정하는지에 따라 나눈다.

primitive무엇인가누가 고르는가
tools모델이 부르는 함수. 파일 쓰기처럼 바깥 상태를 바꿀 수 있다model-controlled
resources모델 입력(컨텍스트)에 넣는 데이터. 파일 내용, 레코드application-controlled
prompts사용자가 골라 쓰는 템플릿user-controlled

MCP는 host가 외부 server의 tools, resources, prompts를 찾아 쓰는 JSON-RPC 규격이다.

Model Context Protocol Specification, 현재 버전 2026-07-28. 규격은 2025년 12월 9일 Anthropic에서 Linux Foundation 산하 Agentic AI Foundation(AAIF)으로 넘어갔다. AAIF는 Anthropic, Block, OpenAI가 공동 설립했다.

tool 하나에는 이름, 무엇을 하는지 적은 자연어 설명, 어떤 인자를 받는지 적은 JSON Schema가 있다. host는 연결된 server들의 tool 목록을 모델에게 넘기고, 모델은 설명을 읽고 어떤 tool을 어떤 인자로 부를지 정한다. 3주차 Contract Net에 대면 설명은 contractor의 bid에, 낙찰을 정하는 manager는 host의 모델에 해당한다. 다만 bid는 작업마다 새로 냈지만, 설명은 server가 한 번 적어 두면 모든 요청에 똑같이 쓰인다. 3주차의 overconfident contractor에 해당하는 것은 설명을 부풀린 server이고, 그런 설명을 걸러 내는 단계는 규격에 없다.

A2

JSON-RPC 메시지와 transport, stateless 규격

host와 server가 주고받는 메시지는 JSON이고, 어느 칸에 무엇을 적을지는 JSON-RPC 2.0이라는 형식으로 정해져 있다. 요청에는 요청 번호(id), 부를 기능(method), 넘길 값(params)을 적는다. 응답에는 같은 번호(id)와 결과(result)나 오류(error)를 적는다. 실습에서 만들 server를 HTTP로 띄우면 터미널에서 curl 명령으로 직접 요청을 보낼 수 있다. 아래는 tools/list 요청과 응답이다. 응답의 tool 목록은 첫 항목만 남겼다.

tools/list, Streamable HTTP, week01-tools server
# request
POST /mcp
Mcp-Method: tools/list
MCP-Protocol-Version: 2026-07-28

{"jsonrpc": "2.0", "id": 2, "method": "tools/list",
 "params": {"_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
                      "io.modelcontextprotocol/clientCapabilities": {}}}}

# response
{"jsonrpc": "2.0", "id": 2, "result": {"resultType": "complete", "ttlMs": 0, "cacheScope": "private",
 "tools": [{"name": "calculator",
            "description": "Evaluate an arithmetic expression such as '3 * (4 + 5)'. Numbers and + - * / ** only.",
            "inputSchema": {"type": "object", "properties": {"expression": {"type": "string"}},
                            "required": ["expression"]}},
           ...]}}

server 코드에서 함수 인자에 붙인 타입(expression: str)이 inputSchema가 되고, 함수 첫 줄의 설명 문자열(docstring)이 description이 된다. 1주차에서 손으로 적던 TOOLS 항목과 같은 내용이다. 모델이 calculator를 부르기로 하면 host는 tools/call을 보낸다.

tools/call
# request (Mcp-Method: tools/call, Mcp-Name: calculator)
{"jsonrpc": "2.0", "id": 3, "method": "tools/call",
 "params": {"name": "calculator", "arguments": {"expression": "48000+9500"}, "_meta": {...}}}

# response
{"jsonrpc": "2.0", "id": 3, "result": {"content": [{"type": "text", "text": "57500"}],
 "isError": false, "resultType": "complete", "structuredContent": {"result": "57500"}}}

host와 server가 메시지를 주고받는 방식을 transport라 한다. stdio에서는 host가 server 프로그램을 직접 실행하고, 그 프로그램의 표준 입력으로 요청을 넣고 표준 출력으로 응답을 읽는다. 표준 입력과 표준 출력은 터미널에서 프로그램이 글자를 받고 내보내는 통로다. host와 server가 같은 컴퓨터에 있을 때 쓰는 방식이고, API 키 같은 비밀값은 1주차처럼 환경 변수로 넘긴다.

MCP-METHOD, MCP-NAMEHTTP로 보낼 때는 모든 요청에 Mcp-Method 헤더를 붙이고, tools/call이면 tool 이름을 Mcp-Name에도 적는다. 헤더가 빠지거나 본문과 다르면 server는 400(HeaderMismatch)으로 거절한다. server 앞에서 요청을 나눠 주거나 걸러 내는 장비(load balancer, gateway)가 JSON을 열지 않고도 어떤 tool 호출인지 알 수 있게 하려는 규칙이다.

Streamable HTTP에서는 server가 웹 서버처럼 주소 하나(보통 /mcp)를 열어 두고, host가 요청마다 그 주소로 POST를 보낸다. 응답은 JSON 하나로 한 번에 오거나, SSE로 여러 조각에 나눠 온다. server가 다른 컴퓨터에 있거나 여러 사용자가 같이 쓸 때 이 방식을 쓴다. 규격의 로그인과 권한 확인 절차(authorization)도 HTTP 방식에만 있다. tools/list의 뜻은 어느 방식이든 같다.

현재 규격(2026-07-28)에서 server는 앞선 요청을 기억하지 않는다. 그래서 요청 하나에 필요한 정보를 모두 담아 보낸다. 위 tools/list 요청의 _meta에 들어 있는 규격 버전과 client 기능 목록이 그런 정보다. 협상 한 판처럼 여러 번의 호출에 걸친 일은 server가 번호(handle)를 만들어 돌려주고, client가 다음 호출마다 그 번호를 tool 인자로 같이 보낸다. 과제의 negotiation_id가 이 번호다.

A3

Elicitation과 sampling: server가 도중에 되물을 때

tool을 실행하던 server에게 정보가 더 필요할 때가 있다. 달력 server가 일정을 넣다가 어느 달력에 넣을지 물어야 하거나, 사용자의 Google 계정에 접근할 허락을 받아야 하는 경우다. 2026-07-28 규격에서 server는 이럴 때 최종 결과 대신 입력이 더 필요하다는 결과(resultType: "input_required")를 돌려준다. client는 필요한 것을 받아 온 뒤 원래 요청을 다시 보낸다. 앞의 tools/list 응답에 있던 "resultType": "complete"가 최종 결과라는 표시다. 규격은 이 방식을 Multi Round-Trip Requests라 부른다.

server가 사용자에게 묻는 기능이 elicitation이다. form 방식에서는 server가 받고 싶은 항목을 보내고, client가 그 항목으로 입력 창을 그린다. 창에는 어느 server가 묻는지 보여야 하고, 사용자는 보내기 전에 답을 고치거나 거절할 수 있어야 한다. form으로 비밀번호, API 키, 토큰, 결제 정보를 물어서는 안 된다.

그런 정보가 필요하면 URL 방식을 쓴다. server가 주소 하나를 보내면, client는 “calendar-server가 accounts.google.com을 열려고 한다”처럼 목적지를 보여 주고 동의를 받은 뒤 브라우저를 연다. 사용자는 브라우저에서 Google에 로그인하고 권한을 허락한다. 이때 입력한 내용은 client를 거치지 않는다. client가 아는 것은 사용자의 선택, 곧 accept(열기), decline(거절), cancel(그냥 닫음) 가운데 하나뿐이다. URL 방식은 2025-11-25 규격에서 들어왔다.

FIG. 05 Elicitation: form mode and URL modethe user can always decline

client가 MCP server에 접속할 권한은 OAuth로 따로 받는다(A4). URL 방식은 server가 사용자를 대신해 Google 달력 같은 다른 서비스의 허락을 받아야 할 때 쓴다.

sampling은 방향이 반대다. server가 client의 모델을 빌려 쓰는 기능으로, server가 “이 글을 요약해 달라”는 요청을 보내면 client가 자기 모델로 답을 만들어 돌려준다. server는 자기 API 키 없이 모델을 쓸 수 있다. 대신 client가 할 일이 많았다. 사람이 요청을 보고 거절할 수 있어야 했고, 보낼 문장을 사용자가 확인하고 고치는 화면, 어떤 모델을 쓸지 고르는 로직, sampling 안에서 tool을 쓰는 처리까지 client가 만들어야 했다.

규격은 이 기능을 단계적으로 줄였다. 2025-11-25 규격은 client가 가진 대화 내용을 프롬프트에 함께 넣어 달라고 하는 값(includeContext의 "thisServer", "allServers")을 쓰지 말라고 했다. 2026-07-28 규격은 sampling 자체를 deprecated로 정했다. 제안서(SEP-2577)가 든 이유는 client가 구현하기 복잡하고, 지원하는 client가 적고, server가 LLM API를 직접 부르면 된다는 것이다. 같은 규격에서 Roots와 Logging도 deprecated가 됐다. deprecated 기능은 최소 12개월 동안 규격에 남아 동작하고, 그 뒤에 빠질 수 있다.

A4

FIPA-ACL의 네 한계와 MCP, 권한 위임

한계FIPA-ACL (2002)MCP (2026-07-28)
의미론 검증메시지의 뜻을 보내는 쪽의 믿음과 바람으로 정의했다. 그 믿음을 밖에서 확인할 방법이 없었다tool 호출은 함수를 실행해 달라는 요청이다. server는 어떤 토큰이 무엇을 불렀는지만 확인한다
추론메시지를 규칙대로 쓰려면 상대가 무엇을 믿는지 추론해야 했다(FP, RE). 실제 구현은 메시지 종류 이름으로 분기하는 데 그쳤다모델이 자연어 설명을 읽고 tool과 인자를 고른다. host 코드에는 도구마다 따로 쓴 처리 코드가 없다
ontology 합의내용을 읽으려면 양쪽이 같은 언어와 용어 사전(:language, :ontology)을 미리 맞춰야 했다인자의 형식은 JSON Schema로, 뜻은 자연어 설명으로 준다. 단어가 조금 달라도 모델이 알아듣고, 설명을 잘 쓰는 일은 server 제작자가 맡는다
채택이 규격으로 메시지를 주고받을 에이전트가 생기기 전에 규격이 나왔다tool calling을 하는 host가 먼저 있었고, 규격이 그 뒤에 나왔다

FIPA-ACL은 그 규격으로 메시지를 주고받을 에이전트가 생기기 전에 나왔다. MCP는 순서가 반대였다. tool calling을 하는 host가 먼저 있었고, 그 host들이 MCP를 붙이면서 사용량이 늘었다. TypeScript SDK(@modelcontextprotocol/sdk)의 npm 월간 다운로드는 공개 직후인 2024년 12월 102,851에서 2026년 8월 28일부터 9월 26일까지 30일 동안 204,541,524로 늘었다.

npm 공개 다운로드 통계(api.npmjs.org). CI와 의존성 설치가 섞인 수치라 사용자 수와 같지 않다.

FIPA-ACL은 메시지의 뜻을 보내는 쪽의 믿음과 의도로 정의했지만, 그 의도를 밖에서 확인할 방법이 없었다. MCP에서도 모델이 어떤 의도로 tool을 불렀는지는 확인할 수 없다. 대신 server는 그 호출이 허락받은 것인지를 확인할 수 있고, 규격은 2025-03-26부터 그 절차를 OAuth 2.1로 정해 두었다. 메시지의 뜻을 믿음이나 의도 대신 밖에서 확인할 수 있는 약속으로 옮기자는 Singh(1998)의 제안과 같은 방향이다.

웹사이트에서 ‘Google로 로그인’을 누르면 Google 화면으로 넘어가 로그인하고, 그 사이트에 무엇을 허락할지 동의한다. 그러면 사이트는 Google이 발급한 토큰을 받고, 이후 요청마다 그 토큰을 붙인다. OAuth는 이 절차를 정한 표준이다. 동의를 받고 토큰을 발급하는 쪽을 authorization server, 토큰을 확인하고 데이터를 내주는 쪽을 resource server라 부른다. MCP에서는 MCP server가 resource server이고, host 안의 client가 토큰을 받아 쓴다.

흐름은 FIG. 07과 같다. client가 토큰 없이 요청하면 server는 401 오류와 함께, 토큰을 어디서 받는지 적힌 문서(Protected Resource Metadata)의 주소를 WWW-Authenticate 헤더로 알려 준다. client는 그 문서에서 authorization server를 찾아 사용자의 동의를 받는다. 동의가 끝나면 일회용 인가 코드를 받고, 이 코드를 토큰으로 바꾼다. 이때 resource 파라미터에 server 주소를 적어서, 이 server에서만 쓸 수 있는 토큰을 받는다. 그 뒤로는 모든 요청의 Authorization: Bearer 헤더에 토큰을 넣는다.

토큰마다 허락된 범위(scope)가 있다. 범위 밖의 일을 요청하면 server는 403 insufficient_scope와 필요한 scope를 돌려주고, client는 더 넓은 scope로 다시 동의를 받는다(step-up).

2026-07-28 AUTHORIZATION RULES2026-07-28 규격은 이 흐름에 규칙을 더했다. authorization server의 응답에 iss(authorization server 이름)가 있으면, client는 인가 코드를 토큰으로 바꾸기 전에 그 값이 Protected Resource Metadata에서 찾은 authorization server와 같은지 확인한다(RFC 9207). 한 authorization server에서 받은 client 자격 증명은 다른 authorization server에 쓰지 않는다. client 등록은 Dynamic Client Registration 대신 Client ID Metadata Documents를 권한다.
FIG. 07 Authorization in MCP, 2025-06-18 onwardthe server checks every request; the model never sees the token

MCP server는 요청마다 토큰을 검사하는 OAuth 2.1 resource server다. 토큰이 이 server를 위해 발급됐는지, scope가 충분한지는 server가 판정한다.

“MCP servers MUST validate that access tokens were issued specifically for them as the intended audience.” MCP Specification 2026-07-28, Authorization, Token Handling.

1주차 토론에서는 Bitter Lesson(사람이 손으로 넣은 지식은 번번이 계산과 데이터의 규모를 앞세운 일반적 방법에 밀려난다는 Sutton의 주장)을 두고, 프로토콜도 더 큰 모델에 흡수될 ‘손으로 심은 지식’인지 물었다. MCP에서는 일마다 답이 다르다. tool 설명을 읽고 어떤 tool을 어떤 인자로 부를지 고르는 일은 모델이 좋아질수록 잘된다. 토큰 검사는 server 코드가 하므로 모델의 성능과 상관없이 결과가 같다.

과제에서는 가격 한도를 지키는 일을 모델에 맡길 때와 server에 맡길 때를 비교한다. 한도를 system prompt에만 적으면 모델이 스스로 지켜야 하고, 토큰에도 실으면 server가 한도 밖의 수를 거부한다.

A5

MCP 운영: 컨텍스트, description, 트래픽

CONTEXTsub-agent와 disposable context

모델은 컨텍스트, 곧 한 번에 입력으로 받는 글 안의 내용만 본다. host가 server를 연결하면 그 server의 tool 이름, 설명, JSON Schema가 모두 이 컨텍스트에 들어간다. server를 많이 붙일수록 실제 작업에 쓸 자리가 줄어든다. 그래서 Claude Code는 tool 정의를 처음부터 다 싣지 않고, 필요할 때 검색해서 싣는 방식(tool search)을 쓴다.

sub-agent는 메인 에이전트가 일을 떼어 맡기려고 새로 띄우는 에이전트다. sub-agent는 빈 컨텍스트에서 시작해 파일을 읽고, 명령을 실행하고, 결과를 확인한다. 일이 끝나면 결과만 메인 에이전트에게 돌려주고 자기 컨텍스트는 버린다. 쓰고 버리는 컨텍스트(disposable context)라서, 메인 컨텍스트에는 sub-agent가 만든 결과 하나만 남는다. 결과만 돌아오므로 결과의 형식이 깨져 있으면 메인 에이전트는 무엇이 잘못됐는지 볼 수 없다. sub-agent에게 결과 형식을 정해 주고, 메인 에이전트가 그 형식을 확인해야 한다.

MCP server로도 같은 구조를 만들 수 있다. server의 tool이 안에서 다른 에이전트를 실행하고(예를 들어 codex exec), 끝난 결과만 돌려주면 된다. 메인 에이전트에게는 tool 하나를 부른 것이고, 그 에이전트가 쓴 컨텍스트는 메인 컨텍스트에 들어오지 않는다. 다른 회사의 모델에 일을 나눠 맡기는 것(model orchestration)도 이렇게 한다. Claude Code도 claude mcp serve로 MCP server가 될 수 있다. server는 세션 밖에 있으므로, 다른 세션에 메시지를 전하거나 메인 세션이 지나온 기록(trajectory)을 따로 보관하는 일도 맡을 수 있다.

DESCRIPTIONtrajectory로 tool description 고치기

모델은 tool의 description을 읽고 어떤 tool을 부를지 정하므로, description을 잘 쓰는 일은 server 제작자가 맡는다. description은 실행 기록을 보고 고칠 수 있다. Langfuse 같은 추적 도구는 에이전트가 어떤 tool을 어떤 인자로 불렀는지, 무엇을 돌려받았는지를 실행마다 남기고, 일이 성공했는지는 점수로 붙인다. 한 번의 실행에서 남은 이 기록 전체를 trajectory라 부른다.

GEPA(Agrawal 외, 2025)는 trajectory를 모델에게 읽혀 실패 원인을 자연어로 적게 하고, 그 내용으로 프롬프트를 고친 뒤 다시 시험한다. Meta-Harness(Lee 외, 2026)는 프롬프트보다 넓게, 이전 후보들의 코드와 점수와 실행 기록을 보고 하네스 코드 자체를 고친다. tool description도 같은 방법으로 고칠 수 있다. 수만 번의 실행 기록에서 실패로 끝난 호출을 모으고, 모델이 description을 어떻게 잘못 읽었는지 찾아 description을 다시 쓴다.

무엇을 목표로 고치는지가 결과를 정한다. 목표가 일의 성공이면 description은 tool이 실제로 하는 일에 가까워진다. 목표가 tool이 선택되는 횟수이면 description은 “this is a silver bullet”처럼 부풀려지고, 3주차의 overconfident contractor가 다시 나타난다. get_feedback 같은 tool을 두고 에이전트에게 tool 평가를 받을 수도 있지만, 그 평가는 모델이 스스로 말한 것이라 3주차의 확신도처럼 믿기 어렵다.

TRAFFICclientInfo와 트래픽 제어

2026-07-28 규격은 client가 요청마다 _meta에 자기 이름과 버전(clientInfo)을 적도록 권한다. 웹 브라우저가 요청마다 보내는 User-Agent와 비슷한 값이다. 이 값으로 요청을 쏟아내는 에이전트를 찾아 막고 싶을 수 있다. 하지만 규격은 clientInfo가 보내는 쪽이 스스로 적은 값이라 확인되지 않으니 보안 판단에 쓰지 말라고 적는다. clientInfo는 로그와 디버깅에만 쓴다.

요청을 막는 기준은 토큰이다. server 앞에 요청을 대신 받아 넘겨주는 proxy를 두면, proxy가 토큰마다 요청 횟수를 세어 제한하고, 넘치는 요청은 큐에 쌓아 두었다가 server가 처리할 수 있는 속도로 넘긴다. 큐에는 Kafka 같은 메시지 큐를 쓸 수 있고, 토큰 확인은 authorization server에 맡긴다. A2 메모의 Mcp-Method, Mcp-Name 헤더가 이런 proxy를 위한 것이다. 이 구성은 MCP 규격 밖의 일로, 일반 웹 서비스에서 쓰는 방법을 MCP server 앞에 그대로 둔 것이다.

DISCUSSION: Bitter Lesson과 MCP 운영
  1. 설명을 읽고 tool을 고르는 일, tools/call을 JSON-RPC로 보내는 일, 토큰을 검사하는 일 가운데 더 큰 모델이 나오면 필요 없어지는 것은 무엇이고, 남는 것은 무엇인가.
  2. 3주차의 overconfident contractor처럼 설명을 부풀린 server를 걸러 내는 일은 host, registry(server 목록을 모아 두는 곳), 사용자 가운데 누가 맡아야 하는가. 4주차의 sincerity 문제(보낸 말을 정말 믿는지 확인할 수 없는 문제)와 같은 문제인가.
  3. 4주차 FIPA 메시지의 :sender는 보내는 쪽이 직접 적는 필드였다. MCP에서 호출자는 토큰으로 정해진다. 한 사람이 같은 토큰을 Claude Code와 Codex에 모두 넣었다면 server는 두 에이전트를 구분할 수 있는가. 구분해야 한다면 무엇이 더 필요한가.
  4. get_feedback처럼 에이전트가 tool을 평가하는 tool을 두고, 그 평가로 description을 고쳐도 되는가. 3주차의 확신도와 무엇이 같고 무엇이 다른가.
  5. clientInfo로 막을 수 없다면, 한 사람이 에이전트 만 개를 띄워 요청을 보낼 때 server는 무엇을 기준으로 막아야 하는가.

협상장을 MCP server로: 한도를 어디에 두는가

4주차 협상을 MCP server 위로 옮긴다. 협상장(market)이 server이고, buyer와 seller는 각자 host를 통해 그 server에 붙는다. 4주차의 네 행위는 propose(negotiation_id, price), accept_proposal, reject_proposal, refuse tool이 된다. 행위의 종류는 tool 이름에, 가격은 정수 인자에 담기므로 4주차의 reader(자연어 메시지를 행위와 가격으로 읽어 내던 모델)는 필요 없다. 여기에 협상 상태를 읽는 get_negotiation이 더해진다.

server는 모델이 개입하기 전에 아래를 직접 판정한다.

신원호출한 쪽이 buyer인지 seller인지는 요청 헤더에 붙은 토큰(bearer token)으로 정한다. tool에 sender 인자는 없다. 토큰이 없으면 HTTP 401.
협상토큰은 협상 하나에 묶인다. 다른 negotiation_id로 부르면 tool 오류. 규격의 보안 문서(Security Best Practices)도 negotiation_id 같은 handle을 안다는 것만으로 호출을 허락하지 말고, handle을 토큰의 주인에게 묶으라고 적는다(State Handle Hijacking).
차례자기 차례가 아닌 수는 tool 오류.

협상을 여는 것은 러너(협상을 진행시키는 스크립트)다. 러너가 POST /admin/open에 시나리오와 조건을 보내면 server는 negotiation_id와 buyer, seller 토큰 한 쌍을 돌려준다. 이 경로는 MCP tool 목록에 없어서 에이전트는 부를 수 없다. server 하나가 여러 협상을 함께 들고 있고, 각 협상의 두 host는 자기 토큰으로 같은 server의 tool을 부른다. 차례는 buyer부터 번갈아 돈다.

class PartyTokens:                       # TokenVerifier: 러너가 발급한 토큰만 통과
    async def verify_token(self, token):
        grant = TOKENS.get(token)            # {role, negotiation_id, limit}
        return AccessToken(token=token, client_id=grant["role"], scopes=["negotiate"],
                           resource=f"{BASE}/mcp", claims=grant) if grant else None

mcp = MCPServer("market", token_verifier=PartyTokens(),
                auth=AuthSettings(issuer_url=BASE, resource_server_url=f"{BASE}/mcp",
                                  required_scopes=["negotiate"], validate_token_resource=True))

@mcp.tool()
def propose(negotiation_id: str, price: int, note: str = "") -> str:
    """Offer a whole-number price for the item. Ends your turn."""
    n, grant = _party(negotiation_id)        # 토큰이 이 협상의 당사자인가

    reason = _outside(grant["limit"], price)  # server 조건에서만 limit이 있다
    if reason:
        _log(n, ..., "refused", reason)
        raise ToolError(reason)             # isError: true, 모델이 이 문장을 읽는다
    ...
