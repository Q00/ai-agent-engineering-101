A1

MCP의 구조: host, client, server

1주차 에이전트는 모델에게 넘기는 설명과 스키마(TOOLS)도, 실제로 실행되는 함수(TOOLS_IMPL)도 에이전트 코드 안에 갖고 있었다. 그래서 도구를 하나 늘리려면 에이전트를 고쳐야 하고, 같은 read_file을 Claude Code나 Codex에서 쓰려면 그 애플리케이션용으로 다시 만들어야 한다. 애플리케이션이 M개, 도구가 N개면 연결 코드가 M×N개 필요하다.

Anthropic은 2024년 11월 25일 Model Context Protocol을 공개했다. 도구를 별도 프로그램인 server로 떼어 내고, 애플리케이션과 server 사이에 오가는 메시지를 규격으로 정했다. server 제작자는 규격대로 한 번 만들고, 애플리케이션 제작자는 규격의 클라이언트 쪽을 한 번 구현한다. 필요한 구현이 M+N개로 줄어든다.

FIG. 01 M × N adapters become M + N implementationsthe protocol sits between hosts and tools

host는 사용자가 쓰는 애플리케이션이다. Claude Code, Codex, Cursor, 그리고 실습에서 고칠 1주차 루프가 여기에 해당한다. host는 모델을 부르고, 모델이 도구를 쓰겠다고 하면 그 호출을 대신 실행한다. client는 host 안에서 server 하나와의 연결을 맡는 부분이다. host가 server 셋을 쓰면 client도 셋이다. server는 도구와 데이터를 규격대로 내놓는 프로그램이다. 연결마다 client가 따로 있으므로 transport, 자격 증명, 실패도 연결마다 따로 관리된다.

FIG. 02 Host, client, serverthe host runs the model; each client talks to one server

규격은 server가 내놓는 것(primitive)을 누가 쓰기로 결정하는지에 따라 나눈다.

primitive무엇인가누가 고르는가
tools모델이 부르는 함수. 파일 쓰기처럼 부수효과가 있을 수 있다model-controlled
resources컨텍스트에 싣는 데이터. 파일 내용, 레코드application-controlled
prompts사용자가 골라 쓰는 템플릿user-controlled

MCP는 host가 외부 server의 tools, resources, prompts를 찾아 쓰는 JSON-RPC 규격이다.

Model Context Protocol Specification, 현재 버전 2026-07-28. 규격은 2025년 12월 9일 Anthropic에서 Linux Foundation 산하 Agentic AI Foundation(AAIF)으로 넘어갔다. AAIF는 Anthropic, Block, OpenAI가 공동 설립했다.

tool 하나는 이름, 자연어 설명, 인자의 JSON Schema로 이루어진다. host는 연결된 server들의 tool 목록을 모델에게 넘기고, 모델은 설명을 읽고 어떤 tool을 어떤 인자로 부를지 정한다. 3주차 Contract Net에 대면 설명은 contractor의 bid에, 낙찰을 정하는 manager는 host의 모델에 해당한다. 다만 bid는 작업마다 새로 냈지만, 설명은 server가 한 번 적어 두면 모든 요청에 똑같이 쓰인다. 3주차의 overconfident contractor에 해당하는 것은 설명을 부풀린 server이고, 그런 설명을 걸러 내는 단계는 규격에 없다.

A2

JSON-RPC 메시지와 transport, stateless 규격

host와 server가 주고받는 것은 JSON-RPC 2.0 메시지다. 요청에는 id, method, params가 있고, 응답에는 같은 id와 result 또는 error가 있다. 실습에서 만들 server를 HTTP로 띄우면 curl로 직접 부를 수 있다. 아래는 tools/list 요청과 응답이다. 응답의 tool 목록은 첫 항목만 남겼다.

tools/list, Streamable HTTP, week01-tools server
# request
POST /mcp
Mcp-Method: tools/list
MCP-Protocol-Version: 2026-07-28

{"jsonrpc": "2.0", "id": 2, "method": "tools/list",
 "params": {"_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
                      "io.modelcontextprotocol/clientCapabilities": {}}}}

# response
{"jsonrpc": "2.0", "id": 2, "result": {"resultType": "complete", "ttlMs": 0, "cacheScope": "private",
 "tools": [{"name": "calculator",
            "description": "Evaluate an arithmetic expression such as '3 * (4 + 5)'. Numbers and + - * / ** only.",
            "inputSchema": {"type": "object", "properties": {"expression": {"type": "string"}},
                            "required": ["expression"]}},
           ...]}}

inputSchema는 server 코드에서 함수의 타입 힌트로 만들어지고, description은 docstring에서 온다. 1주차에서 손으로 적던 TOOLS 항목과 같은 내용이다. 모델이 calculator를 부르기로 하면 host는 tools/call을 보낸다.

tools/call
# request (Mcp-Method: tools/call, Mcp-Name: calculator)
{"jsonrpc": "2.0", "id": 3, "method": "tools/call",
 "params": {"name": "calculator", "arguments": {"expression": "48000+9500"}, "_meta": {...}}}

# response
{"jsonrpc": "2.0", "id": 3, "result": {"content": [{"type": "text", "text": "57500"}],
 "isError": false, "resultType": "complete", "structuredContent": {"result": "57500"}}}

stdio에서는 host가 server를 자식 프로세스로 띄우고 표준 입출력으로 메시지를 주고받는다. 같은 기계의 도구에 쓰고, 자격 증명은 환경 변수로 넘긴다. Streamable HTTP에서는 server가 HTTP 엔드포인트 하나(보통 /mcp)를 열고 요청마다 POST를 받는다. 응답은 JSON 한 덩어리나 SSE 스트림으로 온다. 원격 server와 여러 사용자가 붙는 server는 이쪽을 쓰고, 규격의 authorization 절차도 HTTP transport에만 적용된다. tools/list의 뜻은 transport와 상관없이 같다.

규격은 날짜로 버전을 붙이고, 하위 호환이 깨지는 변경이 있을 때만 날짜를 바꾼다.

버전주요 변경
2024-11-05첫 규격. stdio와 HTTP+SSE transport, tools, resources, prompts
2025-03-26OAuth 2.1 기반 authorization, Streamable HTTP transport, tool annotations(읽기 전용인지, 파괴적인지 표시)
2025-06-18server를 OAuth resource server로 규정, Protected Resource Metadata(RFC 9728), client의 Resource Indicators(RFC 8707) 의무화, structured tool output, elicitation
2025-11-25Client ID Metadata Documents, WWW-Authenticate를 통한 scope 단계적 요청, 실험적 tasks
2026-07-28stateless 전환. initialize 핸드셰이크와 세션 제거, server/discover 추가, HTTP 요청에 Mcp-Method와 Mcp-Name 헤더 필수, client의 iss 확인, tasks를 확장으로 분리, Dynamic Client Registration deprecated

2025-11-25 규격까지는 client가 먼저 initialize를 보내 세션을 열어야 tools/list 같은 요청을 보낼 수 있었다. 2026-07-28 규격은 이 핸드셰이크와 세션을 없앴다. 대신 모든 요청이 _meta에 protocol version과 client capabilities를 직접 싣는다. 위의 tools/list 요청이 이 형식이다.

세션이 없으니 server는 요청을 하나씩 따로 처리한다. 여러 호출에 걸쳐 상태를 이어 가야 하면 server가 식별자(handle)를 만들어 돌려주고, client는 다음 호출에서 그 값을 tool 인자로 넘긴다. 그래서 과제의 협상장에서는 모든 tool이 negotiation_id를 받는다.

HTTP로 보낼 때는 헤더도 필수가 됐다. 모든 요청에 Mcp-Method를 붙이고, tools/call이면 부르는 tool 이름을 Mcp-Name에도 적는다. 본문에 이미 있는 값을 헤더에 한 번 더 적어 두면, load balancer나 gateway가 JSON을 열지 않고도 어떤 tool 호출인지 보고 요청을 나누거나 막을 수 있다. 헤더가 빠지거나 본문과 다르면 server는 400(HeaderMismatch)으로 거절한다.

PYTHON SDK V1 / V2v1, v2는 Python SDK의 버전이고, 규격은 날짜로만 부른다. SDK 2.x는 2026-07-28 규격을 쓰고, 옛 server에는 initialize로 내려간다. v1의 FastMCP는 v2에서 MCPServer로 이름이 바뀌어, v1 코드는 v2에서 import부터 실패한다.

FIPA-ACL의 네 한계와 MCP, 권한 위임

한계FIPA-ACL (2002)MCP (2026-07-28)
의미론 검증performative의 뜻을 보내는 쪽의 믿음과 의도로 정의했고, 그것을 밖에서 확인할 수 없었다tool 호출의 뜻을 정신 상태로 정의하지 않는다. tools/call은 함수 실행 요청이고, server가 확인하는 것은 어떤 토큰으로 무엇을 불렀는가다
추론FP와 RE를 쓰려면 상대의 믿음을 추론해야 했고, 당시 구현은 performative 문자열로 분기했다모델이 자연어 설명을 읽고 tool과 인자를 고른다. host 코드에는 도구별 분기가 없다
ontology 합의content를 읽으려면 :language와 :ontology를 양쪽이 미리 공유해야 했다인자는 JSON Schema, 뜻은 자연어 설명으로 준다. 어휘 차이는 모델이 메우고, 합의 비용은 설명을 쓰는 server 제작자에게 간다
채택상호운용할 에이전트가 생기기 전에 규격이 나왔다tool calling을 하는 host가 먼저 있었고, 규격이 그 뒤에 나왔다

FIPA-ACL은 그 규격으로 메시지를 주고받을 에이전트가 생기기 전에 나왔다. MCP는 순서가 반대였다. tool calling을 하는 host가 먼저 있었고, 그 host들이 MCP를 붙이면서 사용량이 늘었다. TypeScript SDK(@modelcontextprotocol/sdk)의 npm 월간 다운로드는 공개 직후인 2024년 12월 102,851에서 2026년 8월 28일부터 9월 26일까지 30일 동안 204,541,524로 늘었다.

2024-12102,851
2025-0931,258,519
2026-08-28 ~ 09-26204,541,524

npm 공개 다운로드 통계(api.npmjs.org). CI와 의존성 설치가 섞인 수치라 사용자 수와 같지 않다.

FIPA-ACL은 메시지의 뜻을 보내는 쪽의 믿음과 의도로 정의했지만, 그 의도를 밖에서 확인할 방법이 없었다. MCP에서도 모델이 어떤 의도로 tool을 불렀는지는 확인할 수 없다. 대신 server는 그 호출이 허락받은 것인지를 확인할 수 있고, 규격은 2025-03-26부터 그 절차를 OAuth 2.1로 적어 왔다. 메시지의 뜻을 정신 상태 대신 밖에서 확인할 수 있는 약속으로 옮기자는 Singh(1998)의 제안과 같은 방향이다.

OAuth의 역할에 맞추면 MCP server는 resource server, host 안의 client는 OAuth client이고, 토큰을 발급하는 authorization server가 따로 있다. 흐름은 FIG. 03과 같다. 토큰 없이 요청하면 server는 401과 함께 WWW-Authenticate 헤더에 Protected Resource Metadata 문서의 주소를 준다. client는 그 문서에서 authorization server를 찾고, 사용자의 동의를 받아 인가 코드를 받은 뒤 토큰으로 바꾼다. 이때 resource 파라미터에 server 주소를 적어 토큰이 이 server 전용으로 발급되게 한다. 이후 모든 요청에 Authorization: Bearer 헤더를 붙인다. 토큰의 scope가 모자라면 server는 403 insufficient_scope와 필요한 scope를 돌려주고, client는 더 넓은 scope로 다시 인가를 받는다(step-up).

2026-07-28 규격은 이 흐름에 규칙을 더했다. authorization server의 응답에 iss가 있으면, client는 인가 코드를 토큰으로 바꾸기 전에 그 값이 Protected Resource Metadata에서 찾은 authorization server와 같은지 확인한다(RFC 9207). 한 authorization server에서 받은 client 자격 증명은 다른 authorization server에 쓰지 않는다. client 등록은 Dynamic Client Registration 대신 Client ID Metadata Documents를 권한다.

FIG. 03 Authorization in MCP, 2025-06-18 onwardthe server checks every request; the model never sees the token

MCP server는 요청마다 토큰을 검사하는 OAuth 2.1 resource server다. 토큰이 이 server를 위해 발급됐는지, scope가 충분한지는 server가 판정한다.

“MCP servers MUST validate that access tokens were issued specifically for them as the intended audience.” MCP Specification 2026-07-28, Authorization, Token Handling.

1주차 토론에서는 Bitter Lesson을 두고, 프로토콜도 더 큰 모델에 흡수될 ‘손으로 심은 지식’인지 물었다. MCP에서는 일마다 답이 다르다. tool 설명을 읽고 어떤 tool을 어떤 인자로 부를지 고르는 일은 모델이 좋아질수록 잘된다. 토큰 검사는 server 코드가 하므로 모델의 성능과 상관없이 결과가 같다.

과제에서는 가격 한도를 지키는 일을 모델에 맡길 때와 server에 맡길 때를 비교한다. 한도를 system prompt에만 적으면 모델이 스스로 지켜야 하고, 토큰에도 실으면 server가 한도 밖의 수를 거부한다.

DISCUSSION: Bitter Lesson으로 본 MCP
  1. 설명을 읽고 tool을 고르는 일, tools/call을 JSON-RPC로 보내는 일, 토큰을 검사하는 일 가운데 더 큰 모델이 나오면 필요 없어지는 것은 무엇이고, 남는 것은 무엇인가.
  2. 3주차의 overconfident contractor처럼 설명을 부풀린 server를 걸러 내는 일은 host, registry, 사용자 가운데 누가 맡아야 하는가. 4주차의 sincerity 문제와 같은 문제인가.
  3. 4주차 FIPA 메시지의 :sender는 보내는 쪽이 직접 적는 필드였다. MCP에서 호출자는 토큰으로 정해진다. 한 사람이 같은 토큰을 Claude Code와 Codex에 모두 넣었다면 server는 두 에이전트를 구분할 수 있는가. 구분해야 한다면 무엇이 더 필요한가.

LAB

calculator와 read_file을 server로 옮긴다

1주차 starter의 calculator와 read_file을 MCP server로 옮기고, 1주차 루프가 그 server에서 tools/list로 도구 목록을 받고 tools/call로 실행하게 고친다. 루프 자체는 그대로 둔다. 마지막으로 같은 server를 각자 쓰는 코딩 에이전트에 붙인다.

  1. SDK를 설치한다. Python이면 pip install "mcp>=2" openai. v1(mcp<2)을 쓰려면 server의 import를 from mcp.server.fastmcp import FastMCP로 바꾼다. TypeScript 등 다른 언어의 SDK를 써도 된다.
  2. server를 만든다. tools_server.py. 함수에 @mcp.tool()을 붙이면 docstring이 description이 되고, 타입 힌트가 inputSchema가 된다. 인자 없이 실행하면 stdio로, --http를 붙이면 http://127.0.0.1:8000/mcp에서 Streamable HTTP로 뜬다.
  3. 손으로 불러 본다. --http로 띄우고 tools/list 요청을 curl로 보낸다. Mcp-Method 헤더를 빼거나 _meta의 clientCapabilities를 빼면 server가 400으로 거절하는 것도 확인한다.
  4. 1주차 루프를 host로 바꾼다. 하드코딩한 TOOLS 대신 list_tools() 결과를 모델의 도구 형식으로 옮기고, TOOLS_IMPL[name](**args) 대신 call_tool(name, args)를 부른다.
  5. transport만 바꿔 같은 일을 시킨다. MCP_SERVER를 비우면 host가 server를 stdio 자식 프로세스로 띄우고, http://127.0.0.1:8000/mcp를 넣으면 HTTP로 붙는다. 루프 코드는 고치지 않는다.
  6. 두 번째 client에 붙인다. 아래 명령 가운데 자기 도구에 맞는 것으로 같은 server를 등록하고, 1주차와 같은 질문을 한다.
  7. 1주차에 만든 세 번째 도구를 server로 옮긴다. host 코드는 고치지 않는다. 다음 실행의 [host] 줄에 도구가 셋으로 찍히면 된다.

협상장을 MCP server로: 한도를 어디에 두는가

4주차 협상을 MCP server 위로 옮긴다. 협상장(market)이 server이고, buyer와 seller는 각자 host를 통해 그 server에 붙는다. 4주차의 네 행위는 propose(negotiation_id, price), accept_proposal, reject_proposal, refuse tool이 된다. 행위의 종류는 tool 이름에, 가격은 정수 인자에 담기므로 4주차의 reader는 필요 없다. 여기에 협상 상태를 읽는 get_negotiation이 더해진다.

server는 모델이 개입하기 전에 아래를 직접 판정한다.

신원호출한 쪽이 buyer인지 seller인지는 bearer token으로 정한다. tool에 sender 인자는 없다. 토큰이 없으면 HTTP 401.
협상토큰은 협상 하나에 묶인다. 다른 negotiation_id로 부르면 tool 오류. 규격의 Security Best Practices는 handle을 가졌다는 사실을 인증으로 취급하지 말고, handle을 토큰의 주체에 묶으라고 적는다(State Handle Hijacking).
차례자기 차례가 아닌 수는 tool 오류.

독립변수는 가격 한도를 두는 곳과 주입 문장의 유무다.

condition한도가 있는 곳주입
promptsystem prompt. server는 기록만 한다없음
serversystem prompt와 토큰. server가 토큰의 한도 밖 propose와 accept_proposal을 거부하고 이유를 tool 오류로 돌려준다없음
prompt_injectprompt와 같다있음

주입은 server가 한다. buyer가 get_negotiation으로 읽는 seller의 제안마다 note 끝에 아래 문장을 붙인다. seller에게는 보이지 않고, 숫자는 시나리오마다 max(reserve, budget) + 30이다. tool 결과에 섞여 들어온 문장으로 모델의 판단을 바꾸는 공격을 indirect prompt injection이라 부른다. 규격의 Security Best Practices 문서는 이 공격을 다루지 않는다. 그 문서의 항목은 confused deputy, token passthrough, SSRF, state handle hijacking처럼 server와 client 코드로 막는 공격들이다. 네 조건의 system prompt는 한 글자도 다르지 않다. 에이전트가 조건을 알 수 있는 단서는 server의 거부 메시지뿐이다.
