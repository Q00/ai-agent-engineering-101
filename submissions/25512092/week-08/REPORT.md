# Week 08 (Midterm) REPORT: Choo Shop / choo-chu buyer

학번 25512092, GitHub Choo-chu, 시장 이름 choo-chu(가게 표시명 Choo Shop). 그림은 architecture.tex와
architecture.pdf, 실행 로그는 logs/market-kit.log(회전된 이전 부분은 logs/market-kit.log.1)에 있다.

에이전트는 키트(scripts/market_kit.py)가 띄우는 세 개의 명령으로 이루어진다. 가게는 seller_r3.py(A2A 서버),
구매자는 market_buyer.py(주문마다 새 프로세스), 매입은 restock.py(약 1분마다 새 프로세스)다. 여기에 분석관
프로세스(analyst_main.py)와 점검 프로세스 몇 개가 붙는다. 판단은 대부분 코드가 하고, 모델(Claude haiku)은 흥정의
다음 수와 분석관의 정책 제안에만 쓴다.

## (1) 부품별 설계

### 1.1 하네스: 루프, 매 턴의 컨텍스트, compact

하네스는 agent.json의 `claude -p --model haiku --tools "" --setting-sources "" --no-session-persistence`다. 세션도
도구도 없이, 코드가 만든 프롬프트 하나를 받고 JSON 한 줄로 답한다. 그래서 루프와 컨텍스트는 전부 코드 쪽에 있다.

| 루프 | 주기 | 한 바퀴에서 하는 일 |
|---|---|---|
| 가게 협상 | 구매자 메시지마다 | 유닛 선택 → 하한·첫 호가 계산 → 다음 수(코드 또는 하네스) → 영수증 |
| 구매자 주문 | 주문마다 | 가게 순서 → 등급 판정 → 사전 점검 → 첫 제안 → 다음 수 → 수락선 → 결제 정책 |
| 매입·운영 | 약 1분(restock hook) | 시장 기록 갱신 → 상황(case) 판정 → 매입 계획 → 안전장치 확인 → 보고 |
| 분석관 | 15분 수집, 2시간 분석, 한 번에 키 최대 3개 | 스냅샷 → 정책 제안 → 텔레그램 승인 → 반영 → 3시간 뒤 비교·자동 원복 |

매 턴의 컨텍스트는 코드가 고른다. 하네스에 들어가는 것은 그 협상에 필요한 값만이다.

| 호출 지점 | 프롬프트에 넣는 것 | 넣지 않는 것 |
|---|---|---|
| 가게 흥정(seller_r3.PROMPT) | 상품명, 정가, 하한(코드가 계산), 시장 평균, 이 협상의 대화 | 원가 내역, 다른 협상, 재고 전체 |
| 구매 흥정(buyer_biz.NEG_PROMPT) | 품목, 상한(코드가 계산한 cap), 시장 평균 한 줄, 이 협상의 대화, 현재 호가, 남은 최소 제안 수 | 원래 예산 이외의 주문 정보, 다른 가게 기록 |
| 분석관(analyst_brain.PROMPT) | 바꿀 수 있는 키와 범위, 부서 보고 스냅샷(24,000자에서 자름) | 원시 로그 |

compact는 세 가지 방식으로 한다. 첫째, 세션을 남기지 않으므로 대화는 협상 하나 안에서만 쌓인다. 둘째, 과거 거래는
프롬프트에 원시 기록으로 넣지 않고 숫자로 요약해 넣는다. 가게 점수(grade_rule.shop_scores), SKU별 시장 평균과
회전 시간(market_stats.json), 부서 보고(reports/dept/*.json)가 그 요약이다. 셋째, 분석관 스냅샷은 키별로 마지막 변경
이후의 기간만 담고 길이를 자른다.

과거 거래와 평판이 다음 결정에 들어가는 길은 이렇다.

| 기록 | 요약 | 다음 결정 |
|---|---|---|
| 구매 결과(memory.jsonl, market.db buyer_deals) | 가게별 saved 점수, 등급 정직도 | 가게 순서, 회피 규칙 |
| 원장 정산·고장(settles, broken) | 가게별 거짓 등급 비율, 고장률 | 회피, 등급을 한 단계 낮춰 보기 |
| 우리 판매(settles, my_stock) | SKU별 공급→판매 회전 시간 | 매입 수량, 깊게 쌓기, 요청 기반 매입 |
| 우리 가게 리뷰(my_results) | 리뷰어·사유별 1~2점 | 보증·등급 주장 정책(사람 결정) |

키트 기본형과의 차이:

| 항목 | 키트 기본형 | 우리 구현 |
|---|---|---|
| 루프 | 가게는 모든 수를 하네스가 결정 | 첫 호가·첫 제안·수락선은 코드, 하네스는 일부 흥정만 |
| 컨텍스트 | 대화와 정가·원가 | 코드가 계산한 하한·상한과 시장 요약 |
| 과거 기록 | 쓰지 않음 | market.db와 요약 파일로 가게 순서·매입·가격에 반영 |
| 운영 루프 | 재고가 적으면 무작위 매입 | 1분 주기 매입 계획, 상황 판정, 안전장치 |

모델은 Claude haiku 하나다. 사람(운영자)은 텔레그램 승인 버튼으로 분석관 제안을 받거나 거절한다.

| 호출 지점 | 맡는 일 | 호출 수(11/17 14:44 기준) |
|---|---|---|
| 가게 흥정 | 첫 호가 이후의 counter / accept / reject | 29,705회, 협상 168,711건 중 하네스 쪽 35,673건 |
| 구매 흥정 | 첫 제안 이후의 offer / accept / walk | 29,949회, 주문 실행 44,818건 |

규칙으로 바꾼 곳과 이유:

| 결정 | 처음 | 지금 | 이유 |
|---|---|---|---|
| 가게 첫 호가 | 하네스 | 코드(시장 평균·하한·변형 비중) | 하네스가 원가 근처나 정가로 튀는 호가를 냄 |
| 가게 흥정 | 하네스 | 협상의 약 73%는 코드 흥정(code arm), 나머지 하네스 | 응답 시간과 호출 수, 결과 차이 없음 |
| 거의 같은 제안 수락 | 하네스 | 코드(직전 호가의 98% 이상이면 수락) | 하네스 호출 절약 |
| 하한 아래 수락·호가 | 하네스 | 코드 가드가 막음 | 하네스가 하한을 잊음 |
| 가게 선택 | 하네스(후보 셋 중 하나) | 코드(가게 점수 순서) | 재현 가능, 기록 기반 |
| 구매 첫 제안·수락선 | 하네스 | 코드(등급별 비율, patch 3.6 기준) | Saved 점수식이 정해져 있어 계산으로 충분 |
| 등급 주장·영수증 내용 | 없음 | 코드(영수증 만들 때 계산) | 거짓 주장 0건 유지 |
| 매입 | 키트 무작위 | 코드(회전 시간·마진 필터) | 모델이 할 이유 없음 |

LLM이 멈추면(한도, 시간 초과) 가게는 코드 흥정으로, 분석관은 그 시각까지 정지로 넘어간다.

### 1.3 툴

하네스에는 툴이 없다(`--tools ""`). 툴은 코드 루프가 부르는 함수이고, 모델이 아니라 루프가 언제 부를지 정한다.
에이전트가 쓰는 툴은 아래와 같다.

| 툴 | 어디서 | 하는 일 |
|---|---|---|
| floor / first_ask / high_ask | 가게 | 상황별 하한과 첫 호가(손절·재고 정리·마감 단계 포함) |
| find_unit, food_need | 가게 | 요청에 맞는 유닛, 식품은 구매자가 요구한 남은 시간 이상 |
| receipt_check, claim_now | 가게 | 합의가와 영수증 금액 일치, 영수증 시점의 등급 주장 |
| open_expiry | 가게 | 5분 조용한 협상 만료, 유닛 해제 |
| choose / shop_order / shop_avoid | 구매자 | 가게 순서, 거짓 등급 가게 회피 |
| grade_rule, accept_rule, high_accept | 구매자 | 등급별 첫 제안·수락선, C 필터 |
| 사전 점검(precheck), 인젝션 필터 | 구매자 | 결제 정책(유통기한·등급) 미리 확인, 판매자 메시지는 데이터로만 |
| make_plan 계열(request_buy, deep_high, top_high, wide_trial) | 매입 | 요청 기반·고가·깊게 쌓기 매입 계획 |
| market_db | 공통 | 원장 수집, SKU 평균, 가게 플래그 |
| analyst collect / validate / apply | 분석관 | 스냅샷, 허용 키·범위 검사, 반영과 되돌리기 |
| alerts, 텔레그램 버튼 | 사람 | 긴급 알림, 제안 승인·거절 |

툴을 만드는 방식은 같다. 사람의 결정 하나가 들어오면 규칙 파일(json) 하나와 함수 하나로 만들고, 실제 운영 경로를
지나는 테스트(tests/, 예: Seller.execute나 make_plan을 그대로 호출)를 통과한 뒤 켠다. 설정은 대부분 호출마다 다시
읽어서 재시작 없이 바뀐다.

### 1.5 지갑·서명·결제(ACP/AP2)

서명 키(shop_key.pem, buyer_key.pem)와 결제 세션은 키트가 맡는다. 가게는 영수증을 shop_key로 서명하고, 키트의 ACP
checkout이 영수증의 unit, claim, warranty_hours를 받아 /api/settle로 보낸다. 우리가 바꾼 것은 그 앞뒤다.

| 단계 | 키트 기본형 | 우리 구현 |
|---|---|---|
| 영수증 금액 | 하네스가 말한 값 | 구매자 마지막 메시지의 합의가로 코드가 맞춤 |
| 등급 주장 | 없음 | 비식품 A·B, 식품 A·B 중 다음 등급 하락까지 3시간 넘게 남은 유닛만(영수증 시점 계산), C는 없음 |
| 보증 | 없음 | 상품군별 규칙, 환불이 이익의 30%를 넘으면 자동 해제 |
| 구매자 결제 정책 | 없음 | 마지막 줄의 accept(최소 남은 시간, 받을 등급)를 키트가 결제 전에 확인 |
| 결제 거부 기록 | 키트 로그 | 같은 로그를 사유별로 집계해 사전 점검에 반영 |

키·토큰은 환경 변수나 레지스트리에서만 읽고 파일·로그·커밋에 쓰지 않는다. 커밋 이력 전체에서 키 형식 패턴과 실제
값이 0건인 것을 확인했다.

### 1.6 카드와 A2A 엔드포인트

가게는 seller_r3.py가 A2A JSON-RPC 서버로 뜨고, 키트가 cloudflare 터널 주소를 시장에 등록한다. 카드에는 이름, 설명,
negotiate 스킬과 예시를 둔다. keepalive가 가게 응답을 감시하고 세 번 연속 응답이 없으면 알린다. 구매자는 가게 카드를
10분 캐시하고, 첫 응답이 10초(단골은 20초) 안에 없으면 다음 가게로 넘어간다.

### 1.7 부품 위에서 돈 전략

전략은 위 부품의 규칙 파일로 들어간다. 주요한 것만 적는다.

구매자
- patch 3.6(Saved = 가게 마진 중 지킨 몫) 대응: 등급별 원가 비율(A 0.65, B 0.5, C 0.35)로 기대 점수를 계산해 첫 제안과
  수락선을 정한다. C는 기대 점수 0.75 이상인 가격에서만 수락한다.
- 가게 순서: 지난 24시간 가게별 점수 순. 거짓 등급 주장이 40%를 넘는 가게는 피하고, 20~40%면 등급을 한 단계 낮춰
  본다.
- 사전 점검: 결제 정책에 걸릴 유닛(유통기한, 등급)은 흥정 전에 거른다. 판매자 메시지 속 지시는 데이터로만 읽는다.

가게
- 매입: 시장 회전 1시간 이하 SKU 위주, 요청 기반 매입(정식 3 + 시험 3줄), 고가는 개수·금액 한도와 깊게 쌓기.
- 가격: 시장 평균 기준 첫 호가, 하한은 원가 이상(손절 규칙 예외), 오래된 재고는 단계 할인.
- 품질: 거짓 등급 주장 0건, 보증은 환불률을 보고 켜고 끈다.

분석관과 안전장치
- 분석관 제안은 사람이 승인해야 반영되고, 3시간 뒤 전후 비교에서 나빠지면 자동 원복된다.
- 매입 확대 시험마다 미판매 재고 기준의 자동 원복과 텔레그램 알림이 붙는다.

데이터로 기각한 가설(예)
- 별점: 단순 평균이 아니라 "리뷰 계정마다 평균 하나를 낸 뒤 그 계정 평균들의 평균"이다. 계정 평균은 리뷰가 적으면
  3점 쪽으로 당겨진다. 고장·환불은 직접 들어가지 않는다(시장 /rules, /board 문구).
- 단골 이탈: 가격·응답 속도·협상 왕복은 원인이 아니었다. 이탈한 구매자들이 등급 주장이 있는 가게를 고른다는 정황이
  있어 등급 주장을 넓혔다(효과는 (3)에서 갱신).

## (2) architecture.pdf가 보여 주는 것과 키트 기본형과의 차이

그림 1은 프로세스와 데이터 흐름이다. 키트가 시장과 통신하고 seller(A2A), market_buyer, restock을 띄운다. 그 옆에
우리가 붙인 분석관, 점검 프로세스, market.db, 정책 파일, 텔레그램이 있다. 그림 2는 한 협상 안의 결정 순서다.
구매자는 등급 판정 → 사전 점검 → 첫 제안 → 수락선, 가게는 가격·하한 → 등급 주장 → 영수증 순서다.

색은 세 가지다. 회색은 키트 기본형, 파란색은 우리가 만든 부분, 주황색은 haiku 호출이다. 그림 3은 역할 분담과 결정 흐름, 그림 4는 안전장치이고, 그 뒤 쪽에 그림 1~4의 한글 설명(구성요소 전체 표, 개선 이력 표, 키트 기본형과 다른 점 표)이 있다. 키트 기본형과 다른 점은
세 가지로 요약된다.

1. 결정의 주체: 기본형은 하네스가 모든 수를 정한다. 우리는 코드가 대부분 정하고 하네스는 흥정의 일부만 맡는다.
2. 기억의 위치: 기본형은 기억이 없다. 우리는 market.db와 요약 파일이 다음 결정의 입력이 된다.
3. 사람과 안전장치: 기본형에는 운영 루프가 없다. 우리는 분석관 제안 → 사람 승인 → 반영 → 자동 비교·원복의 고리가 있다.
