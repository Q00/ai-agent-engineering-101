## 1. 부품별 설계

### 모델

Gemini `gemini-3.5-flash-lite`를 사용했습니다. 판매자는 현재 재고와 구매 조건을 바탕으로 견적을 고르고, 구매자는 주문에 맞는 가게 후보와 수락 조건을 고릅니다. 재입고에는 SKU·등급·수량을 제안하게 하고, 리뷰와 홍보에는 확인된 거래·재고 사실을 바탕으로 문구를 작성하게 했습니다. 각 역할은 모델 출력을 JSON으로 받고 실행 전 코드에서 검사합니다. 모델명과 인증 정보는 실행 환경에서 설정합니다.

### 컨텍스트와 메모리

`r3_common.py`의 SQLite 저장소에 공개 정산과 자체 주문·견적 이벤트, 정산된 구매 기록, 재고 예약, 모델 호출 상태를 보관합니다. 판매 견적에는 현재 SKU의 재고·원가·등급·잔여기한과 최근 거래 근거를 제공합니다. 구매 후에는 `review_r3.py`가 실제 정산 기록에서 가격·등급·보증을 읽어 구매 기억에 저장합니다. 게시판 글은 출처가 다른 참고 자료로 전달하고, 인용 원장과 작성자 평점도 함께 제공합니다.

`r3_meta.py`는 여러 역할의 프로세스가 호출 횟수와 재시도 상태를 공유하게 합니다. 기본 일일 예산 500회에서 누적 300회부터 리뷰·홍보, 400회부터 구매, 490회부터 판매·재입고 모델 호출을 보류합니다. 공급자의 429 응답은 재시도 가능 시각을 기록하고, 대기 후에는 한 프로세스가 먼저 복구 여부를 확인합니다. 판매자는 검증된 기존 견적에 대한 숫자 제안을 규칙으로 처리하고, 모델 호출이 막히면 재고 조건과 원가 하한을 적용한 견적을 사용합니다.

### 툴

| 역할 | 구현과 실행 조건 |
| --- | --- |
| 판매 | `seller_r3.py`, `sale_conditions.py`, `shop_strategy.py`에서 주문 SKU와 등급·잔여기한·보증 조건을 확인합니다. 원가와 비식품 보관비를 반영한 하한을 적용하고, 해당 재고 단위를 예약한 뒤 합의 가격으로 영수증을 서명합니다. |
| 구매 | `buyer_r3.py`에서 주문 SKU와 가격 상한을 대조하고 서명 영수증과 `accept` 조건을 키트에 전달합니다. 키트 v4가 ACP checkout을 실행하고 결제 전에 증명서·등급·잔여기한·보증 조건을 검사합니다. |
| 재입고 | `restock_r3.py`에서 김치·생수를 기본 재고로 두고, 놓친 주문과 최근 정산 및 관측 가능한 경쟁 재고를 비교해 추가 품목 후보를 찾습니다. 공급창과 잔고·수량 조건을 확인하고, 모델 호출이 막히면 조건을 충족하는 후보를 최대 한 품목 고릅니다. |
| 리뷰·게시판 | `review_r3.py`는 정산된 구매를 저장하고 거래 근거가 있는 후기를 작성합니다. `shop_strategy.py`는 실제 재고에 기반한 홍보 문구를 만듭니다. 게시판 전송은 outbox를 통해 키트가 담당합니다. |

## 2. 아키텍처와 키트 기본형과의 차이

[아키텍처 그림](architecture.pdf)은 판매·구매·재입고·리뷰가 SQLite 메모리와 메타하네스를 공유하는 구조를 보여 줍니다. 시장 주문은 구매 훅으로, 상대 구매자의 협상 요청은 판매 훅으로 들어옵니다. 두 역할이 합의하면 키트가 checkout과 정산을 처리하고, 정산 결과가 확인되면 구매 기억에 기록합니다. 재입고는 공급창 상태와 최근 거래 신호를 이용해 주문이 오기 전에 실행합니다.

키트는 시장 등록, 결제·정산, 재고 조회와 게시판 전송을 맡습니다. 그 위에 역할별 컨텍스트 선택, 재고 단위 예약, 모델 호출 제어, 재입고 후보 선택을 구현했습니다. 특히 견적 재사용과 규칙 기반 처리를 통해 조건이 이미 확인된 협상에서 모델 호출을 줄이고, 공급자 오류가 발생해도 조건을 검증할 수 있는 견적과 입고를 계속 처리하도록 설계했습니다. 경쟁 재고는 관측 가능한 범위에서만 쓰이므로, 추가 입고 후보의 수요는 판매 가능성에 대한 추정으로 다뤘습니다.
