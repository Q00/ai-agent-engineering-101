## 1. 변형 정의

공통 조건과 실행법은 `README.md`, 모델·도구 스키마는 `tools_shared.py`에 있다.
기본 하네스는 강의 스타터를 사용했다. 독립변수는 ReAct와 Plan-then-Execute의
제어 흐름이며, 입력 로그·모델·도구·온도·전체 모델 호출 예산은 고정한다.

다섯 축을 코드를 보면서 본인의 문장으로 설명한다.

| 축 | 설명할 내용 |
| --- | --- |
| 컨텍스트 관리 | ReAct의 단일 대화와 Plan/Executor의 분리된 대화에 어떤 정보가 전달되는가? |
| 도구 세분성 | 두 하네스가 같은 두 도구와 같은 입출력 스키마를 사용하는가? |
| 종료 조건 | 모델 답변, 공통 16회 호출 예산, 단계 내부 도구 왕복 상한은 어떻게 작동하는가? |
| 오류 복구 | 오류 Observation 이후의 판단과 최대 1회 재계획은 어떻게 다른가? |
| 사람 개입 지점 | 읽기 전용 도구의 개입 횟수가 0인 이유와 재계획을 별도로 세는 이유는 무엇인가? |

## 2. 측정

실제 실행 전이므로 수치를 기재하지 않았다. `python summarize_results.py`가 출력하는
`results.csv` 전체 표와 하네스별 성공률·평균·표본분산 표를 이곳에 넣는다.
각 하네스 3회 이상을 포함하며 실패도 그대로 남긴다.

## 3. 해석 — 실행 후 직접 작성할 한 문단

성공률, 토큰, 반복 횟수, 개입 횟수에서 각각 차이 또는 동률을 수치로 설명한다.
차이를 만든 다섯 축 중 하나 이상을 특정하고 `logs/<실제 파일명>`의 모델 호출,
계획 파싱 실패, 도구 결과 또는 재계획을 근거로 연결한다. 평균뿐 아니라 분산과
표본 수 3회의 한계도 함께 언급한다. 모든 실패를 하네스 탓으로 단정하지 말고,
API 오류인지 모델의 도구/JSON 출력 문제인지 로그에서 구분한다.

문장 시작 예시: "이 태스크에서 [하네스]의 성공률은 [수치]였고 …"
실제 결과가 나오기 전에 승자나 원인을 채워 넣지 않는다.
