# Week 08 (Midterm) — bjeon01: 정직한 가게와 기억하는 buyer

가게와 buyer를 `bjeon01`로 Round 3 시장(11/3~11/17)에 올렸다. 서버의 tmux에서 키트 v4를 자동 재접속 루프로 돌리고, 가게는 cloudflared 터널로 공개했다.

**원칙: 숫자로 정할 수 있는 것(원가, 최저가, 상한, 재고 구매, 별점)은 코드가, 말로 판단해야 하는 것(어느 가게를 믿을지, 흥정, 게시판 글)만 모델이 한다.** 날짜별 세부 기록과 실패한 시도는 [REPORT-log.md](REPORT-log.md)에 있다(시각은 UTC).

## 1. 부품별 설계

### 1.1 모델

| 어디에 | 모델(`claude -p --model haiku`)이 하는 일 | 코드가 정하는 것 |
|---|---|---|
| 가게 흥정 (`seller_r3.py`) | 반대제안, 수락, 거절 | 최저가 = 원가×1.08(식품), ×1.2(공산품). 원가 아래로는 팔지 않는다(상하기 직전 식품만 예외) |
| buyer 가게 고르기 (`market_buyer_r3.py`) | **애매할 때만**(거래 20건 미만, 거짓 등급 전력, 게시판 경고, 덜 아는 가게와 점수가 비슷) 툴로 조사해 고름 | 그 밖에는 코드 점수 1등을 바로 고름(약 4건 중 3건) |
| buyer 흥정 | 중간 제안, 포기 | 첫 제안 = 추정 원가, 상한 = 원가 + 마진의 30%, 좋은 값이나 되풀이되는 값은 바로 수락 |
| 게시판 글 (`review_r3.py`) | 정산된 사실로 짧은 글(한국어 + 영어 한 줄) | 별점, 재고 구매, 한도 |

- **호출 방식:** `harness.py`가 프롬프트를 stdin으로 넣는 headless 호출을 한다. 내장 툴과 프로젝트 설정은 끄고(`--tools "" --setting-sources ""`), 빈 임시 폴더에서 돌린다. buyer가 가게를 고를 때만 우리 MCP 툴 4개를 허용한다(`--strict-mcp-config --allowedTools mcp__market__*`).
- **실패 대비:** 모델 호출이 실패하거나 시간을 넘기면 예외를 내지 않고(`safe_ask_json`), 코드가 정한 대로 수락하거나 물러난다.

### 1.2 컨텍스트와 메모리

| 기억 | 내용 | 읽는 곳 |
|---|---|---|
| `buyer_memory_r3.jsonl` | 주문마다 거래 결과, 결제 거부 이유, 고장, 등급 주장이 사실이었는지 | buyer 신뢰 점수, `shop_record` 툴 |
| `sales_memory.jsonl` | 흥정마다 원가, 정가, 제시가와 제안 이력, 결과 | 가게 시작가 조정(`adapt`), 재고 구매 |
| `shop_prices.json`, `unit_costs.json` | 공개 장부를 1분마다 읽은 요약: 물건마다 원가, 가게마다 실제 판매가와 buyer가 깎은 마진 비율, 내 판매와 고장 환불 | 가게 한도 조정(`tune`), buyer 점수와 상한 |
| `market_sales.json` | 시장 전체의 상품별 판매 수와 가격(최근 3시간 스냅샷) | 재고 구매, 시작가, `sku_market` 툴 |
| `.market/forum.json` | 게시판 최신 100개 | 신뢰 점수(경고 글), `forum_search` 툴 |

**모델에게 주는 방법 (meta-harness)**
- 후기, 수천 건의 기억, 게시판 100개를 통째로 넣지 않는다. 코드가 후보(가게 × 상품)마다 한 줄로 요약한다: `가게 | 상품 | 정가 | 그 가게에서 깎인 마진 비율 | 후기 요약 | 내 기억 요약 | 게시판 요약`.
- 후보 순서는 코드 점수 = 신뢰 × 그 가게에서 깎이는 마진 비율 × 물어봤을 때 결제까지 가는 비율. 상위 8개만 보여 주고, 더 필요하면 모델이 툴로 찾는다. 등급 거짓이 두 번 걸린 가게는 빼고, 방금 실패한 가게는 30분 쉬게 한다.
- 가게는 최근 20번 흥정의 성사율과 받은 후기로 시작가를 조금씩 올리거나 내린다.

**주요 수정** (전체 15개와 근거 숫자는 REPORT-log.md)

| 날짜 | 문제 | 고친 것 → 효과 |

### 1.3 툴

| 툴 | 하는 일 | 어떻게 만들었나 |
|---|---|---|
| `shop_record(shop)` | 내 기억 속 그 가게의 성적 | `market_tools_mcp.py`, MCP Python SDK 2.x, stdio. 호출마다 `logs/tool_calls.jsonl`에 기록 |
| `shop_reviews(shop)` | 그 가게의 최신 후기 | 같은 서버. 주문마다 가게 목록 경로를 환경변수로 넘김 |
| `sku_market(sku)` | 시장 전체가 그 상품을 얼마에 몇 번 샀나 | 장부 누적 캐시와 카탈로그 |
| `forum_search(query)` | 검색어가 들어간 게시판 글 | `forum.json` |
| 키트 훅 `restock.py`, `review_r3.py` | 재고 구매 목록 / 별점·후기·게시판 글 | 키트 훅 규격(`{"buy": [...]}`, `outbox.jsonl`) |
| `tune`, `kit_watch.py` | 3시간마다 재고 한도 조정 / 키트가 8분 멈추면 재시작 | 모델 없는 코드 |

대회 전 모의 시험(가짜 재고와 주문)에서 모델은 툴을 6번 불러 게시판의 "등급 거짓" 경고 글을 찾았고, 후기는 별 5개지만 경고가 있는 가게 대신 기록이 깨끗한 가게를 골랐다.

### 1.4 코드가 지키는 선

| 쪽 | 규칙 |
|---|---|
| 가게 | 최저가 아래로 안 팖, 제시가를 올리지 않음, 제안 6번까지 |
| 가게 영수증 | 실제 등급만 주장(더 좋게 말하지 않음), 시장 인증서, 공산품 보증 6시간 |
| buyer | 제안 ≤ min(예산, 원가 + 마진 30%), 가게 호가보다 높게 안 냄, 결제 조건: 인증서 + 남은 유통기한 ≥ 사용 시간 + 1 + 공산품 보증 6시간 |
| buyer 후기 | 별점은 코드가 사실로 정함(등급 거짓 1점, 상하면 2점). 합의보다 싼 영수증은 벌주지 않음(7주차 교훈) |

## 2. 아키텍처와 키트 기본형과 다른 점

[architecture.pdf](architecture.pdf): 위에 시장, 왼쪽에 가게, 오른쪽에 buyer, 가운데에 둘이 함께 쓰는 **공개 장부 요약**이 있다. 그림의 ①②③이 이 구조의 핵심이다. ① 가격의 바닥은 코드가 지키고 모델은 말만 한다, ② 모델은 애매할 때만 부른다, ③ 같은 장부를 보고 스스로 고친다. 상자 안 회색 "기본:" 줄은 같은 자리에서 키트 기본형이 하는 일이다.

| 부분 | 키트 기본형 | 내 구조 |
|---|---|---|
| 재고 구매 | 재고가 줄면 무작위 상품 | 내 판매와 시장 인기 상품을 식품·가구 따로, 공급 창(20분마다 3분)이 열릴 때만. 한도는 3시간마다 자동 조정 |
| 가게 가격 | 원가 아래만 막음 | 시장 시세 + 성사율·후기로 시작가 조정, 오래된 재고는 원가까지 |
| 가게 영수증 | 등급·보증 없음 | 실제 등급, 인증서, 공산품 보증 6시간 |
| buyer 선택 | 가게를 고르지 않음 | 코드 점수 → 애매할 때만 모델 + 툴 |
| buyer 흥정·결제 | 모델이 다 정함, 조건 없음 | 원가 기준 상한, 결제 조건 |
| 기억·게시판 | 없음 | 가게별 기록, 게시판을 읽어 신뢰에 반영하고 정산 사실로 글을 씀 |

### 돌아보면

- **가장 큰 실수는 점수를 잘못 읽은 것이다.** 8일 동안 현금만 점수라고 생각해 재고를 줄이고, 마감 전 원가 이하 판매 규칙까지 만들었다. 규칙 문서를 다시 읽기 전까지 의심하지 않았다.
- **자동 조정이 다른 예산을 잠식할 수 있다는 것을 몰랐다.** 가구 한도를 올린 판단은 맞았지만 같은 구매 줄을 쓰던 식품이 밀려났다. 시장 전체와 비교하고서야 보였다.
- **모델을 덜 부를수록 buyer가 나아졌다.** 주문이 20초에 하나씩 오므로, 모델이 판단에 쓰는 10초가 곧 거래 수였다.
- **로그를 자주 커밋하지 않아** 11/3~6 키트 로그를 잃었다. 그 기간의 거래는 공개 장부와 기억 파일에 남아 있다.
