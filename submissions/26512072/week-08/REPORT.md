# Week 08 (Midterm) — bjeon01: 정직한 가게와 기억하는 buyer

가게와 buyer를 `bjeon01`로 Round 3 시장(11/3~11/17)에 올렸다. **원칙: 숫자로 정할 수 있는 것은 코드가, 말로 판단해야 하는 것만 모델이 한다.** 세부 기록과 실패한 시도는 [REPORT-log.md](REPORT-log.md)에 있다(시각은 UTC).

## 1. 부품별 설계

### 1.1 모델 (`claude -p --model haiku`, `harness.py`)

| 어디에 | 모델이 하는 일 | 코드가 정하는 것 |
|---|---|---|
| 가게 흥정 | 반대제안, 수락 | 최저가 = 원가×1.08(식품), ×1.2(공산품) |
| buyer 가게 고르기 | **애매할 때만**(거래 20건 미만, 거짓 등급 전력, 게시판 경고, 비슷한 후보) 툴로 조사해 고름 | 그 밖에는 점수 1등을 바로 고름(약 4건 중 3건) |
| buyer 흥정 | 중간 제안 | 첫 제안 = 추정 원가, 상한 = 원가 + 마진의 30% |
| 게시판 글 | 정산 사실로 짧은 글 | 별점, 재고 구매 |

모델이 실패하면(시간 초과 등) 코드가 대신 결정한다(`safe_ask_json`).

### 1.2 컨텍스트와 메모리

| 기억 | 내용 | 쓰는 곳 |
|---|---|---|
| `buyer_memory_r3.jsonl` | 주문마다 거래, 결제 거부, 고장, 거짓 등급 | 가게 신뢰 점수 |
| `sales_memory.jsonl` | 흥정마다 원가, 제시가, 결과 | 가게 시작가 조정, 재고 구매 |
| `shop_prices.json`, `unit_costs.json` | 공개 장부를 1분마다 읽은 요약: 물건마다 원가, 가게마다 실제 판매가, 내 판매와 환불 | 가게 한도 조정, buyer 점수와 상한 |

**모델에게 주는 방법 (meta-harness):** 후기·기억·게시판을 통째로 넣지 않는다. 코드가 후보(가게 × 상품)마다 한 줄로 요약해 상위 8개만 보여 주고, 더 필요하면 모델이 툴로 찾는다. 점수 = 신뢰 × 그 가게에서 깎이는 마진 비율 × 결제까지 가는 비율.

**주요 수정** (전체 15개는 REPORT-log.md)

| 날짜 | 문제 | 고친 것 → 효과 |
|---|---|---|
| 11/8 | 떠난 손님의 예약이 안 풀려 8시간에 흥정 17건 | 5분 뒤 해제 → 하루 정산 약 2,000건 |
| 11/11 | **점수를 현금만으로 잘못 이해**(실제는 재고 원가 포함) | 원가 아래 판매 금지, 재고 확대 |
| 11/12 | 키트가 멈추고 서버가 자꾸 재시작 | 감시 프로그램, 서버 이전 → 이후 재시작 0번 |
| 11/13 | 패치 3.6: buyer 점수가 마진 기준으로 바뀜 | 원가 기준 상한, 애매할 때만 모델 → 시간당 결제 50 → 88건 |
| 11/13, 15 | 자동 조정이 가구만 사게 해 식품이 떨어짐 | 식품·가구 따로 구매 → 가게 정산 시간당 40 → 70~100건 |

### 1.3 툴

| 툴 | 하는 일 |
|---|---|
| MCP 툴 4개 (`market_tools_mcp.py`, stdio) | `shop_record` 내 기록, `shop_reviews` 후기, `sku_market` 시세, `forum_search` 게시판 검색 |
| 키트 훅 | `restock.py` 재고 구매, `review_r3.py` 별점·게시판 글 |
| `tune` (r3lib) | 3시간마다 재고 한도를 내 판매·환불로 조정 |

대회 전 모의 시험에서 모델은 툴을 6번 불러 게시판의 "등급 거짓" 경고를 찾고, 후기는 좋지만 경고가 있는 가게를 피했다.

## 2. 아키텍처와 키트 기본형과 다른 점

[architecture.pdf](architecture.pdf): 가운데의 **공개 장부 요약**을 가게와 buyer가 함께 쓴다. 그림의 ①②③이 핵심이다. ① 가격의 바닥은 코드가 지키고 모델은 말만 한다, ② 모델은 애매할 때만 부른다, ③ 같은 장부를 보고 스스로 고친다.

| 부분 | 키트 기본형 | 내 구조 |
|---|---|---|
| 재고 구매 | 재고가 줄면 무작위 | 잘 팔리는 것을 식품·가구 따로, 한도는 3시간마다 자동 조정 |
| 가게 영수증 | 등급·보증 없음 | 실제 등급, 인증서, 공산품 보증 6시간 |
| buyer 선택 | 가게를 고르지 않음 | 코드 점수 → 애매할 때만 모델 + 툴 |
| buyer 흥정·결제 | 모델이 다 정함, 조건 없음 | 원가 기준 상한, 결제 조건(인증서·유통기한·보증) |
| 기억·게시판 | 없음 | 가게별 기록, 게시판을 읽고 쓴다 |

**결제 거부 사유** (키트 로그 원문, 11/6 이후. 11/3~6 로그는 잃었다)

| 횟수 | 로그 |
|---|---|

거부율은 결제 시도의 6.1%였고, 11/13에 첫 답에서 미리 걸러 내게 한 뒤 1~2.5%로 줄었다.

**10주차 LAB 기준 숫자.** LAB을 따로 하지는 않았다. 주문 전에 하는 행동인 restock 규칙을 고칠 때 재 둔 "고치기 전" 숫자를 기준선으로 쓴다.

| 행동 | 기준 (고치기 전) | 고친 뒤 |
|---|---|---|
| 11/13 식품·가구 따로 구매 | 가게 정산 시간당 40건, book 시간당 +12만 원 | 시간당 93~103건, book 시간당 130만~180만 원 |
| 11/15 식품 후보 45 → 150개 | 한 번에 식품 5개 구매 | 한 번에 96개, 가게 정산 시간당 70~80건 |

### 돌아보면

- **가장 큰 실수는 점수를 잘못 읽은 것이다.** 8일 동안 현금만 점수라고 생각했다.
- **자동 조정이 다른 예산을 잠식할 수 있다는 것을 몰랐다.** 가구 한도를 올리자 식품이 밀려났다.
- **모델을 덜 부를수록 buyer가 나아졌다.** 주문이 20초에 하나씩 와서, 모델이 쓰는 10초가 곧 거래 수였다.
- **로그를 자주 커밋하지 않아** 초반 로그를 잃었다.
