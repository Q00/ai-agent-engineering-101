# Week 08 (Midterm) — bjeon01: 정직한 가게와 기억하는 buyer

가게와 buyer를 `bjeon01`(GitHub `@BJEon01`)로 Round 3 시장에 올렸다. 연구실 서버의 tmux에서 키트 v4를 자동 재접속 루프로 돌리고, 가게는 cloudflared 터널로 공개했다. 아키텍처 그림은 [architecture.pdf](architecture.pdf)(원본 [architecture.tex](architecture.tex))에 있다.

**설계 원칙:** 숫자로 정할 수 있는 것(원가, 최저가, 상한, 재고 구매, 별점)은 코드가 정한다. 말로 판단해야 하는 것(어느 가게를 믿을지, 흥정, 게시판 글)만 모델이 한다. 모델이 쓰는 정보는 코드가 한 줄로 요약해 주고, 더 필요하면 모델이 툴로 직접 찾아본다.

| buyer 흥정 | claude -p `haiku` | 중간 제안 가격, 포기. 첫 제안(추정 원가)과 수락·마지막 제안은 코드가 정한다 |
| 게시판 글 (`review_r3.py`) | claude -p `haiku` | 정산된 사실을 짧은 글로 (한국어 + 영어) |
| restock, 최저가, 상한, 별점 | 모델 없음 | 코드 |

- **호출 방식:** `harness.py`는 프롬프트를 stdin으로 넣는 headless 호출이다(`claude -p --model haiku --tools "" --setting-sources "" --no-session-persistence`). 빈 임시 폴더에서 실행해 프로젝트 설정을 읽지 않는다.
- **툴 쓰는 호출(`ask_json_tools`):** MCP 설정 파일을 만들어 `--mcp-config ... --strict-mcp-config --allowedTools mcp__market__*`로 우리 툴 네 개만 허용한다. 내장 툴은 꺼 둔다. 툴 호출이 실패하면 툴 없는 호출로 대신한다.

### 1.2 컨텍스트와 메모리

| 저장소 | 쓰는 쪽 | 내용 | 읽는 쪽 |
|---|---|---|---|

**컨텍스트를 만드는 방법 (meta-harness)**
- buyer 프롬프트에는 후보(가게 × SKU)마다 한 줄만 들어간다: `가게 | SKU | 이름 | 정가 | 수량 | 후기 요약 | 내 기억 요약 | 게시판 요약`.
- 후보 순서는 코드 점수(신뢰도 × 그 가게에서 깎이는 마진 비율 × 결제까지 가는 비율)로 정하고 상위 8개만 보여 준다. 신뢰도는 후기 평균에서 출발해 내 기억(등급 거짓, 고장, 결제 거부)과 게시판 경고로 깎는다. 등급 거짓이 두 번 걸린 가게는 뺀다. 확실한 경우에는 모델에게 묻지 않고 코드가 1등을 고른다.
- 리뷰 10개씩 × 가게 수십 곳, 수천 건의 기억, 게시판 100개를 프롬프트에 다 넣지 않는다. 모델은 요약을 보고, 필요한 것만 툴로 찾는다.

### 1.4 코드가 지키는 선 (guard)

| 쪽 | guard |
|---|---|
| 가게 | 최저가 = 원가 × 1.08(식품) / 1.2(비식품. 11월 4일 1.15 → 1.08로 내렸다가, 우리 비식품 고장률 9%를 보고 11월 5일 1.2로 올림). 24시간 안에 상할 식품만 원가 아래 허용. 호가는 올리지 않음. 3% 차이면 수락. 제안 6번 한도 |
| 가게 영수증 | `claim` = 그 단위의 실제 등급(더 좋게 말하지 않음), 시장 증명서 유지, 비식품 6시간 보증 |
| buyer | 제안 ≤ min(예산, 추정 원가 + 마진의 30%) (11월 11일까지는 정가, 11~13일은 정가의 72%, 패치 3.6 뒤로 원가 기준), 제안 ≤ 가게의 현재 호가, 공산품은 6시간 보증을 요구하고 "no warranty"라고 답한 가게와는 흥정하지 않음, 유통기한이 `use_within_hours`보다 짧은 식품은 후보 제외, 결제 조건 `accept`: 증명서 + 남은 유통기한 ≥ `use_within_hours`+1 |
| buyer 후기 | 등급 거짓 1점, 상해서 가치 0이면 2점, 정가 대비 15%↑ 싸면 5점, 5%↑ 4점, 정가 이하 3점. 합의보다 싼 영수증은 벌주지 않음 (7주차 "억울한 고발" 교훈) |
| buyer 오류 | 상대가 흥정 중 서버 오류를 내도 결과 줄을 남김. 상대 오류는 2점, 연결 실패는 중립 3점 (7주차 "1점 폭격" 교훈) |

## 2. 아키텍처와 키트 기본형과 다른 점

[architecture.pdf](architecture.pdf) (11월 22일, 한국어로 간추려 다시 그림): 위에 시장, 왼쪽에 가게(재고 사기 → 손님과 흥정 → 영수증), 오른쪽에 구매자(가게 점수 → 애매하면 모델, 아니면 코드가 고름 → 흥정), 가운데에 둘이 함께 쓰는 **공개 장부 요약**(물건마다 원가, 가게마다 실제 판매가, 내 판매와 환불)이 있다. 그림의 ①②③이 이 구조의 핵심 세 가지다: ① 가격의 바닥은 코드가 지키고 모델은 말만 한다, ② 모델은 애매할 때만 부른다, ③ 같은 장부를 보고 재고 한도를 스스로 고친다. 상자 안의 회색 "기본:" 줄은 같은 자리에서 수업 키트의 기본형이 하는 일이다. 더 자세한 수치와 차이는 아래 표와 1부에 있다.

| 부분 | 키트 기본형 (starter) | 내 구조 |
|---|---|---|
| restock | 재고가 20개 아래로 떨어지면 무작위 카테고리의 무작위 SKU | 내 판매(×3) + 시장의 최근 3시간 인기 SKU를 정산 금액 순으로, **싼 상품과 비싼 상품을 따로**(한 번에 10줄 / 4줄) + 게시판 "구합니다". 공급 창(20분마다 3분)이 열렸을 때만 산다. 재고 한도·최고 정가는 `tune`이 3시간마다 내 정산·환불·재고 나이로 범위 안에서 조정 |
| 가게 품질 | 등급을 말하지 않음, 보증 없음 | 실제 등급 주장, 증명서, 비식품 6시간 보증 |
| 가게 가격 | 원가 아래만 막음, 고정 | 성사율과 후기로 시작가 조정, 오래된 재고 정리 |
| buyer 선택 | (7주차 starter: 가게 선택 없음) | 코드 후보 점수(신뢰 × 그 가게에서 깎이는 마진 비율 × 결제까지 가는 비율). 확실하면 코드가 고르고, 판단이 필요하면 모델이 MCP 툴로 조사 후 선택 |
| buyer 기억 | 없음 | 정산 결과, 결제 거부, 고장을 가게 이름에 연결 |
| 결제 조건 | 없음 | 증명서, 남은 유통기한, 공산품 6시간 보증 |
| 게시판 | 쓰지도 읽지도 않음 | 읽어서 신뢰와 재고에 반영, 정산 사실로 글쓰기 |

### 3.5 돌아보면

- **가장 큰 실수는 점수를 잘못 읽은 것이었다.** 8일 동안 현금만 점수라고 생각해서 재고를 줄이고, 마감 전 원가 이하 판매 규칙까지 만들었다([REPORT-log.md](REPORT-log.md)). agent.md를 다시 읽기 전까지 이 오해를 의심하지 않았다.
- **자동 조정은 "다른 예산을 잠식할 수 있다"는 것을 몰랐다.** `tune`이 비싼 상품 한도를 올린 판단 자체는 맞았지만, 같은 구매 줄을 나눠 쓰던 식품이 밀려났다. 이 문제는 장부 전체와 비교하고 나서야 보였다(11/13, 11/15 두 번).
- **모델을 덜 부를수록 buyer가 나아졌다.** 시장이 buyer에게 주문을 20초에 하나만 주므로, 주문 하나에 모델 판단 10초를 쓰면 그만큼 거래가 줄었다. 확실한 경우는 코드가, 애매한 경우(새 가게, 게시판 경고, 비슷한 후보)만 모델이 고르게 한 것이 가장 효과가 컸다.
- **로그를 자주 커밋하지 않아 11월 3~6일 키트 로그를 잃었다.** 그 기간의 거래는 공개 장부와 메모리 파일에 남아 있다.
