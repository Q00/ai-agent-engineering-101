## 1. 하네스, 모델, 실행 방법

판매자와 구매자 모두 **Claude Code 2.1.287의 `haiku` 별칭**을 사용한다.
설치와 계정 로그인을 확인한 뒤 기존 구독 인증으로 실행했다. 별도의 API 키를
코드나 제출 파일에 기록하지 않았다. 모델 별칭은 서비스에서 해석되므로 고정된
모델 스냅샷이나 동일한 가격의 재현을 보장하는 의미는 아니다.

`harness.py`가 실행하는 명령은 다음과 같다. 프롬프트와 현재 협상 내용은 stdin으로
전달하며, 매번 새 임시 빈 디렉터리를 작업 디렉터리로 사용한다.

```bash
claude -p --model haiku --tools '' --setting-sources '' --no-session-persistence --strict-mcp-config --disable-slash-commands
```

도구와 MCP 및 슬래시 명령을 사용하지 않고, 저장소 지시문을 읽어 협상 대신
파일을 수정하는 동작이 섞이지 않도록 했다. 판매자와 구매자의 역할은 동일한
모델을 쓰더라도 별도 프롬프트와 명시적으로 전달하는 대화 이력으로 구분한다.

Python 3.12와 전용 `.venv`를 사용했다. 직접 의존성은
`a2a-sdk[http-server]==1.2.2`, `uvicorn==0.54.0`, `httpx==0.28.1`이며,
전이 의존성까지 포함한 실제 환경은 `requirements-lock.txt`에 기록했다.
`agent.json`의 판매자 명령은 `.venv/bin/python seller_agent.py --port {port}`,
구매자 명령은 `.venv/bin/python buyer_agent.py --url {url} --item {item} --budget {budget}`다.
준비·재실행 명령은 `README.md`에 있다.

## 2. 판단 과정과 제한

### 판매자

사용자가 선택한 전략은 **높게 시작해 흥정할 여유를 두는 것**이다.
`prompts/seller_opening.txt`에 그 목표를 명시하고, 처음 구매 요청의 물품과 하한가,
구매자 메시지를 전달한다. 모델이 정한 `price`와 판단 이유 `reason`을 JSON으로 받는다.
예전 실습의 `reserve * 1.3` 계산식은 제거했다. 첫 응답은 과제의 통신 계약에 맞춰
항상 input-required 상태로 그 가격을 제시한다.

이후에는 `prompts/seller.txt`와 함께 물품, 하한가, 현재 제안, 전체 협상 이력을 전달한다.
모델은 `counter`, `accept`, `reject` 중 행동을 정한다. 역제안 가격을 계산하는 평균
공식, 제안이 하한가 이상이면 자동 수락하는 조건, 낮은 제안 세 번 후 자동 거절하는
조건은 모두 제거했다. 수익이 가능한 합의에 점차 접근하되 불가능한 거래는 끝내라는
방향은 프롬프트에 적었으며 정확한 가격과 중단 시점은 모델이 결정한다.

하한가(lamp 100, chair 180, bookshelf 260)는 프롬프트와 코드 양쪽에 둔다.
코드는 모든 제시·수락 가격이 양의 정수이고 하한가 이상인지 검사한다. 수락 가격은
구매자가 실제로 제시한 값과 같아야 한다. 위반한 결정을 하한가로 보정하여 실행하지
않는다. 결정의 출력이 잘못되면 오류를 알려 모델에 한 번만 다시 묻고, 다시 실패하면
task를 failed로 끝낸다. unsupported item과 숫자가 아닌 입력의 처리는 카탈로그 및
입력 형식 검증이며 새로운 협상 가격을 만들지 않는다.

### 구매자

`prompts/buyer.txt`에 예산 내에서 구매하고, 처음 부른 가격이 높다고 즉시 포기하지
말고 협상하라는 목표를 적었다. 구매자는 물품·예산·현재 판매자 응답·대화 이력을
모델에 전달한다. 상대의 비공개 하한가나 검사기의 제안 순서는 전달하지 않는다.
모델이 `offer`, `accept`, `walk_away`를 정하고 가격과 이유를 반환한다. 제안·수락은
숫자 메시지로, 포기는 CancelTask로 전송한다. 첫 물품 요청과 카드 조회는 통신 준비다.

예산 역시 프롬프트와 코드 양쪽에서 검사한다. 코드가 임의로 예산만큼 제안하는
대체 전략은 없다. 가격은 양의 정수이면서 예산 이하여야 하고, `accept`라면 판매자가
실제로 제시한 마지막 가격과 일치해야 한다. completed 응답의 영수증에는 정확히 한 개의
숫자 가격이 있어야 하며, 예산 이내이고 마지막으로 모델이 승인한 제안과도 같아야 한다.

### 실행 및 통신

하네스 출력은 JSON 객체 또는 전체가 하나의 JSON 코드 블록인 경우만 허용한다.
bool, 문자열 가격, NaN/Infinity, 하한가·예산 위반을 거부한다. 형식·제한 위반의 재질문은
최대 한 번이며 두 시도 전체가 한 번의 제한 시간(기본 90초)을 공유한다. 프로세스 실행·인증·
시간 초과 오류에서는 계산식으로 대체하지 않고 실패를 기록한다.

구매자는 카드에서 A2A 1.0 JSONRPC 주소를 읽고 GET/POST에 `A2A-Version: 1.0`을 붙인다.
후속 메시지에는 같은 taskId를 넣는다. HTTP 요청과 응답, 모델 결정은 stdout에 기록하고,
각 하네스 호출의 프롬프트·원본 stdout/stderr·검증 결과는 고유 파일명으로 저장한다.
270초의 실행 기한과 12회 판단 상한은 무한 실행을 막는 운영 제한이며, 여기에 도달하면
오류를 알리고 정리할 뿐 새로운 협상 결정을 대신 만들지 않는다.

## 3. 실패, 수정, 검증 기록

주요 구현·코드 검토·자동 검증은 Codex를 사용해 수행했다. 먼저 사용자가 규칙 기반 실습을 직접 수행했고,
첫 가격의 전략을 선택했다. 이후 첫 가격 연결, 응답 형식 수정, 판매자 후속 판단,
구매자, 실행 설정과 검증을 각각 커밋으로 남겼다. 과제 전체를 한 번의 커밋으로 합치거나
실패 기록을 지우지 않았다.

실제 첫 하네스 실행에서 Claude가 가격 125를 반환했지만 JSON을 Markdown 코드 블록으로
감쌌다. 당시 파서는 순수 JSON만 받았으므로 다음처럼 실패했다.

`logs/opening-c6021350801d472e8daec0dddfdb5162.log`의 원본:

```text
EXIT: 0
VALIDATION ERROR: The harness response was not JSON
```

프로세스 종료 코드가 0이라고 해서 애플리케이션의 응답 형식까지 맞는 것은 아니었다.
`f076172`에 실패 코드와 원본 로그를 먼저 보존하고, `e1ed5a9`에서 전체 응답이 하나의
코드 블록일 때 바깥 표시만 제거하도록 수정했다. 내부 가격을 바꾸거나 임의의 JSON 일부를
추측해 꺼내지 않았다. 회귀 검사는 바로 그 실패 로그를 다시 읽어 원래 가격 125가 유지되는지

## 4. A2A가 해결한 것과 별도로 합의한 것

A2A는 판매자의 주소·기능을 Agent Card로 발견하고, 메시지를 taskId로 이어 붙이며,
입력 대기·완료·거절·취소 상태와 영수증 artifact를 전달하는 공통 틀을 제공했다. 따라서
상대가 내부적으로 어떤 하네스를 쓰는지 몰라도 HTTP 요청과 task 상태로 거래를 이어 갈 수
있었다. 하지만 A2A 자체가 물품 이름, 가격의 단위나 텍스트 표현, 흥정 전략, 수락의 의미를
정해 주지는 않는다. 이 구현은 lamp/chair/bookshelf라는 이름, 정수 가격, 판매자 메시지의
마지막 숫자가 현재 제시가라는 약속, 같은 task에 숫자를 보내는 구매자 제안·수락 표현,
영수증 DataPart의 `price` 필드를 별도로 합의했다. 이 약속이 다르면 A2A 통신은 성공해도
상대의 가격을 잘못 읽거나 거래 의미를 다르게 해석할 수 있다.

## 5. 필수 Challenge 1·2: 큰 문맥의 처리

### 명세 확인에서 놓친 점

처음에는 로컬의 이전 README를 기준으로 기본 테스트 21개가 통과하면 제출 준비가
끝난 것으로 판단했다. 다른 PR을 비교하면서 upstream의 `096c9c3`에서 Challenge 1·2가
필수로 추가된 사실을 발견했다. 자동 검사기는 이 두 항목을 확인하지 않았다.
완료 판단을 정정하고 최신 upstream을 병합한 뒤 아래 구현과 실제 실행을 추가했다.
코드·테스트 작성과 실행은 계속 Codex로 진행했고, 사용자에게 후보 검색 방식과
총예산을 예약하는 방식을 설명했다. 선택한 높은 시작 가격 전략은 유지했다.

### Challenge 1: 설명으로 상품 찾기

`generate_catalog.py`가 `data/catalog.json`의 **4,000개 합성 상품**을 결정적으로
생성한다. lamp/chair/bookshelf/table 각 1,000개이며 재질·높이·폭·색·형태가 다르다.
각 상품은 고유 SKU, 이름, 설명, 하한가와 검증 가능한 속성을 가진다. 외부 데이터셋이나
모델 생성 데이터가 아니다. 기본 검사기의 lamp/chair/bookshelf 하한가 100/180/260과
확장 SKU별 하한가는 별도의 카탈로그 계약이다. 기존 기본 명령은 그대로 재현된다.

`catalog_seller.py`의 첫 요청은 상품명이나 SKU가 아닌 자연어 설명이다.
`catalog_query.txt`로 모델이 용도·재질·치수·수납량 등을 구조화한다. `catalog.py`는
그 조건으로 전체 카탈로그를 검색하고, 수납량 초과분과 크기·ID로 정렬하여 최대
8개 후보만 `catalog_select.txt`에 전달한다. 최종 상품과 첫 가격은 모델이 정한다.
따라서 검색은 코드가 하지만 의미 해석·선택·흥정은 하네스가 맡는다. 지원하지 않는
속성이나 모호한 치수는 확인 질문을 하도록 했고, 모델이 반환한 후보 밖 SKU나 해당
상품의 하한가 미만 가격은 검증 오류다. 가격을 자동 보정하는 대체 전략은 없다.

후속 협상은 선택 상품을 고정한 채 기존 `seller_decision`을 사용한다. 공개 quote의
DataPart는 `{product, ask}`, 영수증은 `{seller, item: SKU, product, price}`다.
하한가는 공개하지 않는다. 취소 중 추론 결과가 늦게 와도 거래가 재개되지 않도록 했다.

실제 명령은 `.venv/bin/python run_challenges.py --challenge 1`이다.
원본 기록: `logs/challenge-1/20261013T170529Z-a07584e4/`.
이 검사의 구매 상대는 현재 제시가를 수락하는 **스크립트 검사 고객**이며,
판매자의 의미 해석·상품 선택·수락은 실제 Claude다. 결과는 4개 사례 모두 통과했다.

| 상품명을 사용하지 않은 요구 | 선택 SKU | 실제 거래가 / 상품 하한가 | 결과 |
|---|---|---|---|
| 나무, 40권 이상, 높이 75cm 이하 | bookshelf-0121 | 160 / 104 | 70cm·40권 상품 |
| 금속, 책상 독서 조명, 높이 55cm 이하 | lamp-0251 | 130 / 57 | 금속·25cm 상품 |
| 패브릭 덮개 좌석, 높이 100cm 이하 | chair-0502 | 130 / 94 | 패브릭·75cm·덮개 있음 |
| 나무, 200권 이상, 높이 20cm 이하 | 선택 없음 | 거래 없음 | 확인 질문 후 검사 고객이 취소 |

`catalog-shop-server.log`에는 목재 수납 요청의 검색 결과가 다음과 같이 남았다
(같은 JSON 행에서 수치 필드만 발췌):

```text
"total": 4000, "matched_count": 30, "candidate_count": 8
```

다른 두 검색은 후보 조건에 맞는 상품 200개·250개 중 각각 8개만 모델에 전달했다.
전체 카탈로그를 매 턴 프롬프트에 붙이지 않았다. 실제 하네스 호출은 10회이고
이 실행에서 형식 수정 재질문은 없었다. `result.json`은 선택 속성, 제시가,
영수증과 상품별 하한가를 독립적으로 비교한 결과다. 불가능한 요청에 대한 확인
질문의 일반적인 가구 설명은 모델의 추정이며, 데이터셋 검증 결과로 해석하지 않는다.

### Challenge 2: 여러 가게의 상태와 총예산 관리

`run_challenges.py`는 품목 4종 × 재고 분할 5개의 **20개 로컬 가게**를 띄운다.
각 가게에는 200개의 서로 다른 SKU가 있고, 가게별 하한가 설정도 다르다.
구매자는 URL 디렉터리에서 20개의 Agent Card를 읽고, skills와 장보기 목록 및
**총예산 450만** `shopping_plan.txt`에 전달한다. 상대 하한가나 검사 정답 SKU를
구매자 프롬프트에 전달하지 않는다. 모델은 품목별 가게와 예산 배분을 선택한다.

계획이 모든 품목을 정확히 한 번 배정하고 합계가 총예산 이내인지 코드가 검사한 뒤,
전체 금액을 먼저 예약한다. 그 후 `asyncio.gather`로 협상을 동시에 진행한다.
이번 계획은 수납 150, 조명 100, 좌석 200이었다. 각 협상은 자기 배정액을 넘을 수
없으며, 구매 영수증을 합산할 때도 전체 예산과 중복 품목을 다시 검사한다. 모델이
정한 배정액을 코드가 나눠 계산하거나, 남은 돈을 임의로 다른 품목에 옮기지 않는다.

각 협상 상태는 정확한 사실과 모델 요약으로 나눈다.

- 정확한 사실: taskId, 가게 ID, 상품 속성, 배정 예산, 현재 제시가, 직전 제안, 턴 수.
- 모델 문맥: 최대 **800자 요약과 최근 메시지 2개**. 모델이 매 결정마다 새 요약을
  작성해 이전 요약을 대체한다. 전체 대화는 로그에 남기지만 다음 프롬프트에는 붙이지 않는다.

요약은 협상 흐름을 이어 가는 보조 정보다. 요약에 다른 가격이나 예산이 적혀도
정확한 상태와 검증 규칙을 바꿀 수 없다. `shopping_negotiate.txt`는 각 제안·수락·포기와
요약을 JSON으로 받는다. 구매 전 상품 조건, 구매 후 정확히 같은 SKU·속성·승인 가격의
영수증인지 확인한다. A2A 카드가 상품 속성·요약·전역 예산의 의미까지 정해 주지는 않으므로
이 부분 역시 두 프로그램이 별도로 공유하는 계약이다.

실제 명령은 `.venv/bin/python run_challenges.py --challenge 2 --budget 450`이다.
원본 기록: `logs/challenge-2/20261013T170604Z-ded15e43/`.
이 실행은 구매자·판매자 모두 실제 Claude를 사용했다.

| 목록 품목 | 모델이 선택한 가게 | SKU | 구매가 | 예약 예산 |
|---|---|---|---|---|
| 목재 수납 | bookshelf-shop-1 | bookshelf-0121 | 124 | 150 |
| 금속 조명 | lamp-shop-2 | lamp-0257 | 100 | 100 |
| 패브릭 좌석 | chair-shop-3 | chair-0518 | 128 | 200 |
| 합계 | 서로 다른 3개 가게 | 3개 모두 구매 | **352** | **450** |

`shopping-result.json`의 실제 값은 다음과 같다(각 필드 발췌):

```text
"total_spent": 352.0,
"budget": 450,
"missing": [],
"duplicates": [],
"cards_read": 20,
"peak_concurrent_negotiations": 3,
"peak_distinct_shops": 3
```

`buyer.log`에는 세 협상 모두 2회씩 판단한 기록이 있다. 예를 들어 조명은 모델이
85를 제안한 뒤, 판매자가 125에서 100으로 낮추자 100을 수락했다. 첫 판단의 요약이
두 번째 `compact_context`에 그대로 전달되었고, 이후 새 요약으로 대체되었다.
두 번째 판단의 원본 요약에는 다음 문장이 들어 있다.

```text
Seller moved from initial 125 to 100.
```

이전 요약 재사용은 실제로 3회 확인했다. 모델에 전달한 요약은 최대 226자였고,
최종 생성 요약까지 포함하면 최대 254자였다. 최근 메시지는 항상 2개 이하였다.
총 29개의 HTTP 요청 모두 버전 헤더를 포함했고 각 협상은 자기 taskId를 유지했다.
하네스 호출은 계획 1회, 카탈로그 해석·선택 6회, 구매자 판단 6회, 판매자 판단 6회로
총 19회였다. 형식 수정 재질문은 없었다. 검사기는 구매자 결과와 별도로 원래
장보기 조건, 각 가게의 하한가, 전체 합계 및 누락·중복을 검사했다.

두 Challenge 모두 첫 전체 실행에서 통과했다. 실패를 만들거나 성공한 것처럼
수정한 로그는 없다. 원본 29회 모델 호출과 두 실행 결과는 `5103e0b`에 보존했다.
오프라인 검사는 기존 21개와 신규 17개를 합친 **38개 통과**이며,
`logs/challenge-unit-a20c4acb7d4049dd9f504a3235d01591.log`에 있다. 이 검사는
모델·통신을 대체한 경계 검사이며 실제 챌린지 로그와 구분한다. 최신 공식 기본
검사 파일의 해시는 기존 결과와 동일하므로 그 21/21 기록도 유효하다.

## 6. 범위와 한계

수업용 로컬 서버이며 task와 협상 이력은 메모리에 있다. 재시작하면 이어서 거래할 수 없고,
실제 결제나 재고 관리는 하지 않는다. 검증은 task당 순서대로 메시지를 보내는 방식이다.
같은 task에 여러 메시지를 동시에 보내는 일반 서비스용 동시성까지 보장하지 않는다.
HTTP 시간 제한은 요청별·남은 시간 기준이며, 비정상적으로 데이터를 조금씩 보내는 외부 서버의
완전한 벽시계 제한까지 별도로 검증하지 않았다. 모델 별칭, 서비스 상태, 자연어 판단에 따라
가격과 호출 수는 달라질 수 있으며 한 번의 통과가 모든 미래 실행의 통과를 보장하지 않는다.

확장 구매자는 최초 가게·예산 배분 후 다른 가게로 갈아타거나 예산을 재분배하지 않는다.
확인 질문, 거절, 형식 오류, 시간 초과가 생기면 임의 상품을 사지 않고 미구매 또는 오류로
보고한다. 자연어 해석이 모든 미지의 요구사항에 정확하다는 보장은 없으며, 고정된 지원
속성의 검색과 세 성공 사례·한 미충족 사례를 검증했다. 상품 설명과 attrs의 정합성도
자체 합성 데이터 범위의 검증이다. 쇼핑 목록의 구조화 조건은 입력 파일의 계약이며,
자연어만으로 모든 사용자 조건을 자동 추출하는 구매자까지 구현한 것은 아니다.

각 협상의 최근 문맥은 일정 크기로 유지하지만, 20개 카드의 skills는 최초 계획에서
함께 읽는다. 임의로 거대한 외부 Agent Card나 초장문 상품 설명에 대한 별도 압축은 없다.
Challenge 3의 장문 속 가격 추출·공격 실험과 공개 서버 배포, 다른 학우와의 교차 거래는
가산점/선택 항목으로 이번 제출에 포함하지 않았다. 두 필수 챌린지의 실험 서버는 모두
종료했으며, `run_challenges.py`가 재실행 시 새 포트와 디렉터리를 만든다.

제출용 `week-06-submit`은 최신 upstream을 기준으로 6주차 작업 커밋을 하나씩 옮긴
별도 브랜치다. 기존 `week-06` 작업 브랜치와 실패·수정 이력은 그대로 보존한다.
이 보고서에서 인용한 커밋 ID는 원래 작업 브랜치의 ID이며, 제출용 브랜치에서도
각 작업을 독립 커밋으로 유지한다. 이전 주차 변경은 제출용 비교에 포함하지 않는다.
