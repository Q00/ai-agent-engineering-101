모델은 도구 없는 단일 CLI 턴에서 JSON 결정을 반환한다. Python 하네스가 형식과 허용 행동을 검사한 다음 실행한다. Shop의 모델 동시 호출은 최대 3개이며, 이는 Shop 에이전트 3개를 뜻하지 않는다. Buyer는 후보를 최대 6곳으로 줄이고, 거래 시도에 공유되는 판단 횟수를 제한한다. 인증된 견적이 조건을 충족하거나 충분히 신선한 거래 기억이 있으면 모델 호출을 생략하는 경로를 둔다.

운영 전략가는 코드 관측을 30분마다 수행하되, 정기 모델 판단은 2시간 간격으로 분리했다. 같은 근거의 반복 분석을 건너뛰며 하루 최대 16회, 이벤트 호출도 최소 5분 간격을 적용한다. **Round 3 설정은 `mode: propose`다.** 제안과 정책 적용 경로는 구현했지만, 운영 전략가가 스스로 실거래 정책을 바꿔 점수를 개선했다고 주장하지 않는다. 이후 Round 4에서 추가한 자동 적용 기능은 이 보고서의 실적으로 포함하지 않는다.

컨텍스트 압축의 검증 범위도 구분했다. 11월 3일 합성 협상에서 판매자 입력 문자 수는 48.0~48.8% 줄었지만, 이는 실제 청구 토큰이나 매출 개선을 측정한 결과가 아니다. 예를 들어 짧은 비식품 문의는 17,710자에서 9,061자로 줄었다. [압축 비교 원본](logs/seller-context-comparison-20261103T015006Z-2d603d90.log)

### 1.3 도구와 실행 경계

공식 v4 키트의 등록, A2A 전송, 재고 동기화, ACP checkout과 AP2 결제 위임장 연동을 사용한다. 해당 키트 전체를 직접 구현했다고 주장하지 않는다. 학생 코드에서 추가한 핵심 도구는 다음과 같다.

- **견적·영수증 도구:** 가격뿐 아니라 SKU·등급·보증·인증서 정보를 구조화해 전달한다. 가격 하한과 실제 unit을 검사한 뒤 영수증을 서명한다.
- **결제 보호 도구:** checkout 생성과 complete에서 같은 영수증 조건을 검사한다. 취소·만료된 예약은 회수하지만 `settling`·`uncertain` 상태를 임의로 미결제 처리하지 않는다.
- **재입고 도구:** 공급창, 실제 재고, 최근 판매 근거, 현금과 원가 한도 안에서 매입 계획을 낸다. 계획 생성과 실제 입고 성공은 구분한다.
- **구매·리뷰·게시 도구:** 협상 결과를 검증하고 실제 정산을 확인한 뒤 리뷰와 거래 보고를 만든다. 같은 거래를 반복 게시하지 않도록 간격과 중복 방지를 적용한다.
- **관측 도구:** [Shop 진단](shop_diagnostics.py)과 [Buyer 진단](buyer_diagnostics.py)이 제한된 로컬 로그를 읽어 협상·정산·거부 이유를 구분한다. 진단 자체는 거래 상태를 바꾸지 않는다.

최종 기본 정책에서 Shop의 등급별 마진 하한은 A 10%, B 5%, C 0%이며 조건부 마감에서는 B 2%를 허용한다. A급 비식품 보증은 6시간이다. 재입고는 현금 유보, 전체 재고 60개, 공급창당 최대 8개 등 여러 한도를 동시에 적용한다. Buyer의 구매 상한은 예산 90%와 정가 85% 등 적용되는 한도 중 더 엄격한 값이며, 비식품 A/B와 보증 최소 3시간을 요구한다. 식품은 A/B/C를 허용하되 사용 기간에 1시간 여유를 더해 검사한다. 구매 허용 조건과 높은 리뷰 점수를 주는 선호 조건은 별개다. [판매 정책](shop-policy.json), [구매 정책](buyer-policy.json)

## 2. 아키텍처와 기본 키트 대비 변경

[한 페이지 아키텍처 PDF](architecture.pdf) · [LaTeX 원본](architecture.tex)

도식의 세 열은 Shop, Buyer, 운영 분석을 나타낸다. 각 하네스는 저장된 근거에서 컨텍스트를 고르고, 모델의 판단을 받아 코드의 제약 검사를 통과시킨다. 아래의 공식 키트가 시장과 통신하고, 결과가 로그와 기억으로 돌아온다. 실선은 거래 실행 경로, 점선은 관측·제안 경로다. 운영 분석과 재고 계산은 구분했으며, 운영 제안이 자동으로 거래 정책에 반영되는 것처럼 그리지 않았다.

실행 진입점은 `run_round3.py → market_runtime.py → vendor/market_kit_v4.py`다. 원본 키트의 Git blob SHA를 먼저 검사하고 학생 코드의 `GuardedAcpShop`, 시장 시각 보정, Buyer 게시 처리를 연결한다. [원본 출처·해시](vendor/SOURCE.json)에 기록된 키트 바이트는 수정하지 않았다.

| 항목 | 공식 Round 3 starter의 기준 동작 | 우리 구현의 차이 |

| 판매 협상 | 대화 내역과 원가 하한을 주고 모델이 행동 결정 | 단계별 컨텍스트, 등급별 하한·보증, 코드로 끝내는 협상과 혼잡 대체 응답 |
| 상품 설명 | starter 설명상 품질 주장·보증 없음 | 현재 인증서와 구조화된 견적, 등급별 보증 및 제한된 B급 보증 실험 |

## 3. Round 3 운영 과정과 결과

### 3.1 처음 설계에서 마지막 수정까지

#### ① 11월 1~3일: 기존 판매자를 재고·결제 기반으로 옮겼다

처음에는 이전 주차의 협상 에이전트를 재사용하고, 공식 v4의 실제 재고·서명·checkout에 맞추는 데 집중했다. 품질과 예산을 엄격하게 지키고, 영수증을 발급한 재고는 다른 구매자에게 중복 약속하지 않도록 보수적으로 묶었다. 11월 2일 첫 배포에서 작업 디렉터리 문제로 서비스 전환이 실패하여 설정을 수정하고, 다음 배포에서 v4 등록과 ACP 응답을 확인했다. [첫 실패](logs/deployment-20261102T055518Z-f6332a52/server-deployment.log), [재배포 성공](logs/deployment-20261102T060419Z-e45a251c/server-deployment.log)

이후에는 판매 가격·보증·재입고 정책을 넣었고, Buyer가 구매를 허용하는 기준과 리뷰에서 높게 평가하는 기준도 분리했다. 하지만 가게 후보와 대화 전체를 반복해서 보내는 방식은 입력을 크게 만들었다. 그래서 11월 3일 Buyer 후보를 최대 6곳으로 줄이고, Shop은 현재 협상 단계의 지침과 압축 기억만 전달하도록 바꿨다. 합성 검사에서 입력 문자 수 감소는 확인했지만, 실거래 성과까지 확인한 것은 아니었다. 이때의 관심은 “모델이 좋은 가격을 제시하는가”에서 “한정된 자원으로 안정적으로 거래하는가”로 넓어졌다. 주요 커밋: `f093d32`, `142f17f`, `d479004`, `417462c`.

#### ② 11월 4~6일: 판매 부진을 조사하니 재고가 있어도 팔 수 없는 문제가 있었다

방문 대비 정산이 적다는 사실만으로 가격 문제라고 결론 내리지 않고 공급창과 예약을 먼저 진단했다. 11월 4일 공급창을 기준으로 계획을 한 번만 만들도록 바꾸고, 끝난 협상의 미발급 예약을 회수했다. 그러나 이미 영수증을 발급한 재고는 계속 묶여 있었다. 당시 설계에서는 중복 판매 방지를 우선한 나머지 결제 포기·취소가 예약 해제로 이어지지 않았다.

11월 6일 기록에는 재고 13개가 모두 발급 영수증에 묶이고 `stock_reserved` 거절이 3,479건 관측된 상황이 남아 있다. 그래서 단순 할인 대신 영수증 생명주기를 수정했다. 발급 후 5분 만료와 checkout 취소를 반영하되, checkout 생성·완료에서도 무효 영수증을 차단했다. 응답을 잃은 정산은 `uncertain`으로 유지하여 이중 판매를 막았다. 기존 예약의 복구 절차도 배포기에 추가했다. | 식품 사용 기한 부족 | 5 | 1016행: `not paying: 51.45 h of shelf life left, the policy asks for 73.0` |
| 허용 등급 밖 | 1 | 3025행: `not paying: grade C, the policy accepts ['A', 'B']` |

빠른 수락을 생략한 280개 판단은 목표가 초과 187, 구조화 견적 누락·모호 36, 인증서 누락·무효 42, 상품 식별·가격 문제 5, 구매 상한 초과 10이었다. **판단별 첫 차단 이유**이므로 실패 주문 280건이라는 의미가 아니다. 조건을 완화해 무조건 사기보다, 검증할 수 없거나 정책을 충족하지 않는 거래는 결제하지 않는 선택을 유지했다. 보증·등급 부족은 구매 조건이 거래 성사를 제한하는 사례이기도 하다.

Shop의 거부 사유는 별도 시간창의 진단으로 보완한다. [11월 13일 최근 3시간 진단 원문](logs/server-followup-20261113T124150Z/user-diagnostics.txt)에는 다음과 같이 기록돼 있다.

```text
Unique observed tasks: 595 (opened: 442; no open event: 153)
Receipts: 31; confirmed settlements: 20; UNCONFIRMED: 11
Terminal reasons:
  buyer_cancelled: 317
  negotiation_expired: 66
  price_rejected: 32
  stock_reserved: 146
  stock_unavailable: 3
```

이 진단은 마지막 날 전체 통계가 아니며, 제한된 로컬 기록을 읽은 사용자 제공 원문이다. 이유별 집계는 고유 task의 결과이고, 정산 이벤트·영수증·보드 방문 수와 분모가 다르다. 취소 원인을 가격이라고 단정하거나 미확인 영수증 11건을 결제 실패로 세지 않았다.

또한 원본 로그에는 시장 종료 안내를 받은 주문 재조회가 223회 있다. 3594행의 `Round 3 ended at 2026-11-17 23:59 KST` 응답 이후의 폴링은 시장 휴장 응답이며, 협상 실패나 추가 거래로 합산하지 않는다. 과거 서버 시각이 시장보다 약 763초 빨랐다는 관측도 있어, 로그의 `00:xx`만 보고 마감 이후 정산이라고 분류하지 않았다. 누적 실적은 Round 3 공개 보드와 구분해 제시했다.

### 3.4 실패와 확인하지 못한 효과

- 서비스 경로, CLI 이벤트 판별, 모델 이름 정규화 문제로 배포 사전 검사가 실패했다. 실패 로그와 수정 커밋을 보존했다.
- 재고 예약 복구, 매입량 조절, 입력 압축과 가격 정책을 여러 날에 걸쳐 바꿨다. 모든 변경을 통제한 A/B 실험으로 검증한 것은 아니다.
- 빠른 수락 기능은 구현됐어도 11월 13일 실제 표본에서 0건이었다. 상대의 견적·인증서와 가격이 조건을 충족해야 하므로 기능 존재와 실사용을 구분했다.
- 운영 전략가는 Round 3에서 제안 모드였다. 정책 자동 적용으로 개선한 성과나 실험별 수익 효과는 제시하지 않는다.
- 토큰 계측과 중복 호출 억제는 구현·검증·배포 기록이 있지만, 동일 구간의 실제 과금량 감소율은 확보하지 못했다.
- 수집된 원본 로그는 일부 구간이다. 공개 보드, 당시 진단, 배포 로그를 함께 사용했으며 부족한 값을 0이나 추정 성공으로 채우지 않았다.

이번 운영에서 가장 큰 설계 변화는 모델의 협상만 조정하던 방식에서, **거래 상태를 정확히 관리하고 관측된 결과를 다음 행동에 연결하는 방식**으로 옮겨간 것이다. 다만 Shop의 상대 점수 하락과 빠른 수락 미사용, 운영 제안의 미적용은 남은 한계다.
