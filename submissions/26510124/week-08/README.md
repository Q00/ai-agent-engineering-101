## 사용자가 선택한 판매 정책과 재입고 (2026-11-02)

`shop-policy.json`의 초기값은 사용자가 선택했다. 아래 수치는 시장 규칙이나 검증된
최적값이 아니라 이번 실험 정책이다. 판매자·구매자·분석자 모두 기존 Haiku를 유지한다.

| 항목 | 적용 내용 |
|---|---|
| 기본 판매 하한 | A 원가 × 1.10, B × 1.05, C × 1.00, 정수 올림 |
| 조건부 마감 하한 | A × 1.10, B × 1.02, C × 1.00; 아래 할인 조건 충족 시 적용 |
| 보증 | A등급 비식품 6시간, B/C 비식품 및 식품은 미제공 |
| 현금 하한 | 시작 자본의 40%: 500만 시작이면 200만 크레딧 |
| 매입 한도 | 15분에 최대 5개, 전체 재고 20개, SKU당 비식품 3개·식품 1개 |
| 탐색 | 판매 근거가 있으면 회당 최대 1개를 새 SKU 탐색에 배정, 근거가 없으면 최대 5개를 서로 다른 SKU로 탐색 |

원가 70,000인 상품의 기본 하한은 A 77,000 / B 73,500 / C 70,000이다.
B의 추가 할인 조건을 충족하면 하한은 71,400이다. 현재 적용되는 하한보다 낮은 가격은
모델과 분석자가 제안해도 코드가 거부한다. 두 하한·할인 조건·보증을 협상 시작 때
고정한다. 식품의 등급이 이후 떨어져도 진행 중인 협상의 하한을 소급해서 다시 계산하지
않으며, 다음 협상에서 새 등급을 사용한다. 식품의 고정 등급 claim은 영수증에 넣지 않는다.
하한이 높아지면 가격에 민감한 구매자와의 거래가 줄 수 있고, 원가 마진만으로 보관비와
환불 손실까지 보전된다고 보장하지 않는다.

6시간 보증은 안내 문구뿐 아니라 판매자가 발급하는 영수증의 `warranty_hours=6`으로
전달된다. 공식 v4 checkout이 그 조건을 서명된 checkout에 포함하며, 보증 기간 내
고장 나면 시장이 가게 잔액에서 전액 환불한다. 구매자 사본에서 시간을 바꿔도 판매자
원본 조건이 사용된다. 이는 우리 코드가 직접 환불 요청을 보내는 기능이 아니다.
[공식 시장 계약](https://market.ourolabs.ai/agent.md)의 공급·보증·hook 규격을 확인했다.

**재입고 선택:** `sales_performance.py`가 내 영수증 이벤트와 공식 kit 로그의
`[acp] settled ... ledger #... unit ...`를 unit·가격으로 대조한다. 해당 라운드의
정산 확인이 있는 SKU와 카테고리를 우선 보충한다. 영수증 발급만으로는 판매로 세지
않는다. `demand.json`은 주문 가능한 카테고리 목록으로만 쓰며 인기 순위로 해석하지 않는다.
새 SKU는 과거 계획 횟수·보유 카테고리 분산·안정적인 일별 순서로 소량 탐색한다.
무슨 등급이 입고될지는 선택할 수 없으며 공급 때 시장이 정한다.

매입 비용은 공식 공급 원가의 최대치인 정가 75%를 올림하고 단위당 1크레딧의 여유를
더해 계산한다. 이 예상 비용을 빼도 시작 자본의 40%가 남는 계획만 키트에 전달한다.
현재 잔액의 40%를 매번 다시 계산해 현금 하한이 계속 낮아지는 방식은 쓰지 않는다.
다만 계획 후 보관비·환불이 발생하면 실제 현금은 달라질 수 있다. 잔액이 이미 하한
아래면 매입을 멈추고, 자동 파산 신청은 하지 않는다. `restock.enabled=false`도
매입 중단을 뜻하며 공식 키트의 무작위 매입으로 돌아가지 않는다.

키트는 hook을 약 60초마다 호출하지만, 우리 hook은 15분 간격을 파일에 먼저 예약한다.
중복 프로세스·재시작으로 같은 시점의 계획이 반복되지 않도록 잠근다. 재고는 45초,
카테고리 정보는 120초 이내여야 하며, 파일 오류나 잘못된 제어 상태에서는 `buy: []`로
멈춘다. 실제 매입 POST는 키트가 수행하고, hook은 네트워크나 모델을 사용하지 않는다.

**기억의 범위:** `.market/sales-performance.json`에 최근 7일·최대 1,000개 정산
표본을 저장한다. 원본 kit 로그는 끝의 최대 2 MB/4,000줄, 영수증 로그는 최대
1 MB/2,000줄만 읽는다. 읽기 범위 밖의 확인, 문구 형식이 바뀐 확인은 놓칠 수 있다.
이는 시장 전체 인기나 평생 실적, 환불 차감 순매출이 아니다. 환불/보관비별 장기 순이익
메모리는 후속 개선이다. 매입 계획도 실제 입고 성공으로 세지 않으며, 실제 재고 파일을
다음 판단에 사용한다. 계획 근거는 `logs/restock-decisions.jsonl`에 원문으로 추가한다.

**가게 소개와 고객 안내:** 분석자가 고른 가격 비교·명확한 조건·검증 가능한 품질 중
강조점에 맞는 고정 문구를 사용한다. 실제 상품명·비식품 등급·식품 기한·보증 조건·호가를
붙이며, 리뷰 원문이나 모델의 자유 서술을 광고로 내보내지 않는다. 가게의 A2A 카드
`/.well-known/agent-card.json`은 요청 시 최신 유효 조언을 반영하고, 각 협상 안내는
그 협상에 고정된 조언을 쓴다. 시장 웹의 카드 캐시는 재조회 시점까지 늦게 보일 수 있다.
게시판 광고 글이나 메시지를 자동 발송하는 기능은 추가하지 않았다.

검증: 판매 정책·실제 A2A 안내·공식 v4 checkout 보증 전달까지 **99개 통과**
(`logs/offline-20261102T065938Z-511fc933.log`), 정산 대조·현금 하한·재고 제한·중복
계획 차단·공식 restock hook 연결을 포함해 **110개 통과**
(`logs/offline-20261102T070330Z-f22f8a49.log`). 모두 합성 재고와 모델/시장 대역으로
수행했다. 실제 Haiku 호출, 서버 갱신, 실매입·환불·순위 개선은 아직 검증하지 않았다.

## 방문한 구매자와 빨리 합의하는 협상 (2026-11-02)

이번 정책은 사용자가 승인한 조기 마감 실험이다. 상품 문의 뒤의 **숫자 가격 제안**을
1회로 센다. 첫 문의나 숫자가 아닌 메시지는 구매자의 가격 제안 횟수에 넣지 않는다.

| 시점 | 동작 |
|---|---|
| 첫 문의 | Haiku가 기본 하한 이상에서 경쟁력 있는 초기 가격을 선택 |
| 구매자 첫 제안 | 좋은 가격이면 즉시 수락하도록 유도; 낮으면 역제안 |
| 두 번째 제안 | 적용 하한 이상이면 수락 필수, 미만이면 마감 방향으로 양보 |
| 세 번째 제안 | 적용 하한 이상이면 수락, 미만이면 적용 하한으로 최종 가격 제시 |
| 최종 가격 다음 응답 | 제시가 이상이면 정확히 구매자가 제안한 금액으로 영수증 발급, 미만이면 종료 |

이미 제시한 가격 이상을 구매자가 보내면 어느 단계에서든 추가 모델 호출 없이 수락한다.
최종 가격을 제시한 직후 횟수 제한으로 끊지 않는다. 수락 응답을 기다리는 동안에도 기존
재고 유효성 검사와 5분 무응답 만료를 적용한다. 최종 가격에 대한 더 낮은 제안에는 모델을
다시 부르지 않으며 unit 예약을 해제한다. 영수증 발급 후 예약은 기존 결제 확인 규칙을 따른다.

**추가 할인 조건:** 두 번째 제안부터 아래 하나를 충족해야 B등급 마감 하한을 연다.

- 구매자가 이전 최고 제안보다 **기본 하한의 1% 이상** 올렸고, 현재 가격이 기본 하한에서
  **3% 이내로 가까워진 경우**. 가격을 내렸다가 복구하거나 1원씩 올리는 행위는 근거가 되지 않는다.
- 공식 재고의 입고 시각 기준으로 비식품이 **24시간 이상** 묵은 경우.
- 공식 재고의 식품 유통기한이 **2시간 이내**로 남은 경우. 이미 지난 식품은 팔지 않는다.

횟수만 채우면 추가 할인되는 것은 아니다. 조건을 충족하지 못한 최종 가격은 기본 하한이다.
한번 허용된 추가 할인은 같은 협상에서 철회하지 않으며, 최종 가격을 보낸 뒤 새 할인 조건을
평가해 다시 흥정하지 않는다. A등급은 보증 부담을 고려해 마감 하한도 원가+10%를 유지한다.
C등급은 원가가 하한이며, 어떤 등급도 원가 이하로 덤핑하지 않는다.

예: B 원가 70,000 → 기본 하한 73,500 / 마감 하한 71,400.
구매자 71,000 → 72,000이면 1,000의 개선이 735를 넘고, 기본 하한과 차이 1,500이
2,205 이내이므로 두 번째 제안 **72,000에 합의**한다. 72,000을 반복하기만 한 새 재고는
추가 할인 조건을 충족하지 않는다. 이 숫자들은 최적값이라는 증거가 없는 초기 실험값이며,
`shop-policy.json`의 `closing`에서 조정해 재배포한다.

모델은 초기 호가와 초기 양보를 결정하고, 마감 시점의 수락 의무·최종 가격·하한은 코드가
검사한다. 유효한 모델 출력 기준으로 협상당 최대 **4회 판단**(초기 + 가격 제안 3회),
출력 수정 재시도까지 포함하면 CLI 실행 최대 8회다. 수락·최종 거절의 단순 처리는 추가
모델 호출이 없다. 새 주기 작업이나 외부 API 호출도 추가하지 않았다.

`logs/inventory-seller-events.jsonl`에 협상 시작·최종 가격·취소·만료·영수증 발급과
단계, 제안 횟수, 적용 하한, 할인 이유, 모델/단순 처리 여부를 기록한다. 분석자에게도
마감 정책과 제한된 최근 이벤트 요약을 제공한다. 이 표본의 영수증 발급률은 정산 전환율이
아니다. 실제 판매·수익 효과는 키트의 정산 기록, 환불, 공개 board와 함께 확인해야 한다.

검증: **125개 통과**, 그중 마감 정책 신규 15개
(`logs/offline-20261102T074958Z-1c3449e7.log`). 실제 A2A 형식에서 72,000 합의,
최종 가격 수락 기회, 추가 호출 생략, 원가/보증 유지, 재고 만료와 정책 고정을 검증했다.
합성 재고와 모델 대역으로 수행했으며 실제 Haiku 협상·순위 효과는 아직 검증하지 않았다.

## 별도 판매 전략 분석자 (2026-11-02)

```text
공식 공개 board + 리뷰 + 내 재고·협상 요약
  → 별도 Haiku 분석자 → 검증된 로컬 조언 파일
  → 판매자 Haiku가 새 협상부터 참고 → 실제 제안·영수증은 기존 검증 통과
```

- **관찰:** 15분에 한 번 공식 시장에 최대 5회 GET 요청을 보낸다. 내 최신 리뷰 최대
  10개, 나를 제외한 상위 3개 가게의 리뷰 각 5개, 공개 소개와 성과를 읽는다.
  순위는 board의 `all` 점수, 동률이면 profit을 사용한다. 점수가 없는 응답에서만
  profit/deals 순서를 쓰고 그 사실을 분석자에게 명시한다. 같은 별점·문구는 중복 제거하고
  작성자와 시각을 보존한다. 다른 가게의 내부 프롬프트·원가·비공개 전략은 알 수 없다.
- **판단:** Haiku를 별도 프로세스에서 최소 1시간 간격, 최근 24시간 최대 6회 호출한다.
  실패한 호출도 횟수에 포함하며 재시도 없이 60초 제한을 적용한다. 입력은 18,000자
  이내다. 관찰 내용이 같으면 재분석하지 않고, Round 3 전에는 board 확인만 한다.
  리뷰가 전혀 없고 내 정산 거래도 3건 미만이면 근거를 기다린다.
- **조언:** 기본 전략과 재고 카테고리 최대 4개의 가격 조정 제안(-5~+5%), 협상 속도
  (`balanced`/`quick`), 강조점(`value`/`clarity`/`quality`)을 저장한다. 모든 제안은
  관찰 자료의 ID를 인용해야 한다. 가격 비율은 판매자가 원래 선택할 호가에 대한
  **권고**이며, 실제 가격의 ±5% 변동을 코드로 보장하는 장치는 아니다. 판매자가
  마감 전 가격을 판단하고 사용자가 정한 등급별 하한·마감 규칙·호가 인상 금지·재고 검증을 적용한다.
- **기억:** 같은 라운드·최근 24시간의 이전 조언과 당시 성과 최대 4개를 다음 분석에
  전달한다. 거래 수가 감소한 시장 초기화는 실패한 가격 실험으로 해석하지 않는다.
  재고 요약은 최대 8개 카테고리, 협상 요약은 최근 24시간/최대 200개 이벤트다.
  영수증 발급은 정산으로 세지 않으며, board 성과 변화가 조언 때문이라고 단정하지 않는다.
- **적용:** 판매자는 로컬 파일만 읽고 새 협상 시작 때 조언을 고정한다. 협상 중간에
  바뀌지 않는다. 조언이 없거나 잘못됐거나 6시간이 지나면 기본 정책을 쓴다. 외부 리뷰
  원문과 분석자의 자유 서술은 판매자에게 전달하지 않고 감사 로그에만 남긴다.
  분석자는 결제·재입고·게시판·리뷰 작성 도구를 갖지 않는다.
- **수명:** 분석자 오류가 판매자를 멈추지 않는다. 프로세스가 종료되면 최소 60초 후
  다시 시작한다. 서비스 종료 시 판매자·분석자와 진행 중인 모델 호출을 함께 정리한다.
  서비스 이름은 기존 `week07-market.service`를 그대로 사용한다.

`advisor-config.json`에서 호출 주기를 늘리거나 일일 한도를 낮출 수 있다.
기본값은 `poll_seconds=900`, `model_interval_seconds=3600`, `max_calls_per_day=6`,
`strategy_ttl_seconds=21600`이다. 분석을 끄려면 `enabled=false`로 바꿔 재배포한다.
**이 한도는 분석자에만 적용된다.** 판매자·구매자의 협상 모델 사용량은 별도다.
분석자는 품질을 지어내거나 사용자가 정한 보증·재입고 한도를 바꾸지 않는다.
등급별 하한·보증 설정과 자체 정산 요약도 분석 입력에 포함한다.

분석 과정은 다음 원본 로그에 추가된다. 기존 기록을 정리하거나 덮어쓰지 않는다.

- `logs/advisor-observations.jsonl`: 공개 관찰과 자료 ID
- `logs/sales-advisor-*.log`: 각 Haiku 호출의 입력·원문 출력
- `logs/advisor-decisions.jsonl`: 채택된 조언 또는 호출 실패
- `logs/inventory-seller-events.jsonl`: 협상 결과와 사용한 조언 버전
- `logs/advisor-errors.jsonl`: 수집·분석 오류

오프라인 검사 **92개 통과** (`logs/offline-20261102T064017Z-76006fbb.log`).
횟수 제한·라운드 분리·주입 문구/임의 출력 거부·유효기간·협상 중 조언 고정·원가
하한·분석자 장애 및 종료 처리를 모델/프로세스 대역과 실제 A2A 직렬화로 검사했다.
첫 91개 검사에서는 리뷰 시각을 매번 바꾸던 테스트 데이터 때문에 변경 없음 검사가
실패했다. 그 원본 로그와 커밋을 보존하고 테스트 시각을 고정한 뒤 다시 검증했다.

실제 공개 읽기 검사는 Round 2에서 `waiting_for_round3`로 끝났다

Haiku 호출은 생략했다. 새 분석자의 실전 판단·매출 효과·서버 실행은 아직 검증하지 않았다.

[LongMemEval-V2](https://github.com/xiaowu0162/LongMemEval-V2)는 장기 기억 평가용

가져오지 않았다. 작은 시각·라운드별 기억을 로컬 JSON에 저장하며, 해당 벤치마크를
통과했다는 의미는 아니다. 공개 데이터 형식은 시장의 `/agent.md`와 board가 사용하는
`/api/board`, `/api/shop-reviews?shop=...&round=...`를 확인했다.

## 매우 강경한 구매자 (사용자가 선택한 정책)

`buyer-policy.json`에서 가격·품질·협상 한도를 관리한다. 사용자가 선택한 구매 상한은
**min(예산 × 70%, 시장 카탈로그 정가 × 65%)**이며 정수로 내림한다. 판매자 말에서
정가를 추측하지 않는다. Round 3 카탈로그 가격이 없으면 거래를 시작하지 않는다.
예산과 정가가 모두 100,000이면 상한은 65,000이다. 협상 목표는 상한의 90%(58,500),
회당 양보는 상한의 5%(3,250)까지, 모델의 협상 결정은 최대 4회다. 한도 초과 제안은
전송하지 않고, 만족스러운 조건에 도달하지 못하면 취소한다. 가격은 여전히 모델이
고르며 코드가 사용자의 경계를 강제한다. 상한이나 목표 금액을 판매자에게 알리지 않는다.

결제 조건은 시장 증명서 필수·A등급만 허용이다. 비식품은 6시간 보증, 식품은 주문의
사용 시간에 1시간을 더한 유통기한 여유를 요구한다. `accept`를 통해 공식 v4 코드가
결제 전에 검사한다. 협상 때의 말만으로 품질이나 보증을 확인했다고 처리하지 않는다.
이 조건으로 실제 거래 수는 줄 수 있다. 현재 우리 판매자는 A등급 비식품에 6시간
보증을 제공하지만, 가격 조건의 충족은 별개다. 같은 GitHub 소유자의 가게와 구매자는
시장 규칙상 서로 정산할 수 없다.

정산 후 리뷰는 추가 모델 호출 없이 실제 영수증과 기록으로 매긴다.

| 조건 | 별점 |
|---|---|
| 등급 주장 불일치, 시장 기록상 사용 가치 0, 구매 상한 초과 | 1 |
| 등급·보증·남은 기한 미달, 목표 가격보다 비싼 구매 | 최대 2 |
| 원래 구매 목표 등 평가 정보가 부족함 | 최대 3, 확인되지 않은 결함은 단정하지 않음 |
| 품질 조건과 목표 가격을 충족 | 4 |
| 모든 조건 충족 + 목표 가격의 80% 이하 | 5 |

불만이 여러 개면 가장 낮은 점수를 적용한다. 거래 전에 저장한 정책을 주문·가게·SKU·
영수증 task·가격으로 대조하므로 설정을 바꿔도 이미 구매한 거래의 가격 기준을
소급해서 바꾸지 않는다. 식품은 **리뷰 작성 시점**에 남은 시간을 명시하며 결제 당시에도
이미 상했다고 추측하지 않는다. 후기에는 실제 상품/금액/등급/불만 근거만 쓰고 예산,
개인 목표 금액, 구매 상한 금액은 쓰지 않는다. 미결제 거래의 평점은 시장에 공개되는
구매 후기가 아니다. `payments.jsonl`로 정산을 확인한 기록에만 실제 리뷰 결과를 붙여
다음 가게 선택에 전달한다. 공개 리뷰가 없는 가게나 단순 통신 오류를 부정직하다고
단정하지 않는다.

## 비밀번호 SSH로 서버에 v4 배포하기

2026-11-02: 자동 SSH 인증은 실패했고, 사용자는 맥 터미널에서 비밀번호를 입력하면
`ssh daintI`로 접속할 수 있다고 확인했다. 사용자가 아래 명령으로 v4 배포에 성공했으며,
새 분석자를 반영할 때도 같은 명령을 사용한다.
아래 명령을 맥의 이 레포 루트에서 실행한다. 이미 서버에 접속한 터미널에서는 실행하지 않는다.

```bash
python3 submissions/26510124/week-08/deploy/deploy_v4.py
```

SSH가 비밀번호를 요청하면 터미널에 직접 입력한다. 입력 글자는 표시되지 않는다.
스크립트는 비밀번호를 받거나 저장하지 않으며, 한 번 연결한 SSH 세션을 전송과 설치에
재사용한다. 설치 중에는 터미널을 열어 둔다. 실행하면 판매자와 구매자가 시작되므로
Haiku 사용량이 발생하며, Round 3에서는 사용자 정의 재입고 계획에 따라 키트가 모의 시장 잔액을 사용한다.

배포 과정:

1. 소스·프롬프트·명시한 공개 설정·고정 v4 키트만 SHA256 명세와 함께 전송한다.
   키, `.env`, 기타 JSON, `.market`, 기존 로그, 가상환경은 전송하지 않는다.
2. 서버의 기존 가상환경으로 전송된 소스의 오프라인 검사를 실행하고, v4 원본 SHA,
   두 신원 키, 기존 비공개 서비스 환경 설정, Claude/cloudflared 경로를 확인한다.
   이 단계가 실패하면 기존 서비스는 중지하지 않는다.
3. 변경할 소스와 서비스 설정을 백업한 뒤 기존 서비스를 중지한다. 서버의 week-07 키를
   week-08에 복사하되, 이미 있는 다른 키를 덮어쓰거나 새 신원을 생성하지 않는다.
4. `week07-market.service`의 이름과 환경 설정은 유지하고, 사용자 systemd drop-in으로
   week-08의 `run_round3.py --join`을 실행한다. 별도 두 번째 키트를 켜지 않는다.
5. 이번 시작 이후 로그에서 `market_kit 4`, week-08 경로, 가게와 구매자의 등록을 확인하고
   새 가게 주소의 ACP 안내를 조회한다. 210초 이내 확인되지 않으면 이전 소스·서비스
   설정으로 복구를 시도한다. 전환 전 실행 중이던 서비스는 다시 시작한다.

완료 표시는 다음과 같다. 이는 등록과 ACP 확인이며 실제 정산 성공을 증명하지 않는다.
Round 3 개장 여부와 정산 건수는 별도로 확인해야 한다.

```text
READY: market_kit 4; week-08; shop and buyer registered; ACP verified.
```

서버 증거는 `week-08/logs/deployment-<실행ID>/`, 백업은
`week-08/.market/deploy-backups/<실행ID>/`에 남는다. 맥에도 업로드 명세와 서버 설치 출력이
같은 실행 ID의 `logs/deployment-.../`에 원문으로 저장된다. 중간에 연결이 끊기거나
`ROLLBACK NEEDS ATTENTION`이 표시되면 완료로 판단하지 않고 현재 서비스를 확인한다.
`SIGKILL`이나 서버 전원 장애까지 자동 복구를 보장하지 않는다. 기존 원본 로그는 보존한다.

배포 파일만 만들고 접속·실행하지 않으려면 `--prepare-only`를 붙인다.
배포 실패/복구, 개인 파일 제외, 변조 검사, 새 실행 로그 구분을 포함한 **오프라인 검사
71개 통과**: `logs/offline-20261102T055202Z-4a77f7cf.log`.
SSH와 systemd는 테스트 대역을 사용했으며 실제 서버에서 성공했다는 의미는 아니다.

### 첫 서버 배포 실패와 설정 수정 (2026-11-02)

`logs/deployment-20261102T055518Z-f6332a52/server-deployment.log`는 사용자가 실제로
실행한 첫 배포 출력이다. 서버의 오프라인 검사는 통과했지만 서비스 설정 확인에서
실패했고 이전 소스·서비스 설정으로 복구됐다. 시장 등록을 시작하기 전의 실패이므로
Round 3 개장 대기 메시지가 아니다. v4 전환이나 현재 서버 동작 성공을 의미하지 않는다.

생성한 `WorkingDirectory="/home/..."`의 따옴표가 잘못됐음을 확인해
`WorkingDirectory=/home/...`로 고쳤다. systemd의 WorkingDirectory는 ExecStart처럼
셸 단어를 분리해 따옴표를 제거하는 설정이 아니다.
[systemd v245의 경로 파서](https://github.com/systemd/systemd/blob/v245/src/core/load-fragment.c#L1958)를
확인했다. 첫 실패 로그에는 실제 적용된 속성이 없어서 다른 override의 존재 여부까지
확정할 수 없다. 따라서 원인을 무조건 다른 override라고 단정하던 오류 문구도 바꿨다.

재배포 시에는 기존 서비스를 중지하기 전에 서버의 `systemd-analyze --user verify`로
후보 설정을 검사한다. 적용 뒤에는 LoadState, WorkingDirectory, 설정 파일 경로,
새 실행 명령의 일치 여부를 `service-configuration.json`에 남긴다. 환경 변수나 실제
ExecStart 인자는 기록하지 않는다. 불일치 시에는 이 진단도 맥의 설치 출력에 표시한다.

회귀 검사 포함 73개 통과: `logs/offline-20261102T055829Z-bfe7fa6a.log`.
맥에는 systemd가 없어 네이티브 파서 실행은 재배포 시 서버에서 수행한다.
그다음 사용자의 재배포는 `logs/deployment-20261102T060419Z-e45a251c/`에 기록된 것처럼
등록·ACP 확인까지 성공했다. 이는 이번 분석자 추가 전의 버전이며 실제 정산 검증은 별도다.

## 동작

`collect_feedback.py`가 공식 공개 `/api/board`, `/api/shops`를 읽는다.
대시보드의 기본 정렬과 같이 `profit`, 동률일 때 `deals`로 비교 대상 3곳을
선택한다. 현재 스냅샷의 누적 순위이며, 최근 성장률이나 내부 전략을 안다고
주장하지 않는다. 다른 가게의 주소에는 접속하지 않는다.

본인의 같은 라운드 최신 리뷰 최대 10개를 읽고, 내용이 같은 리뷰를 중복 제거한다.
API가 리뷰 작성자를 주지 않으므로 서로 다른 사람의 의견이라고 보장할 수 없다.
낮은 별점의 품목별 문구에서 가격·속도·설명·영수증 관련 단어를 분류한다.
이는 부정 표현/반어를 완벽히 이해하지 못하는 약한 신호이다. 외부 문구는
감사 로그에만 보관하고 모델에는 사전에 정한 지침만 전달한다.

`seller_agent.py`는 거래 시작 시 로컬 전략을 읽어 해당 협상에 고정한다.
상품 선택·협상·영수증은 기존 모델과 A2A 경로를 사용한다. 가격은 모델이 고르되
코드가 하한가, 합의 금액, 첫 호가 범위와 역행하는 가격 인상을 검사한다.
서명 형식은 기존 `{shop,item,price,task}` 그대로이다.

## 현재 실험 규칙과 조절할 값

`feedback-config.json`의 기본 호가는 lamp 125 / chair 225 / bookshelf 325이다.
이는 검증된 최적가나 상품 품질 평가가 아닌 **실험 초기값**이다.
하한가 100 / 180 / 260은 기존 설정을 유지한다.

- 새 영수증 발급/명시적 협상 거절 5건 이상, 직전 가격 변경 후 1시간 이상일 때만 평가한다.
- 가격 불만 문구 3개 이상, 자체 거절 비율 50% 이상, 상위 가게의 가격 경쟁력 주장까지
  함께 있을 때 목표 호가를 최대 5% 낮춘다.
- 영수증 발급 비율 80% 이상, 공개 인정 판매 증가 3건 이상, 리뷰 3개 이상/평균 4점 이상,
  가격·영수증 불만 신호 없음이면 목표 호가를 최대 5% 올린다.
- 목표는 초기값의 85~115%와 기존 하한가 안에 제한된다. 실제 첫 호가는 목표의 ±5%
  범위 안에서 모델이 선택한다. 협상 중에는 하한가까지 양보할 수 있다.
- 속도 불만과 경쟁 가게의 빠른 거래 주장이 함께 있으면 신속한 합의를 지시하고,
  설명 부족이 반복되면 명확한 설명을 지시한다. 상품 설명 자체를 자동 재작성하지 않는다.
- 일반 오류·취소·협상 횟수 제한은 가격 때문에 거절했다고 계산하지 않는다.
- 라운드 변경, 시장 카운터 초기화, 1시간 초과 수집 공백이면 비교 기준을 새로 시작한다.

판매가 자동으로 개선되거나 상위권이 된다는 보장은 없다. 가격을 바꾼 이유와
이후 결과를 보고 임계값·초기 호가를 직접 실험해야 한다. 모델이 툴을 골라 호출하는
구조가 아니라, 결정론적 수집기가 요약을 준비하는 구조이다.

## 리소스 예산

| 항목 | 제한 |
|---|---|
| 공개 API 수집 | 15분마다 GET 2회, 실패해도 같은 주기로 재시도 |
| 중복 실행 | 프로세스 파일 잠금으로 수집기 1개만 허용 |
| HTTP 응답 | 건당 최대 1 MB, 네트워크 timeout 10초, 스트림 시간 제한 20초 |
| 전략 분석 모델 호출 | 0회 |
| 판매자 모델 동시 호출 | 최대 2개, 포화 시 추가 요청은 실패 응답 |
| 협상 컨텍스트 | 최대 7개 메시지, 합계 최대 2,800자 + 작은 전략 지침 |
| 협상 횟수 | 기본 재협상 6회, 마지막 제시가 수락 처리는 추가 1회 허용 |
| 로컬 전략 읽기 | 최대 1분에 한 번, 유효 기간 1시간 |
| 자체 이력 분석 | 로그 끝 256 KB / 최근 24시간 / 최대 200개 작업 |

기존 모델 호출 비용 자체를 0으로 만든 것은 아니다. 기본 하네스는 Claude CLI를
호출하며 잘못된 출력은 한 번 재시도한다. 모든 실제 모델 시도의 로그를 보존한다.
위 제한은 추가 기능/컨텍스트의 제한이며 기존 A2A TaskStore 전체의 메모리 상한은 아니다.

## 로그와 결과 해석

- `logs/strategy-decisions.jsonl`: 관찰한 공개 정보, 리뷰 원문 일부, 목표 호가·판단 이유.
- `logs/seller-events.jsonl`: 영수증 발급·거절·오류·취소. `receipt_issued`는 정산이 아니다.
- `logs/feedback-errors.jsonl`: 조회/저장 실패. 오래된 캐시는 만료되면 사용하지 않는다.
- 키트의 `[acp] settled`와 Round 3 ledger로 실제 정산을 별도 확인한다.
- 공개 판매 증가량은 전체 품목 합계라 특정 품목 가격의 인과 효과를 입증하지 못한다.
  리뷰 속 소재/품질 주장은 검증된 품질로 계산하지 않는다.

기존 로그를 편집하거나 가짜 실적을 만들지 않는다. 실패한 테스트 로그도 보존한다.
