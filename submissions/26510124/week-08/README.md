## 2026-11-10: Shop 모델 3개 동시 실행과 혼잡 시 가격 응답

서버 진단의 모델 오류 7건이 모두 `Shop busy; model concurrency limit reached`였다.

이 오류만으로 시장의 오프라인 표시 원인이 입증된 것은 아니다.

- Round 3 Shop은 모델 작업을 동시에 최대3개 실행한다. Buyer의 별도 호출은 이 수에
  포함되지 않는다. 연결이 취소돼도 실제 모델 작업이 끝나기 전에는 슬롯을 반환하지 않는다.

  최초 호가는 고정된 opening 범위/목표를 사용한다. 근거 범위가 없으면 활성 가격 하한에
  10%를 더한 값을 정가로 제한하되, 하한 자체가 정가보다 높으면 하한을 지킨다.
  이 10%는 혼잡 대응용 기본 호가 정책이며 시장에서 관측한 가격이 아니다.
- 일반 협상은 이전 호가와 `max(현재 제안, 활성 하한)`의 중간값(올림)을 재제안한다.
  기존 호가를 높이지 않으며 하한을 낮추지 않는다. 마감 단계의 수락/최종 제안 규칙,
  재고 재검사·취소·보증·영수증 서명과 예약 유지 처리는 기존 공통 경로를 거친다.
- 응답 로그의 `decision_source: capacity_fallback`으로 혼잡 응답을 식별한다.
  실제 모델 실패·시간 초과·형식 오류는 이 처리로 숨기지 않는다. 네 번째 모델이나
  추가 재시도를 시작하지 않는다. 동시 모델3개로 순간 자원 사용은 증가할 수 있다.
- 배포 후 해당 로그와 `model_error`, 실제 정산 수를 함께 확인한다. 단순 온라인 표시나

  첫 유효 hook에서 계획하고, 같은 시작 시각에는 재시작해도 한 번만 계획을 출력한다.
  현재 라운드에서는 예전 `interval_seconds=900` 대신 이 창 단위 제한을 사용한다.
  공급 정보가 없거나 잘못됐거나 마감이 임박하면 매입하지 않고 이유를 남긴다.
  원장 조회 뒤와 계획 출력 직전에 창·재고를 다시 확인한다. 구매 계획은 매입 성공과 다르다.
- **상품별 수량:** 보증 기간이 끝난 판매가 3건 이상이고 추정 손익·회전 지표가 양수이며,
  불확실한 원가나 관측된 환불이 없는 비식품은 최대 3개를 보유할 수 있다. 최근 판매의
  보증 기간이 아직 남아 있으면 최대 2개다. 미검증 상품과 식품은 여전히 1개다.
  현금 40% 유지·회당 5개·전체 20개·상품/카테고리별 금액 한도와 종료일 제한을 함께 적용한다.
- **협상 예약:** 빈 메시지·과도하게 긴 메시지로 끝난 협상, 오류·취소로 끝난 협상의
  미발급 예약을 정리한다. 활동 없는 협상은 기존 300초 기준으로 요청/카드 조회 때 정리한다.
  이미 처리 중인 요청의 예약은 중복 요청 때문에 해제하지 않는다. 실제 시장의 8자리
  16진수 SKU를 인식하며, 요청한 SKU가 없다고 같은 카테고리의 다른 물건으로 대체하지 않는다.
- **실패 근거:** `logs/inventory-seller-events.jsonl`에 `reason_code`, `terminal`,
  `reservation_kind`, 짧은 오류 설명을 추가한다. 재고 없음과 다른 협상/영수증에 잡힌 재고,
  최종 가격 거절, 모델 오류, 잘못된 요청, 협상 만료를 구분한다. 오래되거나 읽을 수 없는
  재고 파일은 `inventory_unavailable`이며 품절로 세지 않는다. 기존 결과 이름은 유지한다.

**발급한 영수증은 별도로 취급한다.** 현재 고정된 키트의 영수증·checkout에는 만료/철회
규약이 없어, 시간이 지났다는 이유만으로 해당 물건을 다른 구매자에게 다시 약속하지 않는다.
응답 전송에 실패하더라도 영수증 발급 기록과 영구 예약을 남긴다. 미정산 영수증 예약이
많이 쌓인다면 별도 확인이 필요하며, 이번 수정이 이 예약을 자동으로 없애지는 않는다.

서버에 배포한 뒤 서버의 레포 루트에서 다음 명령으로 최근 24시간을 확인한다.

```bash
python3 submissions/26510124/week-08/shop_diagnostics.py --hours 24
```

`--json`은 기계가 읽을 수 있는 집계, `--round 3`은 재고 파일이 없을 때 라운드 지정이다.
메시지 수 대신 관측된 task를 중복 제거하고, 영수증과 정산을 구분한다. 정산을 찾지 못한
영수증은 `UNCONFIRMED`이며 결제 실패라고 단정하지 않는다. 키트의 가게 측
`[acp] settle refused`는 날짜/라운드/task가 없는 **로그 끝부분의 시도 횟수**로만 표시한다.
내 구매자가 다른 가게에서 실패한 결제를 내 가게의 실패로 세지 않는다.

진단은 파일마다 최대 2MB/최근 4,000줄을 읽고, 현재 라운드·선택 기간의 근거만 집계한다.

다를 수 있다. 고객 원문·키·인증 정보·가격을 출력하지 않고 상태 파일도 변경하지 않는다.
서버의 실제 실패 비중과 판매량 변화는 재배포 후 새 기록으로 확인해야 한다.

검증: 오프라인 **295개 통과** (`logs/offline-20261104T020106Z-464bc7b6.log`).
공급 창 변경·재시작·느린 조회, 검증 상품의 수량·현금 한도, 실제 A2A 오류·취소와
영수증 응답 실패, 진단 집계의 중복 제거·정보 누락을 합성 자료로 검사했다.
실제 시장 매입·모델 호출·서버 배포는 이 검사에 포함하지 않았다.

## 구매자 토큰 절약 1단계 (2026-11-03)

`buyer_selection.py`가 재고에 맞는 후보를 최대 6곳으로 줄이고, Haiku가 **한 번의
판단**으로 가게와 SKU를 선택한다. JSON 검증 실패 시 기존의 한 차례 수정 호출은
유지한다. 예전의 12곳씩 비교한 뒤 우승자를 다시 비교하는 방식은 사용하지 않는다.
리뷰 수 자체에 인기도 점수를 주지 않는다. 내 영수증 불일치, 정산 후 확인된 불만,
만족스러운 정산 경험, 공개 리뷰의 저평점 비율·평점을 참고한다. 공개 리뷰 수는 작은
표본의 신뢰도 보정에만 사용한다. 시장 리뷰는 최근 최대 10건이라 전체 리뷰 수가 아니다.

후보가 많으면 5곳은 위 근거로, 1곳은 아직 거래하지 않았고 저평점 신호가 없는 가게로
구성한다. 리뷰 없는 가게가 있으면 탐색 후보에서 우선 검토하며, 주문 ID로 순서를
돌려 특정 이름이나 레지스트리 첫 가게에 고정되지 않게 한다. 탐색은 **후보에 넣는 것**이고
실제 선택·가격 제안·수락은 모델이 판단한다. 무리한 구매나 가게별 균등 구매를 강제하지
않는다. 내 거래 기록은 현재 round만 집계하고, 공개 리뷰는 round 표시와 함께 전달한다.

최근 실패는 기존 append-only 거래 기억을 재사용한다. 같은 가게·SKU에서 `no_deal`이
난 뒤 15분 이내이고 당시의 공개 수량·최근 리뷰·구매 조건이 같으면 **대안이 있는 동안**
그 제안을 후보에서 뺀다. 다른 SKU는 계속 검토하고, 수량·리뷰·유효 가격 상한·품질 조건
변화나 15분 경과 시 다시 검토한다. 모든 후보가 대기 중이면 재검토한다. 이는 부정행위
판정이 아니다. 네트워크/모델 오류, 미정산 영수증, 비교 정보가 없는 과거 기록은 이
규칙에 넣지 않는다. 공개 정보에 없는 숨은 가격·품질 변경은 즉시 감지할 수 없다.

리뷰는 통계와 최신/저평점 발췌 각 최대 160자, 내 거래는 최근 2건의 짧은 근거를 전달한다.
`buyer_context.py`는 현재 판매자 메시지 최대 1600자, 첫/마지막 이전 메시지 각 240자,
정확히 파싱된 호가·내 제안 경로를 전달한다. 현재 답변을 대화 이력에 중복해서 넣거나
긴 과거 대화를 반복 전송하지 않는다. 요약을 위한 모델은 추가하지 않는다. 발췌된
내용은 검증된 품질로 취급하지 않으며, 영수증·인증서·등급·보증 검사는 그대로 수행한다.

이 단계 당시 가격 상한(예산 70%와 정가 65% 중 작은 값), A등급·비식품 6시간 보증을
유지했다. 현재 구매 조건은 아래의 **구매·리뷰 기준 분리**로 완화했다. 최대 4회 협상
판단, Haiku, 모델 없는 정산 리뷰는 유지한다. `SELECTION CONTEXT`와 `NEGOTIATION CONTEXT` 로그는 후보
수·입력 JSON 문자 수를 남긴다. 문자 수는 실제 토큰 수나 Claude 구독 사용량이 아니다.
실제 절약률과 정산 성사율은 서버에 재배포한 뒤 운영 로그로 별도 확인해야 한다.

검증: 오프라인 **170개 통과** (`logs/offline-20261103T010036Z-f2f3b1a2.log`).
합성 후보 40곳에서 가게 선택 판단은 5회 → 1회였다. 첫 압축 시도에서는 설명문이
늘어 짧은 협상의 입력이 증가했고 그 기록도 보존했다. 설명문을 줄인 뒤 동일한 4회
협상의 애플리케이션 입력 문자 수는 짧은 대화 9,534 → 7,482, 긴 대화 16,800 → 12,534였다
(`logs/buyer-context-comparison-20261103T010107Z-d5e6427c.log`). 실제 모델 호출·토큰
계측·거래 성사율 비교는 하지 않았으며, 형식 오류 수정 호출이나 CLI 기본 문맥·캐시는
이 수치에 들어 있지 않다.

## 판매자 입력 절약 (2026-11-03)

`seller_context.py`가 협상 이력을 숫자 제안·호가와 짧은 발췌로 바꾼다. 매번 반복되는
상품·보증 안내는 구조화된 상품 사실과 고정된 판매 조건으로 전달하고, 현재 제안을
과거 제안에 중복해서 넣지 않는다. 숫자로만 된 구매 제안과 판매자가 생성한 명확한
호가만 가격 기록으로 취급한다. SKU·보증 시간·애매한 문장의 숫자를 가격으로 추측하지 않는다.

공통 지침을 줄이고 첫 호가·일반 협상·마감·최종 제안 중 **현재 단계의 지침만** 보낸다.
기본/조건부 하한·할인 허용 조건·고정 보증·첫 호가 범위는 기존 코드가 계산하고, 원래
전체 조건으로 모델 출력을 검증한다. 협상 기회, Haiku, 출력 오류 재시도, 별도 분석자의
호출 한도는 유지한다. 최종 답변의 단순 수락/거절에는 계속 모델을 부르지 않는다.
LongMemEval-V2나 임베딩·추가 요약 모델은 도입하지 않았다.

`[seller-context]` 로그는 단계와 입력 JSON 문자 수를 남긴다. 기존 원본 실행 로그는
보존한다. 합성 식품/비식품 및 짧은/긴 문의 4종에서 각각 같은 4회 협상을 비교한 결과,
지침과 JSON을 합친 애플리케이션 입력 문자 수가 **48.0~48.8% 감소**했다
(`logs/seller-context-comparison-20261103T015006Z-2d603d90.log`). 예를 들어 비식품의
짧은 문의는 17,710 → 9,061자였다. 실제 토큰 수·Claude 구독 사용량·캐시·CLI 기본
문맥·출력·재시도는 측정하지 않았다. 모델 대역으로 같은 가격을 사용했으므로 실제
Haiku의 가격 판단이나 거래 성사율이 같다는 증거도 아니다.

검증: 압축 정보·단계별 지침·원래 가격 검증 유지·실제 A2A 형식의 협상과 영수증을
포함해 오프라인 **180개 통과** (`logs/offline-20261103T014821Z-06d3c6e3.log`).
이번 구매자·판매자 입력 절약 변경은 로컬에만 적용했으며 서버 재배포는 하지 않았다.

서버의 v4 전환·week-08 등록·ACP 확인은 사용자가 실행한 배포 로그로 확인됐다
(`logs/deployment-20261102T060419Z-e45a251c/server-deployment.log`).
**이번 전략 분석자·가격/보증 정책·수익 기반 재입고·첫 호가 조정·조기 마감 협상은 로컬 구현·검증까지 완료했으며, 서버 반영에는 아래 배포 명령을
다시 실행해야 한다.** 과거 배포 성공이 현재 서버의 실행 상태를 보장하지는 않는다.

## 모델 호출 없는 재고·자금·종료일 관리 (2026-11-03)

기존 재입고의 15분 주기에 로컬 숫자 계산을 추가했다. 별도 모델·임베딩·요약 호출,
공개 API 조회 주기를 추가하지 않는다. 전체 재고 기록을 판매자나 분석자 프롬프트에
붙이지 않는다. Haiku·기존 협상 횟수·등급별 하한·보증은 유지한다.

**금액 한도:** `stock_budget.py`는 이미 가진 물건의 실제 원가와 이번에 살 물건의
최대 예상 원가(정가 75% 올림 + 1)를 합해 검사한다. 초기 실험값은 다음과 같다.

| 한도 | 시작 자본 대비 | 500만 시작 시 |
|---|---:|---:|
| 남겨 둘 현금 | 40% | 200만 |
| 한 번의 매입 계획 | 최대 10% | 50만 |
| 같은 SKU 보유 원가 | 최대 10% | 50만 |
| 같은 카테고리 보유 원가 | 최대 25% | 125만 |
| 식품 전체 보유 원가 | 최대 10% | 50만 |

기존 15분당 5개·전체 20개·SKU당 비식품 3개/식품 1개도 동시에 적용한다. 수익이
늘었다고 한도가 자동으로 커지지는 않는다. 기존 재고가 이미 한도를 넘으면 추가 매입만
막고 임의로 버리거나 팔지 않는다. 단위의 원가가 없거나 ID가 중복되면 매입을 거부한다.

**실제 관찰과 추정 구분:** `stock_lifecycle.py`가 실제 재고와 정산 증거를 unit별로
연결한다. 매입 계획은 매입 성공으로 세지 않는다. 사라졌지만 정산 확인이 없는 물건은
미확정 비용으로, 그중 유통기한이 지난 식품은 폐기 가능성이 있는 미확정 비용으로
기록한다. 폐기를 사실로 단정하지 않는다. 해당 SKU의 추가 매입을 보류하고, 뒤늦게
unit·SKU·원가가 맞는 정산이 확인되면 보류 원인을 해제한다. 파산 지원금 변동과 함께
사라진 재고는 압류 의심으로 구분한다. 처음 관찰하기 전의 누락된 매입·폐기는 복원할 수 없다.

상품별 기존 판매 손익은 7일 표본이고, 재고 관측은 현재 라운드/초기화 이후 기록이다.
두 기간의 숫자를 합쳐 정확한 총순이익이라고 하지 않는다. 공식 전체 순이익은 계속
`balance - start - injected`다. 새 상태는 `.market/stock-lifecycle.json`, 원본 사건은
`logs/stock-lifecycle.jsonl`, 매입 근거와 현금 부족 상태는 `logs/restock-decisions.jsonl`에 남긴다.
재고 없이 현금 하한에 걸리면 `cash_floor_no_stock`와 `needs_attention=true`를 기록한다.
파산 신청 자격도 기록하지만 자동 파산하거나 현금 하한을 임의로 낮추지는 않는다.

재고 기억은 800KB 안에서 관리한다. 최근 확정 정산 상세는 최대 1,000개를 유지하고,
이전 정산은 SKU별 누적 개수·원가로 압축한다. 영수증 시각과 unit의 경계를 저장해
압축된 기록을 다시 읽어도 중복 집계하지 않는다. 보유·미확정 재고는 압축에서 제외하며,
늦은 정산이 확인되면 여전히 해제할 수 있다. 그 경계보다 오래됐고 전에 관찰하지 못한
영수증은 중복 여부를 알 수 없어 누적 관측에서 제외한다. 상세 기록 2,000개나 파일
크기 한도를 압축 후에도 넘으면, 미확정 기록을 버리는 대신 신규 매입을 거부하고 원인을
로그에 남긴다. 원본 사건 로그는 수정하지 않으며 별도의 파일로 계속 쌓인다.

**종료일:** `shop-policy.json`의 `horizon`은 공지된 Round 3 종료인
`2026-11-17T23:59:00+09:00`에만 적용한다. 다른 라운드는 일정 확인 전 매입을 멈춘다.
마지막 24시간에는 검증 표본이 없는 상품을 사지 않고, 마지막 6시간에는 신규 매입을
전부 멈춘다. 그 전에도 예상 판매 시간과 보증·정산 여유가 부족하면 매입하지 않는다.
보증 대기/불확실 기록 없이 성숙한 판매가 3건 이상이면 평균 판매 시간의 2배를 쓰며,
그 외에는 비식품 24시간·식품 6시간의 2배를 쓴다. 정산 1시간, 비식품 보증 6시간을
추가한다. 따라서 미검증 비식품은 종료 55시간 전부터 제한된다. 관측 평균과 여유 시간은
휴리스틱이며 판매나 공급받을 식품의 실제 유통기한을 보장하지 않는다.

마지막 24시간의 **새 협상**에서는 첫 호가를 기존 기본 하한~하한+1% 범위로 좁힌다.
이전에 계산한 더 낮은 상한이 있으면 그 상한도 지킨다. 기존 거래의 호가·보증·하한은
바꾸지 않으며, 원가 이하 처분이나 서비스 자동 종료는 추가하지 않았다. 종료 일정이
바뀌면 설정을 고쳐 재배포해야 한다. 실제 성과는 정산·환불·폐기 관측으로 확인해야 한다.

통합 검증: 오프라인 **216개 통과** (`logs/offline-20261103T102820Z-f118f2c3.log`).
미확정 식품의 재매입 보류와 늦은 정산 복구, 현금·상품별 한도, 실제 hook의 종료일 적용,
A2A 최종 수락과 6시간 보증, 추가 모델 판단 없음까지 합성 자료로 확인했다. 서버에
배포하거나 실제 매입·모델 호출을 실행한 결과가 아니다.

오래된 정산 압축·재시작 후 중복 방지·잘못된 시간 기록의 저장 차단을 추가해 최종
**221개 통과** (`logs/offline-20261103T103056Z-a174aa55.log`). 상품 5,629개·판매 표본
1,000개의 합성 매입 계산 10회에서 중앙값 99.25ms, 모델 호출 0회였다
(`logs/stock-planner-size-20261103T103137Z-f41d46c4.log`). 네트워크·파일 입출력·실제 서버
성능을 포함하지 않은 로컬 계산 측정이며, 새 기능의 운영 수익 개선을 입증한 것은 아니다.

## 사용자가 선택한 판매 정책과 재입고 (2026-11-02)

`shop-policy.json`의 초기값은 사용자가 선택했다. 아래 수치는 시장 규칙이나 검증된
최적값이 아니라 이번 실험 정책이다. 판매자·구매자·분석자 모두 기존 Haiku를 유지한다.

| 항목 | 적용 내용 |
|---|---|
| 기본 판매 하한 | A 원가 × 1.10, B × 1.05, C × 1.00, 정수 올림 |
| 조건부 마감 하한 | A × 1.10, B × 1.02, C × 1.00; 아래 할인 조건 충족 시 적용 |
| 보증 | A등급 비식품 6시간, B/C 비식품 및 식품은 미제공 |
| 현금 하한 | 시작 자본의 40%: 500만 시작이면 200만 크레딧 |
| 매입 한도 | 15분에 최대 5개, 전체 재고 20개, SKU당 비식품 3개·식품 1개 |
| 탐색 | 판매 근거가 있으면 회당 최대 1개를 새 SKU 탐색에 배정, 근거가 없으면 최대 5개를 서로 다른 SKU로 탐색 |

원가 70,000인 상품의 기본 하한은 A 77,000 / B 73,500 / C 70,000이다.
B의 추가 할인 조건을 충족하면 하한은 71,400이다. 현재 적용되는 하한보다 낮은 가격은
모델과 분석자가 제안해도 코드가 거부한다. 두 하한·할인 조건·보증을 협상 시작 때
고정한다. 식품의 등급이 이후 떨어져도 진행 중인 협상의 하한을 소급해서 다시 계산하지
않으며, 다음 협상에서 새 등급을 사용한다. 식품의 고정 등급 claim은 영수증에 넣지 않는다.
하한이 높아지면 가격에 민감한 구매자와의 거래가 줄 수 있고, 원가 마진만으로 보관비와
환불 손실까지 보전된다고 보장하지 않는다.

6시간 보증은 안내 문구뿐 아니라 판매자가 발급하는 영수증의 `warranty_hours=6`으로
전달된다. 공식 v4 checkout이 그 조건을 서명된 checkout에 포함하며, 보증 기간 내
고장 나면 시장이 가게 잔액에서 전액 환불한다. 구매자 사본에서 시간을 바꿔도 판매자
원본 조건이 사용된다. 이는 우리 코드가 직접 환불 요청을 보내는 기능이 아니다.
[공식 시장 계약](https://market.ourolabs.ai/agent.md)의 공급·보증·hook 규격을 확인했다.

**재입고 선택:** `sales_performance.py`가 내 영수증 이벤트와 공식 kit 로그의
`[acp] settled ... ledger #... unit ...`를 unit·가격으로 대조한다. 해당 라운드의
정산 확인이 있는 SKU와 카테고리를 우선 보충하되, 아래 수익·회전율 규칙으로 순서와
수량을 제한한다. 공개 정산도 unit·SKU·금액이 내 영수증과 일치할 때 대조한다. 영수증 발급만으로는 판매로 세지
않는다. `demand.json`은 주문 가능한 카테고리 목록으로만 쓰며 인기 순위로 해석하지 않는다.
새 SKU는 공개 정산의 수요 표본, 과거 계획 횟수·보유 카테고리 분산·일별 순서로 소량 탐색한다.
무슨 등급이 입고될지는 선택할 수 없으며 공급 때 시장이 정한다.

매입 비용은 공식 공급 원가의 최대치인 정가 75%를 올림하고 단위당 1크레딧의 여유를
더해 계산한다. 이 예상 비용을 빼도 시작 자본의 40%가 남는 계획만 키트에 전달한다.
현재 잔액의 40%를 매번 다시 계산해 현금 하한이 계속 낮아지는 방식은 쓰지 않는다.
다만 계획 후 보관비·환불이 발생하면 실제 현금은 달라질 수 있다. 잔액이 이미 하한
아래면 매입을 멈추고, 자동 파산 신청은 하지 않는다. `restock.enabled=false`도
매입 중단을 뜻하며 공식 키트의 무작위 매입으로 돌아가지 않는다.

키트는 hook을 약 60초마다 호출하지만, 우리 hook은 15분 간격을 파일에 먼저 예약한다.
중복 프로세스·재시작으로 같은 시점의 계획이 반복되지 않도록 잠근다. 재고는 45초,
카테고리 정보는 120초 이내여야 하며, 파일 오류나 잘못된 제어 상태에서는 `buy: []`로
멈춘다. 실제 매입 POST는 키트가 수행한다. hook은 15분에 공개 ledger GET 한 번을
추가하며 모델은 부르지 않는다. 공개 수집 실패 시 유효한 캐시 또는 자체 기록으로 판단한다.

**기억의 범위:** `.market/sales-performance.json`에 최근 7일·최대 1,000개 정산
표본을 저장한다. 원본 kit 로그는 끝의 최대 2 MB/4,000줄, 영수증 로그는 최대
1 MB/2,000줄만 읽는다. 읽기 범위 밖의 확인, 문구 형식이 바뀐 확인은 놓칠 수 있다.
이는 시장 전체 인기나 평생 실적, 완전한 환불 차감 순매출이 아니다. 아래 상품별 추정
손익과 공식 전체 순이익을 구분한다. 매입 계획도 실제 입고 성공으로 세지 않으며, 실제 재고 파일을
다음 판단에 사용한다. 계획 근거는 `logs/restock-decisions.jsonl`에 원문으로 추가한다.

**가게 소개와 고객 안내:** 분석자가 고른 가격 비교·명확한 조건·검증 가능한 품질 중
강조점에 맞는 고정 문구를 사용한다. 실제 상품명·비식품 등급·식품 기한·보증 조건·호가를
붙이며, 리뷰 원문이나 모델의 자유 서술을 광고로 내보내지 않는다. 가게의 A2A 카드
`/.well-known/agent-card.json`은 요청 시 최신 유효 조언을 반영하고, 각 협상 안내는
그 협상에 고정된 조언을 쓴다. 시장 웹의 카드 캐시는 재조회 시점까지 늦게 보일 수 있다.
게시판 광고 글이나 메시지를 자동 발송하는 기능은 추가하지 않았다.

검증: 판매 정책·실제 A2A 안내·공식 v4 checkout 보증 전달까지 **99개 통과**
(`logs/offline-20261102T065938Z-511fc933.log`), 정산 대조·현금 하한·재고 제한·중복
계획 차단·공식 restock hook 연결을 포함해 **110개 통과**
(`logs/offline-20261102T070330Z-f22f8a49.log`). 모두 합성 재고와 모델/시장 대역으로
수행했다. 실제 Haiku 호출, 서버 갱신, 실매입·환불·순위 개선은 아직 검증하지 않았다.

## 수익·회전율·첫 호가 실험 (2026-11-02)

아래는 초기 실험 기록이다. 현재 조회 한도·매입 수량·자체 정산가의 가격 반영·분석자
비활성화 설정은 위의 최신 변경 절을 우선한다.

추가한 정책은 사용자가 승인한 전략의 초기 구현이다. 아래 임계값은 실전 최적값으로
검증된 수치가 아니다. 기존 등급별 판매 하한·A 비식품 6시간 보증·현금 40%·회당 5개
매입 한도는 유지하며, 새 판단에는 추가 모델 호출이 없다.

**1. 상품별 수익과 속도 기억.** 판매자 이벤트에 원가·입고 시각·종류·등급·보증을
남긴다. 공식 정산 확인과 대조한 뒤 `판매액 - 원가 - 관찰된 환불 - 추정 보관비`를
계산한다. 비식품 보관비는 원가의 일 1%를 보유 시간에 비례해 올림한 추정치다.
정산 시각을 ledger에서 확인하지 못하면 처음 정산을 관찰한 시각으로 보수적으로
보유 시간을 계산한다. 원가·시각이 없던 과거 기록을 추측해서 채우지 않는다.

상품별 추정치는 공식 순이익과 다르다. `inventory.json`의 잔액·시작 자본·파산 지원금이
모두 있으면 `balance - start - injected`를 가게 전체 순이익으로 별도 제공한다.
공개 ledger는 표본이므로 놓친 환불이 있을 수 있다. 동일 SKU라도 unit을 특정하지 못한
자체 환불은 금액을 임의 배분하지 않고 불확실 상태로 둔다. 보증기간이 남은 거래는 잠정
상태이며, 보증기간 경과도 모든 환불을 확인했다는 뜻은 아니다.

**2. 재입고 선택.** 보증기간이 지난 계산 가능한 표본이 최소 3건이고 추정 손익이
양수인 SKU를 우선한다. 그 안에서는 평균 `원가 대비 추정 이익 / 보유 일수` 순서로
비교하며, 시간 분모는 최소 1시간으로 둔다. 표본 부족·보증 대기·불확실 기록이 있으면
기존 재고를 포함해 해당 SKU를 최대 1개만 보유하도록 제한한다. 최소 3건의 성숙 표본에서
추정 손익이 0 이하이거나 관찰된 환불 비율이 50% 이상이면 추가 매입을 멈춘다.
24시간 이상 묵은 재고가 있는 SKU도 재매입을 멈춘다. 이미 있는 재고는 계속 판매한다.
상품 등급은 공급 시 무작위이므로 이 규칙이 다음 입고 품질을 보장하지는 않는다.

**3. 공개 수요 탐색.** `market_evidence.py`가 공식 `/api/ledger?after=-500`을
15분마다 한 번 읽는다. 실패도 주기를 소비하며 최대 1 MB·20초 읽기 한도를 쓴다.
같은 라운드의 정산/고장 구조화 필드만 남기고 주문 예산·리뷰 문장은 보관하지 않는다.
최근 7일·최대 2,000개 사실을 보관하며 UTF-8 데이터는 800 KB 안으로 제한한다.
활용 시 캐시는 1시간 이내여야 한다.
수요 점수는 최근 24시간에 최소 3건·서로 다른 2개 가게에서 정산된 SKU에만 부여하며
한 가게의 기여는 최대 3건이다. 이 점수는 새 SKU 소량 탐색에만 쓰고, 인기 순위 전체나
미공개 주문 가중치를 알아냈다고 해석하지 않는다. 원장 순번이 감소하면 표본을 초기화한다.

**4. 첫 호가 조정.** `opening_strategy.py`는 같은 SKU·등급·보증의 최근 24시간
정산이 최소 3건·2개 가게에 있을 때 가게별 가격 중앙값들의 중앙값을 기준으로 삼는다.
보증 필드가 없으면 보증 0으로 간주하지 않고 비교에서 제외한다. 비교 자료가 없으면
최소 10건의 완료 협상에서 관찰한 내 첫 호가를 기준으로 쓴다. 자료가 부족하면 기존
Haiku의 초기 가격 판단을 유지한다.

완료 표본 10건 이상·새 완료 협상 5건 이상일 때 명시적 최종가격 거절이 절반 이상이면
기준에 -2%, 실제 정산 비율이 80% 이상이고 성숙 표본 3건의 추정 손익이 양수면 +2%의
작은 실험을 한다. 같은 관측만으로 반복 할인하지 않는다. **기준 호가** 갱신은 최소
1시간 간격·회당 최대 2% 변동이다. 실제 첫 호가는 모델이 기준의 ±3% 범위에서 고르며,
기본 하한과 정가 경계를 함께 적용한다. 따라서 실제 호가 변동 자체가 2% 이내라는 뜻은
아니다. 새로운 기준을 처음 적용하거나 원가가 다른 새 unit을 팔 때도 같은 보장은 없다.
첫 호가 범위는 협상 시작 때 고정하며, 분석자의 ±5% 권고도 그 범위를 우회하지 못한다.

**5. 오래된 재고 할인과 이탈 구분.** 24시간 이상 묵은 비식품 또는 유통기한이 2시간
이내인 식품은 첫 호가부터 `기본 하한 ~ 기본 하한×1.03` 안에서 제안한다. 기존 마감
할인은 별도로 유지한다. 협상 시작·첫 호가·최종 거절·오류·취소·만료·영수증·정산을
대조해 최근 24시간의 완전한 작업 표본을 집계한다. 여기의 시작은 재고 예약에 성공한
협상이며 웹 방문 횟수가 아니다. 영수증 후 미관찰 정산, 취소, 만료의 원인은 알 수
없으므로 가격 거절로 세지 않는다. 오류도 가격 조정의 분모에서 제외한다.

수집과 집계는 재입고 hook의 15분 주기를 공유한다. `restock.enabled=false`이면
이 갱신도 멈춘다. 판매자는 로컬 첫 호가 캐시를 최대 1분에 한 번 읽고, 만들어진 지
6시간을 넘은 기준은 사용하지 않는다. 기존 Haiku 분석자의 1시간 간격·하루 최대 6회
한도는 그대로다. 전체 주기적 공개 요청은 분석자 최대 5회 + 원장 1회/15분이다.

추가 원본 기록: `logs/market-evidence.jsonl`, `logs/opening-strategy.jsonl`.
집계 기억: `.market/sales-performance.json`, `.market/market-evidence.json`,
`.market/opening-strategy.json`. 모두 원본 로그를 수정하지 않고 만든 별도 파생 파일이다.

검증: 정산/환불 매칭·중복·불확실성·재입고 변경을 포함해 **137개 통과**
(`logs/offline-20261102T080623Z-1d210d6c.log`), 첫 호가·실제 A2A 할인과 기존 마감
회귀 검사를 포함해 **145개 통과** (`logs/offline-20261102T081148Z-c9eaa07a.log`).
공개 계약과 [대시보드](https://market.ourolabs.ai/dashboard)의 ledger 표시 필드를 읽어
정산 `amount`, 고장 `refunded` 사용을 확인했다. 현재 실제 시장은 Round 2였으므로
Round 3 환불·가격 비교 연동은 합성 자료로만 검증했다. 필드가 없으면 해당 비교나
정확한 환불 배분을 생략하며, 실운영에서 규격과 효과를 다시 확인해야 한다.
이후 원장 초기화·일시 장애 시 가격 기억 유지·긴 한글 필드의 캐시 크기 제한을 추가
검증해 **148개 통과** (`logs/offline-20261102T081913Z-97b5f5cf.log`). 환불 대조는 SKU별로
색인해 매번 모든 판매와 모든 공개 이벤트를 교차 순회하지 않도록 했다.

## 방문한 구매자와 빨리 합의하는 협상 (2026-11-02)

이번 정책은 사용자가 승인한 조기 마감 실험이다. 상품 문의 뒤의 **숫자 가격 제안**을
1회로 센다. 첫 문의나 숫자가 아닌 메시지는 구매자의 가격 제안 횟수에 넣지 않는다.

| 시점 | 동작 |
|---|---|
| 첫 문의 | Haiku가 기본 하한 이상에서 경쟁력 있는 초기 가격을 선택 |
| 구매자 첫 제안 | 좋은 가격이면 즉시 수락하도록 유도; 낮으면 역제안 |
| 두 번째 제안 | 적용 하한 이상이면 수락 필수, 미만이면 마감 방향으로 양보 |
| 세 번째 제안 | 적용 하한 이상이면 수락, 미만이면 적용 하한으로 최종 가격 제시 |
| 최종 가격 다음 응답 | 제시가 이상이면 정확히 구매자가 제안한 금액으로 영수증 발급, 미만이면 종료 |

이미 제시한 가격 이상을 구매자가 보내면 어느 단계에서든 추가 모델 호출 없이 수락한다.
최종 가격을 제시한 직후 횟수 제한으로 끊지 않는다. 수락 응답을 기다리는 동안에도 기존
재고 유효성 검사와 5분 무응답 만료를 적용한다. 최종 가격에 대한 더 낮은 제안에는 모델을
다시 부르지 않으며 unit 예약을 해제한다. 영수증 발급 후 예약은 기존 결제 확인 규칙을 따른다.

**추가 할인 조건:** 두 번째 제안부터 아래 하나를 충족해야 B등급 마감 하한을 연다.

- 구매자가 이전 최고 제안보다 **기본 하한의 1% 이상** 올렸고, 현재 가격이 기본 하한에서
  **3% 이내로 가까워진 경우**. 가격을 내렸다가 복구하거나 1원씩 올리는 행위는 근거가 되지 않는다.
- 공식 재고의 입고 시각 기준으로 비식품이 **24시간 이상** 묵은 경우.
- 공식 재고의 식품 유통기한이 **2시간 이내**로 남은 경우. 이미 지난 식품은 팔지 않는다.

횟수만 채우면 추가 할인되는 것은 아니다. 조건을 충족하지 못한 최종 가격은 기본 하한이다.
한번 허용된 추가 할인은 같은 협상에서 철회하지 않으며, 최종 가격을 보낸 뒤 새 할인 조건을
평가해 다시 흥정하지 않는다. A등급은 보증 부담을 고려해 마감 하한도 원가+10%를 유지한다.
C등급은 원가가 하한이며, 어떤 등급도 원가 이하로 덤핑하지 않는다.

예: B 원가 70,000 → 기본 하한 73,500 / 마감 하한 71,400.
구매자 71,000 → 72,000이면 1,000의 개선이 735를 넘고, 기본 하한과 차이 1,500이
2,205 이내이므로 두 번째 제안 **72,000에 합의**한다. 72,000을 반복하기만 한 새 재고는
추가 할인 조건을 충족하지 않는다. 이 숫자들은 최적값이라는 증거가 없는 초기 실험값이며,
`shop-policy.json`의 `closing`에서 조정해 재배포한다.

모델은 초기 호가와 초기 양보를 결정하고, 마감 시점의 수락 의무·최종 가격·하한은 코드가
검사한다. 유효한 모델 출력 기준으로 협상당 최대 **4회 판단**(초기 + 가격 제안 3회),
출력 수정 재시도까지 포함하면 CLI 실행 최대 8회다. 수락·최종 거절의 단순 처리는 추가
모델 호출이 없다. 새 주기 작업이나 외부 API 호출도 추가하지 않았다.

`logs/inventory-seller-events.jsonl`에 협상 시작·최종 가격·취소·만료·영수증 발급과
단계, 제안 횟수, 적용 하한, 할인 이유, 모델/단순 처리 여부를 기록한다. 분석자에게도
마감 정책과 제한된 최근 이벤트 요약을 제공한다. 이 표본의 영수증 발급률은 정산 전환율이
아니다. 실제 판매·수익 효과는 키트의 정산 기록, 환불, 공개 board와 함께 확인해야 한다.

검증: **125개 통과**, 그중 마감 정책 신규 15개
(`logs/offline-20261102T074958Z-1c3449e7.log`). 실제 A2A 형식에서 72,000 합의,
최종 가격 수락 기회, 추가 호출 생략, 원가/보증 유지, 재고 만료와 정책 고정을 검증했다.
합성 재고와 모델 대역으로 수행했으며 실제 Haiku 협상·순위 효과는 아직 검증하지 않았다.

## 별도 판매 전략 분석자 실험 기록 (2026-11-02, 현재 비활성)

이 절은 과거 구현과 실험을 보존한 기록이다. 현재 `enabled=false`이며 분석 프로세스·
모델 호출·판매자의 조언 캐시 사용은 중단했다. 아래 주기와 동작은 활성화 당시의 설명이다.

```text
공식 공개 board + 리뷰 + 로컬 게시판 표본 + 내 재고·협상·정산 요약
  → 별도 Haiku 분석자 → 검증된 로컬 조언 파일
  → 판매자 Haiku가 새 협상부터 참고 → 실제 제안·영수증은 기존 검증 통과
```

- **관찰:** 15분에 한 번 공식 시장에 최대 5회 GET 요청을 보낸다. 내 최신 리뷰 최대
  10개, 나를 제외한 상위 3개 가게의 리뷰 각 5개, 공개 소개와 성과를 읽는다.
  순위는 board의 `all` 점수, 동률이면 profit을 사용한다. 점수가 없는 응답에서만
  profit/deals 순서를 쓰고 그 사실을 분석자에게 명시한다. 같은 별점·문구는 중복 제거하고
  작성자와 시각을 보존한다. 다른 가게의 내부 프롬프트·원가·비공개 전략은 알 수 없다.
- **게시판:** 키트가 약 30초마다 저장하는 `.market/forum.json`을 재사용한다.
  추가 웹 요청 없이, 120초 이내에 갱신된 파일에서 최근 24시간의 글 중 내 가게·상위
  가게 이름·현재 재고 SKU·카테고리와 관련된 글을 최대 5개, 글당 180자만 추린다.
  파일은 1 MB/100개 글, 게시판 자료는 JSON 3,000자 이내로 제한한다. 중복 문구를
  제거하고 서로 다른 작성자를 우선하며 작성자·제공된 소유자별 최대 2개를 허용한다.
  좋아요 수는 수요나 사실 여부의 근거로 쓰지 않는다. 내 홍보 글은 따로 표시한다.
  구매 요청은 관심의 단서, 불만은 설명·협상 개선의 단서로만 참고한다. 라운드가
  없는 글은 `unreported`로 표시하며 현재 라운드 수요로 확정하지 않는다. 원장 참조도
  이미 가진 현재 라운드 표본과 대조할 뿐, 글의 주장이나 작성자 독립성을 입증하지 않는다.
- **판단:** Haiku를 별도 프로세스에서 최소 1시간 간격, 최근 24시간 최대 6회 호출한다.
  실패한 호출도 횟수에 포함하며 재시도 없이 60초 제한을 적용한다. 입력 JSON은 이전
  조언까지 포함해 18,000자 이내다(기본 프롬프트 제외, 토큰 수와는 다름). 초과하면
  오래된 조언·상위 가게 리뷰·소개부터 제외하며 내 최신 리뷰와 정책을 우선 보존한다.
  게시판이 있으면 최소 1개를 보존하며 생략 내역을 표시한다. 별도 요약 모델은 없다.
  관찰 내용이 같으면 재분석하지 않고, 파일 갱신 시각·좋아요만 바뀌어도 호출하지 않는다.
  Round 3 전에는 board 확인만 한다. 리뷰가 없고 내 정산도 3건 미만이면 서로 다른
  외부 작성자명 2개 이상의 관련 게시글이 있어야 분석한다. 이는 광고 한 건에 대한
  불필요한 호출을 줄이는 조건이며 작성자가 실제 다른 사람이라는 검증은 아니다.
  게시판의 새 근거로 기존 분석 슬롯을 사용할 수 있지만 시간·일일 호출 상한은 같다.
- **조언:** 기본 전략과 재고 카테고리 최대 4개의 가격 조정 제안(-5~+5%), 협상 속도
  (`balanced`/`quick`), 강조점(`value`/`clarity`/`quality`)을 저장한다. 모든 제안은
  관찰 자료의 ID를 인용해야 한다. 가격 비율은 판매자가 원래 선택할 호가에 대한
  **권고**이며, 실제 가격의 ±5% 변동을 코드로 보장하는 장치는 아니다. 판매자가
  마감 전 가격을 판단하고 사용자가 정한 등급별 하한·마감 규칙·호가 인상 금지·재고 검증을 적용한다.
- **기억:** 같은 라운드·최근 24시간의 이전 조언과 당시 성과 최대 4개를 다음 분석에
  전달한다. 거래 수가 감소한 시장 초기화는 실패한 가격 실험으로 해석하지 않는다.
  재고 요약은 최대 8개 카테고리, 협상 요약은 최근 24시간/최대 200개 이벤트다.
  영수증 발급은 정산으로 세지 않으며, board 성과 변화가 조언 때문이라고 단정하지 않는다.
- **적용:** 판매자는 로컬 파일만 읽고 새 협상 시작 때 조언을 고정한다. 협상 중간에
  바뀌지 않는다. 조언이 없거나 잘못됐거나 6시간이 지나면 기본 정책을 쓴다. 외부 리뷰·
  게시판 원문과 분석자의 자유 서술은 판매자에게 전달하지 않고 감사 로그에만 남긴다.
  게시판을 읽어도 자동 재입고 선택이나 가격 하한·보증은 바꾸지 않는다. 분석자는
  결제·재입고·게시글/답글·투표·리뷰 작성 도구를 갖지 않으며 outbox도 만들지 않는다.
- **수명:** 분석자 오류가 판매자를 멈추지 않는다. 프로세스가 종료되면 최소 60초 후
  다시 시작한다. 서비스 종료 시 판매자·분석자와 진행 중인 모델 호출을 함께 정리한다.
  서비스 이름은 기존 `week07-market.service`를 그대로 사용한다.

`advisor-config.json`에서 호출 주기를 늘리거나 일일 한도를 낮출 수 있다.
기본값은 `poll_seconds=900`, `model_interval_seconds=3600`, `max_calls_per_day=6`,
`strategy_ttl_seconds=21600`이다. 분석을 끄려면 `enabled=false`로 바꿔 재배포한다.

## 구매·리뷰 기준 분리 (2026-11-03, 사용자가 선택한 정책)

`buyer-policy.json`의 현재 버전은 `balanced-buy-strict-review-v2`다. 실제 구매의
최소 조건과 높은 별점을 주는 이상 조건을 분리한다. 구매 상한은
**min(예산 × 90%, 시장 카탈로그 정가 × 85%)**이며 정수로 내림한다. 판매자 말에서
정가를 추측하지 않는다. Round 3 카탈로그 가격이 없으면 거래를 시작하지 않는다.
예산과 정가가 모두 100,000이면 구매 상한 85,000, 협상 목표 76,500이다. 목표는
희망 가격이며 그보다 비싸다는 이유만으로 포기하도록 지시하지 않는다.

결제 조건은 시장 증명서 필수·**A/B등급 허용**이다. 비식품은 **3시간 이상 보증**, 식품은 주문의
사용 시간에 1시간을 더한 유통기한 여유를 요구한다. `accept`를 통해 공식 v4 코드가
결제 전에 검사한다. 협상 때의 말만으로 품질이나 보증을 확인했다고 처리하지 않는다.

협상 결정은 최대 4회다. 새 역제안은 이전 제안에서 구매 상한의 5%까지만 올리지만,
모델이 명시적으로 **현재 호가 그대로 수락**할 때는 이 양보폭을 넘어 구매 상한까지
수락할 수 있다. 마지막 결정에는 허용 조건을 충족한 호가의 수락을 우선 검토하게 한다.
수락 가격의 일치·구매 상한·실제 영수증 검사는 계속 적용한다. 자동 강제 구매나 추가
모델 호출은 없다. 주문당 한 가게를 선택하는 구조이며 실패 후 다른 가게 재시도는 없다.

높은 별점의 가격 기준은 **min(예산 × 70%, 정가 × 65%)**, 품질은 A등급,
비식품 보증은 6시간이다. 이 `review_preferences`를 구매 당시 `purchase_policy`에
함께 저장하고 리뷰에서만 사용한다. 가게 선택·협상 모델에는 이 별도 평가 기준을
보내지 않아 구매 최소 조건으로 오해하지 않게 하고 입력도 줄인다. 판매자에게 낮은
별점을 위협하며 할인을 요구하지 않도록 프롬프트에 명시한다.

정산 후 리뷰는 추가 모델 호출 없이 실제 영수증과 기록으로 매긴다. 가격·등급·보증
(식품은 남은 기한)의 선호 미충족을 각각 한 항목으로 센다.

| 조건 | 별점 |
|---|---|
| 등급 주장 불일치, 시장 기록상 사용 가치 0, 구매 상한 초과 | 1 |
| 실제 최소 조건 미달·필수 사실 미보고 또는 이상 조건에 못 미치는 항목 2개 이상 | 최대 2 |
| 구매 최소 조건은 충족하지만 이상 조건에 못 미치는 항목 1개 | 3 |
| 원래 구매 목표 등 평가 정보가 부족함 | 최대 3, 확인되지 않은 결함은 단정하지 않음 |
| 이상적인 가격·품질·보증/기한 조건을 모두 충족 | 4 |
| 모든 이상 조건 충족 + 이상 가격 상한의 90% 이하 | 5 |

예산·정가가 100,000인 상품이라면, A등급·6시간 보증에 62,000은 4점,
58,500 이하는 5점이다. 같은 조건에 80,000이면 가격 선호 미충족으로 3점,
B등급·3시간 보증에 80,000이면 여러 선호 미충족으로 2점이다. 마지막 경우는
**허용하고 산 타협 조건**이며, 허위 설명이나 계약 위반이라고 쓰지 않는다.

위반이 여러 개면 가장 낮은 점수를 적용한다. 거래 전에 저장한 정책을 주문·가게·SKU·
영수증 task·가격으로 대조하므로 설정을 바꿔도 이미 구매한 거래의 가격 기준을
소급해서 바꾸지 않는다. 식품은 **리뷰 작성 시점**에 남은 시간을 명시하며 결제 당시에도
이미 상했다고 추측하지 않는다. 새 정책에서는 리뷰 시점에 만료됐다는 사실만으로
1점을 주지 않고 최대 2점으로 평가한다. 후기에는 실제 상품/금액/등급/불만 근거만 쓰고 예산,
개인 목표 금액, 구매 상한 금액은 쓰지 않는다. 미결제 거래의 평점은 시장에 공개되는
구매 후기가 아니다. `payments.jsonl`로 정산을 확인한 기록에만 실제 리뷰 결과를 붙여
다음 가게 선택에 전달한다. 실제 문제(`issues`)와 수용한 타협(`preference_shortfalls`)
을 구분해 기억한다. 후자는 `accepted_tradeoffs`로 집계하여 자신의 낮은 별점을 다시
계약 위반으로 오해해 가게를 피하지 않는다. 공개 리뷰가 없는 가게나 단순 통신 오류를
부정직하다고 단정하지 않는다.

예전 `very-strict-v1` 기록은 원래의 예산 70%·정가 65%·A등급·6시간 보증 및 기존
별점 기준을 유지한다. 당시 정책 자체를 찾을 수 없으면 현재 정책을 소급 적용하지 않는다.
현재 변경은 **260개 오프라인 검사 통과**
(`logs/offline-20261103T121401Z-d2c00a28.log`). 구매 상한·서명된 B등급/3시간 보증
검사·최종 수락·리뷰 단계·과거 정책·기억의 구분을 검증했다. 실제 모델 호출이나 거래
수 증가, 실제 토큰 변화는 측정하지 않았으며 서버 적용은 기존 배포 명령으로 수행한다.

## 이번에 추가한 실행 기반

- 공용 `scripts/`를 수정하지 않고 공식 v4를 `vendor/market_kit_v4.py`에 보존했다.
  `vendor/SOURCE.json`에 GitHub blob SHA를 기록하고 실행 전에 원본 일치를 검사한다.
  join에 필요한 코드만 사용한다. 원본의 starter 명령에 필요한 템플릿은 동봉하지 않았다.
- `run_round3.py`: 기본은 읽기 전용 점검. `--prepare-identity`는 기존 week-07의 두 키가
  모두 유효한지 확인하고 없는 키만 week-08에 복사한다. 다른 신원으로 덮어쓰거나
  새 키를 만들지 않는다. 키·환경 파일은 git에서 제외한다.

  오래된 재고 파일 거부, 실제 unit을 담은 서명 영수증을 지원한다. 명시적인 Round 2
  재고 응답이 오면 기존 판매자 경로를 사용한다. 초기 동기화 중에는 재고를 지어내지 않는다.
- 영수증 발급 예약은 재시작 후에도 유지한다. 공식 영수증에 만료/철회 계약이 없으므로
  재고에서 사라질 때까지 다른 구매자에게 같은 unit을 약속하지 않는다. 미결제 영수증이
  재고를 오래 묶을 수 있는 보수적인 선택이다. 결제·취소 확인 후 해제하는 개선은 남았다.
- 가격은 **사용자가 정한 등급별 적용 하한 이상**이어야 한다. 초기 호가는 모델이 정하고
  조기 마감 규칙이 후반 수락·최종 가격을 제한한다. 이는 시장 규칙이 아니라 이번 실험
  정책이다. 분석자의 소폭 가격 조정 권고도 하한을 바꾸지 못한다.
  증명서는 공개하며 비식품 등급만 고정 claim에 넣는다. 식품 등급은 변할 수 있어
  claim을 고정하지 않고 실제 checkout 증명서로 확인하게 한다.
- 구매자는 주문의 acceptable SKU와 가게의 offers를 교차 확인한 뒤 가게당 최대 5개
  후보만 모델에 전달한다. 숫자 SKU/보증 시간을 가격으로 잘못 읽지 않도록 명시적인
  호가를 읽는다. 여러 가격이 모호하게 쓰인 메시지는 자동 수락하지 않는다.
- 구매자의 가격·품질·보증 조건은 위의 매우 강경한 구매 정책을 따른다.

  정산 성공/거절을 기억에 반영한다. 원래 로그를 수정하지 않는다. 읽기는 최근 2 MB,
  최대 2,000줄이므로 평생 통계가 아니다. 장기 집계와 고장/환불 연계는 후속 과제다.
- `review_settled.py`는 실제 정산 hook에서 상품·등급·가격과 엄격한 평가 사유를 기록한다.
  추가 모델 호출 없이 위 표대로 평가하며 사용자 예산을 리뷰에 노출하지 않는다.
- 사용자 정의 `restock.py`가 위의 현금·재고 한도 안에서 매입 계획을 낸다.
  게시판 글/투표를 자동 전송하는 기능은 아직 없다.


실제 운영 전에는 기존 week07-market 서비스를 중지하고, 해당 서비스의 비공개 환경
설정과 동일한 인증을 사용해 `run_round3.py --join`을 실행하도록 서비스를 전환한다.
`--join`은 모델 사용량 및 모의 시장 재고 구매를 발생시킨다. 아래 자동 배포 명령이
기존 서비스 설정을 유지하며 전환과 갱신을 담당한다.
키트의 `--orders` 제한은 구매 주문 수 제한이고,
그동안 판매자 거래나 공급 수량을 제한하는 옵션은 아니다.

2026-11-01 서버 상태 조회는 SSH 인증 오류(`Permission denied`)로 실패했다.
이후 사용자의 비밀번호 배포로 2026-11-02 전환 성공을 확인했다. 키 파일을 요청하거나
출력하지 않는다. 로컬 검증은 합성 재고, 모델 대역, 실제 A2A 직렬화·Ed25519 및 공식 v4 checkout 코드로
수행했다. 실제 Haiku 실행 및 공개 시장 정산 실적을 의미하지 않는다.

1차 실행 기반의 오프라인 검사: 43개 통과
(`logs/offline-20261101T113923Z-0455a05f.log`). 문법 검사, kit CLI 및 실행 전 점검도
통과했다(`logs/runtime-check-8e7e0f8079.log`). 로컬 week-08에는 아직 신원 키를
복사하지 않았다. ANTHROPIC_API_KEY가 없어서 저장소 지침에 따라 실제 모델 실행은
생략했고, CLI 로그인 상태도 확인하지 않았다. 최초 원본 SHA 검사는 복사 과정의
여분 줄바꿈을 발견해 실패했으며 그 로그/커밋을 보존한 뒤 원본 바이트와 일치시켰다.

## 비밀번호 SSH로 서버에 v4 배포하기

2026-11-02: 자동 SSH 인증은 실패했고, 사용자는 맥 터미널에서 비밀번호를 입력하면
`ssh daintI`로 접속할 수 있다고 확인했다. 사용자가 아래 명령으로 v4 배포에 성공했으며,
새 분석자를 반영할 때도 같은 명령을 사용한다.
아래 명령을 맥의 이 레포 루트에서 실행한다. 이미 서버에 접속한 터미널에서는 실행하지 않는다.

```bash
python3 submissions/26510124/week-08/deploy/deploy_v4.py
```

SSH가 비밀번호를 요청하면 터미널에 직접 입력한다. 입력 글자는 표시되지 않는다.
스크립트는 비밀번호를 받거나 저장하지 않으며, 한 번 연결한 SSH 세션을 전송과 설치에
재사용한다. 설치 중에는 터미널을 열어 둔다. 실행하면 판매자와 구매자가 시작되므로
선택한 거래 모델과 Haiku 분석자의 사용량이 발생하며, Round 3에서는 사용자 정의 재입고 계획에 따라 키트가 모의 시장 잔액을 사용한다.

배포 과정:

1. 소스·프롬프트·명시한 공개 설정·고정 v4 키트만 SHA256 명세와 함께 전송한다.
   키, `.env`, 기타 JSON, `.market`, 기존 로그, 가상환경은 전송하지 않는다.
2. 서버의 기존 가상환경으로 전송된 소스의 오프라인 검사를 실행하고, v4 원본 SHA,
   두 신원 키, 기존 비공개 서비스 환경 설정, 선택 모델 CLI/cloudflared 경로를 확인한다.
   Astra 프로필이면 서버 ChatGPT 로그인과 작은 모델 응답 1회도 확인한다.
   이 단계가 실패하면 기존 서비스는 중지하지 않는다.
3. 변경할 소스와 서비스 설정을 백업한 뒤 기존 서비스를 중지한다. 서버의 week-07 키를
   week-08에 복사하되, 이미 있는 다른 키를 덮어쓰거나 새 신원을 생성하지 않는다.
4. `week07-market.service`의 이름과 환경 설정은 유지하고, 사용자 systemd drop-in으로
   week-08의 `run_round3.py --join`을 실행한다. 별도 두 번째 키트를 켜지 않는다.
5. 이번 시작 이후 로그에서 `market_kit 4`, week-08 경로, 가게와 구매자의 등록을 확인하고
   새 가게 주소의 ACP 안내를 조회한다. 210초 이내 확인되지 않으면 이전 소스·서비스
   설정으로 복구를 시도한다. 전환 전 실행 중이던 서비스는 다시 시작한다.

완료 표시는 다음과 같다. 이는 등록과 ACP 확인이며 실제 정산 성공을 증명하지 않는다.
Round 3 개장 여부와 정산 건수는 별도로 확인해야 한다.

```text
READY: market_kit 4; week-08; shop and buyer registered; ACP verified.
```

서버 증거는 `week-08/logs/deployment-<실행ID>/`, 백업은
`week-08/.market/deploy-backups/<실행ID>/`에 남는다. 맥에도 업로드 명세와 서버 설치 출력이
같은 실행 ID의 `logs/deployment-.../`에 원문으로 저장된다. 중간에 연결이 끊기거나
`ROLLBACK NEEDS ATTENTION`이 표시되면 완료로 판단하지 않고 현재 서비스를 확인한다.
`SIGKILL`이나 서버 전원 장애까지 자동 복구를 보장하지 않는다. 기존 원본 로그는 보존한다.

배포 파일만 만들고 접속·실행하지 않으려면 `--prepare-only`를 붙인다.
배포 실패/복구, 개인 파일 제외, 변조 검사, 새 실행 로그 구분을 포함한 **오프라인 검사
71개 통과**: `logs/offline-20261102T055202Z-4a77f7cf.log`.
SSH와 systemd는 테스트 대역을 사용했으며 실제 서버에서 성공했다는 의미는 아니다.

### 첫 서버 배포 실패와 설정 수정 (2026-11-02)

`logs/deployment-20261102T055518Z-f6332a52/server-deployment.log`는 사용자가 실제로
실행한 첫 배포 출력이다. 서버의 오프라인 검사는 통과했지만 서비스 설정 확인에서
실패했고 이전 소스·서비스 설정으로 복구됐다. 시장 등록을 시작하기 전의 실패이므로
Round 3 개장 대기 메시지가 아니다. v4 전환이나 현재 서버 동작 성공을 의미하지 않는다.

생성한 `WorkingDirectory="/home/..."`의 따옴표가 잘못됐음을 확인해
`WorkingDirectory=/home/...`로 고쳤다. systemd의 WorkingDirectory는 ExecStart처럼
셸 단어를 분리해 따옴표를 제거하는 설정이 아니다.
[systemd v245의 경로 파서](https://github.com/systemd/systemd/blob/v245/src/core/load-fragment.c#L1958)를
확인했다. 첫 실패 로그에는 실제 적용된 속성이 없어서 다른 override의 존재 여부까지
확정할 수 없다. 따라서 원인을 무조건 다른 override라고 단정하던 오류 문구도 바꿨다.

재배포 시에는 기존 서비스를 중지하기 전에 서버의 `systemd-analyze --user verify`로
후보 설정을 검사한다. 적용 뒤에는 LoadState, WorkingDirectory, 설정 파일 경로,
새 실행 명령의 일치 여부를 `service-configuration.json`에 남긴다. 환경 변수나 실제
ExecStart 인자는 기록하지 않는다. 불일치 시에는 이 진단도 맥의 설치 출력에 표시한다.

회귀 검사 포함 73개 통과: `logs/offline-20261102T055829Z-bfe7fa6a.log`.
맥에는 systemd가 없어 네이티브 파서 실행은 재배포 시 서버에서 수행한다.
그다음 사용자의 재배포는 `logs/deployment-20261102T060419Z-e45a251c/`에 기록된 것처럼
등록·ACP 확인까지 성공했다. 이는 이번 분석자 추가 전의 버전이며 실제 정산 검증은 별도다.

## 동작

`collect_feedback.py`가 공식 공개 `/api/board`, `/api/shops`를 읽는다.
대시보드의 기본 정렬과 같이 `profit`, 동률일 때 `deals`로 비교 대상 3곳을

주장하지 않는다. 다른 가게의 주소에는 접속하지 않는다.

본인의 같은 라운드 최신 리뷰 최대 10개를 읽고, 내용이 같은 리뷰를 중복 제거한다.

낮은 별점의 품목별 문구에서 가격·속도·설명·영수증 관련 단어를 분류한다.

감사 로그에만 보관하고 모델에는 사전에 정한 지침만 전달한다.

`seller_agent.py`는 거래 시작 시 로컬 전략을 읽어 해당 협상에 고정한다.
상품 선택·협상·영수증은 기존 모델과 A2A 경로를 사용한다. 가격은 모델이 고르되
코드가 하한가, 합의 금액, 첫 호가 범위와 역행하는 가격 인상을 검사한다.
서명 형식은 기존 `{shop,item,price,task}` 그대로이다.

## 현재 실험 규칙과 조절할 값

`feedback-config.json`의 기본 호가는 lamp 125 / chair 225 / bookshelf 325이다.
이는 검증된 최적가나 상품 품질 평가가 아닌 **실험 초기값**이다.
하한가 100 / 180 / 260은 기존 설정을 유지한다.

- 새 영수증 발급/명시적 협상 거절 5건 이상, 직전 가격 변경 후 1시간 이상일 때만 평가한다.
- 가격 불만 문구 3개 이상, 자체 거절 비율 50% 이상, 상위 가게의 가격 경쟁력 주장까지
  함께 있을 때 목표 호가를 최대 5% 낮춘다.
- 영수증 발급 비율 80% 이상, 공개 인정 판매 증가 3건 이상, 리뷰 3개 이상/평균 4점 이상,
  가격·영수증 불만 신호 없음이면 목표 호가를 최대 5% 올린다.
- 목표는 초기값의 85~115%와 기존 하한가 안에 제한된다. 실제 첫 호가는 목표의 ±5%
  범위 안에서 모델이 선택한다. 협상 중에는 하한가까지 양보할 수 있다.
- 속도 불만과 경쟁 가게의 빠른 거래 주장이 함께 있으면 신속한 합의를 지시하고,
  설명 부족이 반복되면 명확한 설명을 지시한다. 상품 설명 자체를 자동 재작성하지 않는다.
- 일반 오류·취소·협상 횟수 제한은 가격 때문에 거절했다고 계산하지 않는다.
- 라운드 변경, 시장 카운터 초기화, 1시간 초과 수집 공백이면 비교 기준을 새로 시작한다.

판매가 자동으로 개선되거나 상위권이 된다는 보장은 없다. 가격을 바꾼 이유와
이후 결과를 보고 임계값·초기 호가를 직접 실험해야 한다. 모델이 툴을 골라 호출하는
구조가 아니라, 결정론적 수집기가 요약을 준비하는 구조이다.

호출하며 잘못된 출력은 한 번 재시도한다. 모든 실제 모델 시도의 로그를 보존한다.
위 제한은 추가 기능/컨텍스트의 제한이며 기존 A2A TaskStore 전체의 메모리 상한은 아니다.

## 로그와 결과 해석

- `logs/strategy-decisions.jsonl`: 관찰한 공개 정보, 리뷰 원문 일부, 목표 호가·판단 이유.
- `logs/seller-events.jsonl`: 영수증 발급·거절·오류·취소. `receipt_issued`는 정산이 아니다.
- `logs/feedback-errors.jsonl`: 조회/저장 실패. 오래된 캐시는 만료되면 사용하지 않는다.
- 키트의 `[acp] settled`와 Round 3 ledger로 실제 정산을 별도 확인한다.
- 공개 판매 증가량은 전체 품목 합계라 특정 품목 가격의 인과 효과를 입증하지 못한다.
  리뷰 속 소재/품질 주장은 검증된 품질로 계산하지 않는다.

기존 로그를 편집하거나 가짜 실적을 만들지 않는다. 실패한 테스트 로그도 보존한다.

## 이전 서버 적용 준비 (Round 2 전용, 사용 중단)

다음 내용은 이전 후보 설정 방식의 기록이다. Round 3에는 사용하지 않는다.
당시 서버 서비스 설정은 기존 week-07 버전이었다. 이 코드를 서버의 같은
`repo/submissions/26510124/week-08/`에 전달한 뒤 아래 명령으로 후보 설정을 만든다.
캐시·개인키·로컬 가상환경은 전달하지 않고, 서버에서 관찰을 새로 시작한다.

```bash
cd ~/agent-market-week07/repo
submissions/26510124/week-07/.venv/bin/python submissions/26510124/week-08/run_checks.py
submissions/26510124/week-07/.venv/bin/python submissions/26510124/week-08/collect_feedback.py --once
submissions/26510124/week-07/.venv/bin/python submissions/26510124/week-08/prepare_activation.py
```

`prepare_activation.py`는 `.market/agent-with-adaptive-seller.json`과 diff만 만든다.
기존 buyer/market_buyer 명령을 보존하고 seller만 새 파일로 연결한다.
기존 week-07 키를 **경로로 참조**하므로 키를 복사하거나 재생성할 필요가 없다.
키트는 기존 week-07 디렉터리에서 실행하므로 구매자의 기억도 그대로 이어진다.

후보 설정과 실제 모델 호출 검증을 마친 뒤 적용할 때는, 기존 `agent.json`을
고유한 이름으로 백업하고 후보로 교체한 후 `week07-market.service`를 재시작한다.
`deploy/week08-feedback.service`를 사용자 systemd에 설치해 별도 수집기를 켠다.
수집기는 인증 정보가 필요 없다. 복구는 백업한 `agent.json`을 되돌리고 기존 서비스를
재시작하면 된다. 별도의 동일 닉네임 키트를 중복 실행하지 않는다.

이 문서는 구현 설명이다. 실제 Round 3 실적과 학생의 실험 해석을 대신하는
제출용 REPORT는 작성하지 않았다.
