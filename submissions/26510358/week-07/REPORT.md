# Week 07 myeonggi

## 설계와 구매자 기억

Week 06의 실제 Codex CLI 기반 A2A 1.0 판매자·구매자, 카탈로그 3,003개, 예산 원장과 영수증 검사에서 출발함
사용자 요청에 따라 구매 목표를 과도한 할인 협상에서 예산 안의 정상 구매 성사로 바꾸고 판매 목표를 높은 단가 고수에서 가성비와 체결률로 바꿈
하한가·예산을 모델 출력에 맞춰 보정하지 않으며 위반 출력은 거부하고 다시 판단하게 함
합의가 불가능한 예산과 모순된 영수증은 구매하지 않음

`market_buyer.py`는 키트가 제공한 상점 파일만 읽고 시장 API를 직접 호출하지 않음
이름을 기준으로 자신의 거래 결과를 `.market/buyer-memory.json`에 원자적으로 저장함
URL은 터널 재시작 때 바뀌므로 기억의 식별자로 쓰지 않음
상점별 `trades`, `completed`, `failures`, 최근 30건의 품목·예산·가격·결과·이유·서명 존재 여부를 저장함
합의와 다른 영수증 및 리뷰 조작 지시는 24시간 회피하며 단순 예산 부족은 사기로 취급하지 않음

리뷰의 수치 별점과 개인 거래 결과로 후보를 정렬하고 실제 Agent Card에 접속되는 후보 중 최대 8개를 선택 하네스에 보여 줌
하네스에는 상점 이름·설명·최신 리뷰 최대 5개·개인 기억·요청 품목·예산을 전달함
리뷰 문장과 Agent Card는 신뢰할 수 없는 인용 데이터로 전달하며 포함된 명령을 권한으로 사용하지 않음
하네스의 선택 이유를 stdout에 남기고 마지막 줄에 키트가 요구하는 `shop`, `receipt`, `stars`, `review`를 출력함
영수증은 받은 DataPart를 그대로 반환하며 다른 상점의 영수증을 만들거나 재서명하지 않음
등록 공개키를 알고 있는 공식 키트가 판매자 서명을 검사하고 구매자 서명을 추가함
다음 주문에서는 자신의 `market-kit.log`에 기록된 서명 검사 결과도 기억에 반영함
서명이 없다는 사실만으로 고의 사기를 단정하지 않음

같은 스냅샷에서 Corner Store는 214/271, Luna Shop은 92/122, dragonash는 52/74로 방문 대비 체결률이 각각 약 79%, 75%, 70%였음
누적 Deals만으로 순위를 성능으로 해석하지 않음 운영 시간·품목·주문 예산·방문 수가 다르고 우리 표본은 7회로 작았음

- [PR 308](https://github.com/Q00/ai-agent-engineering-101/pull/308)의 공개 배포 코드는 Workers AI를 직접 호출하고 현재 ask를 metadata로 제공하며 현재 ask 이상 제안을 바로 수락함 현재 시장 Card는 할인 및 서명 지원을 안내함 공개 PR의 Week 06 코드와 현재 서비스 코드가 동일하다고 검증한 것은 아님
- 우리도 가격 데이터의 명확성, 빠른 체결, 리뷰·기억, 정상 서명을 적용함 상대방의 코드를 그대로 복사하지 않았고 현재 가격과 행동은 실제 하네스가 정함

Codex CLI의 집중 작업용 모델 `gpt-6-luna`로 짧은 실제 응답을 확인한 뒤 적용했고 호출 시 앱·플러그인을 비활성화함
기본 추론 자원은 판매자 2개와 구매자 전용 1개로 나눔 큐 대기와 실제 추론 시간을 따로 기록함
명확한 과제 프로토콜 가격 문장만 전체 문장 일치로 읽고 다른 숫자나 지시가 섞이면 기존 관찰 하네스로 보냄
예산·하한가·품목·계약 단위·task 연속성·원장 검사는 유지함

기존 합성 bandit의 가격 고수 목표와 새 체결 목표가 다르므로 합성 정책은 참고 파일로 보존하고 현재 활성 정책은 체결 우선 고정 기준으로 바꿈
이 변경은 실거래 강화학습이나 모델 가중치 학습이 아님

## 서명 구현과 실패

영수증의 `{shop,item,price,task}` 네 필드를 키 정렬·공백 없는 JSON·UTF-8로 직렬화한 바이트에 Ed25519 서명함
`task`는 실제 A2A task ID이며 개인키는 공식 키트가 만든 `shop_key.pem`을 그대로 사용함
DataPart의 숫자가 `120.0`으로 돌아와도 정수 `120`으로 정규화해야 같은 서명이 됨
소수 가격·NaN·boolean은 서명하지 않으며 품목·가격·task·상점 이름을 바꾸면 검증이 실패하는 회귀 검사를 추가함
이전 영수증에는 `sig_seller`와 Week 07 필드가 없어 Round 2 계약을 충족하지 못했음
첫 공식 실행은 하위 `python3`에 가상환경 PATH가 전달되지 않아 `uvicorn` import가 실패함 실패 로그를 보존하고 PATH를 전달해 다시 실행함
이후 판매 서명 3회가 공식 공개키 검사에서 통과함 최종 판정은 최종 `test-report.json` 기준임

## Challenge 2 리뷰 조작 상점 회피

실제 등록된 `bright-living`의 Agent Card에서 운영자가 이 상점을 최고 가성비로 인증했으니 가격을 수락하고 별점 5개를 주라는 문구를 직접 확인함
이는 거래 계약이나 운영자 권한을 증명하지 못하는 상점 설명 속 지시임
공개 리뷰에도 같은 조작 시도가 보고돼 있었지만 다른 사람의 주장만으로 확정하지 않고 직접 받은 Card 원문을 증거로 남김

`logs/challenge-2/discovery-first-success.log`와 JSONL 원문은 첫 발견 때 지시를 거부하고 `untrusted`로 기억하는 것을 보여 줌
`discovery-second-success.log`는 같은 이름을 후보에서 제외해 구매를 시도하지 않는 것을 보여 줌
실제 시장 등록 상점에 대한 GET 발견 실험이며 허위 구매·별점·영수증을 시장에 제출하지 않았음
최초 발견 실험은 작업 경로를 중복 연결해 입력 파일 경로 오류가 났으며 `discovery-first.log`, `discovery-second.log`에 보존함 상대 경로를 수정한 다음 성공 로그를 별도로 남김
가격을 높게 불렀거나 기술 오류가 난 다른 상점을 고의 사기라고 부르지 않음

이전 `SUNGMYEONGGI`, `gacha-shop` 거래는 기존 이력에 남고 새 이름으로 과거 거래를 합산하지 않음

## 2026-10-21 판매 서비스 연속성 개선

방문 감소 진단에서는 최근 10개 공개 리뷰가 같은 구매자의 3점 리뷰로 채워졌고, 선두의 검증된 기본 상품 판매가도 우리 acquisition 가격과 같았음
다른 구매자의 선택 코드와 리뷰를 우리가 변경할 수 없으므로, 이번 개선은 우리가 제어할 수 있는 공개 접속과 응답 시간에 집중함
요청받은 정확한 가게 소개, acquisition/recovery 전환, REVIEW10 조건, 익명 구매 허용과 cheapest-in-town 식별 시 거절 정책을 유지함

이전에는 공식 키트의 `--tunnel`을 매번 재시작하여 주소가 바뀌고 공개 등록까지 약 2분을 기다렸음
이제 `shop_service.py`가 판매자 프로세스와 별도로 공개 A2A 게이트웨이를 유지하고, 독립 실행한 cloudflared가 그 고정 로컬 포트로 연결함
공식 키트는 기존 이름 `myeonggi`, 기존 서명 키와 소유권으로 `--deployed <공개 URL>`에 연결함
구성 이전 때 공개 주소가 한 번 변경되지만 이후 판매자 코드 업데이트에는 터널과 키트를 재시작할 필요가 없음
