## 목표

중간평가 순위 = 가게 ALL + buyer ALL (각 지표 백분위).

- 가게 ALL = 0.5 순이익 + 0.3 매출 + 0.2 별점
- buyer ALL = 0.5 잉여 + 0.3 게시판 표 + 0.1 거래 수 + 0.1 buyer로 쓴 글 수 (숨겨진 글 제외, 시장 `/agent.md` 2026-11-03 확인)

## 구조

```
                 공개 시장 (ledger, /api/shops, forum)        키트 v4 (.market/*.json, 훅 실행)
                              │                                       │
                              ▼                                       ▼
   ┌──────────────────────── r3lib/memory.py (SQLite) ────────────────────────┐
   │ 1층 공개 사실: settles, breaks, 가게별 재고                               │
   │ 2층 내 기록: purchases(결제·고장 연결), negotiations                       │
   │ 3층 게시판: forum posts + LLM 분류 신호(약한 증거)                        │
   │ 뷰: category_demand · price_ratio · break_rate · shop_reputation          │
   └───────┬──────────────┬──────────────┬──────────────┬─────────────────────┘
           ▼              ▼              ▼              ▼
     restock_r3     shop_r3 (A2A)   buyer_r3        forum_r3 (10분마다)
     수요×몫×12h    시장가 기반 호가  기대 잉여×신뢰도  분류·투표·리포트
     + 탐색 예산    정직 등급·보증   accept 정책      (문장만 LLM)
           │              │              │              │
           └──────── r3lib/pricing.py: 돈에 관한 결정은 전부 결정적 함수 ────────┘
                         r3lib/llm.py: 말에 관한 일만 (실패 시 규칙으로 대체)
```

키트 기본형과 다른 점:

- 기본형은 무작위 매입, 원가 하한, 품질·보증 없음, LLM이 가격을 정함.
- 이 구조는 하나의 메모리가 가게, buyer, 게시판을 모두 먹이고, 돈은 코드가, 말은 LLM이 맡음.

## Week 09 반영: 결정 경로 두 갈래

week-09 강의의 주제는 pro-activeness임(Wooldridge & Jennings 1995). 먼저 매입하고 먼저 말하는 에이전트임.
먼저 말할지는 Horvitz(1999)의 임계값으로 정함.
그래서 판단을 두 경로로 나눔.

| 결정 | 경로 | 이유 |
|---|---|---|
| 호가, 하한, 역제안, 보증 | 규칙 `r3lib/pricing.py` | 숫자로 정해지는 결정임. LLM 호출이 없어 마이크로초 단위로 끝나고 테스트 가능함 |
| buyer 후보 점수, 제안가, 결제 허용 조건 | 규칙 `buyer_r3.py`, `pricing.py` | 300초 제한 안에서 끝나야 하며 돈이 걸림 |
| 매입 수량(60초 훅) | 규칙 `restock_r3.plan` | 공급 창(20분마다 3분) 안에 바로 답해야 함 |
| 매입 계획 검토 | ReAct `restock_review_r3.py` (30분마다, 백그라운드) | 판매율, 유통기한, 보관 일수, 게시판 수요를 엮어 해석해야 함. 결과는 카테고리별 배율로만 반영되며 0~1.5로 제한하고 2시간 뒤 만료됨 |
| 게시판 선제 발화 | ReAct + Horvitz 게이트 `forum_r3.py`, `r3lib/initiative.py` | 무엇을 쓸지는 추론이 필요함. 올릴지는 코드가 p ≥ p*로 결정함 |

ReAct 루프(`r3lib/react.py`)의 동작:

- Thought → Action(읽기 전용 툴) → Observation을 최대 6단계, 240초 안에서 반복함.
- 각 단계는 Codex CLI 호출 한 번이며, 지난 기록은 DATA로 넘겨 외부 문장을 지시로 읽지 않게 함.
- ReAct는 제안만 함. 실제 적용 전에 코드가 검증함. 게시글은 ledger seq 실재 여부와 길이, 매입 배율은 카테고리 실재 여부와 범위를 확인함.
- 모든 단계는 `logs/r3/react.jsonl`에 기록함.

Horvitz 게이트: p* = C / (B + C), B = 1, C = 0.5 + 2·(내 글의 비추천 비율, 사전값 1/4) + 0.25·(최근 6시간 내 글 수).
처음에는 p* = 0.5임. 비추천을 받거나 글을 자주 올릴수록 문턱이 올라감(상한 0.9).
새 정산이나 새 글이 없으면 LLM을 부르지 않음. 결정 기록은 `logs/r3/initiative.jsonl`에 남김.
