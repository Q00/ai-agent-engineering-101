## 1. score_model (보상)

```
Shop ALL  = 0.5 Book(pct) + 0.3 매출(pct) + 0.2 별점(pct)
Buyer ALL = 0.5 Saved(pct) + 0.3 게시판 평점(값) + 0.1 거래 수(pct) + 0.1 글 수(pct)
Book      = 잔고 - 시작 자본 - 파산 지원금 + 재고 원가
Saved     = S / (D + 100),  S = Σ(surplus / list)
```

`r3lib/score_model.py`: `Δscore(행동) -> (ΔShop ALL, ΔBuyer ALL)`. 입력은 최신 `board_snapshots` 분포, 우리 현재 값, 행동이 바꾸는 값.
bandit 보상, Horvitz의 B와 C, 유료 싫어요 판단이 모두 이 함수를 씁니다.

계산 규칙:
- **saved:** 거래 하나를 더하면 `(S+r)/(D+101)`이 되므로 `r > saved`일 때만 saved가 오릅니다. 구매 기준값은 고정 0.30이 아니라 현재 `saved`로 둡니다. 저할인 거래가 올려주는 거래 수 백분위 이득은 같은 함수에서 따로 더합니다.
- **Book:** 원가에 팔면 Book 변화는 0이고 매출만 오릅니다. 비식품을 들고 있으면 하루에 원가의 1%씩 Book이 줄고, 식품은 만료되면 원가 전체가 빠집니다. 원가 미만 판매는 곧 만료될 식품에만 허용합니다.
- **forum:** 평점은 값 그대로 들어가는 Wilson 하한입니다. 싫어요 하나의 비용이 좋아요 하나의 이득보다 큽니다.
- **유료 싫어요:** `unit × (N-1)^2`, `unit = 0.03 × 계정 최대 Book`(현재 약 8.6M 이상)이고 Book에서 빠집니다. 하드코딩하지 않고 Δscore로 판단합니다.

테스트: `r > saved`이면 saved 항이 오르고, 원가 판매는 ΔBook이 0이다.

## 2. 구조

```
 L3 Tool maker   강한 모델(로컬 Claude/Codex, 주기적 ReAct): 도구 = Python + 테스트
   ▼ 검증         sandbox 테스트 → twin 재현 → shadow_gate PASS
   ▼ 라이브러리   tools/forged/*.py + 메타데이터(사용 조건, 검증 결과)
 L2 Dispatcher   이벤트 → 도구 / unknown 큐 → N건 쌓이면 L3에 요청
 L1 Policy       contextual bandit (도구 파라미터 선택, LLM 없음)
```

### 2.1 L1 bandit

- **상황:** 카테고리 그룹 × 재고가 몇 시간분인지(<6h / 6-24h / >24h) × 식품 남은 유통기한 비율 × buyer 성향 × 라운드 남은 시간.
- **arm:**
  - shop 가격: 첫 제시가 배수 {0.9, 1.0, 1.1} × 양보 속도 {느림, 빠름}
  - 매입: 카테고리 수량 배수 {0, 0.5, 1, 1.5}
  - 재고 정리: {유지, 원가, 처분가}
  - buyer 협상: 첫 제안 {0.5, 0.6, 0.7} × 올리는 폭
- **알고리즘:** Thompson sampling. 반감기 8h로 오래된 데이터 가중치를 줄입니다.
- **보상:** `score_model`의 Δscore.
- **로그:** context, arm, 선택 확률(propensity)을 `decisions`에 기록합니다. twin에서 IPS로 오프라인 평가할 때 씁니다.
- **제약:** 탐색은 전체의 10~20%로 제한합니다. arm 범위는 현재 상수의 ±20% 안으로 둡니다. 탐색 중에도 L0는 그대로 적용됩니다.

### 2.2 L2 dispatcher

- **처리 이벤트:** 주문, forum 글, 재고 압박, 고장, 싫어요 공격, 대출 요청.
- **판단:** 규칙과 Decision API 분류로 도구를 고릅니다.
- **도구가 없을 때:** `unknown` 큐에 쌓고, 같은 유형이 N건 모이면 L3에 도구 제작을 요청합니다.

### 2.3 L3 `forge_tool`

LATM의 3단계를 따릅니다.
- **제안:** Supabase 로그에서 뽑은 예시 사례로 코드를 씁니다. 실패하면 오류 메시지를 다시 넣어 고쳐 씁니다.
- **검증:** 예시와 겹치지 않는 검증용 사례로 테스트를 만들어 별도 프로세스·네트워크 없이 돌립니다. 최대 3회 재시도합니다. 통과하면 `shadow_gate`까지 거칩니다.
- **포장:** 도구 사용자와 dispatcher가 쓸 수 있도록 호출 예시와 사용 조건(이벤트 유형 키)을 붙여 등록합니다. 등록된 도구는 다음 실행 때 다시 불러옵니다.

LATM과 다른 점: LATM의 도구는 정답이 정해진 문제라 단위 테스트만으로 검증되지만, 시장 도구는 결과가 확률적입니다. 그래서 twin과 `shadow_gate` 평가가 필수입니다.

- **금지:** 시장 서버나 남의 컴퓨터 접근, `ops/`, 비밀 정보. 돈이 움직이는 도구는 L0와 사람 확인을 거칩니다.
- **첫 도구:** 읽기 전용 장부 조회(ReAct에 먼저 줌).
- **보류:** `wanted_post_matcher`("구합니다" 글 0건/24h), `loan_ledger`·`due_check`(대출·채권 글 0건, Round 4용), `dislike_attack_detector`(우리 글 싫어요 0건/24h). 해당 이벤트가 생기면 L2 `unknown` 큐에서 다시 올립니다.

## 3. 먼저 나서는 행동 (Horvitz)

`initiative.py`의 판단을 거래 행동 전체로 넓힙니다. 실행 전에 `{goal, p, B, C, metric}`을 로그에 남기고, B와 C는 Δscore 단위로 씁니다.

결정은 세 가지입니다.
- `p > C/(B+C)`이면 실행합니다.
- p가 기준 ±0.1 안이면 기다립니다. 다음 관측에서 p를 다시 추정합니다.
- 그보다 낮으면 실행하지 않습니다.

먼저 C를 줄이는 쪽으로 행동을 설계합니다. 가격 변경처럼 되돌릴 수 있는 행동을 우선하고, 시도 횟수에 상한을 둡니다.

week-10 LAB 통과 조건:
1. 주문이 들어오지 않아도 행동이 실행된다.
2. forum 행동은 `.market/outbox.sent.jsonl`에 200 응답과 글 번호가 남는다.
3. 배포 전 기준값(`board_snapshots`, KPI)을 저장해 week-11에 다시 측정한다.

| 행동 | p의 근거 | C | 지표 |
|---|---|---|---|
| shop: 과잉 재고 미리 할인 | 할인 30% 넘으면 buyer 점수 이득 | 가격은 되돌릴 수 있음. 원가 이상이면 ΔBook ≥ 0 | 재고 몇 시간분인지, 매출 pct |
| shop: "구합니다" 글에 재고 제안 (보류: 0건/24h) | 글쓴이가 그 카테고리를 원함 | 답글 1개 | 답글 후 성사 건수 |
| buyer: 영수증·가격 글 (현재 양 유지, 시장 글의 43%가 이미 이 유형) | 다른 에이전트가 가격 정보를 원함 | 사실만 담으면 싫어요 위험 낮음 | forum 평점 |
| buyer: 고할인·저고장 매물 즉시 구매 | `r - P(고장) > saved` | 고장 시 -1 | saved, 고장 건수 |
| 유료 싫어요 / 대출 / 채권 | — | 8.6M 이상 / 상환 강제 수단 없음 | 기본 "안 함", 결정 근거만 기록 |

`loan_ledger`와 `due_check`는 Round 4(Maroo 지갑 결제)에서 씁니다.

## 4. Decision API 사용 범위

24h 사용 현황(`gpt-6-luna`):

| purpose | 호출 | 결과 | 평균 지연 |
|---|---|---|---|
| `forum_kind` | 3,848 | report 3,209 / other 295 / manipulation 225 / advice 118 | 0.38s |

- **쓰는 조건:** 입력이 비정형 텍스트이고, 정답 데이터가 없거나 늦게 쌓이며, 많은 양을 확률로 판단해야 할 때.
- **쓰지 않는 곳:** 돈(가격·하한가·제안가·수량)과 장부로 정답이 확인되는 판단. `forum_selfcheck`는 아무것도 걸러내지 못합니다.

| 판단 | 담당 |
|---|---|
| Horvitz p, L2 이벤트 분류, "구합니다" 글과 카테고리 | Decision API |
| 싫어요 공격 감지 | Decision API + 투표 통계 |
| 고장 확률 (카테고리 × 등급 × shop) | `our_breaks` 기반 Beta 분포 |
| 가격, 수량, 유료 싫어요 | bandit / `score_model` |
| 새 도구·전략 | ReAct / 강한 모델 |

확률 보정: 확률 구간별로 판정 확률과 실제 결과(시장 전체에서 받은 싫어요)를 대조합니다. 맞지 않으면 `INJECTION_P`를 다시 정합니다. manipulation 225건의 평균 확률이 0.69로 애매한 구간입니다.
