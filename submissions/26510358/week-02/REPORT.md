## 1. 변형 정의

같은 원본 `app.log`에서 ERROR가 가장 많은 시간을 답하게 했다. 두 하네스는 같은 모델과
`tools_shared.py`의 도구를 사용한다. `TASK.md`에 미리 정한 `14:00`이 최종 답변에 포함되면
성공이다. 두 하네스 본문은 starter 그대로이며, 공통 API 설정·환경 파일 접근 제한·준비
검사만 보완했다.

모듈 구성과 두 하네스의 제어 흐름은 [Mermaid 구조도](ARCHITECTURE.md)에 정리했다.

| 설계 요소 | ReAct | Plan-then-Execute |
|---|---|---|
| 컨텍스트 관리 | 한 대화에 도구 결과를 누적하고 매번 다음 행동 결정 | 계획용·실행용 대화 분리; 실행 대화에는 문제·계획·단계 결과 누적 |
| 도구 단위 | `read_file`, `count_pattern` | 같은 도구·스키마 사용; 최초 계획 생성에서는 도구 비활성화 |
| 종료 조건 | 도구 호출 없는 응답 또는 `max_steps=8` | 계획 단계 실행 뒤 별도 최종 답변 요청; 단계별 `max_tool_rounds=3` |
| 오류 복구 | 도구 오류를 Observation으로 전달 | 같은 도구 오류 처리에 `OFF_PLAN` 재계획 최대 1회 추가 |

## 3. 해석

실행 전에는 Plan-then-Execute가 계획하고 반복하기 때문에 모델을 더 많이 호출할 것으로
예상했고, 실제로 ReAct는 매 실행 2회, Plan-then-Execute는 6회 호출했다.
두 방식 모두 최종 정답 기준 3/3 성공했지만, 평균 토큰은 각각 1812.3과 7341.0으로
Plan-then-Execute가 약 4.05배를 사용했다.
[ReAct 로그](logs/react-01.txt)에서는 파일 읽기 요청 후 다음 호출에서 답하고 종료한 반면,
[Plan-then-Execute 로그](logs/plan_exec-04.txt)에서는 계획 생성 후 3개 단계를 수행하고,
3단계에서 이미 답을 출력했어도 별도 최종 답변 호출을 진행했다.
6회 모두 `read_file`은 1회, `count_pattern`은 0회였고 계획 실행의 재계획도 모두 0회였다.
따라서 이번 호출 차이는 계획 생성과 단계별 실행, 특히 계획 단계가 끝난 뒤에도 최종 답변을
다시 요청하는 종료 조건에서 발생했다고 해석한다. 추가 호출과 계획·단계 응답을 누적하는
대화 구조는 토큰 증가를 설명하지만, 각 요소의 기여도를 분리해서 측정한 것은 아니다.
이 짧은 로그 분석 문제에서는 같은 최종 정답 성공률을 유지하면서 호출과 토큰을 적게 쓴
ReAct가 더 효율적이었다고 판단한다. 다만 [실행 5](logs/plan_exec-05.txt)는 14시 ERROR를
실제 6개 대신 7개로 중간 집계했으므로, 최종 답변에 `14:00`이 포함되었다는 성공 판정이
중간 계산의 정확성까지 보장하지는 않는다. 한 입력에서 각 3회, ReAct를 먼저 실행한 결과이므로
복잡하거나 다른 태스크에서도 같은 우열이 나타난다고 일반화할 수는 없다.

작성 과정: 실행 전 예상은 학습자가 기록했으며, 결과 해석은 원본 코드·로그를 근거로
코딩 어시스턴트의 도움을 받아 정리했다.
