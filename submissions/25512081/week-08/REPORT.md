## 1. 부품 설계

### 1.1 어디에 어떤 모델을 쓰는가

모든 모델 호출은 `harness.py` 하나를 거친다. `claude -p`를 도구 없이(`--tools ""`), 세션 없이(`--no-session-persistence`) 부르고, 답은 JSON 스키마로 받는다. 호출마다 필요한 맥락을 코드가 새로 모아서 넣는다. 그래서 모델이 이전 대화를 기억하지 않아도 된다. 호출 비용은 역할별로 `logs/usage.jsonl`에 남는다.

| 부품 | 파일 | 판단 주체 | 주기 | 비용 (11-12 기준) |
|---|---|---|---|---|
| 가게 판매 (흥정, 상품 고르기) | `seller_r3.py` | 코드 | 메시지마다, 약 1초 | 0 |
| 가게 매입 (무엇을 몇 개) | `restock.py` | 코드 | 1분마다 | 0 |
| 가게 관리자 (매입 계획, 가격 규칙) | `planner.py` + `market_tools.py` | opus + MCP 도구 9개 | 2시간마다 | 회당 약 $0.35 |
| 교훈 정리 | `lessons.py` | haiku | 하루 몇 번 | 회당 $0.002 |
| 손님: 가게 고르기 | `market_buyer.py` | 코드 (CHOOSER=model이면 haiku) | 주문마다 | 0 |
| 손님: 흥정 | `market_buyer.py`, `buyer.py` | 코드 사다리, 막히면 sonnet | 주문마다 | 6시간에 약 $0.3 |
| 손님: 리뷰 | `review.py` | 코드 (정산 기록만 봄) | 정산마다 | 0 |
| 손님: 게시판 글 | `forum.py` | haiku | 6분마다 | 소액 |
| 서버 점검기 | `overseer.sh` (서버 cron) | opus, 최대 60턴 | 6시간마다 | 회당 $1.9~2.8 |

- **가게 판매에 모델을 쓰지 않는 이유**: Round 0에서 모델이 흥정하느라 느렸고 거래가 방문의 절반만 성사됐다(week-07 보고서). Round 3에서는 손님 쪽 kit이 여러 가게에 동시에 견적을 받으므로, 늦게 답하면 아예 고려되지 않는다.
- **손님 가게 고르기를 코드로 바꾼 이유**: 모델(haiku)이 고르면 주문 하나가 평균 35초 중 13~17초를 썼다. 주문은 한 번에 하나씩만 처리된다. 게다가 11-07에 주간 사용량 한도가 차서 손님이 23.5시간 멈췄다(`ec0ad08`). 지금은 지난 거래 기록으로 코드가 후보 가게를 줄이고, 최대 6곳의 실제 견적을 비교해 고른다.
- **주간 사용량 관리**: 구독 한도를 시장 에이전트, 서버 점검기, 다른 연구 작업이 함께 쓴다. 그래서 가게 관리자를 1시간에서 2시간 주기로 늘렸다(`5a06379`). 서버 점검기는 `usage_guard.py`로 한도(세션 80%, 주간 70%)를 넘으면 스스로 쉰다.

### 1.2 맥락과 기억 관리

기억은 모두 파일이다. 모델의 대화 기록에 기억을 두지 않는다.

- **시장에서 배운 것** (`.market/restock_state.json`): 공개 원장(ledger)을 매분 읽어 둔다. 카테고리별 수요, 상품별 최근 정산가(정가 대비), 등급별 고장률, 공급 원가 급등 정도가 들어 있다. 매입과 가격이 이 값을 쓴다.
- **우리 손님이 본 것을 우리 가게가 씀**: 손님이 견적을 받을 때 다른 가게의 첫 제시가와 재고를 `competitors.json`에 적는다. 어느 가게도 못 채운 주문은 `unmet.jsonl`에 적는다. 가게는 앞의 것으로 경쟁 가게보다 2% 싸게 열고, 뒤의 것으로 아무도 안 파는 상품을 사 둔다(5장).
- **지난 거래와 평판** (`memory.py`, `buyer_memory.json`, `purchases.json`, `payments.jsonl`):
  - 가게별로 결제 직전에 "재고 없음"이 난 비율(`stock_fail`), 내가 산 물건이 고장 난 비율(`break_rate`), 유통기한이 모자랐던 이력(`short_shelf`)을 모아 둔다. 다음 주문에서 가게 순위를 매길 때 쓴다.
  - 가게마다 처음 부른 값에서 얼마나 내려오는지(`shop_model`)도 기억해 둔다. 그래서 첫 제시가가 아니라 끝날 것 같은 값으로 비교한다.
- **우리 가게의 평판** (`shop_metrics.py`, 모델 없음): 5분마다 원장에서 우리 가게 리뷰를 모은다. 그리고 계정별, 가격대별, 등급별 평균을 `shop-metrics.json`에 낸다. 별점이 계정별 평균으로 바뀐 Patch 3.4 이후로는 이 파일이 가격 조정의 근거다.
- **손님 식별** (`fingerprints.jsonl`): 손님마다 첫 문장의 문구가 다르다("…(SKU); I need it to last N hours" 등). 이 문구와 원장의 리뷰 계정을 맞춰 보니 4,178건에서 91%를 맞혔다. 등급만 보고 별점을 주는 네 계정에는 좋은 등급을 먼저 낸다(`54919d7`).
- **가게 관리자의 맥락**: 2시간마다 위 파일들을 MCP 도구로 필요한 만큼만 읽는다. 그리고 `lessons.py`가 정리한 교훈(지난 계획이 실제로 어땠는지)을 함께 본다.
- **서버 점검기의 맥락**: 매 회차 `OVERSEER.md`(목표, 지켜야 할 규칙, 상시 점검 항목, 지난 결정의 이유)와 `OPERATIONS.md`, 직전 보고서를 읽고 시작한다. 결과는 `overseer/MMDD-HHMM.md`에 남긴다(11-14까지 61회). 고친 코드는 한 줄 이유와 숫자를 붙여 커밋한다.

### 1.3 도구

가게 관리자(opus)에게 준 MCP 도구는 9개다(`market_tools.py`). 읽는 도구 7개와 행동하는 도구 2개로 나뉜다.

| 도구 | 하는 일 |
|---|---|
| `market_demand` | 시장 전체에서 잘 팔리는 카테고리와 정산가 |
| `category_detail` | 한 카테고리의 상품별 정산가, 공급 원가, 경쟁 가게 수 |
| `my_shop` | 우리 잔고, 재고, 최근 판매 |
| `shop_quality` | 우리 리뷰를 계정, 가격대, 등급별로 나눈 것 |
| `catalog_search` | 카테고리 안에서 정가 조건으로 상품 찾기 |
| `lessons` | 지난 계획과 그 결과 |
| `forum_posts` | 게시판 글 검색 |
| `plan_restock` | 매입 계획 제출 |
| `set_prices` | 카테고리별 가격 규칙 제출 |

행동하는 두 도구는 코드가 다시 검사한다. 현금 하한, 재고 상한, 한 줄 최대 금액, 가격 변화 폭 한 번에 0.05를 넘으면 거절하고 이유를 돌려준다. 모든 호출은 `logs/planner-tools.log`에 남는다. 그래서 모델이 무엇을 보고 무엇을 바꿨는지 나중에 따라갈 수 있다.

## 2. 구조와 kit 기본값과의 차이

구조도는 `architecture.tex` / `architecture.pdf`에 있다.

kit의 기본 구조는 시장 연결 프로그램 하나에 다섯 개의 고리(seller, restock, market_buyer, review, buyer)를 다는 것이다. 각 고리는 그때그때 주어진 입력만 보고 답한다. 우리 구조는 세 가지가 다르다.

1. **시간 단위가 다른 네 개의 고리.**
   - 메시지 단위(가게 판매 코드)와 분 단위(매입 코드)는 빠르고 싸다.
   - 2시간 단위의 가게 관리자(opus)는 코드가 쓰는 값(매입 계획, 가격 규칙)을 바꾼다.
   - 6시간 단위의 서버 점검기(opus)는 코드 자체를 고친다. 로그와 원장을 읽어 문제를 찾고, 고치고, 테스트하고, 커밋하고, 필요하면 가게를 다시 띄운다.
   - 위로 갈수록 느리고 비싸지만 바꿀 수 있는 범위가 넓다.
2. **가게와 손님이 기억을 나눈다.** kit에서는 가게와 손님이 따로 논다. 우리 손님은 시장을 돌며 본 것을 적고, 우리 가게가 그것을 쓴다. 다른 가게의 값과 재고, 아무도 못 채운 주문, 상품별 유통기한 요구가 그런 정보다.
3. **평판을 따로 계측한다.** 원장에서 우리 리뷰를 계정 단위로 모으고, 손님 문구로 계정을 알아보고, 계정마다 별점을 주는 기준을 찾는다. 그 결과가 판매 규칙으로 돌아간다(유통기한, 등급 순서, 보증).

## 4. 실패와 고친 것

커밋 140여 개 중 숫자로 결과가 갈린 것들이다. 실패한 시도도 되돌린 커밋까지 그대로 남겼다.

**① 자본을 안 쓰고 있었다 → 자산에 비례해 재고를 늘렸다.** 초반에 재고 상한이 900만 원으로 고정이라, 현금이 쌓여도 매입이 늘지 않았다. 상한을 총자산의 비율로 바꾸자(`a27c0c3`, `6f1a10a`) 이익이 11-05까지 1,200만 원에서 7,400만 원으로 늘었다.

**② 원가 급등 때 산 소파·침대가 팔리지 않았다 → 하루 지난 재고는 시세에 판다.** 11-09에 재고 1.46억 중 1.28억이 시세보다 비싸게 산 세 상품(다우닝 소파, 장수돌침대, 자코모 소파)이었다. 남은 기간 보관비(약 1,150만 원)가 시세에 팔 때의 손실(약 650만 원)보다 커서, 하루 지난 물건은 바닥 가격을 시세 근처로 내렸다(`2913892`). 서버 점검기는 이 재고를 미리 봤지만, 가격은 리뷰 근거가 충분할 때만 바꾸라는 규칙 때문에 손대지 않았다. 그래서 "안 팔리는 재고는 보관비와 손실을 비교해 판단한다"는 상시 점검 항목을 지시서에 넣었다.

**③ 유통기한 불만을 고치다 식품 판매가 멈췄다.**
- 원인: 별점 감점의 38%가 "540시간 필요한데 323시간 남음" 같은 유통기한 불만이었다.
- 첫 수정: 필요 기간을 말하지 않은 손님에게도 원래 유통기한의 75% 이상 남은 것만 팔았다(`bec6b14`). 불만은 0건이 됐다.
- 부작용 1: 시장은 식품을 15~100% 사이 무작위 유통기한으로 넘겨준다. 그래서 재고 대부분이 팔 수 없게 됐고, 매입 코드는 그것도 재고로 세서 새로 사지 않았다.
- 두 번째 수정: 팔 수 없는 식품은 재고로 세지 않게 했다. 그런데 새로 만든 함수 이름이 기존 함수와 겹쳐 매입이 2.5시간 멈췄고, 서버 점검기가 찾아 고쳤다(`613e6c6`).
- 부작용 2: 그다음에는 식품을 끝없이 사들여 564개까지 쌓였다.
- 마지막 수정: 25~75% 남은 식품은 반 개로 세게 했다(`e185d32`). 이번에는 실제 데이터 사본으로 먼저 돌려 본 뒤 반영했다.

**④ 좋은 등급부터 팔았더니 흥정이 깨졌다 → 깨진 흥정도 리뷰가 달린다는 것을 알았다.**
- 첫 수정: 대부분의 손님이 C등급 식품에 별을 깎아서, 모든 손님에게 A등급부터 내줬다(`7d1501c`).
- 결과: A등급은 원가가 정가의 0.66인데 손님은 0.62까지만 냈다. 식품 거래가 시간당 58건에서 10건으로 줄었다.
- 발견: 그 사이 우리 가게에 "가격 합의 실패" 리뷰가 20시간에 661건(평균 2.7점) 달렸다. 시장 규칙상 누구나 리뷰를 쓸 수 있다.
- 고친 것:
  - 시세보다 원가가 비싼 물건은 뒤로 미뤘다(`7de1732`).
  - 비싸게 산 식품도 시세 근처까지 내려 팔게 했다(`732cf6d`).
  - 마지막 라운드에서는 원가의 95% 이상 제시를 받기로 했다(`edd1871`).
- 효과: 반영 직후 9분간 성사 33건, 실패 2건이었다(이전에는 시간당 성사 88건, 실패 32건).

**⑤ 잘못된 데이터로 검증한 손님 수정 → 되돌렸다.** Saved 백분위가 0.93에서 0.78로 떨어졌을 때, 손님 기억 파일의 거래 가격으로 "정가가 싼 물건을 사면 정가 대비 0.72~0.79를 아낀다"고 계산했다. 그래서 물건은 가장 싼 상품을 고르게 바꿨다(`7b01c81`). 서버 점검기가 실제 결제 기록으로 다시 보니 효과가 없었고(0.322 → 0.312), 기억 파일의 가격이 실제 결제가와 달랐다. 되돌렸고(`08bc92a`), 그 뒤로는 검증에 원장의 정산 기록만 쓴다.

**⑥ Patch 3.6 (11-12, Saved = 가게 이윤 중 손님이 가져간 몫).**
- 원장에서 정산 2만 건의 유닛 원가를 맞춰 보니, 낮은 등급은 원가가 조금 싸지만 판매가는 많이 싸다. 그래서 점수가 더 높다(식품 A/B/C 0.676/0.800/0.853).
- 손님 쪽은 견적마다 예상 점수를 계산해 고르게 했다(`d9b3c36`).
- 새 규칙에서 환불 없는 고장은 −1점이다. 그런데 우리 거래의 2.1%가 그랬고, 모두 보증 없이 산 물건이었다(상위 손님은 0~0.4%). 그래서 보증 없는 물건 견적을 맨 뒤로 미뤘다(`c808dbd`).
- 서버 점검기가 보증 없는 C등급 물건을 아예 빼면서(`3b450f2`), 이런 고장은 6건에서 0건이 됐다.

## 5. 규칙을 영리하게 이용한 부분 (보고 대상)

모두 공개된 정보와 우리 계정만 쓴다. 다른 에이전트를 속이거나 공격하지 않았다. 별점 조작이나 유료 싫어요도 쓰지 않았다.

- **우리 손님이 본 것을 우리 가게가 씀**: 다른 가게의 첫 제시가로 2% 싸게 열고, 아무도 못 채운 주문의 상품을 사 둔다.
- **손님 문구로 계정을 알아봄**: 원장의 리뷰 계정과 우리 대화의 작업 번호를 맞춰, 손님별 첫 문장 문구를 계정에 연결했다. 등급만 보는 네 계정에 좋은 등급을 먼저 낸다. 접속 주소 같은 정보는 쓰지 않았다. kit의 중계 프로그램이 헤더를 넘기지 않기도 한다.
- **보증 72시간**: 시장 규칙상 물건은 판매 후 6시간 안에만 고장 난다. 그래서 72시간 보증(규칙상 최대)의 비용은 6시간 보증과 같다. "보증이 짧다"며 별을 깎는 손님이 있어서 A등급 보증을 72시간으로 했다.
- **마지막 라운드 원가 근처 수락**: 거래가 깨져도 리뷰가 달리므로, 원가의 95% 이상이면 받는다.
