## 1. 부품별 설계

### 1.1 모델 (Model)
처음에는 구매 협상, 판매 문의 해석, 재고관리와 운영 기획에 LLM을 활용하려 했다.  
실제로 판매자에는 모델 응답이 늦으면 정규식으로 전환하는 문의 해석기를, 구매자에는 Codex 호출 실패 시 Gemini API를 사용하는 대체 경로를 구현했다.  
운영 과정에서 게시판 모델 호출의 지연과 사용량 제한을 경험하면서 가격 상한·보증·가용 현금처럼 판단 기준이 명확한 업무는 모델 응답을 기다리지 않고 코드로 처리하는 편이 적합하다고 판단했다.  
최종 Round 3에서는 거래와 입고를 규칙 기반으로 운영했고, 초기 게시판 글 작성에 사용한 LLM도 이후 템플릿으로 대체했다.

- **사용 모델**: `gpt-5.6-sol` (`agent.json`의 `harness`: `codex exec --skip-git-repo-check -m gpt-5.6-sol`, Codex CLI 경유). Round 3 초기에 이 모델을 **게시판 글 작성(`forum_writer.py`)**에 사용했다.
- **판매(Seller)와 구매(Buyer)**: 다수의 에이전트가 동시에 협상을 요청하는 환경에서 빠르게 응답하고, 원가·보관료·등급별 파손 확률·보증 조건을 일관되게 계산하기 위해 가격 산출과 수락 판단을 모두 규칙 기반으로 구현했다. 거래 경로에서는 모델을 호출하지 않는다.
- **게시판(Forum)**: [게시판 작성 기록](logs/model-calls.log) 2,539건 중 모델 호출을 시도한 기록은 342건이다. 그중 **158건**에서 모델이 작성한 문안을 사용했다(11/03 21:07~11/05 08:53, 성공 건의 소요 시간 중앙값 약 36초). 나머지는 **90초 타임아웃 140건**과 **사용량 한도 오류 44건**으로 템플릿을 사용했다. 11월 5일 오전 9시부터는 모델 호출을 끄고 원장 데이터를 조합한 템플릿으로 글을 작성했다.
템플릿으로 전환한 목적은 세 가지였다.
1. 단일 거래 후기에서 시장 분석으로 내용 개선  
2. 근거 없는 주장과 지시문 방지
3. 모델 호출 지연과 서버 부하 감소

초기 모델 글과 폴백 글의 좋아요 중앙값은 모두 6개였다. 모델 글은 평균 싫어요가 더 적었지만, 작성 방식 자체의 효과인지는 검증하지 않았다.
- **설계 회고와 한계**: 이 구조는 자율성·반응성·능동성·사회성을 갖춘 규칙 기반 에이전트로서 빠른 응답과 일관된 손익·파손율 계산에는 강점이 있었지만, 본질적으로는 사람이 규칙을 미리 정의해 둔 고빈도 자동화 프로그램에 가까웠다. 실제로 운영 도중 채점 규칙이 바뀌거나(Patch 3.4/3.6) 마감 전 조기 청산 계획을 수정해야 하는 일이 생겼을 때 에이전트가 스스로 규칙 변화를 추론해 전략을 바꾸지 못하고 사람이 직접 코드를 수정·배포해야 하는 한계가 있었다.

### 1.2 컨텍스트와 메모리 관리 (Context & Memory)
시장 원장을 협상할 때마다 처음부터 읽지 않도록, store.py가 새 거래에서 상품·가격·등급·보증 정보를 추려 공유 상태 허브(state_hub.json)에 저장했다. 구매자는 최근 체결가를 다음 상점 선택에 활용하고, 판매·입고 정책은 판매와 문의 이력을 견적과 매입 판단에 활용한다. 이는 Medallion 아키텍처의 원본·정제·활용 구분을 참고한 설계이나 Bronze·Silver·Gold를 각각 별도 저장소로 구축한 것은 아니다. 아래 표는 처리 단계가 아니라, 보존 기간과 용도가 다른 다섯 가지 메모리 유형을 정리한 것이다.
 
#### Medallion 아키텍처
Databricks 등 데이터 레이크하우스에서 대량의 거래 데이터를 단계별로 정제할 때 쓰이는 데이터 설계 패턴이다.  
대량의 클릭·주문·반품 로그가 쌓이는 환경에서 원본 로그를 매번 처음부터 끝까지 읽으면 응답이 느려지고 서버를 유지하기 어렵다. 반대로 원본은 삭제하고 요약본만 남기면 나중에 버그 발생이나 기준 변경 시 다시 검증할 수 없다.  
따라서 원본은 그대로 두고(Bronze), 깨끗하게 정리한 뒤(Silver), 의사결정에 바로 쓸 요약표(Gold)를 미리 만들어 두는 것이 Medallion 구조의 핵심이다.

- **Bronze (원시 데이터)**: 키트가 생성하는 `.market/` 스냅샷·원장 파일(`payments.jsonl`, `broken.jsonl`, `inventory.json`, `forum.json`)과 시장 공개 원장(`/api/ledger`)의 원시 이벤트
- **Silver/Gold (집계·정규화 허브, `state_hub.json`)**: `store.py`가 원시 데이터를 증분 수집·정규화해 4개 독립 프로세스(`seller`, `restock`, `market_buyer`, `review`)가 즉시 조회할 수 있는 요약 피처(최근 3시간 상품·등급별 체결가, 수요 레이더, 자본·현금 한도, 파손 통계)로 유지

| 메모리 유형 | 저장 위치 | 보존 범위 및 갱신 방식 | 활용 방식 |
| :--- | :--- | :--- | :--- |
| **공유 상태 허브 (Gold)** | `state_hub.json` | 수급 주기마다 시장 공개 원장(`/api/ledger`)과 원시 로그(Bronze)를 증분 수집·정규화해 파일 락으로 갱신. 상품별 최근 3시간 체결가(최대 50건), 자체 판매·파손 통계(최근 8시간) 유지 | 판매 1차 견적 기준가, 구매 시세 비교, 인기 품목 판별 및 파손 환불률 추정 |
| **가게 평판 메모리** | `memory.json` | 가게별 최근 5건 거래 기록과 과거 누적 평점 요약 유지 | 구매 후보 가게 순위 산정, 불량·반복 거절 가게 일시 회피(쿨다운), 방문 다양성 유지 |
| **정산 후 구매 기록** | `state_hub.json`의 `my_purchases` | `review.py`가 정산 후 갱신하며, 최근 구매 내역을 최대 150건 보관 | 최근 구매 이력 유지 및 사후 파손 발생 시 판매 상점 귀속 추적(게시판 시세 브리핑은 `forum_intel` 집계 참조) |
| **판매 작업 메모리** | 판매 서버 메모리 | 진행 중인 협상(90초) 및 영수증 서명 완료 재고(120초) 임시 보관 | 동시 협상 상태 유지 및 같은 재고 단위의 중복 서명 방지 |
| **사후 감사 저널** | `runtime/buyer-outcomes-v1.jsonl` | `store.py`가 원장 수집 후 허브 락 해제 시점에 원장 기반 정산·파손·환불 결과를 순차 기록(256 MiB 상한) | 사후 정산·파손 분석 및 정책 수정 전후 비교 |

### 1.3 툴 (Tools)
제공된 키트(`market_kit.py` v4)는 통신·결제 프로토콜을 맡고 어떻게 장사하고, 무엇을 사고, 무엇을 기억할지 결정하는 전략을 추가하였다.

- **기본 마켓 키트(`market_kit.py`)** : A2A 프록시 및 Cloudflare 터널 연결, ACP 체크아웃, AP2 결제 서명 검증, 시장 정산 요청(/api/settle), .market/ 파일 자동 동기화, 게시판 전송(별도 수급 훅 미등록 시 무작위 재고 매입)

#### 추가한 5가지 툴
- **Buyer 상품 구매 (`market_buyer.py`)**: 주문이 들어오면 허용 품목을 보유한 가게를 평판과 예상 절감률 순으로 정렬해 상대 Shop에 A2A 협상을 직접 요청한다. 상대 가게의 영수증을 받으면 서명 존재 여부, 예산 상한, 시장 시세 기반 가격 상한(거래가 충분히 쌓인 상품은 공산품 정가 67%·식품 66% 이하), 공산품 파손 위험을 반영한 기대 절감률(기본 0 초과, 정산 표본 5건 이상 SKU는 0.25 초과)을 통과한 경우에만 수락한다. 식품은 판매자가 제시한 만료 정보로 잔여시간 부족이 드러나면 협상 단계에서 제외하고, 실제 출고품은 키트가 결제 전에 인증서로 검사한다.
- **Shop 판매·가격·보증 (`seller.py`, `seller_cash_policy.py`)**: 공산품은 등급별 차등 보증(A등급 72시간, B등급 6시간, C등급 0시간)을 적용하고, 보증 환불 위험과 보관료(일 1%)를 반영한 하한 위에서 동일 조건 최근 시장 체결가 중앙값을 참고해 협상한다. 임박 식품은 별도 할인 정책을 적용한 뒤 서명 영수증을 발급한다.
- **Shop 재고 입고·배분 (`restock.py`, `seller_forum.py`)**: 파산선·안전마진·1일 보관비를 반영한 **현금 하한(`cash_floor`) 기반 가용 현금 한도** 내에서, 20분마다 열리는 입고 창에서 최근 문의·품절·시장 정산량으로 상품을 인기 등급별로 분류한 뒤 파손 환불 비용과 보관료를 빼고도 이익이 남는 품목만 골라 입고 계획을 출력하고, 보유 재고의 등급·정가·원장 근거를 담은 Shop 재고 공지글(`seller_forum.py`)을 작성한다.
- **정산 후기·게시판 (`review.py`, `forum_writer.py`)**: 정산이 끝나면 가게 평판 메모리와 구매 기록을 갱신하고, `forum_intel` 집계와 실제 원장 번호 3건 이상이 뒷받침되는 Buyer 카테고리 시세 분석글을 작성한다.
- **가시성 보호 래퍼 (`guarded_market_kit.py`)**: 기본 키트 실행을 감싸 가게 노출 상태를 감시하고 가시성 문제가 생겼을 때 보호 동작을 수행한다.

## 2. 아키텍처 구조와 키트 기본형과의 차이

[architecture.pdf](architecture.pdf)는 C4 Container/Component 관점에서 `mjforge` 전체 시스템을 **상단 관문 → 4개 정책 모듈 → 중앙 공유 허브 ETL → 하단 3종 저장소** 계층으로 정리하고, 외부 시스템(시장 서버·상대 에이전트)과의 경계를 분리하였다.

1. **상단 관문 — 기본 마켓 키트**: 제공 키트(`market_kit.py` v4)가 시장 서버(`/api/settle`, `/api/supply`, `/api/forum`) 통신과 상대 에이전트와의 ACP 결제·정산 및 Shop 측 A2A 프록시를 중계하고(Buyer 측 A2A 협상은 `market_buyer.py`가 상대 Shop에 직접 요청), `guarded_market_kit.py`가 가게 노출 상태를 감시한다.
2. **4-Process 정책 계층**: 실행 시점과 목표 지표가 서로 다른 **Buyer 상품 구매**, **Shop 판매·가격·보증**, **Shop 재고 입고·배분**, **정산 후기·게시판** 으로 분리해, 한쪽의 지연이나 오류가 다른 거래를 멈추지 않도록 격리했다. 
이는 **실제 기업에서** 구매, 기획, 영업, 물류관리, 마케팅 팀을 별도로 운영하는 것과 **유사한 시스템** 을 구축하고자 한 것이다.
3. **중앙 공유 인텔리전스 허브 ETL (Silver, `store.py`)**: 키트가 내려주는 `.market/` 원시 로그(Bronze)와 시장 공개 원장(`GET /api/ledger`)을 증분 수집·정규화(Silver)해 4개 프로세스가 공유하는 집계 허브(Gold)로 적재한다.
4. **하단 3종 영구 저장소**: 모든 데이터를 파일 하나에 몰아넣지 않고, 데이터 수명과 접근 주체에 따라 3개 저장소로 분리했다.
   - **원본 보관 (Bronze, `.market/` · `buyer_outcomes.py`)**: 기본 마켓 키트가 내려받는 결제·파손·재고 원본(`.market/`)과 `store.py`가 원장 수집 후 허브 락 밖에서 기록하는 원장 기반 정산·파손·환불 감사 저널(`buyer_outcomes`)을 보관한다. `payments.jsonl`·`broken.jsonl`과 감사 저널은 덧붙이기(append) 방식으로 누적 보존되고, `inventory.json` 같은 스냅샷 파일은 키트가 최신 상태로 덮어쓴다. `store.py`(Silver)가 원본 로그를 읽어 집계에 활용하고, 장애나 정책 변경 시 원인을 되짚는 블랙박스 역할을 한다.
   - **공유 상태 허브 (Gold, `state_hub.json`)**: `store.py`(Silver)가 원본 로그와 시장 공개 원장(`/api/ledger`)을 정제해 단방향으로 적재하는 공용 요약 테이블이다. 4개 프로세스가 무거운 원본 로그를 매번 풀스캔하지 않고 최근 3시간 시세·수요·파손 통계를 빠르게 공유할 수 있게 한다.
   - **가게 평판 메모리 (`memory.json`)**: `Shop` 측에서는 필요 없는 Buyer 전용 데이터(가게별 최근 5건 거래, 누적 평점, 반복 거절 시 일시 회피용 쿨다운)를 별도 저장소로 분리했다. 공용 허브의 파일 락을 기다리지 않고 `Buyer`가 협상 직후 조회·기록하고 `정산 후기`가 사후 결과를 보강하는 독립 피드백 루프를 이룬다.

### 키트 기본형과의 핵심 차이

| 구분 | 키트 기본형 | mjforge 구현 구조 |
| :--- | :--- | :--- |
| **컨텍스트 공유** | 각 프로세스가 `.market/` 파일만 단발성으로 읽음 | **Bronze(원시 로그·원장) → Silver/Gold(`state_hub.json`)** 계층으로 집계해 4개 프로세스가 공유 |
