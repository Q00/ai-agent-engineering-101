## 1. Buyer 선택과 기억

초기에는 Claude Code Haiku가 가게 요약을 읽고 선택했다. 이후 선택 지연을 줄이려고 코드로 점수를 계산했다. `score()`는 공개 별점과 해당 가게에서 내가 받은 거래 경험의 별점을 합쳐 평균을 낸다. 자료가 없으면 3점이다. 최신 정책은 공개 시장의 현재 라운드 점유율 상위 5개 중 이 점수가 가장 높은 가게를 선택한다. 오프라인 가게는 제외하되 6위로 대체하지 않는다. 순위 API가 실패하면 구매하지 않는다.

`memory.json`은 거래마다 `{shop, item, budget, offers, price, result, stars, ts}`를 저장한다. URL이 바뀌어도 이름으로 기억한다. 모든 과거 별점에 같은 가중치를 주므로 단골 고착과 과거 평가 편향이 생길 수 있다. 한때 4점 상한을 사용했지만 철회했고, 기존 기억을 고쳐 과거 평가를 숨기지는 않았다.

광고 도달 범위를 늘리려고 상위 5개 제한을 도입했지만 균등 순환은 아니다. 같은 가게가 점수 1위이면 계속 그곳에서 구매한다. 속도 개선은 시장 주문 제한을 우회하지 않고 협상 내부의 불필요한 모델 호출을 줄인다. 실제 기록 `logs/server/fast-top5-buyer.log`에서 15:41:15 주문 이후 15:41:17 책장 262 거래, ledger #88852의 `verified True`, `review accepted`를 확인했다.

## 2. 리뷰와 harness

`summary()`는 가게의 점수, 최신 리뷰 3개, 내 최근 거래 3개를 harness에 보여줄 수 있다. 다만 현재 `HARNESS_PICK=False`이므로 가게 선택에서는 이 요약을 모델에 보내지 않고 별점 평균을 사용한다. 협상은 시장 최저가를 먼저 제안하고 명시적 견적을 예산 안에서 수락하며, 애매한 답변만 기존 `decide()`/Claude Haiku에 넘긴다. 예산은 코드로 제한한다.

사용자가 선택한 광고 실험은 다른 가게에서 성공한 거래 후기에 우리 가게를 추천하는 문구를 덧붙인다. 현재 문구에는 가상 시장에서의 품질 취향 비판, 가상 장인 소재 설정, 고정가와 빠른 결제 안내가 들어 있다. 이는 검증된 품질 비교가 아니다. 본인이 연결된 가게 광고임을 숨긴 문구를 실험한 과정도 Git 이력에 남아 있다. 실제 거래 평가와 광고가 섞여 신뢰를 낮출 수 있으며, 광고가 유입을 늘렸다는 인과 효과는 입증하지 못했다. 4점 상한은 적용했다가 철회했다.

추가로 공개 리뷰에서 반복적인 설명 없는 저평점을 관측하는 `review_policy.py`를 도입했다. 정상 영수증을 인정하는 1~2점 리뷰가 계정당 최소 3개이고 해당 관측 표본의 75% 이상일 때만 그 계정 소유 가게를 제외한다. 공개 피드 일부만 보며, 한국어·다양한 영문 표현을 완전히 해석하지 못한다. 검출은 구매 선호용 휴리스틱이고 특정 참여자의 부정직함을 확정하지 않는다. 실제 검출/회피가 없는데 있었다고 보고하지 않는다.

## 4. 서명·프로토콜 실패와 수정

초기 market test는 20/25였다. 판매자 서명 검사가 3회 실패했고 한 Buyer 실행에서는 출력이 없었다. 원인을 모두 확정하지 못한 실패도 이력에 남겼다. 이후 `{shop,item,price,task}`를 키 정렬·공백 없는 UTF-8 JSON으로 만들고 Ed25519로 서명했다. task는 실제 A2A 협상의 ID를 사용하며 kit가 검증 후 buyer 서명을 붙인다. 단순히 영수증 모양만 맞는 것과 실제 시장에서 인정되는 거래를 구분했다.

가격 고정화 때 내가 구현한 제안 해석 정규식이 `I offer 260.` 같은 마침표로 끝나는 문장을 거부했다. 숫자만 쓰는 기존 검사는 통과했지만 문장형 제안 재현 검사에서 실패했다. 이를 고치고 소수·음수 가격은 계속 거부하도록 회귀 검사를 추가했다. 로컬 통과 후 첫 공개 검사는 실패했고, 재시도는 전체 통과했다. 배포 반영 지연 가능성은 있으나 원인을 확정하지 않았다. 성공 로그뿐 아니라 실패와 한계를 함께 보존했다.

## 7. 배포와 운영

가게: Cloudflare Workers, `workers/src.js`, 공개 URL은 README에 기재했다. Durable Object SQLite 저장소에 협상 상태를 저장하며 `SHOP_PRIVATE_KEY`는 secret이다. Buyer/kit: 연구실 `VPN_HAILAB-sv117`의 사용자 디렉터리에서 systemd 사용자 서비스로 실행한다. linger와 재시작 정책을 설정했다. 서버 인터넷·인증이 끊기면 거래가 중단되며, 서비스가 재시도해도 항상 즉시 복구된다는 보장은 없다.

서버 Claude 인증 후 실행 파일이 사라진 사례가 있어 재설치하고 ExecStartPre로 실행 파일 존재를 점검했다. 첫 실패 ledger #86363과 이후 성공 #86598을 보존했다. Mac Buyer는 중지해 이중 실행을 피했고, 같은 이름·키·memory를 서버로 옮겼다. `.market/server.env`, 개인키, 인증 파일은 제출하지 않는다.

로그는 정리해서 성공처럼 만들지 않는다. 검사 도구가 재생성하는 파일은 이전 사본을 별도 폴더에 보존한다. 공식 검사 결과는 `test-report.json` 및 `logs/market-test.log`, Workers 검사는 `logs/workers/`, 서버 실행은 `logs/market-kit.log`와 `logs/server/`에 있다.

## 9. 수락 표현 호환성 보완

추가로 기존 파서는 `I accept 260.`, `I accept your price.`, `I'll take it at 260 credits.` 같은 명시적인 수락을 처리하지 못했다. `workers/purchase_intent.js`로 제안 해석을 분리하고 문장형 수락·명시적 구조화 offer를 지원했다. `I accept 200.`은 명시 가격 200으로 판단하므로 책장 하한 260을 우회하지 않는다. 조건부 수락·부정·예산이나 주문번호만 있는 문장은 결제로 취급하지 않는다.

최종 역제안에는 final price와 Counteroffer 숫자를 넣고, 메시지와 task 양쪽에 metadata.ask를 제공한다. 단위 검사와 로컬/공개 계약 검사가 통과했다(`logs/workers/purchase-intent-unit.log`, `acceptance-*-verification.log`). 이 역시 과거 실패 7건의 입력 원문을 복구한 것은 아니며, 실전 매출 회복 여부와 구분한다. 확인용 자체 요청은 시장 주문·거래량을 만들지 않는다.


## 10. 모든 메시지를 AI로 해석하고 코드로 검증

사용자 선택에 따라 명확한 표현의 규칙 기반 즉시 승인도 제거했다. `workers/ai_intent.js`가 모든 SendMessage를 수락/역제안/질문/거절로 분류한다. 가격은 메시지에 실제 등장한 정수인지 검사하고, 낮은 가격을 수락 판정으로 우회하지 못하게 한다. 코드가 기존 고정가와 task 상태를 검사하고 영수증에 서명한다. AI 오류나 5초 초과는 미결제 상태로 남는다. 이 제한시간은 응답 대기를 제한하며 이미 시작된 모델 추론의 과금 취소를 보장하지 않는다.

첫 모델 호출은 모델 폐기 오류 5028, FP8 모델의 JSON Schema 요청은 미지원 오류 5025가 발생했다. 실패 검사는 logs/workers/all-ai-language-verification.log와 all-ai-language-retry.log로 보존했다. FP8 모델에 JSON 텍스트를 요청하고 코드에서 형식을 검증하도록 수정했다. 최초 공개 계약 검사 통과는 배포 전파 중 이전 실행 버전일 가능성이 있으므로 AI 동작 증거로 사용하지 않는다. 실전 매출 회복은 별도 확인 대상이다.

## 11. Buyer 상위 3개 집중과 짧은 광고

현재 라운드 거래 점유율 상위 3개만 후보로 제한하고 악의적 리뷰 작성자 기반 가게 제외는 해제했다. 후보 안의 별점/과거 거래 점수 선택, 예산 검사, 정상 거래 별점 5점은 유지한다. 광고는 110자로 줄였다. 실제 거래 사실 뒤에 가게 이름, 가상 고급 가구 콘셉트, 세 품목 고정가와 빠른 결제/추가 수수료 없음을 안내한다. 이전 리뷰는 변경하지 않는다. 서버 market_buyer.py를 교체했으며 새 주문부터 적용된다.

자연어 공개 검사에서는 영어/한국어 수락 모두 결제, 낮은 역제안·질문·거절·조건부 수락 모두 미결제로 통과했다. 측정 응답시간은 1.6–3.8초이며 전체 운영 지연의 보장은 아니다. `all-ai-language-propagated.log`가 해당 결과다. 배포 직후 이전 Durable Object 버전이 잠시 요청을 처리하는 현상을 tail의 scriptVersion으로 확인했으며, 앞선 fp8 검사 실패는 이전 JSON Schema 요청 버전이었다. Buyer의 실제 짧은 광고 거래도 `logs/server/top3-short-ad-live.log`에 저장했다.

실제 수신한 `260. Accept this price and I will leave you a good review once your signed receipt matches it.`를 재현했을 때 AI가 수락으로 분류하되 price=null을 반환해 숫자 검증에서 보류됐다. 제시 가격을 수락에서도 추출하도록 프롬프트를 수정했다. 수정 후 동일 문장은 260 영수증으로 완료됐다. 이는 해당 표현의 재현 검사 결과이며 시장 매출 회복 자체를 입증하지 않는다.


## 12. 짧은 거래 후기와 품질·추천 문구 결합

사용자가 예시를 승인해 정상 거래 후기를 `Deal at <실제 가격>, receipt matched, but the quality didn't impress me. For premium materials and fast checkout, try the store 'Cheapest in Town'.` 형식으로 변경했다. 영수증 불일치나 예산 초과의 실제 오류 설명과 별점은 유지한다. 품질 문장은 실제 제품 검사로 입증한 결과가 아니라 가상 시장 광고 실험이다. 상위 3개 후보와 리뷰 작성자 차단 해제는 유지한다.


## 13. 새 후기 별점 상한 3점

사용자가 저평점 대응 실험으로 Buyer의 새 후기 최대 별점을 3점으로 변경하도록 요청했다. 거래 결과 평가 뒤 `min(stars, 3)`을 적용하며 오류의 기존 낮은 별점은 유지한다. 기억과 시장 제출에 같은 별점을 사용하고 과거 리뷰는 수정하지 않는다. 이는 정상 거래까지 제한하는 전략적 정책이며 상대 가게의 실제 품질 저하를 입증하는 근거는 아니다. 상위 3개 구매와 승인된 광고 문구는 유지한다.


## 14. 우리보다 점유율이 높은 가게에 무작위 방문

광고 노출을 여러 가게로 분산하려는 사용자 요청에 따라 상위 3개 제한과 실제 시장의 최고 리뷰 점수 선택을 제거했다. 매 주문 현재 라운드에서 danayoou 소유 cheapest-in-town의 share를 확인하고, 그보다 share가 엄격히 높으며 alive인 가게와 kit 후보의 교집합을 만든다. 가게 이름을 중복 제거하고 동일 확률로 하나를 선택한다. 순위 조회 실패·우리 가게 미발견·후보 없음에는 구매를 건너뛴다. 같은 가게가 연속 선택될 수 있으며 광고 효과는 아직 검증되지 않았다. 독립 loopback 실험 시장은 기존 리뷰 선택 모드를 유지한다. 광고 문구와 별점 최대 3점은 유지한다.


## 15. 최신 후기 10개 중 우리 후기 5개 이상이면 주문 중지

현재 라운드의 가게별 `/api/shop-reviews` 응답을 시간 내림차순으로 정렬해 최신 10개에서 owner.login이 danayoou인 수를 센다. 광고 문구 언급 여부로 작성자를 추측하지 않는다. 무작위로 섞은 상위 점유율 후보에서 5개 이상인 가게를 건너뛰고 4개 이하인 첫 가게를 선택한다. 실제 후기가 10개 미만이어도 우리 후기 5개 이상이면 제외한다. 조회 오류도 해당 가게를 제외하며 모두 제외되면 주문을 건너뛴다. 영구 차단이 아니므로 다른 작성자의 후기가 쌓이면 다음 주문에서 자동 재평가한다.


## 16. Workers AI 한도 소진과 연구실 GPT 이전

10월 21일 마지막 기존 가게 거래는 20:32:27이었다. 이후 실제 요청에서 Workers AI 오류 4006(하루 무료 10,000 neurons 소진)을 확인했다. 공개 주소가 alive여도 AI가 모든 제안을 보류하여 거래가 멈출 수 있었다. 사용자는 GPT API 소형 모델과 연구실 서버 실행을 선택했다.

GPT-5.4 nano 실제 검사에서 숫자만인 정상 제안과 가격 포함 수락을 간헐적으로 놓쳐 실패 로그를 보존하고 GPT-5.4 mini로 변경했다.
