# 포럼 수집 주기와 토큰 비용

## 결정

사용자는 **5분 수집·30분 분석**을 선택했다. 기본 30분 설정으로 독립 기능을 구현한 뒤, 선택을 받은 다음 수집 설정을 300초로 변경했다. 분석·게시 판단은 1,800초를 유지한다.

## 직접 비용

| 수집 간격 | 하루 파일 확인 | 하루 정기 분석 | 추가 LLM 토큰 | 추가 포럼 API 요청 |
|---|---:|---:|---:|---:|
| 1분 | 1,440 | 48 | 0 | 0 |
| **5분** | **288** | **48** | **0** | **0** |
| 10분 | 144 | 48 | 0 | 0 |
| 30분 | 48 | 48 | 0 | 0 |

이는 계획된 주기 기준이며 키트 실행·훅 지연에 따라 실제 횟수는 적을 수 있다. `forum_capture.py`는 로컬 JSON을 읽고 제한된 버퍼를 갱신한다. `forum_monitor.py`·`forum_demand.py`는 문자열·카테고리 규칙을 적용한다. `forum_policy.py`·`forum_engagement.py`는 정산·가격·재고를 템플릿으로 표현한다. 이 경로는 `harness.py`나 모델 API를 호출하지 않는다. 수집 버퍼와 포럼 원문을 buyer·seller 모델 프롬프트에 추가하지 않았다.

추가 API 요청 0은 **수집·분석 경로**에 대한 수치다. 실제로 게시하는 글은 기존 키트의 포럼 POST 요청을 발생시킨다. 기존 buyer·seller 협상은 여전히 LLM을 사용한다.

## 간접 비용과 로컬 자원

포럼 답변으로 새 협상이 유입되거나 매입 품목이 달라지면 기존 협상용 LLM 호출이 늘 수 있다. 이 증가는 수집 자체의 토큰과 구분해야 하며 현재 자료만으로 수량·요금은 확정할 수 없다. 게시문을 인용하는 상대와 대화가 길어져도 협상 입력 토큰이 늘 수 있다. 따라서 전체 운영 토큰이 늘지 않는다는 주장은 하지 않는다.

늘어나는 직접 작업은 CPU·메모리·파일 I/O다. 13:21 측정 원본 스냅샷은 약 165KB였으므로 같은 크기가 유지되면 5분 간격 원본 읽기는 약 47MB/일이다. 버퍼 읽기·쓰기 비용은 별도이며 최대 2,000글·글당 2,000자 및 메타데이터로 제한한다. 토큰 비용을 줄이기 위해 별도 LLM 요약을 도입하지 않는다.

## 현재 게시 속도와 누락 가능성

11월 4일 **13:21:44 KST** 스냅샷 기준이며 모든 구간이 최신 100글에 포함됐다.

| 직전 구간 | 전체 | buyer | shop | 분당 평균 |
|---|---:|---:|---:|---:|
| 1분 | 5 | 4 | 1 | 5.0 |
| 5분 | 26 | 20 | 6 | 5.2 |
| 10분 | 56 | 43 | 13 | 5.6 |

최신 100글은 약 18분치였다. 앞선 13:16:53 측정에서는 각각 6·31·59건이었다. 현재 속도가 유지되면 30분마다 최신 100글만 받는 방식은 중간 글을 놓칠 수 있다. 5분은 약 30건을 모으므로 여유가 있지만, 갑자기 5분에 100건을 넘으면 누락될 수 있다. 주기 단축이 완전 수집을 보장하지는 않는다.

재측정: `python analyze_forum_traffic.py`. 원본 결과는 `logs/forum-traffic/`와 `logs/forum-traffic-analysis.log`에 보존했다. 수집 설정은 `forum_capture.json`, 분석 결과는 `.market/forum-intel.json`에서 확인한다.
