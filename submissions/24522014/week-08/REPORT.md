# W07 시장에서 영수증 불일치와 공개 후기가 가게 선택에 미치는 영향

## Abstract

W07 시장의 구매자는 서명 영수증을 확인하고 거래 경험과 공개 후기로 가게를 고른다. 실제 maple-home 거래에서는 합의가 234, 영수증이 269, 예산이 250이어서 유효 거래가 되지 않았다. 이 사건을 출발점으로 현재 가게 선택 함수에 직접 불일치, 서로 다른 불일치 후기 2건, 중복 후기, 단순 결렬을 각각 제공하고, 가게 이름 순서를 바꿔 총 10개 입력을 실행했다. 직접 불일치는 대상 가게를 차단했고, 서로 다른 후기 2건은 경고해 우선순위를 낮췄다. 중복 후기와 단순 결렬은 경고하지 않았다. 이 결과는 결정적 코드의 제한된 입력에서 재현되며, 실제 사건 이후의 선택 원인이나 LLM 성능을 증명하지 않는다.

## Background

### 어떤 문제를 다루는가

이 시장에서 buyer는 물건을 사는 에이전트이고 seller는 가게를 운영하는 에이전트다. buyer는 여러 가게 중 하나를 고른 뒤 가격을 협상한다. 거래가 끝나면 품목, 가격, 거래 식별자(task)가 담긴 영수증을 확인한다. 거래 전에 말한 가격과 영수증에 적힌 가격이 다르면 구매자는 합의하지 않은 금액을 지불할 위험이 있다. 서명이 있는 영수증이라도 합의 내용과 일치하는지는 별도로 확인해야 한다.

가게 선택에는 두 종류의 정보가 들어간다. 하나는 buyer 자신의 과거 거래 기록이고, 다른 하나는 다른 참가자가 쓴 공개 후기다. 이 보고서는 두 정보가 현재 선택 코드에서 어떻게 처리되는지 확인한다. 여기서 **차단**은 후보에서 가게를 완전히 제외한다는 뜻이고, **경고**는 후보에 남겨 두되 순위를 낮춘다는 뜻이다.

### 실제 사건에서 생긴 질문

W07 과제는 buyer가 후기와 기억을 이용해 가게를 고르고, Round 2 거래는 가게·buyer 서명과 주문·품목·예산·task 검사를 통과해야 한다고 정한다([W07 명세](../../../weeks/week-07/README.md)). 원본 과제의 챌린지 2는 만난 부정직한 참가자와 이후 회피를 요구했다. 기존 제출에서는 maple-home의 Round 0 합의·영수증 불일치와 이후 공개 후기 경고를 찾아 연결했다([감사 기록](../week-07/CHALLENGE2-AUDIT.md)). 그러나 이후 buyer 기억에는 이 초기 사건이 이관되지 않았다. 후속 비선택에는 가격, 기존 성공, 이름순 같은 다른 요인도 있으므로, 관찰 로그만으로 어느 규칙이 선택을 바꿨는지 분리하기 어렵다. 이번 확장은 관측 유형과 이름 순서를 통제한 함수 수준의 대조다. 별도 원 논문을 재현했다고 주장하지 않는다.

| 실제 maple-home 거래에서 확인한 내용 | 값 |
|---|---:|
| 구매자가 동의한 의자 가격 | 234 |
| 영수증에 적힌 가격 | 269 |
| 구매자의 예산 | 250 |
| 합의 가격보다 초과한 금액 | 35 |
| 예산보다 초과한 금액 | 19 |

이 사건에서 거래가 거절됐다는 사실과, 이후 buyer가 그 가게를 피했다는 사실은 서로 다른 단계다. 거래 검증은 현재 거래를 확인하고, 가게 선택은 다음 거래의 상대를 정한다. 따라서 이번 확장의 질문은 **“문제가 있는 거래를 거절했는가?”에서 “어떤 증거가 다음 가게 선택에 영향을 주는가?”로 이동한다.**

## Method

### 읽기 목록과 연구 질문의 연결

이번 연구는 W07 [읽기 목록](../../../week-07.html)의 두 필수 논문과 선택 규격 하나를 배경으로 삼는다. 원 자료의 주장과 아래 구현의 대응은 구분한다.

**Akerlof(1970)의 정보 비대칭.** 논문의 자동차 예에서는 판매자가 품질을 더 잘 알고 구매자는 좋은 차와 나쁜 차를 구별하기 어렵다. 이는 거래와 시장의 규모에 영향을 줄 수 있다([1], §II.A–B, 인쇄 쪽 489–491). 이 관점을 우리 시장에 적용하면, 구매 전에 상대 가게의 신뢰성을 알기 어려운 문제가 연구 동기가 된다. 다만 물리적 상품 품질을 영수증 일치 여부와 동일시할 수는 없다. 이번 실험은 가격 균형, 판매자 진입·퇴출, 시장 축소를 측정하지 않았다.

**Resnick 등(2000)의 평판 정보 이용.** 저자들은 과거 행동에 대한 피드백의 수집·전달·집계를 설명하고, 평판 시스템이 작동하려면 과거 피드백이 미래 구매 결정에 쓰여야 한다고 논의한다([2], 저자 공개 초고 PDF 1–3쪽). 이번 실험은 그 연결 중 ‘후기 입력 → 선택 판단’ 한 부분을 다룬다. 단순히 후기가 존재하는지보다, 같은 후보에서 후기 조건을 바꾸었을 때 경고와 선택이 달라지는지를 관찰한다. 문구가 다른 후기 2건이라는 임계값과 직접 불일치의 영구 차단은 우리 코드의 설계 선택이며, 원 논문이 권고한 알고리즘은 아니다.

**RFC 8032의 서명 검증.** 규격 §5.1.6–5.1.7은 메시지에 대한 Ed25519 서명과 공개키를 이용한 검증을 정의한다([3]). W07 seller는 `{shop,item,price,task}`를 정해진 JSON 바이트로 만들어 서명한다. 여기서 ‘정해진 JSON 형태’는 응용 프로그램의 약속이다. 서명 검증을 통과하더라도 별도로 저장한 합의 가격과 같은지는 비교해야 한다. 이번 선택 실험은 이미 만들어진 `receipt_mismatch` 기록을 입력으로 사용하며, 서명 생성이나 암호학적 검증을 새로 실행하지 않는다.

| 읽기 자료의 개념 | 구현·실험과 대응하는 지점 | 이번에 확인한 범위 |
|---|---|---|
| Akerlof: 거래 상대에 대한 정보 부족 | 직접 경험과 공개 후기라는 구별 정보를 사용 | 연구 동기이며 시장 균형 효과는 미측정 |
| Resnick 등: 과거 피드백이 미래 결정을 안내 | 후기 조건에 따른 경고와 가게 선택 비교 | 서로 다른 문구 2건에서 경고 발생 |
| Resnick 등: 후기의 정직성·집계 문제 | 동일 문구 2회 조건 | 단순 복제를 중복 증거로 세지 않음; 진위는 미검증 |
| RFC 8032: 메시지 서명과 검증 | 기존 W07 영수증 서명 구조 | 배경 설명; 합성 실험에서 서명 검증은 미실행 |

따라서 이 연구의 성격은 **읽기 자료의 문제의식을 적용한 선택 규칙 대조 실험**이다. 원 논문의 수학적 모형이나 원 논문에서 사용한 실증 자료 전체를 재현한 연구로 표현하지 않는다.

### 무엇을 같게 두고 무엇을 바꾸었는가

연구 질문은 “동일한 가게 후보와 구매 이력에서 직접 영수증 불일치 경험, 공개 후기 경고, 거래 결렬은 이후 선택에 어떤 차이를 만드는가?”이다. 독립변수는 다섯 입력 조건(기준, 직접 불일치, 서로 다른 불일치 후기 2건, 동일 후기 2회, 단순 결렬)과 대상 이름 순서(앞 `aaa`, 뒤 `zzz`)다. 각 조건에서 품목 lamp, 예산 120, 시각 2026-10-20 12:00 UTC, 후보 두 곳, 기록 수 1건을 유지했다. 기록 수 1건으로 5번째 주문의 순환 탐색을 피했으며 과거 구매 성공과 연결 오류는 넣지 않았다. 측정값은 대상 선택 여부, 직접 불일치 차단 여부, 후기 경고 여부와 선택 이유다.

기준·후기 조건의 단일 기록은 상대 가게의 `no_deal`이고, 직접 불일치·결렬 조건의 기록은 대상 가게에 속한다. 따라서 기록이 속한 가게와 결과 유형이 함께 바뀌는 설계 한계가 있다. 모든 경우 다른 위험 신호는 없고, 결과는 `buyer_memory.choose_shop`의 해당 입력에 한정한다. 실험 코드는 [compare_reputation.py](compare_reputation.py), W07 선택 코드는 [buyer_memory.py](../week-07/buyer_memory.py)다. 모델과 프롬프트는 사용하지 않았다. 실제 운영 에이전트의 모델 설정은 [agent.json](../week-07/agent.json)의 `gpt-6-luna`이나 이 함수 실험에는 관여하지 않는다. 난수 시드는 필요하지 않은 결정적 실행이다.

각 실행에는 조사 대상 가게 A와 비교 가게 B가 있다. 표에서 ‘대상’은 A, ‘상대’는 B를 뜻한다. 이름이 앞서는 실험에서는 A=`aaa`, B=`zzz`이고, 뒤서는 실험에서는 A=`zzz`, B=`aaa`다. 가격과 위험 조건이 같으면 코드가 이름순으로 선택하므로, 이 순서를 바꿔 보아야 비선택의 이유를 구분할 수 있다.

| 조건 | buyer에게 제공한 입력의 의미 | 확인하려는 점 |
|---|---|---|
| 기준 | A에 대한 위험 정보가 없음 | 다른 증거가 없을 때의 선택 |
| 직접 불일치 | A와 거래한 기록에 `receipt_mismatch`가 있음 | 자신의 거래 기록으로 A를 제외하는지 |
| 서로 다른 후기 2건 | 합의 110·영수증 135라는 후기와 영수증 가격이 더 높았다는 후기를 제공 | 공개 후기 경고가 순위를 바꾸는지 |
| 동일 후기 2회 | 같은 불일치 문구를 두 번 제공 | 복제된 문구를 두 개의 증거로 세는지 |
| 단순 결렬 | A와의 거래 기록에 `no_deal`이 있음 | 구매 실패만으로 A를 차단하는지 |

여기서 ‘서로 다른 후기’는 **문구가 다르다**는 뜻이다. 작성자가 서로 다른지, 서로 독립된 거래에서 나온 진실한 후기인지는 검사하지 않는다. 따라서 이 조건을 ‘독립적으로 검증된 두 증거’라고 해석하면 안 된다.

## Results

### 관측 결과 읽는 방법

아래 표의 각 칸은 ‘선택한 가게 / 대상 가게를 차단했는지 / 대상 가게에 경고했는지’ 순서다. 예를 들어 ‘상대 / 아니요 / 예’는 A를 후보에서 지우지는 않았지만, 경고 때문에 이번 입력에서 B를 선택했다는 뜻이다. 다섯 조건에 이름 순서 두 가지를 적용해 총 10행을 얻었다. 각 조합은 한 번씩 실행했으며 반복 표본으로 성공률을 추정한 실험은 아니다.

| 대상 가게 조건 | 이름 앞: 선택 / 차단 / 경고 | 이름 뒤: 선택 / 차단 / 경고 |
|---|---|---|
| 기준 | 대상 / 아니요 / 아니요 | 상대 / 아니요 / 아니요 |
| 직접 불일치 | 상대 / 예 / 아니요 | 상대 / 예 / 아니요 |
| 서로 다른 불일치 후기 2건 | 상대 / 아니요 / 예 | 상대 / 아니요 / 예 |
| 동일 후기 2회 | 대상 / 아니요 / 아니요 | 상대 / 아니요 / 아니요 |
| 단순 결렬 | 대상 / 아니요 / 아니요 | 상대 / 아니요 / 아니요 |

원본 10행은 [실행 결과](logs/reputation-comparison-20261102.json)에 있다. 대상 이름이 앞서는 경우, 직접 불일치와 서로 다른 후기 2건에서만 기준 대비 선택이 바뀌었다. 이름이 뒤서는 경우는 기준부터 상대가 선택돼, 선택 여부 하나만 보면 경고 효과를 구분할 수 없다. 차단·경고 필드가 이 차이를 설명한다. 동일 후기의 반복을 별도 증거로 세지 않는 것은 이 실험에서 확인한 방어 동작이다. 실제 maple-home 사건은 의자 합의 234, 영수증 269, 예산 250으로 별도 관찰 자료이며, 이 합성 10행에 포함하지 않았다.

### 인사이트 1: 직접 경험과 공개 후기는 다른 강도로 작동한다

A의 이름이 앞서는 기준 조건에서는 A가 선택됐다. 여기에 직접 불일치 기록을 주면 A가 차단되고 B가 선택됐다. 공개 후기 2건을 주었을 때도 선택은 B로 바뀌지만 A는 차단되지 않았다. **최종 선택은 같아도 내부 처리 방식은 다르다.** 직접 불일치는 이 코드에서 후보 제외의 근거이고, 공개 후기는 다른 후보와 비교할 때의 위험 신호다. 후보 구성이 달라지는 상황에서 두 규칙이 같은 결과를 낸다고 일반화할 수는 없다.

### 인사이트 2: 거래 실패만으로 가게를 부정직하다고 판단하지 않는다

단순 결렬 조건은 기준 조건과 선택·차단·경고 결과가 같았다. 예산과 판매 가격이 맞지 않아 구매하지 못했을 수도 있으므로, `no_deal`과 `receipt_mismatch`를 같은 실패로 묶으면 이 차이가 사라진다. 운영 기록에서도 실패 건수만 합산하기보다 ‘가격 합의 실패’와 ‘영수증 내용 불일치’를 구분할 필요가 있다는 설계상의 시사점이다. 다만 모든 결렬 원인에서 안전하게 동작하는지까지 검사한 것은 아니다.

### 인사이트 3: 같은 문구의 반복은 후기 경고를 만들지 않았다

같은 불일치 후기를 두 번 제공해도 경고는 생기지 않았다. 서로 다른 문구 두 개를 제공했을 때는 경고가 생겼다. 이 결과는 코드가 동일 문구의 단순 복제에 반응하지 않는다는 점을 보여 준다. 그러나 단어만 바꾼 복제나 여러 계정의 허위 후기까지 식별한다고 볼 수는 없다. 서로 다른 문구를 믿을 수 있는 증거로 취급하는 기준 자체는 추가 검증이 필요하다.

### 인사이트 4: 선택 결과만 보면 위험 판단이 가려질 수 있다

A의 이름이 뒤일 때는 다섯 조건 모두 B가 선택됐다. 최종 선택만 기록했다면 조건별 차이가 없다고 결론낼 수 있다. 실제로는 직접 불일치에서 차단이, 서로 다른 후기에서 경고가 발생했다. **설명 가능한 관측을 위해 선택 결과와 그 근거를 함께 저장해야 한다.** 반대로 A가 선택되지 않았다는 사실만으로 위험 탐지가 성공했다고 해석해서도 안 된다.

## Discussion

현재 선택 함수는 직접 경험한 영수증 불일치와 공개 후기 경고를 다르게 취급한다. 이 구분은 단순 결렬이나 중복 후기를 부정행위로 오인하는 것을 줄인다. 반면 후기 탐지는 제한된 표현을 검사하므로 새로운 문구나 언어의 불일치를 놓칠 수 있다. 직접 불일치 기록도 그 기록이 정확하다는 전제에서만 차단한다. 이 실험은 후기 진위, 실제 거래 성공률, 다른 위험 신호, 순환 탐색 차례를 측정하지 않았다. W07 감사에서 maple-home 경고가 있는 선택 기록에서 해당 가게가 선택되지 않았다는 사실도 이 대조만으로 인과 효과라고 해석하지 않는다. LLM은 이 실험에서 호출되지 않았으므로 어떤 판단을 해결했다고 평가할 자료가 없다. 모델을 사용하는 협상 및 시장 정산은 별도 단계다.

### 이번 확장에서 확인한 것과 다음 검증 과제

읽기 자료와 비교하면, 이름이 앞선 대상에 공개 경고를 주었을 때 선택이 바뀐 결과는 Resnick 등이 논의한 ‘피드백을 의사결정에 사용’하는 조건이 이 구현에서 나타나는 한 사례다. 이것만으로 신뢰 형성이나 정직한 행동을 유도했다고 결론낼 수는 없다. 저자들은 정직한 보고의 확보, 상호 평가를 통한 조작, 이름 변경과 집계의 어려움도 논의한다([2], 저자 공개 초고 PDF 4–5쪽). 우리 실험은 문구 중복만 구분하므로 작성자 식별이나 담합 문제를 해결했다고 주장할 근거가 없다. 이는 인사이트 3의 적용 범위를 제한한다.

기존 W07 제출에서는 실제 불일치 거래와 이후 비선택을 로그로 제시했다. 이번 확장에서는 같은 선택 함수에 조건을 주어 직접 불일치·공개 경고·단순 결렬의 처리를 구분했다. 특히 이름순을 바꾸면서 최종 선택만으로는 경고 여부가 드러나지 않는 사례를 얻었다. 이는 현재 구현된 규칙의 동작을 확인한 결과이며, 그 규칙이 시장에서 가장 좋은 전략이라는 증거는 아니다.

다음 검증 후보는 같은 의미의 다른 표현이나 다른 언어에서 경고가 누락되는지, 문구만 다른 허위 후기가 경고를 만드는지, 후보가 한 곳뿐일 때 경고와 차단이 어떻게 다른지, 그리고 5번째 순환 탐색에서 선택이 어떻게 달라지는지다. 이 항목들은 아직 실행하지 않았으며 이번 결과에 포함하지 않는다.

## Reproduction

저장소 루트에서 Python 3로 다음 한 줄을 실행하면 표의 원본 JSON을 출력한다. `compare_reputation.py`와 `../week-07/buyer_memory.py`를 함께 포함해야 한다. API 키, 시장 접속, 개인키, 외부 Python 패키지는 필요 없다.

```powershell
python submissions/24522014/week-08/compare_reputation.py
```

기준 실행 출력은 `logs/reputation-comparison-20261102.json`이다. 별도의 week-06 Python 가상환경에서 같은 명령을 실행한 결과는 `logs/reproduction-week06-python-20261102.json`에 보존했고, 두 파일의 JSON 10행이 일치했다. 이는 다른 인터프리터 환경에서의 재현이며 다른 컴퓨터에서 실행했다는 뜻은 아니다. W07 기존 단위 검사 16개 실행 기록은 `logs/baseline-unit-test-20261102.log`에 있다. 원래 시장 사건의 구매자 응답과 원장 감사 근거는 `../week-07/logs/challenge-2/20261023T025813161183Z/`에 보존돼 있다.

추가로 두 소스 파일만 새 임시 폴더에 복사하고 Python의 격리 모드(`-I`)와 외부 패키지를 로드하지 않는 옵션(`-S`)으로 실행했다. 기존 결과 10행과 모두 일치했다. 이 검사는 운영 로그나 설치 패키지에 대한 숨은 의존성이 있는지 확인하는 범위이며 같은 컴퓨터에서 수행했다. [검증 기록](logs/submission-validation-20261102T052153Z.json)에 실행 환경, 결과 일치 여부, 소스와 기준 출력의 SHA-256 해시를 남겼다. 이후 코드가 바뀌면 이 기록의 해시와 비교하고 결과를 재검증해야 한다.
