## 1. 부품별 설계

계약 전환의 첫 구현은 `seller_r3.py`, `r3_harness.py`, SKU·order 대응 buyer에 준비했고 설정 후보는 `agent-r3.json`이다. 상세 출처와 한계는 [R3-CONTRACT-ADAPTATION.md](R3-CONTRACT-ADAPTATION.md)를 본다. 오프라인 검사 19개가 통과했지만 실제 R3 모델 호출과 정산은 아직 검증하지 않았다. 활성 `agent.json`은 기존 운영 설정이다.

### 모델

복사한 활성 설정은 Codex gpt-6-luna다. 기존 seller는 첫 가격과 제시가 확인을 코드로 처리하고 그 밖의 협상에서 모델을 호출한다. buyer는 예산 안에서 협상한다. 이는 이전 세 품목 구현 기준이며 새 SKU·재고·인증서에 대한 입력과 검증은 전환 후 기록한다.

### 컨텍스트와 메모리

buyer_memory.py는 가게 이름에 거래 결과를 연결하고, 영수증 불일치·연결 오류·후기 경고·과거 성공 가격과 순환 탐색을 고려한다. 기존 기억은 보존하지만 현재 코드가 새 SKU, 유통기한, 고장, 정산 실패를 학습한다고 주장하지 않는다. 새로운 .market/ 계약과 메모리 구조의 연결이 필요하다.

기존 모니터는 30분마다 공개 지표를 기록하고 monitor_triage.py는 짧은 분석 후보를 만든다. 모델 자동 호출과 자동 정책 수정은 없다. 운영 전환 때 모니터 경로도 확인한다.

### 툴과 키트

키트 v4는 ACP/AP2 정산, 재고·카탈로그·수요·게시판 파일과 공급·후기 훅을 제공한다. 계약 원본은 logs/agent-contract-20261102.md에 있다. 자체 restock·review 훅은 아직 활성 설정에 없다. 기본 무작위 공급은 판매 수요를 학습하지 않으므로 자금과 폐기 위험을 고려한 정책을 설계해야 한다.

## 2. 아키텍처와 기본형 대비 차이

기존 자체 구성은 신뢰성·가격 기반 선택과 탐색, 영수증 일치 확인, 규칙과 모델 협상의 분리, 모델 호출 없는 관측이다. 새 계약에 맞춘 실제 구조를 확정한 뒤 architecture.tex와 한 페이지 architecture.pdf를 작성한다. 두 제출 파일은 현재 미완료다.
