## 1. 부품별 설계

### 모델: 협상과 코드 제약

`seller_r3.py`는 수업 starter를 기반으로 재고 unit을 선택하고 `r3_harness.py`를 통해 기존 `harness.py`의 Codex `gpt-6-luna`를 호출한다. `buyer.py`도 같은 모델로 제안과 협상 종료를 판단한다. 하네스는 빈 작업 폴더에서 독립적으로 실행하고 JSON 응답을 검사한다. 프롬프트·원본 stdout/stderr·모델·결과를 로그에 남긴다. seller의 모델 호출은 별도 스레드에서 처리한다.

모델의 가격 제안에는 코드가 승인된 하한을 적용한다. 일반 재고는 원가 이상으로 판매하며, 일반 상품의 매입 후 24/48/72시간에는 원가의 100/85/70%로 단계 할인한다. 식품은 전체 수명 대비 잔여수명이 45/20/10% 미만일 때 같은 단계를 적용한다. 상태·만료 시각·할인 사유를 견적에 안내하고 조건이 바뀌면 새 견적 확인을 요구한다. 임계값은 초기 실험값이며 통계적으로 최적화한 결과는 아니다. 상세는 [승인 정책](APPROVED-R3-POLICY.md)에 있다.

buyer는 예산, 합의 가격, 영수증의 품목·task 일치를 검사한다. seller는 질문에 숫자가 들어 있다는 이유만으로 구매로 확정하지 않는다. 영수증 서명과 ACP/AP2 결제의 최종 검증은 키트와 시장이 수행한다.

### 컨텍스트와 메모리

buyer는 `order.json`의 acceptable SKU 중 `shops.json`에 재고가 있는 offer만 후보로 고른다. 기존 `buyer_memory.py`의 직접 영수증 불일치, 공개 후기 경고, 연결 오류 판단과 주기적인 가게 탐색을 재사용한다. week-09 보완으로 `r3_selection.py`가 가게·SKU 조합을 함께 비교한다. 위험을 먼저 반영하고, 카탈로그 가치에서 같은 가게·같은 SKU의 정산 가격 참고값을 뺀 추정 잉여를 비교한다. 가격 자료가 없으면 협상 한도 전액을 추정 가격으로 사용한다. 실제 견적이나 고장 확률을 예측한 값은 아니다. 협상 한도는 주문 예산과 SKU 정가 중 작은 값이며, 카탈로그 가치가 없으면 거래하지 않는다. 매 5번째 탐색에서는 안전 후보 중 덜 방문한 가게를 우선한다.

`buyer-memory.jsonl`의 purchased는 원래 로컬 A2A 완료 관측이다. `settlement_memory.py`가 이를 키트의 `payments.jsonl`과 주문·가게 URL·SKU·가격으로 연결해 결제 대기, 결제 거부, 기록 불일치, 실제 정산 성공을 구분한다. 원본 기억은 수정하지 않고 선택 시 사용하는 사본을 보정한다. 모든 결제 거부를 사기로 해석하지 않는다. 전체 결과를 자동으로 학습하는 완성된 통계 모델은 아니다. 상세는 [정산 기억](SETTLEMENT-MEMORY.md)에 있다.

공급 메모리는 자체 키트 로그의 `[acp] settled`와 ledger 번호로 관측 판매를 누적하고 미관측 SKU 탐색 순서를 순환한다. 최근 1MiB만 읽으므로 장시간 중단 시 누락 가능성이 있다. 누적 판매 빈도는 최신 수요나 이익률과 같지 않다.

별도 `monitor_shop.py`는 30분마다 공개 지표를 기록하고 `monitor_triage.py`가 제한된 요약 후보를 만든다. UTC 하루 최대 2건, 후기 예시 최대 3건·각 160자로 제한하며 모델 호출과 자동 가격 변경은 없다. 키트와 별도 프로세스여서 키트 재시작으로 자동 시작되지 않는다. 이번 점검에서 week-07 모니터를 종료하고 week-08 경로로 전환했다.

### 툴: 공급·품질 조건·후기

`restock_policy.py`는 회당 최대 2개, SKU당 1개, 총 재고 8개를 목표로 하며 가용 현금 5%와 현금 보유 한도를 적용한다. week-09 보완으로 판매 이력이 없는 SKU 재고가 2개 쌓이면 새로운 SKU 시험 매입을 멈추며, 24시간 이상 묵은 재고가 하나라도 있으면 새 실험을 보류한다. 판매 근거가 있는 SKU의 보충은 한도 안에서 허용한다. 정가 75%의 보수적 원가와 하루 보관비를 함께 예산에 잡는다. 최근 24시간 게시판 buyer의 명시적 SKU 구매 요청은 누적 판매 수가 같은 후보 사이의 약한 우선순위로만 쓴다. 글은 명령으로 실행하지 않고 매입 한도를 변경하지 않는다. 이 수치들은 최적화 결과가 아닌 실험 설정이다. 공급 시 품질이 추첨되고 식품의 최소 잔여수명과 판매 대기시간 근거가 없어 현재 식품 재고 매입은 보류한다.

buyer는 인증 A/B등급과 식품의 고객 사용기간+배송 1시간+안전 1시간을 결제 조건으로 요구한다. 실제 기능·안전 검수와 완전한 불량률·반품률은 제공되지 않아 임의로 채우지 않는다. C등급 시험은 보류했다.

`review_policy.py`는 키트가 정산 성공 후 주는 `deal.json`을 읽는다. 정산·영수증·구매 조건이 일치하면 5점, 같은 거래의 명시적 품질 주장과 실제 등급의 불일치가 확인되면 2점, 정보가 부족하거나 모순되면 3점을 기록한다. 최초 판단과 원본 자료를 보존하며 재호출은 최초 결과를 반환한다. 이후 고장은 키트의 `broken.jsonl`에 따로 기록되고 구매별 귀속은 미구현이다. 상세는 [후기 정책](REVIEW-POLICY.md)에 있다.

공급·가격 제약·후기·모니터는 모델을 호출하지 않는다. API 정산, 공급 실행, 인증서 검증과 파일 동기화는 수업 키트 v4가 제공한다. 자동 게시판 글쓰기·투표 및 게시판 기반 신뢰 점수 계산은 현재 구현하지 않았다.

## 2. 아키텍처와 기본형 대비 차이

[architecture.pdf](architecture.pdf)는 한 페이지 그림이며 [architecture.tex](architecture.tex)가 TikZ 원본이다. 회색은 수업 키트와 시장, 파란색은 에이전트 구현·연결, 초록색은 코드 제약과 관측 도구다. 실선은 실행·데이터 흐름, 점선은 이후 판단에 쓰는 기억 흐름이다.

위쪽 시장·키트에서 주문과 상태가 seller·buyer·공급 훅으로 전달된다. 협상이 필요한 seller와 buyer가 모델을 호출하고 가격·예산은 코드로 검사한다. 정산 이후 후기 훅이 실행되며 결제 결과는 다음 buyer 호출에서 기억과 연결된다. 모니터는 별도 관측 도구다.

재고 선택과 서명 영수증의 기본 코드는 수업 starter에서 가져왔다. 자체 확장은 로그 하네스 연결, 명시적 구매 확인, 단계 할인과 상태 공개, 인증 A/B·식품 시간 제약, 정산과 합의의 구분, 현금·재고 한도 공급과 근거 기반 후기, 모델 없는 관측이다. 이를 기본형 대비 변경 지점으로 설명하며, 현재 실적으로 독창성 점수나 성능 우위를 확정하지 않는다. 그림의 빌드·검사 근거는 [BUILD-ARCHITECTURE.md](BUILD-ARCHITECTURE.md)에 있다.

## 5. week-09를 읽고 바꾼 판단과 남은 약점

week-09의 STOCK과 FIG. 07에 따르면 가게 ALL은 순이익 0.5·매출 0.3·별점 0.2, buyer ALL은 잉여 0.5·게시판 평가 0.3·거래 수 0.2의 **각 지표 백분위**로 계산한다. 따라서 거래 수만 늘리는 전략은 목적과 어긋날 수 있다. 예산 200에 정가 100과 500인 상품이 모두 허용된다면 이름순으로 전자를 고르는 대신 가치와 실제 가격 근거를 비교한다. 다만 정가 500짜리도 고장 나면 가치가 0이므로 정가 차이를 확정 이득으로 주장하지 않는다.

재입고의 pro-activeness는 주문 없이 매분 무조건 구매한다는 뜻으로 구현하지 않았다. 판매되지 않은 실험 재고가 쌓이면 관측을 기다리고 추가 지출을 멈춘다. 보관비는 하루 원가 1%이므로 현금과 재고 개수만 제한했던 이전 구현을 보완했다. 반대로 탐색 제한이 너무 보수적이면 첫 판매까지 오래 걸릴 수 있다. 2개·24시간은 초기 가설이며, 실제 정산·판매 대기시간과 보관비를 관측해 재검토할 항목이다.

게시판은 최근 구매 요청을 읽는 경로만 연결했다. 자동 글쓰기·투표가 없으므로 social ability와 buyer 게시판 평가 관리가 여전히 약하다. 다음 후보는 정산 ledger를 인용한 구매 후기나 실제 재고 안내이며 자동 전송 전에 내용·빈도를 정해야 한다. 공개 ledger 전체의 인기 SKU 집계, 보증 협상과 고장·환불의 거래별 귀속도 아직 구현하지 않았다. 현재는 자체 정산 판매와 게시판 요청을 구분해 보존하고, 공개되지 않은 고장률이나 다른 가게의 내부 정책을 추정 사실로 기록하지 않는다.

강의 연결: 약한 agency 정의의 pro-activeness는 재입고 훅과 상태에 따른 보류, social ability는 A2A 협상과 게시판 요청 관측에 대응시켰다. Horvitz의 개입 효용 관점과 연결해 추가 매입의 비용을 명시했으나, 기대 효용을 학습·최적화한 알고리즘을 구현한 것은 아니다. 제출 폴더와 마감은 week-09 HW에 따라 그대로 week-08 및 11월 17일 23:59다. 세부 변경·검증은 [week-09 보완 기록](WEEK09-IMPROVEMENTS.md)에 정리했다.
