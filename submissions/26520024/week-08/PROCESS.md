# Week 08 구현 과정

## 범위와 승인

2026-11-02 사용자와 Round 3 규칙, 시장 분석/연관 상품 탐색, 근거 기반 메모리와 리뷰 관리 방향을 논의한 뒤 구현했다.
사용자는 수업시간 전 배포하지 말라고 명시했다. 따라서 join, tunnel, 실제 매입·거래·게시글·투표, push/PR은 실행하지 않았다.
기존 Week 7은 수정하지 않았고, 복사본의 기존 기록은 참고 자료로 보존했다. 구현은 코딩 에이전트가 지원했다.

## 확인한 계약

- 로컬 `week-08.html`, `scripts/market_kit.py` v4 및 공개 `https://market.ourolabs.ai/agent.md`를 읽었다.
- 공개 문서 GET 외에 시장 데이터 조회나 인증 요청은 하지 않았다. 운영자가 붙여넣었던 claim code와 개인키를 읽거나 사용하지 않았다.
- `demand.json`은 판매량이 아닌 카테고리 목록이다. 원래 생각한 인기 순위 입력으로 사용하지 않았다.
- 공급 시 등급/원가가 무작위로 정해지므로 특정 등급을 주문한다는 가정을 버리고 최악 원가로 매입 예산을 계산했다.
- buyer가 출력한 signed receipt는 결제 완료가 아니다. `payments.jsonl`와 정산 후 review hook을 별도 처리했다.
- 음식 유통기한, goods 보관비, 고장/보증 처리와 공개 정산 기록의 제한된 필드를 확인했다.

## 작업 단위

1. 공통 계약 검증, 원자적 JSON, SQLite 사건 메모리, 읽기 전용 공개 관측기를 추가했다.
2. 기존 Codex transport를 재사용하고 판매자, 구매자/리뷰, 발견/매입을 역할별 모듈로 구현했다.
3. 검증된 거래와 게시판 주장을 분리하고, 역할별 bounded context와 선택적 조건부 교훈/게시판 초안을 추가했다.
4. 기본 live 잠금과 Round 3 전용 manifest를 연결했다. 기존 가위바위보는 새 경로에서 제외했다.
5. 오프라인 테스트와 교차 검토를 반복했고, 아래 수정 이유를 보존한다.

## 실패와 수정

- 이 환경의 파일 sandbox helper가 Update File 패치에서 namespace 오류를 냈다. 이미 읽은 자기 소유 파일만 전체 Add File 패치로 교체했다. 기존 사용자 파일은 먼저 내용을 확인하고 참고본을 보존했다.
- 초기 seller 테스트에서 SQLite 연결을 ASGI 테스트 스레드와 공유해 thread-affinity 오류가 났다. 요청 스레드에서 연결을 열고 닫도록 수정했다.
- seller action을 task ID만으로 저장하면 같은 협상의 ask/accept가 중복으로 제거됐다. task+round 키로 바꿨다.
- buyer가 마침표로 끝나는 가격 문장을 읽지 못하는 테스트를 수정했다. 별도의 task ID로 바뀐 응답과 중복 주문 재협상을 거절하도록 테스트했다.
- 재고 파일 수정 시각을 내용 변경으로 취급하면 키트의 10초 갱신 때문에 매입이 계속 취소될 수 있었다. 내용 지문과 갱신 epoch를 분리하고 테스트했다.
- 발주 대기 재조정에서 이미 배정된 unit을 다른 주문으로 옮길 수 있었다. 기존 배정을 먼저 보존하도록 고쳤다.
- 보관비를 선택적 flat 필드로 계산하던 로직을 goods 원가의 일 1%로 수정했다. 식품은 보관비를 부과하지 않는다.
- 공통 메모리의 pending 검색이 다른 가게와 buyer의 주문 정보를 seller에게 전달할 수 있었다. SQL 필터, 역할 분리, 내용 축약을 추가했다.
- 첫 통합 검증은 74개 테스트 자체는 통과했지만 CLI 잠금 판정 2개 때문에 FAIL이었다. restock의 정상적인 빈 매입 응답도 잠금으로 인정하도록 검증기를 수정했고, review CLI에는 실행 잠금을 추가했다. 해당 실패 로그를 삭제하지 않았다.

## 검증의 의미와 한계

`run_r3_offline.py`의 원문 로그와 JSON은 `logs/round3-offline/`에 보존된다. 가짜 모델은 단위 테스트용이며 실제 모델 성과로 보고하지 않는다.
별도 패키지 설치나 conda 환경 변경은 하지 않았다. 기존 `.venv`의 Python 3.10.22, a2a-sdk 1.2.0, cryptography 50.0.2, httpx 0.28.1을 사용했다.
Starlette TestClient/httpx 관련 deprecation 경고와 SDK dispatcher 종료 메시지가 보일 수 있다. 실제 시장 통신 테스트를 했다는 뜻이 아니다.
현재 저장소에는 Week 8 전용 structural checker가 없다. Week 7 market test로 Round 3 정합성이 검증됐다고 주장하지 않는다.
LaTeX 엔진이 없어 `architecture.tex`는 아직 컴파일/렌더 검증하지 못했다.

## 2026-11-03 읽기 전용 검토 후 보완

사용자가 시장 규칙과 구현의 차이를 확인한 뒤 수정을 승인했다. 변경은 Week 8 코드/테스트/문서에만 한정했으며 배포·join·매입·거래·게시·push/PR은 하지 않았다. 기존 사용자 스테이징 파일은 포함하지 않는다.

1. 정상 카테고리 영수증을 거절하던 정확한 SKU 일치 조건을 수정했다. 실제 정산 SKU는 acceptable 목록에 있어야 하고, SKU로 서명한 영수증은 배송 SKU와 같아야 한다. 서명 원본은 보존했다.
2. A2A 요청 입구에서 task 변경을 직렬화하고 messageId별 요청 내용과 완료 응답을 기록했다. SDK 큐 정리가 끝나기 전에 다음 요청이 들어가지 않도록 실제 SDK를 사용하는 인프로세스 테스트로 확인했다. 잠금 획득 전 실패까지 실행 중으로 기록하면 정상 재시도가 막히는 문제를 발견해 journal 시작 시점을 수정했다.
3. 서명 후 재고를 signed_pending/quarantined/settled로 구분했다. 공개 정산의 unit/SKU/가게/금액을 함께 확인하고, 진단 상태 파일을 추가했다. 취소 callback이나 기존 영수증의 무효화 보장이 없으므로 TTL 해제 방식은 도입하지 않았다. 이 재고 복구 제약은 미해결로 명시한다.
4. 원본 사건은 append-only로 유지하고 조회용 SQL view에서 결제 결과를 주문/당시 URL/가게 이름에 연결했다. 고장 알림은 유일한 상품명/시간 후보만 추정으로 표시하고 이후 모호해지면 철회한다. 이름/시간 검색 인덱스를 추가했지만 장기 운영 규모의 성능 측정은 별도다.
5. 교차 검토에서 최초 선택 상품과 실제 배송 상품이 다르면 협상 이력에 잘못된 구매 성공이 남는 사례를 발견했다. 결제 이력뿐 아니라 협상·대기 문맥도 실제 정산 SKU, 명시된 허용 영수증 SKU 순으로 조회하도록 고쳤고 회귀 테스트를 추가했다.
6. 모델이 매입을 고민하는 동안 정상 판매가 발생해도 최신 정책/재고/잔액/진행 중 매입으로 제약을 다시 계산한다. 모델 승인 상품과 수량의 확대는 금지한다. 이미 입고된 물건이 도중에 팔려도 미입고로 되돌아가지 않도록 확인 기록도 보존한다.
7. 공개 정산의 amount/order 등 원본 필드를 보존하고, 오프라인 검사에 비동기 HTTP 전송 차단도 추가했다.

파일 읽기 sandbox 오류 때문에 기존과 같이 최신 원문을 읽은 뒤 소유 파일의 Add File 패치로 편집했다. 자동 승인 사용량 오류로 한 차례 작업이 중단되었고, 사용자의 계속 진행 요청 후 실제 적용 상태를 확인하고 재개했다. 실패 로그나 기존 데이터는 삭제하지 않았다.

최종 검증: **132 tests, 0 failures, 0 errors, CLI 잠금 5/5**. 증거는 `logs/round3-offline/20261103T114916288364Z.{log,json}`이다. 중간 `20261103T114542526765Z` 로그는 당시 테스트 보조 클래스의 중복 발견을 포함하므로 최종 고유 테스트 집계에 사용하지 않는다. 기존 .venv만 사용했고 패키지/conda 환경은 변경하지 않았다. 실제 모델 품질, 시장 정산과 순위는 여전히 미측정이다.

## 2026-11-03 장기 운영용 Luna 전환

사용자가 2주 운영 시 Astra 사용량 부담을 지적해 Luna 전환을 요청했다. 현재 로컬 Codex 모델 캐시(`2026-11-03T12:12:58Z` 갱신)에 표시된 `gpt-5.6-luna`와 지원되는 `low` reasoning을 확인했다. 공개 문서는 더 최신 Luna도 안내하지만 이 계정/클라이언트 목록에 없는 모델로 임의 변경하지 않았다. 인증 토큰은 읽지 않았다.

- 공통 `codex_backend.py`의 MODEL만 `gpt-6-astra`에서 `gpt-5.6-luna`로 변경하고 reasoning low, 시간 제한, 제한된 재시도, 네이티브 도구 차단은 유지했다.
- 판매/구매/발견/매입/선택적 성찰이 공통 모델을 사용한다. 강제 예산/재고/서명 검증과 결정론적 리뷰는 변경하지 않았다. Astra 자동 대체 경로도 추가하지 않았다.
- 현재 manifest 설명과 README/REPORT/LaTeX 구조 원본을 갱신했다. 이전 주차의 참고 문서와 실제 로그는 역사적 기록이므로 모델명을 바꾸지 않았다.
- 모델 선택/CLI 인자/metadata/도구 차단 테스트를 추가했다. 상수 변경 전 최초 테스트는 Astra를 검출해 3개 실패했고, 변경 후 4개 모두 통과했다. 이 테스트는 CLI/로그인 상태까지 가짜 subprocess로 대체하므로 실제 모델 접속이나 인증 확인이 아니다.
