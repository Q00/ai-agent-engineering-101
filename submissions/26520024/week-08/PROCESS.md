## 실패와 수정

- 이 환경의 파일 sandbox helper가 Update File 패치에서 namespace 오류를 냈다. 이미 읽은 자기 소유 파일만 전체 Add File 패치로 교체했다. 기존 사용자 파일은 먼저 내용을 확인하고 참고본을 보존했다.
- 초기 seller 테스트에서 SQLite 연결을 ASGI 테스트 스레드와 공유해 thread-affinity 오류가 났다. 요청 스레드에서 연결을 열고 닫도록 수정했다.
- seller action을 task ID만으로 저장하면 같은 협상의 ask/accept가 중복으로 제거됐다. task+round 키로 바꿨다.
- buyer가 마침표로 끝나는 가격 문장을 읽지 못하는 테스트를 수정했다. 별도의 task ID로 바뀐 응답과 중복 주문 재협상을 거절하도록 테스트했다.
- 재고 파일 수정 시각을 내용 변경으로 취급하면 키트의 10초 갱신 때문에 매입이 계속 취소될 수 있었다. 내용 지문과 갱신 epoch를 분리하고 테스트했다.
- 발주 대기 재조정에서 이미 배정된 unit을 다른 주문으로 옮길 수 있었다. 기존 배정을 먼저 보존하도록 고쳤다.
- 보관비를 선택적 flat 필드로 계산하던 로직을 goods 원가의 일 1%로 수정했다. 식품은 보관비를 부과하지 않는다.
- 공통 메모리의 pending 검색이 다른 가게와 buyer의 주문 정보를 seller에게 전달할 수 있었다. SQL 필터, 역할 분리, 내용 축약을 추가했다.
- 첫 통합 검증은 74개 테스트 자체는 통과했지만 CLI 잠금 판정 2개 때문에 FAIL이었다. restock의 정상적인 빈 매입 응답도 잠금으로 인정하도록 검증기를 수정했고, review CLI에는 실행 잠금을 추가했다. 해당 실패 로그를 삭제하지 않았다.

## 2026-11-03 읽기 전용 검토 후 보완

사용자가 시장 규칙과 구현의 차이를 확인한 뒤 수정을 승인했다. 변경은 Week 8 코드/테스트/문서에만 한정했으며 배포·join·매입·거래·게시·push/PR은 하지 않았다. 기존 사용자 스테이징 파일은 포함하지 않는다.

1. 정상 카테고리 영수증을 거절하던 정확한 SKU 일치 조건을 수정했다. 실제 정산 SKU는 acceptable 목록에 있어야 하고, SKU로 서명한 영수증은 배송 SKU와 같아야 한다. 서명 원본은 보존했다.
2. A2A 요청 입구에서 task 변경을 직렬화하고 messageId별 요청 내용과 완료 응답을 기록했다. SDK 큐 정리가 끝나기 전에 다음 요청이 들어가지 않도록 실제 SDK를 사용하는 인프로세스 테스트로 확인했다. 잠금 획득 전 실패까지 실행 중으로 기록하면 정상 재시도가 막히는 문제를 발견해 journal 시작 시점을 수정했다.
3. 서명 후 재고를 signed_pending/quarantined/settled로 구분했다. 공개 정산의 unit/SKU/가게/금액을 함께 확인하고, 진단 상태 파일을 추가했다. 취소 callback이나 기존 영수증의 무효화 보장이 없으므로 TTL 해제 방식은 도입하지 않았다. 이 재고 복구 제약은 미해결로 명시한다.
4. 원본 사건은 append-only로 유지하고 조회용 SQL view에서 결제 결과를 주문/당시 URL/가게 이름에 연결했다. 고장 알림은 유일한 상품명/시간 후보만 추정으로 표시하고 이후 모호해지면 철회한다. 이름/시간 검색 인덱스를 추가했지만 장기 운영 규모의 성능 측정은 별도다.
5. 교차 검토에서 최초 선택 상품과 실제 배송 상품이 다르면 협상 이력에 잘못된 구매 성공이 남는 사례를 발견했다. 결제 이력뿐 아니라 협상·대기 문맥도 실제 정산 SKU, 명시된 허용 영수증 SKU 순으로 조회하도록 고쳤고 회귀 테스트를 추가했다.
6. 모델이 매입을 고민하는 동안 정상 판매가 발생해도 최신 정책/재고/잔액/진행 중 매입으로 제약을 다시 계산한다. 모델 승인 상품과 수량의 확대는 금지한다. 이미 입고된 물건이 도중에 팔려도 미입고로 되돌아가지 않도록 확인 기록도 보존한다.
7. 공개 정산의 amount/order 등 원본 필드를 보존하고, 오프라인 검사에 비동기 HTTP 전송 차단도 추가했다.

파일 읽기 sandbox 오류 때문에 기존과 같이 최신 원문을 읽은 뒤 소유 파일의 Add File 패치로 편집했다. 자동 승인 사용량 오류로 한 차례 작업이 중단되었고, 사용자의 계속 진행 요청 후 실제 적용 상태를 확인하고 재개했다. 실패 로그나 기존 데이터는 삭제하지 않았다.

## 2026-11-03 피드백 반영과 11월 4일 중단 작업 재개

사용자가 피드백 반영과 DB/ledger 구현 확인을 요청했고, 작업 중단 후 다시 진행하도록 승인했다. 수정은 본인 Week 8 코드/테스트/문서에 한정했다. 기존 키, Week 7 코드, 공유 market kit, conda 패키지에는 손대지 않았다. 공개 `agent.md` GET을 제외한 시장 접근, 실제 모델 호출, join/tunnel, 거래/게시, push/PR은 수행하지 않았다.

### 전략과 운영 변경

1. 공급 창의 명시적 open/시작/종료 값을 확인하고, 모델 판단 전후 같은 창이 열려 있는지 다시 검사한다. 새 창을 이전 창의 재매입 cooldown으로 막지 않는다. 신규 발주 대기는 창 종료에 맞춰 제한하며 입고 확인은 유지한다.
2. Luna 응답에 기본 20초를 배정하고 실패 후 300초 대기한다. 선택/협상/발견/매입의 결정론적 대체도 같은 validator를 통과해야 하며 `policy_fallback`으로 별도 기록한다. 이것은 모델 성능 결과가 아니며 무제한 호출을 전역으로 직렬화한 것도 아니다.
3. 기존 고정 원가 가산 호가를 정가·공개 실거래 비율·재고 나이 기반 범위로 바꿨다. 기존 호가 인상은 금지한다. buyer는 추정 사용가치와 가격의 차이를 비교하며 goods 10% 위험 사전 가정과 성숙한 자체 구매를 사용한다. 이름/시간으로 연결한 고장 정보는 추정으로 유지한다.
4. 공식 ledger로 확인한 자체 구매의 카테고리별 가격·주장 일치 요약을 신규 정산 3건 이상일 때 만든다. 중복 근거 재활용과 자동 투표는 하지 않는다. `forum_enabled=true`라도 live 잠금이 열려야 outbox에 전달한다. reflection은 기본 false다.
5. 종료 기본값을 공지의 11월 17일 23:59 KST로 설정하고 전체 재고/대기 원가 60% 한도를 추가했다. 기존 `.market/policy.json`은 덮어쓰지 않았다. 정책 예제와 기본값의 일치도 테스트한다.

### checkout과 저장소
