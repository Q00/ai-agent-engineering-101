빠른 협상과 느린 시장 분석을 분리한다. 5,629개 상품 전체를 매 턴 모델에 넣지 않고 수치적으로 좁힌 후보와 관련 경험만 전달한다.
공개 게시판의 주장은 판매 증거로 세지 않는다. `demand.json`도 카테고리 목록이지 수요 순위가 아니다.
인기 상품과 연관된 후보는 **아직 검증되지 않은 가설**로 표시하며, 같은 구매 주문의 대체 상품을 여러 수요로 중복 계산하지 않는다.

## 보수적 기본 정책

- 현금 25% 보유, 한 번 매입 제안은 잔액의 최대 10%, SKU당 최대 3개, 전체 40개.
- 카테고리 재고와 발주 대기는 현금+기존 재고 원가 기준 35% 이내. 공급 원가는 최악의 등급 A 상단인 정가 75%로 예산을 잡는다.
- 근거 없는 초기 탐색은 총 3개 이내. 관측이 없다는 이유로 인기 또는 비인기라고 단정하지 않는다.
- 분석 캐시 15분, 재매입 간격 15분, 발주 대기 30분. 실제 잔액/재고 변경과 단순 파일 갱신을 구분한다.
- goods 보관비는 원가의 일 1%; 식품에는 적용하지 않는다. 음식은 예상 회전 시간보다 수명이 짧으면 매입하지 않는다.
- 판매 보증은 현재 0시간이다. 증명서 제공과 솔직한 품질 표시를 기본으로 하며, 보증 최적화는 아직 구현하지 않았다.
- 판매가는 원가와 실제 재고 상태로 제한한다. 폐기/종료가 임박한 경우 제한적 원가 이하 청산을 허용한다. 따라서 손실이 없다는 보장은 없다.
- 구매 가격은 코드에서 예산 이하로 제한하며, 음식은 사용 예정 시간+5분 이상 남아야 한다. 서명된 협상 영수증과 실제 결제 성공은 구별한다.
- 이미 영수증을 발급한 unit은 재판매하지 않는다. 결제되지 않은 unit의 안전한 재해제는 추후 검증이 필요하므로 현재는 보수적으로 묶어 둔다.

## 메모리와 리뷰

상태는 `.market/r3-memory.sqlite3`에 저장하고 Git에서 제외한다. 기존 Week 7 구매 메모리를 Round 3 사실로 자동 이관하지 않는다.
`payment`, `settlement`는 확인된 결과, `negotiation`은 협상, `forum_claim`과 `shop_review`는 검증되지 않은 주장으로 분리한다.
예산·주문 상세·다른 가게의 미정산 거래가 seller 프롬프트에 섞이지 않도록 역할/가게/SKU 단위로 검색한다. 개별 검색 문맥은 6,000자, buyer 선택 문맥 전체는 36,000자 이내다.
후기는 정산된 가격, 등급, 주장 일치 여부를 근거로 작성한다. 단순 모델 오류나 연결 실패에 경쟁 가게를 비난하지 않는다.
결제 결과는 주문 ID와 당시 가게 URL로 원래 가게 이름에 연결한다. 협상·결제 문맥은 최초 선택 SKU보다 실제 정산 SKU를 우선하며, 원본 사건은 수정하지 않는다.
고장 알림이 상품명만 제공되면 상품명/시간으로 유일한 구매 후보를 찾아 **추정**으로 표시한다. 후보가 여럿이면 특정 가게에 귀속하지 않고, 뒤늦게 후보가 추가되면 이전 추정도 조회 시 철회한다. 판매자의 책임이나 자동 감점 근거로 단정하지 않는다.

느린 관리 기능은 구현했지만 기본 설정에서 `reflection_enabled=false`, `forum_enabled=false`다. 게시판은 로컬 초안만 만들고 자동 투표는 하지 않는다.
수업시간 배포 승인 후 두 옵션을 검토해 켜면, 증거가 있는 교훈을 제한된 문맥으로 전달하고 ledger 번호가 있는 구매 사실을 6분 이상 간격으로 게시할 수 있다.
가짜 후기, 강제 평점 유도, 경쟁 가게 공격은 포함하지 않았다.

## 2026-11-03 계약/상태 보완

- A2A 요청 입구에서 같은 task의 변경을 SDK 응답 정리까지 직렬화한다. 동일 messageId의 완료 응답은 원본 영수증과 함께 재사용하며, 내용이 달라진 중복 ID는 거절한다.
- 지원하지 않는 streaming/nonblocking 요청은 거절한다. 실행 전 잠금 대기 실패는 재시도 가능하지만, 실행 시작 후 결과가 불명확한 요청은 임의로 재실행하지 않는다.
- 시장 규칙대로 카테고리/허용 SKU 영수증을 원본 그대로 받는다. 실제 정산 SKU, 예산, 가격, task 검사는 유지한다.
- 매입 판단 중 정상 판매가 생겨도 최신 재고/정책/잔액으로 모든 한도를 재검증한다. 승인한 SKU·수량을 늘리지 않고 축소 또는 제외만 한다.
- 서명 재고 상태를 `signed_pending`, `quarantined`, `settled`로 구분한다. 공개 정산의 가게·unit·SKU·금액이 일치할 때만 정산 확인으로 표시한다.
- 진단 파일 `.market/seller-stock-status.json`은 다음 seller 처리 때 갱신된다. 키트에 판매자용 영수증 무효화/취소 확정 callback이 없으므로 **서명 후 미결제 재고의 자동 재판매는 아직 지원하지 않는다**. 시간 초과나 재고 목록에서 사라졌다는 사실만으로 잠금을 풀지 않는다.

## 배포 전 남은 확인

1. 수업에서 Round 3 개시와 최신 키트 계약을 확인한다. 현재 로컬 키트는 v4다.
2. `.market/policy.json`은 `r3_policy.example.json`을 바탕으로 설정한다. `trading_deadline`은 명시적 시간대가 있는 종료 시각으로 설정해야 한다. 아직 임의로 설정하지 않았다.
3. 게시판/교훈 옵션과 현금·재고 한도를 사용자가 확인한 뒤에만 live 잠금을 해제한다. **이 작업에서는 join/tunnel을 실행하지 않았다.**
4. 실제 모델 지연, 키트 정산, 보증/고장, 재시작 복구를 소규모로 검증한다. 이후 seller/buyer 각각 20건 이상 실제 정산 증거와 순위를 수집한다.
5. `architecture.tex`를 LaTeX 환경에서 컴파일하고 1페이지 figure를 확인한다. 현재 머신에 TeX 엔진이 없어 PDF는 아직 생성하지 않았다.

운영 중 seller 프로세스가 재시작되면 재고 예약과 완료된 동일 메시지의 응답 재사용은 보존되지만, 새 메시지로 이어가는 SDK의 진행 중 task 대화는 복구되지 않는다. 재시작 복구 전체가 완료됐다는 뜻은 아니다.
이 설계는 구현 검증을 마친 출발점이지, 수익·평점·중간평가 순위를 입증한 결과가 아니다.
