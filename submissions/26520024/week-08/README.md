## 2026-11-10 경쟁 거래 추적

`r3_competition.py`는 공개 Cash(`profit`, 시작 자본/파산 지원금을 뺀 값) 상위 두 외부 가게를
5분마다 다시 선정하고, 공개 소유자/URL 이력과 최근 6시간 정산 표본을 SQLite에 보존한다.
동일 buyer의 3회 이상 반복 구매는 관계 후보일 뿐 비공개 제휴나 담합의 증거로 단정하지 않는다.
Cash와 Book 변화, 판매 카테고리, 고객 집중도, 같은 SKU의 등급별 실결제 가격을 기록한다.

- 과거 원장 복구 cursor는 유지하면서 최신 500개 원장 항목도 분당 최대 한 번 별도 수집한다.
  이는 전수 수집이 아니며 데이터가 30분 이상 오래되면 경쟁 전략을 적용하지 않는다.
- 다양한 buyer가 구매한 동일 SKU/연관 후보의 우선순위를 최대 20%/10% 가산한다.
  추정 마진이 양수일 때만 적용하며 기존 현금·할증·재고·실험용 한도는 그대로다.
- 같은 SKU/등급, 정직한 품질 주장, 무보증 거래가 3건 이상이고 buyer가 2명 이상이면
  중앙 실결제 가격의 98%를 경쟁 호가로 검토한다. 기존 호가 대비 최대 5% 인하,
  원가+3%와 보관비 포함 기존 하한을 모두 지킬 수 있을 때만 적용한다.
- 반복 구매 수요와 일치하는 실제 비예약 재고가 있을 때 시간당 최대 한 번 가게 안내를
  기존 outbox에 넣는다. 정확한 가격·재고 보장, 파트너 사칭, 평점 조건부 할인은 하지 않는다.
  식품은 최소 6시간 이상 남아야 하며 유료 투표 예산과 자동 투표는 계속 0이다.
- `.market/competition-latest.json`에 상위 가게·관계 후보·상품 기회·우리 가게로 이어진
  관측 거래를 기록하고 2시간 보고서에도 포함한다. 고객 이동과 전략의 인과 효과는 구별한다.

추가 모델 호출은 없다. 끄려면 기존 `.market/policy.json`에
`"competitive_tracking_enabled": false`를 설정한다. 모델은 계속 Luna/low다.
운영 가격과 고객 유입의 개선 여부는 앞으로 축적되는 실제 정산으로 평가해야 한다.

## 장기 운영 모델

2026-11-03 사용량 절약을 위해 공통 모델 기본값을 `gpt-6-astra`에서 **`gpt-5.6-luna`**로 변경했다. reasoning은 `low`를 유지한다. 로컬 Codex 모델 캐시에 표시된 정확한 ID를 사용하며, 사용자 전역 Codex 설정이나 다른 주차 코드는 바꾸지 않았다.

판매·구매·상품 발견·매입과 선택적 성찰은 동일한 공통 호출부를 사용한다. 리뷰 점수와 강제 예산/재고/영수증 검증은 기존 Python 코드가 담당한다. Luna 호출 실패 시 Astra로 자동 전환하지 않는다.

기본 활성인 `fallback_enabled`는 협상·상품 선택·발견·매입에서 모델에 최대 20초를 배정하고, 실패하면 300초 동안 추가 모델 호출을 건너뛴다. 그동안 결정론적 대체 정책도 **동일한 예산·재고·가격 검증**을 거친다. `policy_fallback`으로 출처를 기록하므로 모델 판단이나 실제 성과로 위장하지 않는다. 선택적 성찰은 이 대체 경로에 포함하지 않는다. 동시에 시작된 호출까지 모두 직렬화하지는 않으며 총 사용량을 보장하는 한도는 아니다.

이미 실행 중인 seller는 Python import 시점의 모델값을 유지한다. 현재는 Luna 설정으로 시작한 프로세스다. 새로운 buyer/restock hook은 실행할 때 소스를 다시 읽는다. 11월 4일 발견/매입 역할명이 이전 호출부에서 거부되는 오류도 회귀 테스트와 함께 수정했다.

[공식 OpenAI 문서](https://developers.openai.com/api/docs/models/gpt-5.6-luna)는 Luna를 비용에 민감한 대량 작업용 모델로 설명한다. 그러나 이 프로젝트는 API 직접 과금이 아닌 기존 Codex 로그인을 사용하므로 API 단가를 구독 사용량 절감률로 환산하지 않는다. 실제 호출 성공·품질·소모량·2주 연속 가동 가능 여부는 아직 검증하지 않았다.

## 보수적 기본 정책

- 현금 25% 보유, 한 번 매입 제안은 잔액의 최대 10%, SKU당 최대 3개, 전체 40개.
- 카테고리 재고와 발주 대기는 현금+기존 재고 원가 기준 35% 이내, 전체 재고와 발주 대기 원가는 같은 기준 60% 이내. 공급 원가는 최악의 등급 A 상단인 정가 75%로 예산을 잡는다.
- 근거 없는 초기 탐색은 총 3개 이내. 관측이 없다는 이유로 인기 또는 비인기라고 단정하지 않는다.
- 공급 창의 `open`, `opens_at`, `closes_at`를 확인하고 닫혀 있거나 마감까지 20초 미만이면 매입하지 않는다. 판단 후에도 최신 공급 창과 한도를 재검사한다.
- 분석 캐시 15분, 같은 공급 창에서 재매입 간격 15분. 새 창은 이전 창의 대기 시간에 막히지 않는다. 미입고 대기는 최대 30분 또는 공급 창 종료+120초 중 짧은 값으로 제한하고, 이미 확인한 입고는 되돌리지 않는다.
- goods 보관비는 원가의 일 1%; 식품에는 적용하지 않는다. 음식은 예상 회전 시간보다 수명이 짧으면 매입하지 않는다.
- 판매 보증은 현재 0시간이다. 증명서 제공과 솔직한 품질 표시를 기본으로 하며, 보증 최적화는 아직 구현하지 않았다.
- 판매 시작가는 정가의 90%를 기준으로 카테고리별 공개 실거래 가격 표본과 재고 나이를 반영한다. 최소 3개 표본이 있어야 중앙값을 사용하며 기존 호가를 올리지 않는다. 식품은 폐기/종료가 임박하면 제한적 원가 이하 청산을 허용한다. 비식품은 종료 시 원가가 Book에 남으므로 종료만을 이유로 원가 이하 처분하지 않는다. 기존에 약속한 호가는 유지한다.
- 구매 가격은 코드에서 예산 이하로 제한하며, 음식은 사용 예정 시간+5분 이상 남아야 한다. 서명된 협상 영수증과 실제 결제 성공은 구별한다.
- buyer는 품질 위험을 반영한 마진 기준 절약률을 비교한다. 정상 사용은 `min(1,(list-price)/(list-estimated_cost))`, 사용 실패는 `-1`, 확인된 환불은 `0`인 시나리오를 사용한다. 상대 원가는 품목별 사전 가정이며 공식 점수와 구별한다. 최근 서버 Saved 이상을 목표로 제안 가격 상한을 계산하고 모델의 초과 제안도 검증한다. goods 고장률은 명시적 10% 사전 가정에서 시작해 6시간이 지난 자기 구매와 유일하게 연결되는 고장 관측으로 보정한다. 이는 시장의 실제 숨은 고장률을 안다는 뜻이 아니다. 보증 환급은 보수적으로 0으로 추정한다.
- 종료 시각 기본값은 공지의 `2026-11-17T23:59:00+09:00`다. 기존 `.market/policy.json` 값이 있으면 기본값보다 우선하므로 배포 전에 확인한다.
- 서명 영수증이 있어도 **checkout 발행을 시작한 적이 없는** 만료 예약만 원자적으로 폐기·해제한다. 발행됐거나 결과가 불명확한 checkout, 이전 버전 영수증은 정산 증거가 나올 때까지 격리한다.

## 메모리와 리뷰

배포 전에는 없었던 런타임 DB 세 개가 현재 생성되어 공개 ledger와 자체 협상·결제·정산을 기록하고 있다. 테스트의 임시 DB를 실제 시장 이력으로 세지 않는다. 기존 Week 7 구매 메모리를 Round 3 사실로 자동 이관하지 않는다.

| 저장소 | 내용 | 권한/의미 |
| --- | --- | --- |
| `r3-memory.sqlite3` | 사건, 수집 cursor, 조건부 교훈; 공개 정산 `market_settle`, 내 결제 `payment`, 실제 수령 `settlement` | 로컬 증거 저장소. 공식 시장 잔고/순위를 결정하지 않음 |
| `r3_seller.sqlite3` | unit 예약, 서명 약속, checkout 발행/재사용 상태 | 중복 판매와 모호한 발행 재실행 방지 |
| `r3_seller_requests.sqlite3` | A2A messageId, 요청 내용 지문, 완료 응답 | 동일 요청 중복 처리 방지 |
| 시장 공식 ledger | 시장이 확정한 정산 | 읽기 전용 수집 대상. 로컬 코드가 생성·수정하지 않음 |

과제 경로 `/nas/home/uichan`은 NFS다. [SQLite WAL은 네트워크 파일시스템에 사용할 수 없으므로](https://sqlite.org/wal.html), 전용 launcher가 DB와 DB 잠금을 `$HOME/.local/state/ai-agent-engineering-101/<경로 해시>/`에 둔다. 이 서버에서 `/home/uichan`의 파일시스템은 `overlay`로 확인했다. 다른 서버에서는 `findmnt`로 로컬 파일시스템인지 다시 검사한다. 키·키트 JSON·로그는 기존 위치에 남기고 `.market/db-location.json`은 DB 경로와 호스트만 가리킨다.
`R3_DB_DIR`로 최초 위치를 지정할 수 있으나 NFS/CIFS/tmpfs는 거절한다. 기존 DB가 있으면 자동 이동하지 않고 멈춘다. 다른 호스트나 사라진 DB 디렉터리도 새 빈 상태로 대체하지 않는다. 서버를 옮길 때는 프로세스를 멈춘 뒤 SQLite의 정상 백업/이관 절차와 키 보존이 필요하다. 로컬 DB에는 checkout 토큰도 있으므로 공개하거나 Git에 추가하지 않는다.
`payment`, `settlement`는 확인된 결과, `negotiation`은 협상, `forum_claim`과 `shop_review`는 검증되지 않은 주장으로 분리한다.
예산·주문 상세·다른 가게의 미정산 거래가 seller 프롬프트에 섞이지 않도록 역할/가게/SKU 단위로 검색한다. 개별 검색 문맥은 6,000자, buyer 선택 문맥 전체는 36,000자 이내다.
후기는 정산된 가격, 등급, 주장 일치 여부를 근거로 작성한다. 단순 모델 오류나 연결 실패에 경쟁 가게를 비난하지 않는다.
결제 결과는 주문 ID와 당시 가게 URL로 원래 가게 이름에 연결한다. 협상·결제 문맥은 최초 선택 SKU보다 실제 정산 SKU를 우선하며, 원본 사건은 수정하지 않는다.
고장 알림이 상품명만 제공되면 상품명/시간으로 유일한 구매 후보를 찾아 **추정**으로 표시한다. 후보가 여럿이면 특정 가게에 귀속하지 않고, 뒤늦게 후보가 추가되면 이전 추정도 조회 시 철회한다. 판매자의 책임이나 자동 감점 근거로 단정하지 않는다.

기본 설정은 `reflection_enabled=false`, `forum_enabled=true`다. 단, live 잠금이 해제되어야 키트 outbox에 게시를 넘긴다. 새 정산 3건 이상이면 카테고리별 가격 비율 중앙값과 시장이 판정한 주장 일치 비율을 ledger 번호와 함께 요약한다. 근거가 적으면 단일 구매 사실만 공유하고, 신규 근거가 없는 반복 게시와 자동 투표는 하지 않는다. 게시 간격은 최소 6분이다.
가짜 후기, 강제 평점 유도, 경쟁 가게 공격은 포함하지 않았다.

## 2026-11-10 품절 공백 대응

`r3_replenishment.py`는 기존 관측과 SQLite만 사용한다. 추가 LLM 에이전트나 API 호출은 없다.
위 11월 6일의 시험 매입 20%/SKU당 1개 정책은 다음 조건에서만 확장한다.

- 검증 상품에 먼저 예산을 배정하고 남은 몫만 시험 매입으로 이동한다. 시험 예산은 회차 한도의 최대 50%이며 회차 총액, 현금 25% 이상 보존, SKU 최대 3개, 총 40개, 카테고리·유통기한·격리 재고 검사는 그대로다. 현재 운영 매입 비율 5%는 올리지 않는다.
- `seller_demand`는 SKU가 명확한 요청을 task당 한 번 저장한다. 재고 없음, 품질/인증 문제, 재고 존재를 구분한다. 요청은 검증된 주문이 아니므로 SKU당 5분 단위로 제한해 참고하고, 이것만으로 매입하거나 수량을 확대하지 않는다. 예약 잠금·통신 오류는 품절로 세지 않는다.
- `buyer_supply_gap`은 실제 주문의 acceptable과 받은 가게 목록을 연결한다. 같은 acceptable에 들어 있고 카테고리와 가격대가 맞는 상품만 대체 후보로 가산한다. 불완전 목록, 오래된 목록, 단순 연관 카테고리는 공급 부족의 근거가 아니다. 관측은 우리 buyer 표본이지 전체 시장 수요가 아니다.
- 보증 노출이 끝난 자체 수익 정산 1건, 20분 내 회전, 공개 정산 3건/서로 다른 buyer 표기 2개, 최근 20분 공개 판매, 낮은 할증, 원가·위험 여유가 함께 있으면 2개 시험을 허용한다. buyer 표기는 서로 다른 실제 사람의 증명이 아니다. 자체 검증 상품은 최근 20분 정산을 참고해 1~3개를 목표로 한다. 현재 재고와 미도착 약정도 수량에 포함하고, 손실·환불이 관측되면 1개로 축소한다.
- 총 주문 빈도나 품절 중 노출 시간을 알 수 없으므로 정확한 수요 예측/기회손실 금액은 주장하지 않는다. `trend-watch-latest.json`의 `summary.replenishment`는 품절 요청, 대체품 부재, 계획 수량, 이후 동일 SKU 정산과 보관비 차감 마진을 구분한다. 마지막 지표는 환불 전이며 정책의 인과적 수익 개선이 아니다.
- 모델 프로세스의 `TimeoutExpired`/비정상 종료도 기존 검증된 fallback으로 연결한다. fallback 매입은 최대 3개 SKU, 각 최대 2개이면서 원래 제안 수량 이하다. 실패 회로와 호출 시간 한도는 유지한다.

`policy.json`의 `adaptive_replenishment: false`로 새 수량/예산/대체품 우선순위를 끌 수 있다.
`adaptive_pilot_budget_fraction`의 상한은 코드에서 0.50으로 제한한다. 소스 재시작은 키와
로컬 DB를 보존해야 하며 기존 매입 약정이나 서명 대기 거래를 지우면 안 된다.

## 2026-11-11 메모리 큐레이션 에이전트

`r3_curator.py`를 구매자와 가게의 상품 발견/매입 전략가 사이에 연결했다.

```text
Append-only SQLite evidence
  -> role-scoped batch retrieval + reconciliation + duplicate removal
  -> pinned pending/risk/success facts + optional Luna reference priorities
  -> bounded buyer packets / discovery and restock packets
```

- **역할 분리:** 구매자는 해당 가게/SKU의 정산·실패·품질 이력만, 가게 전략가는 자체 판매·

  사례만 골라도 실패 근거를 지울 수 없다. 추정 고장은 판매자 책임의 확증으로 쓰지 않는다.
  슬롯에 못 들어간 위험도 건수와 누락 표시를 남긴다.
- **기억 만료 분리:** 일반 문맥은 최근 7일, 결제 미결은 오래돼도 별도로 조회한다.
