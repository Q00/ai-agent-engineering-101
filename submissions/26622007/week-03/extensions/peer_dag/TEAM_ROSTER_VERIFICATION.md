# 공통 팀 역할표와 협업 계획 규칙

2026-09-21. 구현 및 실호출 소스: `b880a70`.

모든 peer Worker의 propose/review/execute/synthesize 시스템 입력에 동일한 팀 역할표를 추가했다.
역할표는 기존 `contract_net.SKILLS`에서 생성한다.

| ID | 전문성 |
|---|---|
| A | 제품·기술: 오류 분석, 구현 의존성, 재현·회귀 테스트, 배포·롤백 판단 |
| B | 사업·분석: 수요, 손익, 불확실성, 사업 우선순위 분석 |
| C | 운영·커뮤니케이션: 고객 안내, 상담 절차, 팀 간 일정·담당·전달 계획 |

동료의 전문성을 참고해 하위 작업의 목표와 검증 기준을 구체화하고, 서로의 결과가 필요 없는 작업은
독립 steps로 분리하도록 안내한다. 결과 의존성은 depends_on, 자원 충돌은 reads/writes로 선언한다.
같은 Worker도 서로 다른 작업의 독립 세션에서 병렬 실행할 수 있다는 규칙을 함께 전달한다.
실제 배정은 기존 입찰·평가·선정 절차로 결정하며 역할 수에 맞춘 불필요한 분해는 하지 않도록 명시했다.

baseline/overconfident에는 위 전문성 정보를 전달한다. homogeneous에서는 본인의 역할 설명뿐 아니라
공통 역할표의 A/B/C도 모두 같은 범용 역할로 교체한다. 과신 지시는 C의 propose에만 적용한다.
역할표에 평가 정답, 다른 호출의 대화나 현재 부하, 확신도를 포함하지 않는다.
실행 설정에도 팀 역할표를 기록한다. 중단된 연구·메모리 확장의 프롬프트는 수정하지 않았다.

## 검증 결과

- 오프라인 테스트 71개(기본 20, peer DAG 34, 연구 확장 17) 통과.
- 모든 Worker·단계·조건에서 공통 역할표가 일치하는지, homogeneous에 전문성 정보가 남지 않는지 검사.
- 실제 직렬화 요청에서 역할표와 strict JSON Schema 전달을 검사.
- 실제 baseline 시도 `20260921-team-roster-live-1`: 요청 19개 모두 역할표·프롬프트·response_format 일치.
- 수신한 모델 응답 12개 모두 JSON Schema 검사 통과. 실행 추적 감사도 실패 전파를 포함해 통과.

채택된 실제 루트 계획에는 다음 행동이 포함됐다.

> 수익성 검토(P/Q 공헌이익, 월이익, 손익분기, 75%~125% 저/고 시나리오)를 B에게 위임
>
> 기술 위험 검토(마이그레이션 선행, 롤백·재시도 결제·취소 결제 미검증)를 A에게 위임

계획의 `profitability`와 `tech_risk`는 둘 다 선행 작업이 없고,
`release_recommendation`은 둘에 의존하도록 작성됐다. 실제 배정도 수익성 B, 기술 위험 A였다.
이는 역할을 반영한 계획 사례이며, 역할표 추가가 품질을 향상시켰다는 인과적 증거로 해석하지 않는다.

이번 실행은 Fireworks의 HTTP 429가 7회 발생해 **전체 실패**로 종료됐다.
수익성 검토만 완료됐고 기술 위험 검토가 실패해 후속 권고가 차단됐다.
최종 산출물이 없으므로 결과 검사는 0/12이며, 12개의 값이 각각 오답이었다는 뜻은 아니다.
실호출에서 도달하지 못한 synthesize 단계의 역할표 전달은 오프라인 전송 테스트로 확인했다.
실패 원본과 중간 결과를 보존했고 성공 실행으로 집계하지 않았다.
