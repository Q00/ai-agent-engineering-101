# 공통 역할표 적용 후 최종 실험 결과

2026-09-21 · 실행 배치 `20260921T093041-84990d` · 실행 소스 `5aa1a55`

**9회 중 8회가 완료되어 모두 12/12를 통과했다. 완료된 8회의 핵심 facts는 동일했지만 계획·담당 배정·최종 문장은 반복마다 달랐다.**
나머지 1회는 제공업체 HTTP 429로 수익성 작업이 실패했으며 최종 산출물이 없다. 실패를 제외하거나 성공 실행으로 대체하지 않았다.

필드 검사는 최종 산출물이 없는 1회를 0/12로 집계한다. 실제 12개 값이 모두 오답이었다는 뜻은 아니다. homogeneous 평균 시간에는 33.6초 만에 실패한 실행이 포함돼 있으므로 더 빠른 조건이라고 해석하지 않는다.
총 174개 모델 호출, 186개 HTTP 시도, 수신 응답 보고 비용 합계 **$0.120377046**이다. 응답 없는 요청의 실제 청구 여부는 이 로그로 확인할 수 없다. 실험 사이 대기를 포함한 전체 시간은 약 11분 16초이며 API 호출 시간만의 비교가 아니다.

## 무엇이 반복 가능했고 무엇이 달랐는가

- 완료된 8개 산출물의 필수 수치 10개 및 판단 2개는 모두 같고 정답과 일치했다. P/Q 월이익은 2,000,000/2,160,000원, 손익분기는 200/125명, 마이그레이션 선행 true, 현재 출시 가능 false다.
- 모든 조건에서 채택된 루트 계획은 각각 3종, 작업 ID별 담당 배정 맵도 각각 3종이었다. 이는 정확한 문자열·키 기준이며, 작업 ID나 문구만 달라도 다른 계획으로 센다. 의미상 모든 분해 방식이 다르다는 뜻은 아니다.
- 최종 산출물 전체(summary/facts/evidence)는 baseline 3종, homogeneous 2종, overconfident 3종이다. 완성된 8개 문서가 서로 완전히 동일하지 않았다.
- 실행 순서·자원 충돌·세션 격리·출력 형식은 코드로 제약했지만, LLM의 계획·점수·확신도·문장 선택은 여전히 달라졌다. 핵심 값의 반복 일치와 전체 시스템의 완전한 결정성은 다르다.
- 역할표만의 개선 효과는 측정하지 않았다. 과거 실험과 스키마·라우팅·동시성·프롬프트가 함께 달라졌으며, 역할표 유무만 비교한 대조군이 없다.

## 실제 병렬성과 재귀 깊이

성공한 8회 모두 입찰 단계뿐 아니라 실제 execute 분석 호출 2개가 겹쳤다. 이 두 작업은 모두 성공했고 최종 통합은 의존 작업 뒤에 실행됐다. HTTP 429로 실패한 마지막 실행은 실제 분석 호출이 겹치지 않았다.

|실행|동시 분석 담당|겹친 시간|
|---|---|---:|
|baseline 1|A + C|5.811273초|
|homogeneous 1|C + B|5.636875초|
|overconfident 1|A + C|6.383588초|
|homogeneous 2|B + C|6.073791초|
|overconfident 2|C + C|3.203729초|
|baseline 2|A + B|7.380320초|
|overconfident 3|C + C|7.222375초|
|baseline 3|C + A|4.335108초|

overconfident 2회차와 3회차에서는 **C가 맡은 독립 작업 두 개가 각각 3.204초, 7.222초 겹쳤다.** 같은 Worker 이름이 병렬 실행을 막지 않는다.
모든 실제 최대 깊이는 1이었다. max_depth=5는 상한으로 유지했지만 이 사례에서 깊이 2~5의 실제 재위임은 관찰하지 못했다. 또한 원래 과제 문장이 독립 검토 두 개와 후속 통합을 명시하므로, 역할표만 보고 병렬 구조를 새로 발견했다고 주장하지 않는다.

## 과신·제공업체 오류·산출물 품질

overconfident의 C는 유효 제안 12/12에서 confidence>=95로 입찰했고, 루트 3/3 및 전체 10/12를 맡았다. baseline C 배정은 4/12, homogeneous는 3/11이었다. 다만 하위 작업은 모델이 만들어 사전 gold가 없으므로 이 비율은 오배정률이 아니다. 표본도 작고 HTTP 429로 일부 후보가 빠져 과신 지시만의 효과로 단정하지 않는다.
HTTP 429는 총 16회(baseline 5, homogeneous 9, overconfident 2), 전송 오류/타임아웃은 1회였다. 오류 응답은 Fireworks 공유 제공업체 풀의 일시 제한을 명시했다. overconfident 2회차 전송 오류는 고정된 재시도 범위 안에서 회복했다. baseline 1회차 A/B 루트 입찰은 429로 거절되어 C만 남았다. 이를 순수한 계획 우수성으로 해석하면 안 된다.
실패한 homogeneous 3회차는 수익성 B의 execute에서 429가 두 번 발생했다. 해당 작업을 실패로 남기고 의존하는 출시 권고를 blocked 처리했으며 독립 기술 위험 검토는 C가 끝냈다. 없는 최종 결과를 만들어 성공 처리하지 않았다.
성공한 산출물은 계산식, 마이그레이션 선행, 세 미검증 테스트와 출시 보류를 설명했다. 그러나 baseline 3회차 summary에는 저수요 구간을 "고정비를 겨우 상회하는 취약 구간"으로 부르는 표현이 있다. 제시된 월이익은 이미 고정비 차감 후 값이므로 비교 대상이 모호하고, "겨우/취약"의 판단 기준도 주어지지 않았다. **12/12 통과는 summary의 모든 문장까지 검증한 결과가 아니다.** 원문은 수정하지 않았다.

## 검증과 재생

- 오프라인 회귀 테스트 73개 통과: 기본 20, peer DAG 36, 중단된 연구 확장 17. 실험 일정·실패 보존·소스 변경 차단 검사를 포함한다.
- 9회 모두 입력·설정·소스 고정 검사와 의존성·자원·예산·종료 상태 추적 감사를 통과했다. 실패 전파가 올바르면 추적 감사는 통과할 수 있으며 업무 성공과 다른 지표다.
- 실제 HTTP 요청 186개 모두 조건에 맞는 공통 역할표, 정확한 단계 프롬프트, strict JSON Schema 및 고정 전송 설정을 포함했다.
- 수신한 모델 응답 169개 모두 각 요청의 JSON Schema를 통과했다. HTTP 오류 16개 및 전송 오류 1개는 모델 JSON 응답이 아니다.
- 각 조건의 첫 실행을 응답 고정 후 parallel=1/3으로 각각 재생한 6회 모두 12/12, 원본 전체 산출물·담당 배정 일치, replay_complete=true를 확인했다. 실제 실행 호출 최고 동시성은 순차 1, 병렬 2였다.
- 재생은 새 API 호출 0회이며 인공 지연 100ms를 사용했다. 원래 HTTP 오류 상세나 지연은 재현하지 않고, baseline 1회차의 없는 응답은 없는 상태로 거절된다. 이 결과는 스케줄러의 반복 가능성을 확인하며 새 LLM 응답의 결정성이나 실제 속도 향상을 입증하지 않는다.
