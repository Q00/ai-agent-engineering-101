# HTTP 429 재시도 보강 후 homogeneous 재실행

2026-09-21. 실행 소스 `2046939`. [사전 규약](../RETRY_PROTOCOL.md).

**기존에 HTTP 429로 중단됐던 사례를 다시 실행해 모든 작업과 최종 산출물 생성을 완료했다.
다만 최종 정확도는 11/12이며, Q 고수요 월이익 계산 오류를 발견했다.**
이번에는 HTTP 429가 발생하지 않아 live의 재시도 횟수는 0이다. 전송 재시도 기능과 산출물 정확도를 구분한다.

## 재시도 변경

- 429는 최대 6회 시도. 기본 대기 15→30→60→60→60초.
- Retry-After가 있으면 초/HTTP 날짜를 해석해 서버의 최소 대기보다 빨리 요청하지 않는다.
- 누적 대기 상한은 300초. 초과 대기가 필요하면 실패를 명시하고 재요청하지 않는다.
- 일반 오류와 타임아웃은 기존 최대 2회. 인증 오류/미지원 스키마/잘못된 모델 JSON은 재시도하지 않는다.
- 같은 직렬화 요청을 재사용하며 response_format, 모델, 제공업체와 프롬프트를 바꾸지 않는다.
- 회귀 테스트 81개 통과: 연속 429 5회 뒤 성공, 정확한 요청 바이트 유지, Retry-After, 횟수·대기·HTTP 예산 종료 등을 확인했다.

## 새로 드러난 계산 오류

정답은 `(22000 - 6000) × (260 × 1.25) - 2000000 = 3200000`이다.
수익성 작업의 B가 `16000*325 - 2000000 = 3760000`으로 잘못 계산했고,
A의 출시 권고와 최종 통합이 같은 값을 그대로 전달했다. 3,760,000원은 정답보다 560,000원 크다.
나머지 11개 필수 값과 출시 보류 판단은 맞았다.

이 사례는 JSON Schema 준수·병렬 실행·LLM 통합 단계가 계산 정확성을 보장하지 않음을 보여준다.
평가 정답이나 원본 산출물을 바꾸지 않았으며, 정답이 나올 때까지 반복하는 추가 실행도 하지 않았다.
원래 9회 실험은 8/9 성공 기록으로 남기고, 이번 추가 실행은 수행 완료·정답 11/12로 별도 보존한다.
