# 재귀 Worker 세 조건 실험 사전 규약

실제 실행 전에 이 규약, 코드, 입력, 평가 기준을 커밋한다. 결과를 본 뒤 조건이나 정답을 바꾸지 않는다.

## 질문과 조건

같은 Plan-then-Execute·동료 선정·재귀 DAG 구조에서 전문성과 과신 지시만 바꾸었을 때
최종 결과 정확도, 배정 분포, 반복 일치, 호출 비용이 어떻게 달라지는지 측정한다.

- baseline: 기존 A 제품·기술, B 사업·분석, C 운영·커뮤니케이션.
- homogeneous: A/B/C의 전문성 문장만 모두 동일한 범용 역할로 교체한다. 모든 단계에 적용한다.
- overconfident: baseline과 같고 C의 propose 시스템 프롬프트 마지막에 항상 입찰하고 confidence>=95로 답하라는 문장만 추가한다.
- 모든 조건에서 confidence를 가린 계획 평가, 점수→confidence→고정 순환 동점 처리, 재귀 실행과 실패 전파는 그대로다.
- 원래 propose의 과장 금지 문장은 유지하므로 과신 지시와의 긴장이 있다. 실제 지시 준수 여부도 집계한다.

## 고정과 실행

- 동일 `case.json`의 합성 출시 검토 사례 하나를 각 조건에서 3회, 총 9회 실행한다. 새 대화와 새 Runtime을 사용하고 장기 메모리를 연결하지 않는다.
- 동일 `expected.json`의 12개 정답을 사후 평가에만 사용한다. 평가 정답은 모델에게 전달하지 않는다.
- 모델, temperature=0, 토큰 한도, 제공업체 라우팅, 요청자 A, max_depth=5, max_tasks=12, max_steps=4, max_calls=64, max_parallel=3을 고정한다.
- max_depth는 상한이다. 무의미한 분해를 강제하지 않고 실제 도달 깊이를 기록한다.
- 3개 블록에서 각 조건을 한 번씩 동시에 실행한다. 블록 내 시작 순서는 B/H/O, H/O/B, O/B/H로 순환한다. B=baseline, H=homogeneous, O=overconfident.
- 한 실행은 벽시계 600초로 제한한다. 초과 시 해당 실행을 종료하고 기존 원본과 종료 기록을 남긴다. 성공할 때까지 실행 횟수를 추가하지 않는다.
- 실제 제공업체는 자동 라우팅된다. 블록 내 공유 부하와 제공업체 차이 때문에 실행 시간의 차이를 구조의 속도 개선으로 단정하지 않는다.
- HTTP 재시도는 기존 설정의 최대 2회뿐이다. 파싱·평가 실패를 자동 수정하지 않는다.

## 측정과 한계

- 주 지표: 전체 검사 통과율(분모 3), 12개 facts 정확도(조건당 분모 36), 실패율.
- 보조 지표: 핵심 facts 벡터의 종류 수와 산출물 있는 실행 수, 작업·호출·계약 메시지 수, 실제 깊이, A/B/C 배정 수와 C의 루트 선정, C의 95 이상 유효 입찰 비율, 제안 거절·거부, 시간과 보고 비용.
- 계약 메시지 = propose 호출 시작 + propose 응답 + award. 평가·실행·통합은 모델 호출 수로 따로 센다.
- 하위 작업은 모델이 생성하므로 사전에 고정된 하위 gold가 없다. C의 배정 비율을 오배정률이나 전문성 적합률이라고 부르지 않는다.
- 산출물이 없으면 전체 검사 실패 및 필드 정답 0/12로 집계한다. facts 일치 계산에서는 제외하고 빠진 실행 수를 표시한다.
- 같은 오답도 반복 일치에 포함된다. 일치도와 정확도는 별도로 해석한다.
- 이 실험은 현재 재귀 구조의 확장 실험이다. 기본 Contract Net 필수 tasks.json/results.csv/logs와 합산하지 않는다.
