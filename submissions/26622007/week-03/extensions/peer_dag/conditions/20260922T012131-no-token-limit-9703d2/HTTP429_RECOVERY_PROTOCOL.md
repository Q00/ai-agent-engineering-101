# 본 실험 종료 후 429 실패의 별도 복구 확인

기존 사용자 지시인 "HTTP 429는 리트라이 처리해서 실패한거 다시"에 따라, 이번에도 요청별 6회 재시도를 소진한 실행의 복구 여부를 별도로 확인한다.
본 45회 결과와 원본 실패를 대체하지 않는다. 본 실험 성공률은 계속 최초 45개 슬롯을 분모로 한다.
이 문서와 실행기를 추가할 당시 26회가 끝났고 첫 회차의 growth-roadmap/launch-operations 세 조건씩 6회가 429로 실패한 상태였다.

- 본 45개 슬롯이 모두 끝난 뒤 시작한다. 동시에 같은 제공업체로 추가 실험을 돌리지 않는다.
- 선택 기준: 최종 오류가 `CallError: HTTP 429`이거나, `ValueError: no valid bids`이고 모든 제안 거절 원인이 HTTP 429인 실행.
- 31번째 실행에서 하위 작업의 429가 상위 의존성 실패로 전파된 사례를 관측해, 복구 시작 전 선택 규칙을 보완했다. 루트가 `child failed or blocked; partial results retained`이면 실제 하위 실패 원인이 모두 위 429 조건에 해당하는 경우만 포함한다. 내용 오류와 혼합된 실패는 제외한다.
- 위 조건에 맞는 모든 실패를 원래 스케줄 순서로 정확히 한 번씩 새 run_id로 실행한다. 내용 오답·JSON 오류는 이 복구 대상으로 골라내지 않는다.
- source_run_id와 새 ID를 대응표에 남긴다. 새 실행도 실패하면 그대로 보존하고 성공할 때까지 반복하지 않는다.
- 모델, provider, 모든 프롬프트, 작업/정답, response_format, max_depth/parallel, HTTP 재시도 설정은 본 실험과 동일하다. API 출력 토큰 상한은 넣지 않는다.
- 본 실험의 frozen_sources hash와 현재 설정을 매 실행 전에 대조한다. 코드·정답을 수정하지 않는다.
- 외부 실행은 직렬, 시작 전과 사이에 15초, 실행당 600초. 기존 요청별 429 최대 6회 정책도 동일하게 적용한다.
- `recovery_429/`의 별도 manifest·attempt·metrics·summary·콘솔과 기존 logs/runs의 새 ID로 증거를 보존한다.
- 보고에는 최초 45회와 별도 복구 실행의 결과를 각각 제시한다. 복구 결과로 조건별 통과율을 소급 수정하지 않는다.

실행: 이 폴더의 `recover_429.py`. API 호출이므로 본 실험 summary가 완성되지 않았거나 기존 복구 폴더가 있으면 시작하지 않는다.

## 준비 검사 이력

준비 커밋 `6c4bfed`의 메시지 중 "현재 6개 대상 선택 ... 오프라인 확인"은 잘못된 기술이다.
실제 첫 선택 검사에서는 6개 중 1개만 선택돼 AssertionError가 발생했다.
최종 오류에는 `CallError: HTTP 429`, proposal_rejected에는 `HTTP 429`가 저장되는 차이를 놓친 원인이며,
복구 API 호출 전에 실제 6개 기록을 사용하는 회귀 검사로 수정·검증한다. 기존 실패 증거와 커밋은 수정하지 않는다.
