# 같은 Worker의 독립 작업 병렬 실행

2026-09-21. 구현 소스: `596e1c4`. 성공 실호출 시점: `ae1dd2a`.

## 변경

기존에는 Worker C가 작업 두 개에 선정되면 C 전체의 잠금 때문에 순차 실행됐다.
이제 `(작업 ID, Worker)`별 잠금으로 서로 다른 작업의 C 호출을 병렬 실행한다.
각 호출의 시스템 역할은 C이지만 작업 입력과 두 메시지 문맥, API 클라이언트는 별개다.
진행 중 대화를 공유하지 않는다. 같은 작업·Worker 세션의 호출 중첩은 계속 금지한다.

전체 호출 상한 `max_parallel=3`, 깊이/호출 예산, 선행 의존성, 공유 자원 충돌 검사,
배정 점수·확신도 규칙, `response_format`은 유지했다. 연구·메모리 확장은 기존 순차 정책을 명시적으로 유지한다.
새 정책은 `concurrency_policy=task-worker-isolated-v1`로 기록하며, 감사기는 실제 `call_start`/`call_end`로
전체 및 Worker별 실행 동시성을 계산한다. 작업 준비 시점인 `execution_start`만으로 겹침을 판단하지 않는다.

## 검증

오프라인 테스트 70개(기본 20, peer DAG 33, 연구 확장 17)가 통과했다.
새 테스트는 같은 C의 독립 실행이 모두 시작돼야 완료되는 동기화 장벽을 사용한다.
공유 쓰기 자원이 충돌하거나 병렬도가 1이면 순차 실행하며,
후속 작업은 두 선행 결과를 받은 뒤 시작한다. 취소 후 잠금과 호출 슬롯의 반환도 확인했다.

기존 baseline 원본 `20260921-response-format-live-4`를 그대로 재생했다.
이는 LLM을 다시 호출하는 품질 실험이 아니라 같은 입력·응답에서 실행기 변경을 확인하는 검사다.

| 재생 병렬도 | C의 최대 동시 실행 | 결과 검사 | 추적 감사 |
|---|---:|---:|---|
| 1 | 1 | 12/12 | 통과 |
| 3 | 2 | 12/12 | 통과 |

실호출은 기존 `overconfident` 조건을 사용해 동일 C 배정 상황을 관찰했다.
첫 시도는 두 작업이 C에서 5.868674초 겹치고 각각 완료했으나,
후속 출시 권고 평가가 Fireworks의 HTTP 429 두 번으로 실패했다. 원본과 중간 결과를 보존했다.

두 번째 시도는 전체 흐름과 결과 12/12를 통과했다. 실행 구간은 한국시간 기준이다.

| 실제 작업 | Worker | 시작 | 종료 |
|---|---|---|---|
| 수익성 검토 | C | 18:07:20.308 | 18:07:28.115 |
| 기술 위험 검토 | C | 18:07:21.624 | 18:07:27.716 |

**실제 겹침은 6.092452초이며 C의 최대 동시 실행은 2다.**
모델 호출은 20회, HTTP는 재시도 포함 21회였고, 수신한 모델 응답 20개 모두 스키마 검사를 통과했다.
HTTP 429 한 번은 기존 제한 안에서 재시도해 회복했다. 최종 제공업체는 Fireworks였다.
이번 결과는 병렬 동작 확인이며, 다른 조건의 이전 실행과 소요 시간을 비교해 속도 향상률을 주장하지 않는다.
