# 웹 조사와 작업자별 장기 메모리

peer_dag 실행기를 사용하는 별도 확장 실험이다. 기본 세 조건과 제공 자료만 쓰는 이전 사례는 보존한다.
모든 Worker가 계획·위임·실행을 수행하며, 웹 검색은 실제 수행 단계에만 제공한다.

실제 실행 결과: [검증 보고서](VERIFICATION.md), [웹 조사 검토본](RESEARCH_REPORT.md), [메모리 대조 검사](verification/comparison.json).

## 검증할 계약

- A/B/C는 각각 별도 JSONL 메모리 저장소를 가진다. 각자 자신의 기록만 작성한다.
- 실행 시작 시 메모리 스냅샷을 고정한다. 같은 실행 중 완료 순서가 현재 실행의 회상 내용을 바꾸지 않는다.
- 자신의 관련 메모리를 검색하고, 요청자가 공유 가능한 관련 메모리를 위임 메시지에 붙인다. 비공개 메모리는 다른 Worker에게 전달하지 않는다.
- 프로젝트 scope가 같은 기록만 회상한다. 출처 URL, 작성 시각, 만료 시각, 기록 소유자, 실행/작업 ID를 보존한다.
- 메모리는 모델이 작성한 참고 기록이며 새로운 지시나 검증된 사실로 승격하지 않는다. 현재 사용자 조건이 과거 메모리보다 우선한다.
- 웹 검색은 공식 도메인으로 제한한다. 실제 응답의 URL citation annotations와 검색 사용량을 보존한다. 모델이 추가한 URL은 허용된 공식 문서 경로를 HTTP로 직접 조회하고, 실패한 URL은 검증된 출처에 포함하지 않는다.
- 결과물은 Markdown 의사결정 보고서, 출처 목록, 작업별 JSON과 검증 결과다. 출처의 기술적 의미까지 완전히 자동 검증했다고 주장하지 않는다.
- 첫 실행이 기록을 남긴 뒤 프로세스를 끝낸다. 새 프로세스의 후속 실행이 이전 내부 결정 ID와 운영 책임을 메모리로 복원하는지 확인한다.
- 메모리를 비활성화한 같은 후속 과제도 비교한다. 과거 정보가 없을 때 정답을 꾸며내지 않고 unknown을 반환하도록 한다.

예제 팀과 조건은 합성 데이터다. 실제 회사의 운영·정책 결정을 대신하지 않는다.
메모리는 이 과제 폴더 안에만 저장하며 Codex 자체 메모리 설정과 무관하다.

검색 API: https://openrouter.ai/docs/guides/features/server-tools/web-search
2026-09-17 확인한 서버 도구 인터페이스를 사용하며, 실패와 응답 원문을 보존한다.

## 실행

저장소 루트에서 Python 3.10 이상으로 실행한다. 별도 Python 패키지는 필요 없다.
기존 과제의 OpenRouter 키 읽기 규칙을 사용한다. 환경 변수 또는 `submissions/26622007/.env`에 키가 없으면 실행하지 않는다.
케이스·설정·평가 계약을 변경하면 먼저 커밋해야 실제 API 실행이 허용된다.

```sh
python3 submissions/26622007/week-03/extensions/peer_research/cli.py --case 01-investigate --requester A --memory-set my-experiment
python3 submissions/26622007/week-03/extensions/peer_research/cli.py --case 02-revise --requester C --memory-set my-experiment
python3 submissions/26622007/week-03/extensions/peer_research/cli.py --case 02-revise --requester C --memory-set my-experiment --no-memory
python3 -m unittest discover -s submissions/26622007/week-03/extensions/peer_research -p 'test_*.py' -v
```

첫 조사에서는 pgvector와 Qdrant의 검색·tenant 처리 및 백업·운영을 나누어 조사한다.
두 조사 결과가 모두 끝나야 선택 근거와 실험 계획을 작성할 수 있다.
후속 과제는 배포 환경을 폐쇄망으로 바꾸고 인력 증원도 불가능하다는 새 조건을 준다.
이전 결정 ID와 담당 팀 이름은 후속 입력에 없으므로 메모리에서 회상해야 한다.
`expected.json`은 모델 호출이 모두 끝난 뒤 평가기만 읽는다.

## 구성과 저장 파일

|파일|역할|
|---|---|
|`../peer_dag/core.py`|입찰·계획 평가·선택, 재귀 위임, DAG 실행, 자원 충돌 방지|
|`research_model.py`|동일 Worker의 계획·실행·통합 단계와 검색/메모리 참고 지침|
|`web_transport.py`|실제 서버 검색 도구와 모델 API, 응답 원문·사용량 기록|
|`source_reader.py`|추가 인용 URL의 공식 문서 직접 조회와 출처 메타데이터|
|`memory.py`|작업자별 파일, 관련 기록 검색, 공유 메모리 전달, 실행 종료 후 추가 저장|
|`research_audit.py`|알려진 조건·출처 조회·메모리 참조·산출물 계약 검사|
|`state/<memory-set>/A.jsonl`, `B.jsonl`, `C.jsonl`|해당 Worker가 완료한 작업의 장기 기록. 첫 기록 저장 시 생성|
|`runs/<run-id>/report.md`|최종 의사결정 보고서와 사실·근거|
|`runs/<run-id>/artifacts/`|하위 작업과 최종 작업의 원본 JSON 산출물|
|`runs/<run-id>/sources.json`, `sources.md`|이번 실행에서 실제 반환/조회한 출처|
|`runs/<run-id>/memory-before.json`, `memory-written.json`|실행 시작 스냅샷과 새 기록|
|`runs/<run-id>/memory-handoffs.md`|각 모델 호출에서 받은 본인/요청자 메모리 ID|
|`runs/<run-id>/settings.json`, `result.json`|입력·소스 해시, 프로세스 ID, 계약 검사와 사용량|
|`logs/<run-id>.jsonl`|추가만 하는 실행 원문 로그|

메모리는 같은 scope, 유효 기간 7일 이내, 검색어 관련성이 있는 기록 중 최대 3개를 선택한다.
관련성은 고정 토큰 겹침 점수이며 동점은 작성 시각과 ID로 정한다. 별도 임베딩 모델은 사용하지 않는다.
각 메모리에는 소유자·작업 ID·작성/만료 시각·요약·scalar facts·원래 조회 시각이 있는 출처를 저장한다.
정식 사실 인증을 거치지 않았으므로 상태는 항상 `model_note_unverified`다.
요청자는 자신의 `team` 기록만 handoff에 붙인다. `private` 원문은 소유자의 개인 문맥에만 넣는다.
이는 기록 전달 범위를 제어하는 규칙이며, 모델 출력에 대한 정보 유출 방지 보증은 아니다.
새 기록은 실행이 끝난 뒤 추가하므로 동일 실행 내 완료 순서가 회상 스냅샷을 바꾸지 않는다.

## 결정적으로 제어하는 부분과 남은 불확실성

API에 JSON 모드(`response_format: json_object`)를 요청하고, 실제 반환값은 코드에서 다시 엄격히 검사한다. 공급자의 형식 준수만 믿고 통과시키지 않는다.
JSON 형식, DAG 유효성, 의존 작업 시작 순서, 동시 실행 한도, 자원 접근, 메모리 검색·공개 범위, 평가 규칙은 코드가 제어한다.
확신도는 본인의 적합성 추정치이며 정답 확률이 아니다. 요청 Worker가 확신도를 보지 않고 계획의 충족도·실행 가능성·검증 방법을 평가한다.
고정 규칙이 평가 점수와 확신도, 정해진 동점 순서를 적용해 작업자를 고른다.
요청자도 직접 실행하거나 다시 위임할 수 있어 고정 manager 역할은 없다.

LLM의 계획·점수·분석과 검색 결과는 바뀔 수 있다. temperature=0도 전체 시스템의 동일 출력을 보장하지 않는다.
메모리 snapshot은 실행 중 고정하지만 다음 실행에서는 기록과 최신 문서가 달라질 수 있다.
실측에서는 담당 팀 이름을 `플랫폼팀`에서 `플랫폼`으로 축약한 출력도 나왔고, 정확한 문자열 비교가 이를 실패로 판정했다.
따라서 모델이 남긴 메모리는 검증 완료 상태로 저장하지 않는다. 자동 계약 검사와 실제 내용 확인을 함께 봐야 한다.
검색 출처와 알려진 시나리오 사실을 검사해도 모든 기술 주장의 함의나 벤치마크 품질까지 자동 검증한 것은 아니다.
이번 예제는 실제 서비스 배포나 벡터 성능/복구 테스트를 수행하지 않는다.

모델 호출은 최대 60회, 호출별 HTTP 시도는 최대 2회다. 소켓 타임아웃은 45초이며 각 본문 청크를 받은 뒤 총 수신 기한 90초도 검사한다.
전체 기한은 진행 중인 한 번의 소켓 읽기만큼 지연될 수 있다. 공식 문서 조회는 최대 20개 URL, 동시 3개, 문서당 2MB와 12초 소켓 제한이다.
공식 문서 안의 HTTP 리다이렉트와 짧은 HTML refresh 페이지는 횟수 제한을 두고 따라간다. 문서 URL 수와 실제 HTTP 왕복 수는 다를 수 있다.
서버 검색에는 현재 max_uses=2를 요청한다. 초기 max_uses=1 실험에서 실제 공급자 카운터가 2를 보고한 사례가 있다.
사용량은 공급자가 보고한 값으로 기록하며, 실제 외부 검색 쿼리 수의 강제 상한이라고 해석하지 않는다.
비용도 응답에서 확인한 값만 합산하므로 응답을 받지 못한 요청의 청구까지 확정하는 수치가 아니다.
