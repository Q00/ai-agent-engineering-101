# 복합 작업 5개: 사전 작업 설계 v2

2026-09-21. 사용자가 게임 기획과 코드 구조 설계를 함께 수행하는 큰 작업을 요청해 목록을 개편했다.
강의 README의 조건은 **최소 5개**이며 이번 목록은 정확히 5개다. 모두 합성 자료이며 실제 고객·거래·운영 기록이 아니다.
새 목록의 실제 API 비교 실험은 아직 수행하지 않았다.

|ID|작업|gold|최초 책임 분야를 정한 이유|
|---|---|---|---|
|release-review|출시 수익성·기술 위험 통합 검토|B|손익 비교를 포함한 출시 의사결정 자료 통합|
|game-design-architecture|게임 기획·코드 구조·테스트·개발 일정|A|게임 규칙을 코드 및 검증 가능한 인터페이스로 연결|
|payment-redesign|결제 중복 방지·코드 구조·온라인 전환|A|경쟁 요청·상태 전이·마이그레이션·기술 검증 설계|
|growth-roadmap|서비스 확장 손익·MVP 범위·개발 로드맵|B|수요 불확실성·수익·개발 예산으로 대안 비교|
|launch-operations|운영 일정·상담 용량·안내문·비상 계획|C|확정 정책 아래 팀 간 인계·일정·고객 안내 조율|

gold는 기본 Contract Net에서 최초 책임자의 역할 적합도를 측정하는 사전 기준이다.
복합 작업은 다른 역할도 기여할 수 있어 gold가 유일한 유능한 작업자를 뜻하지 않는다.
peer DAG 하위 작업은 계획이 생성하므로 사후에 하위 작업별 gold를 붙이지 않는다.
실행 결과를 보고 gold를 바꾸지 않으며 이 문서와 gold는 모델에게 전달하지 않는다.

## 동일 작업 목록의 두 실행 방식

- `tasks.json`: 강의의 id/desc/gold 계약. 기본 `run.py`는 작업 수행 없이 세 후보의 입찰·배정을 측정한다.
- `extensions/peer_dag/cases/catalog.json`: 같은 ID와 설명의 실제 계획·위임·실행·통합 사례.
  사례별 `case.json`은 공개 요구사항, `expected.json`은 실행 뒤 평가에만 쓰는 값이다.
- 작업 선택 및 실행 명령과 정성 평가 기준은 [복합 작업 안내](extensions/peer_dag/cases/README.md)에 있다.
- 기존 출시 검토는 작은 비교 기준으로 그대로 유지했다. 새로운 4개 작업은 산출물 범위를 늘렸지만 분해 깊이나 특정 DAG를 강제하지 않는다.

## 평가의 한계와 이력

정해진 계산 결과와 제약의 facts 검사는 게임 재미, 설계 완성도, 코드의 실행 가능성을 자동 검증하지 않는다.
기획·모듈·테스트·일정의 일관성은 원문 산출물을 별도로 검토한다. 실제 구현·테스트 실행을 했다고 간주하지 않는다.

기존 6개 출시 업무와 설계 문서는 [launch-v1](task_sets/launch-v1/)에 바이트 그대로 보존했다.
기존 results.csv와 로그·REPORT는 수정하지 않았다. 새 tasks.json은 새로운 입력 해시와 experiment_id로 실행되므로
이전 6개 작업 결과와 같은 실험으로 합산하지 않는다. 새로운 세 조건 비교 시 같은 5개 작업·프롬프트·모델·설정을 고정해야 한다.
