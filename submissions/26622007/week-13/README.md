## 다시 돌려 보는 법

Python 3.10 이상, 표준 라이브러리만 쓴다. 이 폴더에서 실행한다.

```bash
# 제출한 기록을 재생해 검사한다. 문제가 없으면 종료 코드 0
python verify.py --head 27ea7446a7f1e7d3a9eb0bc28a6f67f0b0bcb6b1173a5782d29800402fb5a09c
python -m unittest -v test_week13        # 시험 49개
python trade.py trade                    # 새 거래 1건을 기록 끝에 덧붙인다
python trade.py trade --qty 3            # 30,000 > auto_limit 20,000 → y/n을 묻는다
python trade.py refund --contract <id>   # 정산된 거래를 환불한다
python trade.py status
```

`--head`는 기록 마지막 줄의 해시다. 주지 않아도 돌지만, 그러면 끝에서 잘려 나간 줄은 알아채지 못한다. 라우팅은 기록 안에 적힌 mandate가 아니라 이 폴더의 `mandate.json`으로 다시 판정한다.

`trade.py`는 기록 파일 끝에 줄을 덧붙이기만 한다. 제출한 기록을 그대로 두고 싶으면 `--record /tmp/x.jsonl`을 준다.

## 제출물 1: 끝까지 간 거래

계약 `ctr-20261124T112722Z-9327`. 과제가 요구한 다섯 가지가 기록에 이 순서로 있다.

| 순서 | 과제 항목 | 줄(seq) | 내용 |
|---|---|---|---|
| (1) | 협상 합의문 | 1 `negotiation` | 판매자 12,000에서 시작, 유저 7,200에서 시작, 5번째 차례에 10,000으로 합의. 주고받은 제안 전부와 합의문 |
| (2) | 계약 wrapper | 2 `contract` | `meshkit.transaction-contract/v1`. `body`, `hash`, `auth_tags`(유저·판매자). `body.negotiation_hash`가 1번 줄의 제안 목록을 가리킨다 |
| | 상태 | 3 `state` | 없음 → created |
| (3) | 라우팅 판정 | 4 `routing` | `auto`. 10,000 ≤ auto_limit 20,000이고 nocha12가 trusted에 있다. 판정에 쓴 mandate가 같이 적혀 있다 |
| | 상태 | 5 `state` | created → paid |
| (4) | 장부 항목과 잔고 | 6 `ledger` | user −10,000 / seller +9,700 / platform +300, 잔고 합 0 |
| (5) | 정산 이벤트 | 7 `event` | `meshkit.transaction-event/v1`, `settled`, `contract_id`, `contract_hash`, `platform_auth_tag` |
| | 상태 | 8 `state` | paid → settled |

W13 코드는 계약을 고치지 않는다. 계약 wrapper는 2번 줄에 한 번 적히고, 그 뒤의 이벤트는 계약 ID와 해시만 가리킨다.

## 제출물 2: 환불

계약 `ctr-20261124T112757Z-6c08`(쌀 5kg, 17,000). 24~31번 줄에서 정산까지 갔고, 32~35번 줄이 환불이다.

| 줄(seq) | 내용 |
|---|---|
| 29 `ledger` | 원 결제: user −17,000 / seller +16,490 / platform +510. **환불 뒤에도 그대로 남아 있다** |
| 32 `ledger` | 환불: 같은 txn으로 user +17,000 / seller −16,490 / platform −510. 잔고 합 0 |
| 33 `event` | `meshkit.transaction-event/v1`, `refunded`. 정산 이벤트의 태그(`refunds_event_tag`)를 가리킨다 |
| 34 `refund_check` | 검산 한 줄 |
| 35 `state` | settled → refunded |

검산 한 줄 (`logs/run-10-refund.txt`):

```
[check] user -40000 -> -40000, seller 38800 -> 38800, match=True
```

이 거래 전에 정산된 거래가 2건 있어서 "거래 전 잔고"가 0이 아니다. 유저와 판매자 잔고가 환불 뒤에 이 거래 전 값으로 돌아왔다.

거래와 환불 사이에 다른 거래가 정산되면 두 숫자가 그대로 같을 수 없다. 그때는 그 사이 다른 거래가 움직인 금액을 따로 적고, 그만큼을 빼고 비교한다. 44~47번 줄이 그 경우다(계약 `…-d51e`, 30,000. 그 뒤에 34,000짜리 거래가 정산됐다. `logs/run-14-refund-older-trade.txt`):

```
[check] user -10000 -> -44000, seller 9700 -> 42680 (other trades since: user -34000, seller +32980), match=True
```

같은 거래를 한 번 더 환불하면 상태 기계가 막는다 (`logs/run-11-refund-again-refused.txt`):

```
refused: ctr-20261124T112757Z-6c08: refunded -> refunded is not allowed
```

## 상태 기계

```
(없음) → created → paid → settled → refunded
            ↓
        cancelled
```

표에 없는 이동은 `IllegalTransition`으로 거부한다. 정산된 거래를 cancelled로 되돌릴 수 없고, 취소된 거래나 이미 환불된 거래는 환불할 수 없다. 이 모의 레이어에서는 결제와 정산이 한 단계(`settle_and_receipt`)라서 환불은 settled에서만 한다.

## 제3자가 확인하는 것 (`verify.py`)

- 줄 번호가 이어지고, 줄마다 앞 줄 해시를 가리키며, 줄 해시가 내용과 맞는다.
- `--head`를 주면 마지막 줄 해시가 그 값과 같다.
- 계약 해시가 `body`와 맞고, 양쪽 인증 태그가 맞고, 계약이 기록된 흥정을 가리키며, 합의문의 금액·당사자·문장이 계약과 같다.
- 라우팅에 쓴 mandate가 공개한 `mandate.json`과 같고, 판정이 그 mandate로 다시 계산한 값과 같다. confirm이면 사람의 `y`가 있어야 paid로 간다.
- 장부 항목이 계약 금액과 수수료 3%로 계산한 값과 같고, 정수이며, 합이 0이고, 적힌 잔고가 항목의 합과 같다.
- 이벤트가 계약 ID와 해시를 가리키고 플랫폼 태그가 맞다.
- 상태 이동이 표에 있는 것뿐이다. 거래마다 결제 장부 줄과 settled 이벤트가 정확히 한 번씩 있다. refunded가 되려면 그 거래 자신의 환불 장부 줄, refunded 이벤트, 검산 줄이 한 번씩 있어야 한다. 환불 항목은 원 결제의 정확한 반대다. 검산 줄이 재생한 값과 같다. "그 사이 다른 거래"는 `trade.py`와 같이 이 거래의 결제 장부 줄 다음부터 센다.

해시 체인까지 다시 맞춘 위조도 잡는지 시험했다: 계약 금액 변경, 합의문 바꿔 쓰기, 장부 항목 변경, 이벤트 금액 변경, `n` 답 뒤 결제, 기록 안의 mandate 바꾸기, mandate와 다른 라우팅, 환불 장부 줄 삭제, 결제 장부 줄·settled 이벤트를 두 번 넣고 다른 거래의 환불을 끼워 refunded로 꾸민 기록, 자기 환불 줄 없이 refunded로 옮긴 기록, 허용되지 않는 상태 이동, 끝에서 잘라 내기(`--head`가 있을 때) (`test_week13.py`의 `Replay`).

## 한계

- **흥정은 LLM이 아니라 규칙이다.** 판매자는 정가에서 500씩 내리고 바닥가 아래로 가지 않는다. 유저는 정가의 60%에서 700씩 올리고 예산을 넘지 않는다. 로그만으로 같은 결과가 다시 나오게 하려고 이렇게 했다. Round 4의 내 가게 에이전트와 연결한 것은 아니다(round-4는 별도 제출이고 이 PR에는 없다). 판매자 이름만 같은 `nocha12`를 썼다.
- **HMAC은 부인 방지가 아니다.** 유저·판매자·플랫폼 태그 모두 데모용 공유 키로 만든다. 키를 아는 쪽이 만들었고 그 뒤 바뀌지 않았다는 것까지만 보여 준다. 누가 서명했는지는 증명하지 못한다. 공개키 서명은 하지 않았다.
- **해시 체인은 혼자서 위조를 막지 못한다.** 파일을 통째로 다시 쓰면 체인은 맞출 수 있다. 그 경우는 계약 해시, 플랫폼 태그, 금액 재계산이 잡는다. 다만 데모 키가 코드에 있어서, 키까지 써서 전부 다시 만든 기록은 가려낼 수 없다.
- **기록을 통째로 지우거나 끝을 자르는 것은 `--head` 없이는 못 잡는다.** 거래 하나를 통째로 빼고 뒤의 잔고 숫자를 다시 맞춘 기록도 체인은 통과한다. 그래서 마지막 줄 해시를 이 문서와 커밋에 적었다.
- **사람의 y/n 답에는 태그가 없다.** 답을 `n`에서 `y`로 바꾸고 플랫폼 데모 키로 정산 이벤트를 새로 만들면 가려낼 수 없다.
- **쓰는 쪽은 하나라고 가정한다.** 잠금이 없어서 `trade.py`를 동시에 두 개 돌리면 줄 번호가 겹친다. 거래 도중 프로세스가 죽으면 그 거래는 paid에서 멈춘 채 남고 `verify.py`가 문제로 보고한다. 결제는 됐는데 정산이 안 된 거래를 정상으로 보이게 하지 않으려는 것이다. 이어서 마무리하는 기능은 없다.
- **사람 확인의 y/n은 사람이 친 것이 아니다.** 제출한 실행에서는 `printf 'y\n' |`로 넣었다. 터미널에서 직접 돌리면 프롬프트가 뜬다.
- **선택 심화(Maroo testnet 실제 전송)는 하지 않았다.** 금액은 모두 메모리 장부의 숫자다. Round 4 가게의 실제 체인 결제 기록은 round-4 별도 제출에서 따로 다룬다(이 PR에는 없다).
- 금액과 품목은 예시다.

## 반복 시간, 폐기율, 인간 개입

- **반복 시간.** 거래 1건은 시작부터 판정까지 0.001~0.005초(각 `run-*.txt` 마지막 줄). 코드 쪽은 첫 커밋 20:23:44에서 흥정을 고친 커밋 20:27:57까지 약 4분이다. 시험과 구현은 같은 커밋에 들어 있다(계약, 거래, 재생 검사, 흥정 수정 순서).
- **폐기율.** 기록에 쓰는 명령(거래 7번, 환불 5번) 12번 가운데 3번을 버렸다(3/12).
  - `run-02`: 쌀 5kg 거래가 합의 없이 끝났다. 바닥가 15,000 < 예산 17,000인데 흥정이 10번째 차례에서 멈췄다(17,500 대 17,000).
  - `run-03`, `run-04`: 그 거래를 환불하려다 거부됐다. 환불할 거래가 없었다.
  - 원인은 흥정 횟수 상한이었다. 시험을 먼저 추가하고(`test_a_wide_gap_still_closes_...`) 고친 뒤 `run-09`부터 다시 돌렸다. 실패한 출력과 기록 9번 줄은 지우지 않았다. `run-02`와 `run-07`의 마지막 차례가 20으로 찍힌 것도 그때의 버그다(지금은 마지막 제안의 다음 차례).
  - 의도한 거절은 버린 것으로 세지 않았다: `run-05`(n → 취소), `run-07`(예산이 바닥가보다 낮음), `run-11`(두 번째 환불).
  - 커밋에 남지 않은 폐기 1건: `verify.py` 첫 초안은 거래별로 줄을 모아 검사했는데, 환불이 나중에 오면 잔고 순서가 틀어져서 커밋 전에 줄 순서대로 재생하는 방식으로 다시 썼다.
- **인간 개입.** 작업 중 사람이 멈추거나 고치거나 승인한 일은 없다. 사람이 한 것은 시작 지시 하나다(11/24 20:21 "week-13 페이지를 보고 안 된 작업이 있으면 하라").

## LLM 도구 사용

이 폴더의 코드, 시험, 실행, 이 문서는 LLM 에이전트(Claude Fable 5.2, OpenClaw)가 썼다. 시킨 일은 week-13 페이지의 과제 요구를 뽑고, `mock_payment.py`를 고치지 않은 채 거래 1건과 환불 1건을 재생할 수 있는 기록으로 남기는 것이다. 버린 것은 위 폐기율 항목에 있다. 리뷰도 LLM 에이전트가 했다. 커밋은 작업 단위마다 나눴고 합치지 않았다.
