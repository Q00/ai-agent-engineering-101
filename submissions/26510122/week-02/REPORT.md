## 3. 해석

이번 조건에서는 ReAct가 성공률에서 우세했다. logs/react-05~07.txt에서 read_file 한 번 뒤 14:00을 답한다. 3022자의 입력 전체가 4000자 읽기 제한 안에 들어가 추가 count_pattern 없이 답할 수 있었다. 반면 logs/plan_exec-08~10.txt는 첫 응답이 JSON 목록이 아닌 설명문이라 실행 단계 전에 실패했다. 따라서 계획 방식의 낮은 토큰·반복은 효율적 해결이 아니라 **초기 파싱 실패를 복구하지 않는 오류 처리와 즉시 종료 조건**의 결과다. 도구 단위와 개입에는 측정상 차이가 없었고, 계획·실행 문맥 분리의 실제 비용은 계획 실행에 도달하지 못해 평가할 수 없다. 응답 예산 2048토큰도 출력 형식에 영향을 주었을 가능성이 있으나 종료 사유를 따로 수집하지 않아 단정할 수 없다. 제한 없는 파일럿 4행은 유효한 4단계 계획을 만들었지만 두 번째 실행 단계 응답 대기에서 수동 중단되어 주 비교에서 제외했다. 각 3회·단일 모델·고정 실행 순서이므로 일반화는 제한되며, 더 큰 동일 응답 예산이나 초기 계획 검증·재시도를 넣은 후속 비교가 필요하다.
