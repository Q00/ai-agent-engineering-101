# 실험 과정

- Codex와 함께 시작 코드를 읽고 실험을 준비했다. TASK.md와 원본 app.log는 실험 전 커밋 9e00637에 고정했다.
- 두 하네스와 공통 도구는 시작 코드 그대로 비교한다. API 제공자만 OpenRouter로 설정하며 모델은 nvidia/nemotron-3.5-lightning:free로 동일하게 고정한다.
- ReAct는 전체 대화 기록으로 다음 행동을 결정한다. Plan-then-Execute는 별도 계획 대화와 실행 대화를 사용하며 재계획은 최대 1번이다.
- 공통 도구는 읽기 전용이라 두 방식 모두 사람 개입은 0으로 예상된다.
- 저장소 루트 .env를 값 출력 없이 읽는 실행 파일을 추가했다. 두 하네스의 코드, 입력, 성공 판정은 수정하지 않았다.

## ReAct 실행 관찰

- run 1~3 모두 14:00으로 성공. 모델 응답은 각 2회, 토큰은 3589 / 3912 / 3975, 개입은 모두 0.
- 세 실행 모두 read_file 한 번만 호출하고 모델이 시간별 ERROR를 직접 집계했다. count_pattern은 사용하지 않았다.
- 원본 로그는 3022바이트의 ASCII 텍스트로 4000자 읽기 제한 안에 들어갔다. 직접 집계한 정답은 14:00의 ERROR 6개다. 이 검산은 모델에 제공하지 않았다.
- 실행 순서는 시작 코드의 고정 순서이므로 공급자 부하 변화와 순서 효과가 섞일 수 있다.

## 중단과 계측 개선

- 원본 실행기의 Plan-then-Execute 첫 실행이 단계 2의 HTTP 응답 대기에서 장시간 정지해 SIGINT로 중단했다. 성공으로 처리하지 않았다. 원본 실행기는 실행 종료 전에 로그를 디스크에 쓰지 않으므로 전체 로그를 회수하지 못했다. 관찰한 출력과 중단 사실만 plan_exec-04.txt에 부분 기록임을 명시해 남겼다. CSV 4행의 토큰·반복은 미상이며 0이 아니다. 중단 개입 1회는 하네스 도구 승인과 별도로 발생했다.
- 기존 1~4행은 파일럿으로 보존하고, 새 비교 코호트에서는 양쪽 모두 응답 최대 2048토큰, 실행당 벽시계 180초 제한을 적용한다. 모델·도구·문제와 두 하네스 자체는 유지한다. 실시간 로그와 완료된 응답의 부분 계측을 보존하도록 공통 실행기를 수정한다.
- 개선 실행기는 임시 디렉터리의 모의 성공/시간초과 실행으로 검증했다. 실패를 X로 저장하고 부분 토큰·호출과 실시간 로그를 보존함을 확인했다. 모의 결과는 제출 CSV/로그에 넣지 않았다.
