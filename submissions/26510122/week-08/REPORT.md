## (1) 부품별 설계

### 1.1 모델: 선택은 모델이 하고, 실행 조건은 코드가 검사한다

운영 모델은 **`gpt-5.6-luna`**다. `harness.py`가 각 판단에 필요한 JSON을 준비하고 Codex CLI를 일회성으로 호출한다. seller의 최초 가격·맞제안·거절, buyer의 가게·품목 선택과 협상, 매입 승인, 포럼 문구와 느린 정책 검토에 사용한다. 운영 buyer는 시장이 발급한 주문을 처리하는 plain 모드이며, 역할극이나 자체 주문 생성은 활성화하지 않았다.

| 판단 위치 | 모델이 결정하는 것 | 코드가 맡는 것 |
|---|---|---|
| seller | 판매 단위, 호가, 수락·맞제안·거절 | 실제 재고·예약 확인, 가격 하한, 조건 검증, 영수증 발행 |
| buyer | 허용 후보 중 선택, 최초 제안, 협상·중단 | 예산·기한·등급·인증서·보증 검사, 결제 권한 확인 |
| 매입 | 계산된 후보의 수요·가격 가설과 매입 승인 또는 보류 | 수량 계산, 잔액·노출·미확정 매입 예약·창 시간 재확인 |
| 선제 행동·메타 검토 | 근거가 있는 글, 제한된 정책 변경 제안 | 게시 응답 확인, 변경 폭·평가 기간·효과 검사 |

`decide_json()`은 출력 스키마를 지정하고, 모델 입력·응답·소요 시간을 기록한다. 호출의 기본 제한은 60초다. 대화 전체를 계속 이어 붙이는 대신 필요한 상태를 매번 구성한다. 임시 작업 폴더와 읽기 전용 실행 설정을 사용하지만, 이것만으로 모델의 모든 도구 호출이 기술적으로 제거된다고 주장하지는 않는다. 외부 글은 데이터로 취급하라는 지시와 실제 실행 전 검사를 함께 사용한다.

형식에 맞는 JSON도 잘못된 단위나 가격을 담을 수 있다. 따라서 유효한 단위인지, 이미 팔렸는지, 가격이 허용 범위인지 다시 확인한다. 모델의 답과 보정·차단된 실행은 `decision_proposed`, `decision_guard`, `decision_executed`로 구분한다. **모델 응답이나 영수증 서명 자체를 정산 성공으로 세지 않는다.**

근거 코드: `harness.py`, `agent.json`, `seller_r3.py`, `market_buyer_r3.py`, `buyer_r3.py`, `decision_audit.py`, `ops/buyer_service.py`.

### 1.2 컨텍스트: 원본은 보존하고 다음 판단에 필요한 근거만 가져온다

메모리는 모델 가중치를 갱신하는 방식이 아니다. 원본 JSONL은 덧붙여 보존하고, SQLite 인덱스와 계산된 요약을 통해 다음 판단에 필요한 사례를 읽는다. 현재 주문·재고 사실과 과거의 추정을 분리한다.

| 메모리 / 요약 | 다음 판단에 들어가는 정보 | 제한 또는 검증 |
|---|---|---|
| 짧은 거래 기억 | 최근 사례와 다른 결과를 낸 대조 사례, 등급별 가격 범위 | 대표 사례 최대 3개, 협상 최근 4턴 |
| buyer 입력 | 후보별 가격·위험·과거 결과 | 전체 입력 32,000 UTF-8 바이트, 기본 기억 3,200바이트 |
| seller 입력 | 동일 품목·등급의 제안·정산, 반복 상대의 근거 | 과거 기억 3,600바이트, 불확실한 신원은 확정하지 않음 |
| checkout 기억 | 같은 가게·SKU의 품절·조건 거절 | 정해진 재확인 조건과 TTL, 새 가격·재고·보증이면 다시 검토 |
| 성숙 구매 조합 | 가게·SKU·식품 사용 기간별 구매 후 고장·환불 | 6시간 5분~48시간 전 정산, 불명확한 결과는 unknown |

이 제한은 **토큰 수가 아니라 직렬화한 UTF-8 바이트 수**다. 사례를 제거할 때에도 전체 관측 수와 가격 범위 요약은 유지한다. 외부 게시글이나 상대의 메시지를 상위 지시로 올리지 않는다.

최근 추가한 `buyer_cohort.py`는 구매 후 시간이 지난 결과를 묶는다. 충분히 관측된 조합은 기존 16개 후보 중 최대 4자리를 우선 배정할 수 있다. 표본 5건 이상, unknown 없음, 현재 Saved를 기준으로 한 prior 10의 축소 추정에서 0.015 초과 우위가 있어야 한다. 가게당 후보 제한과 적격 가게·SKU 쌍에 대한 **10% 무작위 탐색**은 유지한다. 추정이 나쁜 조합도 무조건 금지하지 않고 가격이나 보증이 개선되면 다시 본다.

조합 캐시는 별도 작업이 300초마다 갱신한다. 주문 처리 중에는 이미 만들어진 캐시만 읽고, 900초보다 오래됐거나 잘못된 캐시는 일반 선택으로 돌아간다. 키트의 고장 알림과 공개 원장의 주문·SKU를 대조하며, 상대를 특정할 수 없는 알림을 임의의 가게에 붙이지 않는다.

데이터 보존 과정에서 로그 파일 세대가 바뀔 수 있다. SQLite의 과거 세대까지 합하면 같은 정산을 중복 집계하게 된다. 보고서 집계는 현재 원본의 장치·inode와 세대·오프셋을 확인하고, 인덱스 경계의 실제 원문까지 대조한 뒤 미반영 꼬리를 읽었다. 이는 운영 DB를 교체하거나 과거 기록을 지우는 작업과 다르다.

근거 코드: `context_compaction.py`, `buyer_memory.py`, `buyer_logdb.py`, `buyer_checkout_memory.py`, `buyer_breakage.py`, `buyer_cohort.py`, `buyer_exploration.py`, `seller_state.py`.

### 1.3 툴: 가격 계산, 매입 준비, 실제 결과 검증을 분리한다

여기서 툴은 직접 구현한 Python 계산·검증 함수다. 모델이 임의로 MCP 서버를 호출하는 구조는 아니다. 하네스가 계산 결과를 준비해 모델에 전달하고, 모델이 선택한 행동을 코드가 검증해 실행한다.

**seller 가격·재고.** 판매 가격은 원가, 보관·보증 비용, 비교 가능한 거래와 재고를 갖고 있을 때의 Book 가치를 함께 본다. 유통기한이 넉넉한 재고는 원가와 누적 보관 비용을 보호하는 하한을 적용한다. 임박 식품의 손실 허용은 별도 조건이며 모든 상품을 같은 할인율로 처리하지 않는다. 단위별 SQLite 예약과 정산 단위 목록을 통해 이미 정산된 재고의 영수증 재발행을 막는다. 협상 예약은 만료·취소·영수증 보류를 구분하며, 서명 후에는 원래 결제 조건과 기한을 임의로 연장하지 않는다.

**매입.** `newsvendor_tool.py`와 포트폴리오 도구는 수요 가설, 품목 노출, 보관·유통기한, 매입 급증 비용을 반영한 수량 후보를 계산한다. 모델의 수요값은 관측된 확률분포가 아니라 가설이다. 실제 판매·이익 근거가 있는 중가 품목을 보충하되, 정가가 아니라 **실제 정산 가격대**로 성과를 확인한다. 미확정 매입은 전송되지 않았다는 근거 없이 풀지 않는다.

매입 창 직전에는 모델 승인과 계산을 준비하고, 창이 열리면 새 잔액·재고·예약·카탈로그·시간을 재검사해 기존 키트의 매입 프로토콜로 보낸다. 준비와 실행의 잠금을 분리했고, 승인 만료와 내용 해시를 둔다. 따라서 느린 모델 호출 때문에 짧은 매입 창을 놓치는 문제를 줄이면서 중복 전송을 방지한다. 기존 재고와 매입 의도 원장은 유지한다.

**buyer 가격·위험.** 시세 참고선과 Saved 목표 가격을 따로 계산한다. 시세는 상대가 받아들일 가능성의 근거이고, Saved 가격은 품목을 정상 사용한다는 조건의 목표다. 여기에 같은 가게·품목의 검증된 고장과 환불, 가격·보증 조건을 반영한다. 조건을 만족할 수 없으면 협상을 중단하고 다른 후보로 이동한다. 시간이 충분할 때 1차 협상은 최대 80초로 제한하고 대체 가게에 필요한 시간을 남긴다. 최종 가격과 영수증의 가격·SKU·등급·인증서·보증을 다시 검사한다. open mandate 상한을 넘는 checkout은 완료하지 않는다.

**선제 행동.** seller는 찾는 글과 실제 보유 재고를 맞춰 조건·유효기한이 있는 견적을 만들고, buyer는 검증된 정산 원장을 인용하는 구매 기록을 게시한다. 상대 buyer의 목표는 광고 문구를 읽는 것이 아니라 구매 가능한 조건을 확인하는 것이다. 잘못된 견적은 예약 시간과 평판을 소모하므로, 게시 성공 ACK와 실제 정산은 별개로 추적한다. seller 메타 검토도 제한된 설정만 제안하며, 변경 후 최소 2시간과 성숙 판매 20건의 평가 조건을 둔다. 현재 제약에 잘려 아무 효과가 없는 변경은 보류한다.

주요 구현: `economy_r3.py`, `seller_quality.py`, `seller_warranty.py`, `newsvendor_tool.py`, `inventory_portfolio.py`, `procurement_scheduler.py`, `procurement_audit.py`, `buyer_value.py`, `seller_forum.py`, `buyer_forum.py`, `seller_meta.py`, `meta_effects.py`.

### 1.4 점수와 경제적 목표

현재 코드의 점수 계약은 `market_scoring.py`에 모았다. Shop ALL은 Book·매출·평점 백분위의 0.5/0.3/0.2 가중합이다. Buyer ALL은 Saved 백분위 0.5, 포럼 평점 원값 0.3, 정산 수 백분위 0.1, 게시글 수 백분위 0.1이다. Players Class는 가게나 buyer 표 한쪽 순위가 아니라 학생끼리 다시 계산한 종합 결과를 본다.

Book은 `현금 잔액 - 시작 자금 - 파산 주입금 + 미판매 재고 원가`다. 원가로 재고를 매입하면 최초에는 현금이 재고로 바뀌므로 Book이 바로 이익만큼 늘지는 않는다. 보관·폐기·판매 차익·환불을 함께 봐야 한다.

패치 3.6의 정상 사용 거래 기여값은 `min(1, (정가-결제가)/(정가-판매자 원가))`이며, 사용 불가 거래는 -1, 환불되면 0이다. 누적 Saved는 거래 기여 합을 `정산 수+100`으로 나눈다. **buyer는 판매자 개별 원가를 모르므로 정상 거래의 실제 기여를 정확히 계산할 수 없다.** 품목 평균 원가를 사용한 값은 시나리오이고, 등급별 원가 범위로 구한 값도 경계다. 공식 Saved와 같은 값으로 보고하지 않는다.

## (2) 아키텍처와 키트 기본형과의 차이

[한 페이지 그림 PDF](architecture.pdf) · [LaTeX 원본](architecture.tex)

그림의 주 흐름은 `시장 근거 → 제한된 컨텍스트와 계산 결과 → 모델의 JSON 선택 → 실행 검사 → 실제 결과`다. 결과는 원본 로그·SQLite와 성숙 조합으로 돌아간다. 주문 응답 경로와 느린 매입 준비·메타 검토·조합 갱신을 분리했다.

| 키트가 제공하는 영역 | 이번에 추가한 영역 | 의미 |
|---|---|---|
| 시장 연결·신원·서명·결제·동기화 | 근거를 고르는 하네스와 단발성 구조화 판단 | 모델이 볼 수 있는 사실과 실행 권한 분리 |
| 주문·재고·게시판 파일 | 바이트 예산 기억, 세대 검증 SQLite 인덱스 | 긴 원본 전체를 매 턴 넣거나 중복 집계하지 않음 |
| 기본 협상·checkout 흐름 | 원가·위험 가격 도구, 영수증 재검사, 예약 영속화 | 합의처럼 보이는 응답과 유효한 정산 구분 |
| 입고 프로토콜 | 창 전 승인과 창 안 재검사·실행 | 모델 지연을 줄이되 예약·예산 검증 유지 |
| 과거 정산 기록 | 주문·결정·시도 ID와 고장·환불까지의 연결 | 성공 사례만 기억하지 않고 실제 후속 손실 반영 |

독창성은 키트의 결제 부분을 다시 만드는 데 있지 않다. 모델 판단 앞에는 경제 계산과 검증된 기억을, 뒤에는 실제 실행 검사를 둔 점이다. 다만 규칙과 기억을 추가하는 것만으로 모델의 거래 품질이 좋아졌다고 주장할 수는 없다. 아래의 같은 시간 비교에서는 Saved 개선을 확인하지 못한 경우도 남겼다. 선택 과제인 `acp.json` 기반 툴 자동 생성이나 Round 4의 `forge_tool`을 구현했다고 주장하지 않는다.

운영은 buyer와 seller를 별도 서비스로 유지하고 해시가 검증된 고정 릴리스를 사용한다. 터널 갱신이나 프로세스 교체가 기존 DB·재고·매입 예약을 초기화하지 않도록 했다. 이번 보고서 작성은 읽기 전용 집계와 문서·그림 추가이며, 실행 중 정책을 재배포하지 않았다.

도입 전보다 우선 조합 정산은 **26.9% 증가**했지만 전체 정산은 **3.2% 감소**했다. 실제로 앞쪽에 노출된 긍정 조합을 모델이 선택하고 그 가게·SKU에서 정산한 사례는 26건이었다. 이 기능이 없던 과거의 우선 노출 플래그를 0으로 놓고 증가율을 만들지는 않았다.

비교의 한계도 있다. 직전 시간은 구·신 정책이 섞였다. 도입 전 Saved 시작 관측은 시간 경계보다 28.18초 뒤의 공식 캐시값이므로 정확히 경계에서 읽은 값이 아니다. 52조합은 추가 관찰 시작에 고정한 목록으로 과거 구간에도 동일하게 적용했으나, 일부 고장 관측은 과거 구간 뒤에 도착했다. 따라서 무작위 대조 실험이나 인과적 개선으로 해석할 수 없다. 이 시간에 들어온 고장 알림 6건은 모두 이전 정책의 구매분이었다. 새 구매의 품질은 6시간 이후까지 관찰해야 한다.

상세 결과·공개 원장 매칭·보존 점검은 `snapshot.json`의 `fixed_hour_experiment`에 포함했다. 그 관찰의 기존 DB·매입·원가 하한·예산·보증·탐색 정책 보존 검사는 모두 통과했다.

### 3.5 실패 기록, 검증과 남은 한계

1. **가격 툴을 만들어도 실제 호출 경로에 연결되지 않으면 효과가 없다.** 11월 17일 첫 통합에서는 `purchase_value_terms`가 협상 메모리에서 빠져 가격 제한과 빠른 중단이 의도대로 작동하지 않았다. 최초 관찰과 실패 로그를 남기고 호출 경계 회귀 검증 후 수정했다. 수정 후 같은 30분 비교에서도 정산은 38→37건, Saved 변화는 양쪽 0이었다. 이익이 입증된 수정으로 포장하지 않았다. [이전 실험 근거](logs/report-round3-20261117-verified/prior-experiments.json)를 함께 보존했다.
2. **근거를 추가하다 후보를 줄이는 역효과가 있었다.** 성숙 조합을 넣은 최초 전체 테스트는 623개 중 1개가 실패했다. 같은 위험 정보를 반복해 넣으면서 16개 후보가 15개로 줄었다. 중복 정보와 선택용 문맥을 줄인 뒤, 성숙 근거가 있는 경우와 없는 경우 모두 16개를 유지하도록 수정했다.
3. **보고서 집계도 실패할 수 있다.** 최초 캡처는 점수 없는 비활성 행의 `all` 필드를 바로 읽다가 중단됐다. [최초 오류](logs/report-round3-initial-capture-20261117.log)를 보존하고, 누락 점수를 0으로 취급하도록 진단 코드만 고쳤다. 과거 로그 세대 중복도 제외했다. 운영 정책은 바꾸지 않았다.

운영 릴리스 `f6729ad`의 당시 전체 검증은 **625개 통과**다. [최초 문맥 실패 로그](logs/buyer-cohort-full-tests-initial-20261117.log)와 [625개 통과 로그](logs/buyer-cohort-full-tests-release-verified-20261117.log)를 함께 보존했다. 이 테스트는 상태·경계·실행 검증이 중심이며 모델 응답을 모의하는 경우가 많다. 따라서 모델의 최적 가격 판단이나 장기 수익을 검증한 수치가 아니다. 11월 22일 제출 전 재검사에서는 실제 날짜 때문에 종료된 시장을 매입 가능하다고 가정한 테스트 10개가 먼저 실패했다. 시험 전용 48시간 기간을 둔 뒤 공유 픽스처의 종료 시각 참조 1개도 맞췄고, **전체 625개가 다시 통과**했다. [최초 실패](logs/submission-full-tests-20261122.log), [공유 종료 참조 실패](logs/submission-full-tests-fixed-clock-20261122.log), [최종 통과](logs/submission-full-tests-verified-20261122.log)를 모두 보존했다. 운영 코드·실제 종료 상수·DB는 바꾸지 않았다.

현재 남은 과제는 buyer에서 좋은 조건의 정산을 **구매 후 손실까지 포함한 Saved**로 연결하는 것이다. 조합 노출이 늘어도 실제 가격·보증·상대 재고와 주문 구성이 바뀐다. 6시간 후 결과, unknown 비율, 같은 시간의 정산과 공식 Saved를 함께 봐야 한다. 포럼도 게시 수 증가만으로 신규 첫 정산의 원인이라고 할 수 없다.
