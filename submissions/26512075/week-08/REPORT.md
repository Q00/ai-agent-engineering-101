### 1.1 어떤 모델을 어디에 사용하는가

`agent.json`과 `harness/model_decisions.py`의 기본 협상 모델은 Codex CLI의 `gpt-6.1-terra`이다. TypeScript buyer는 Python 하네스를 호출하고, 요청마다 예산, 현재 호가, 대화, 리뷰, 확인된 가격 비교 자료를 전달한다.

모델 출력은 가격과 행동을 포함하는 구조화된 JSON으로 받는다. 예산 초과, 잘못된 가격, 합의와 다른 영수증은 코드에서 거절한다. Seller의 현재 회전 판매 모드는 첫 호가를 원가 기반 하한에 맞추며, 숫자 제안이 이미 호가를 충족한 경우 등은 결정적 검증으로 처리한다. 모든 거래 판단에 모델을 호출한다고 주장하지 않는다.

| 사용 위치 | 모델/실행 방식 | 전달 정보와 반환값 | 코드가 책임지는 부분 |
|---|---|---|---|
| Buyer 가격 제안 | `harnessBridge.ts` → `harness/decide.py` → `model_decisions.py`; 기본 Codex CLI / `gpt-6.1-terra` | 예산·현재 호가·대화·최근 리뷰·정산 근거 → 행동·가격 JSON | 구조 검사, 예산·기한 제한, 영수증 검증 |
| Seller의 비정형 협상 판단 | `seller.py`의 하네스 호출을 `seller_r3.py`가 사용 | 상품·제안·가격 하한·대화 → offer/accept/reject 및 가격 | 가용 재고·정책 하한·서명·상태 전이 확인 |
| 선택 가능한 API 경로 | `HARNESS_BACKEND=openai`, OpenAI Responses API, 모델은 `OPENAI_MODEL` 지정 | 같은 요청 컨텍스트 → 구조화한 응답 | CLI와 동일한 후속 검증; 실제 운영 모델명은 설정에 따라 달라짐 |

모델 호출마다 별도 하네스 실행으로 요청을 분리하며 CLI 타임아웃을 둔다. 상품 선택·재고 검사·숫자 제안 수락 등 규칙으로 가능한 경로는 모델 없이 처리한다. 모델이 스스로 툴이나 프롬프트를 재작성하는 meta-harness는 구현하지 않았다. 여기서 하네스는 모델 호출·출력 해석·시간 제한을 담당하는 실행 계층이다. 기본 설정은 확인했지만 모든 운영 호출의 실제 모델 버전을 전수 기록한 근거는 없다.

Saved 패치에 맞춰 `(정가-결제가)/(정가-실제 원가)`의 상한 1을 협상 컨텍스트에 설명한다. 상품군 평균 원가 비율은 참고 시나리오일 뿐 개별 원가나 정확한 점수가 아니다. 쓸모없는 구매 -1, 환불 0과 구매 조건을 함께 고려하도록 한다.

### 1.2 컨텍스트·메모리를 어떻게 관리하는가

| 수명 | 저장/구성 위치 | 다음 판단에 쓰는 방법 |
|---|---|---|
| 현재 요청 | 주문·예산·재고·최근 대화·선택 상점 리뷰를 JSON으로 구성 | 해당 협상의 모델 입력에 필요한 조건을 전달 |
| 협상 진행 상태 | Redis task/deal, 기본 TTL 30일; Redis 미설정 시 메모리 | 같은 task의 상태·버전을 다시 읽어 후속 협상 처리. 예약은 별도 메모리 |
| 주문 사이 기억 | `buyer_memory.json`, 결제·구매 관측 JSONL | 정산 여부·재고 거절·확인 가능한 고장을 연결해 후보 점수와 다음 컨텍스트에 반영 |
| 공개 관측 근거 | 게시판·원장 수집 SQLite 및 후보 파일 | 등급·보증·관측기간이 맞는 가격 자료만 참고; 자료 부족 시 기존 선택 유지 |

기존 `buyer_memory.json`은 가게 이름, 품목, 협상 가격, 협상 결과, 영수증 불일치 여부, 시각을 저장했다. 가게 URL이 바뀌어도 같은 이름의 이력을 사용한다. 그러나 협상 완료는 실제 결제 완료와 다르며, 기존 기억에는 결제 후 결과를 보정하는 연결이 없었다.

현재 구현은 새 기록에 주문 ID, 거래 당시 가게 URL, 선택 SKU를 추가한다. 다음 buyer 실행 시 `payments.jsonl`과 주문 ID·가게 URL을 대조하여 `paymentStatus`, `ledger`, `paymentReason`을 보정한다. 상충하는 기록은 추측하지 않는다. 최근 가게별 결과는 협상 하네스에도 전달한다. 반복 실행은 같은 거래를 새 거래로 추가하지 않는다.

가게 선택은 리뷰 평균·영수증 불일치·기존 오류 cooldown을 유지하면서, 최근 20회 자기 거래의 연결된 고장 1건당 1점, 명시적 재고 없음 결제 거절 1건당 0.5점을 감점한다. 이는 임시 정책 계수이며 성능 개선이 입증된 최적값은 아니다. API 오류나 일반적인 결제 거절을 부정직한 판매자의 증거로 취급하지 않는다. 식품 수명 부족 등의 거부 사유는 하네스 컨텍스트로 전달한다.

### 고장·보증 추적

`review` 훅 `tracking/record_buyer_purchase.py`는 kit가 정산 후 전달하는 `deal.json`의 `settled` 정보를 `.market/buyer-purchases.jsonl`에 기록한다. 주문, ledger, 가게 URL, SKU, unit, 상품명, 등급, 보증 시간, 관측 시각을 보존한다. ledger 기준으로 중복 기록을 막고 `{}`를 출력하므로 기존 buyer의 별점·리뷰를 바꾸지 않는다.

`broken.jsonl`에는 이름과 고장 시각만 있다. 최근 6시간 안에 같은 이름의 정산 구매가 유일한 경우에만 기억에 연결한다. 추적 시작 후 첫 6시간, 동일 이름의 복수 구매, 거래 연결 실패는 미확인으로 남긴다. 훅 관측 시각은 정확한 시장 정산 시각과 다를 수 있으며, 이름·시간 연결은 추론이다. `warrantyEligible`은 보증 대상일 가능성의 추정이고 실제 환불 완료를 의미하지 않는다. 환불 확인 피드는 아직 연결하지 않았다.

과거 기억은 주문 ID와 보증 정보가 부족하다. 이번 변경으로 과거 모든 구매와 고장을 소급 복구했다고 주장하지 않는다. 훅 수집 누락과 미확인 고장은 운영 로그에서 계속 확인해야 한다.

### 1.3 어떤 툴을 어떻게 만들었는가

아래 툴은 자유로운 텍스트 지시를 그대로 실행하는 대신 Python 함수·CLI 훅·큐 처리기로 만들고, 입력과 실행 조건을 코드로 검사한다.

| 툴/구현 | 입력 → 출력 | 실행 전후 검증 |

| 게시판·원장 분석 (`buyer-forum/analyst.py`) | 공개 ledger·게시글 → SQLite 관측·후보 파일 | cursor 추격과 3시간 관측을 따로 검사; 오래된 자료 구분 |
| 광고 검토·전송 (`advertise_bc_once.py`, `publisher.py`, `shop_ads.py`) | 상품·가격·재고 검토 → 승인 큐·전송 결과 | seller의 가격 하한·가용 재고·최신성, 중복·게시 간격 검사 |

| 협상 상태 저장·관측 (`storage.py`, `storage_audit.py`) | task/deal → Redis 상태·작업 결과 로그 | task 버전 충돌·TTL·terminal 정리; 로그에서 접속 정보·협상 본문 제외 |

인증·ACP/AP2 checkout·시장 정산은 기본 키트의 기능을 사용한다. 제출 코드가 이를 모두 새로 구현했다고 주장하지 않는다. `review` 훅은 작업 폴더의 `agent.json`에 등록돼 있으나, 마지막 점검 커밋의 등록 누락은 부록 A에 구분한다.

`restock/restock_policy.py`가 재고·카탈로그·관측 정산·공급 시간으로 매입안을 만들고, `SupplyGuard`가 최신 재고를 다시 읽어 실행 전에 검증한다. 현금 유보, 전체 구매 상한, 품목·범주·총 재고 제한, 공급 시간, 보관비와 미해결 구매 의도를 확인한다. 관측된 판매와 미검증 탐색 매입을 구분한다.

현재 `restock/small_batch.json`은 최대 재고 50개, SKU당 1개, 범주당 3개, 한 번에 최대 1개 매입안을 설정한다. `purchase_budget`과 `exploration_budget`은 모두 `null`로 고정 누적 예산 상한을 해제한 상태다. 그렇다고 현금 유보와 재고 제한까지 없어진 것은 아니다. `reserve_floor=600000`, `reserve_fraction=0.6`, `spend_fraction=0.2`를 별도로 적용한다. 과거의 1,000,000/500,000 고정 상한을 현재 설정으로 기재하지 않는다. Commitment는 보수적 예약액으로 실제 지출과 다르다. `food_life_hours_by_sku`가 비어 있어 식품 신규 매입은 제외한다. 만료 재고를 살아 있는 재고에서 제외하고 일반 상품 보관비를 예산에서 유보한다.

2026-11-16  `.market/restock-paused.json`을 생성했다. `restock_policy.py`는 이 파일이 있으면 `{"buy": []}`를 반환한다. Guard는 훅이 허용한 SKU와 최신 계산안을 교집합으로 제한하므로 빈 구매안은 매입을 막는다. `logs/restock-paused-20261116.log`에 `operator_paused` 검증 결과가 있다. `supply_closed`는 공급창이 닫혔다는 뜻이고, `restock_shortage`는 내부 계획 사유이므로 실제 구매 완료 증거로 세지 않는다.

현재 `seller/strategy.py`의 가격 하한은 A등급 `ceil(원가 × 2.00)`, B/C등급 `ceil(원가 × 1.06)`이다. 회전 판매 모드에서는 이 하한을 첫 호가에도 적용하며 보증은 0시간이다. 보관비는 별도로 가격에 가산하지 않는다. `advertise_a_after_bc.py`와 `resume_a_ads.py`의 A등급 검증 배수도 200%로 맞췄다. 새 광고 7건에서 실제 가격이 원가의 2배임을 확인했다. 이는 상품 원가 자체를 바꾼 것이 아니라 판매가격 정책 변경이다. 실행 중 객체는 코드·설정 변경을 자동으로 다시 읽지 않으므로 일반적으로 재시작 후 검증해야 한다.

Buyer는 식품을 구매할 수 있다. 식품 재입고 금지는 seller 재고 정책이고, buyer의 식품 주문 처리는 별개이다. Buyer는 주문의 acceptable SKU, 예산, 사용기한을 확인하고 kit의 checkout 전 accept 검사에 전달한다.

## 2. 아키텍처 figure의 구조와 기본 키트와의 차이

구조도는 [LaTeX 소스](architecture.tex)와 [빌드된 PDF](logs/architecture-build-20261117T143642/architecture.pdf)로 제공한다. [빌드 로그](logs/architecture-build-20261117T143642/architecture.log)에 1페이지 생성이 기록돼 있다.

- **상단:** 시장과 기본 키트가 외부 주문·결제·최종 정산의 기준을 제공한다.
- **중단:** TypeScript Buyer와 Python Seller·하네스·검증 툴이 선택, 제안, 검증, 실행을 분담한다.
- **하단:** Redis는 진행 상태, SQLite·파일은 장기 근거와 결과 기억을 보존한다. 결과는 다음 주문의 후보와 협상 컨텍스트로 돌아간다.
- **화살표:** 실선은 요청·판단·상태 저장/조회, 녹색 점선은 근거·기억 피드백이다. Redis 운영 저장·조회가 확인돼 적용 대기 표시를 제거했다.

이 배치는 실제 웹앱 서비스 배포에서 모델·API·저장소의 책임을 나누려는 설계다. 현재 ASGI 진입점은 협상 API이며, 시장 거래 전체는 키트의 결제 경로와 연결된다. 전체 서비스 배포 완료를 의미하지 않는다.

실제 흐름은 다음과 같다.

1. 시장 주문·상점·재고 스냅샷 → kit → buyer/seller/restock.
2. buyer 기억 + 이전 결제 결과 + 게시판 후보 → 상점/SKU 선택 → 모델 협상 → 코드 검증.
3. kit의 ACP/AP2 결제 → 시장 정산 → payments 기록 + review 훅 구매 관측.
4. 다음 buyer 실행에서 정산·고장 결과를 기억에 연결하여 선택과 협상에 반영.
5. seller 정산 관측 → 재입고 판매 이력 → 다음 매입안 및 실행 전 재검증.

기본 키트가 담당하는 인증·결제·시장 통신 위에, 독립적인 기억 보정과 재입고 검증을 붙인 구조이다. 공개 체결가는 현재 구매 가능한 가격과 구분한다. 외부 텍스트는 모델 컨텍스트에 포함될 수 있으므로, 프롬프트 주입에 대한 완전한 방어를 검증한 근거는 없다.

### 기본형 대비 추가한 구조와 선택 이유

| 경계 | 기본 키트가 맡는 부분 | 제출 코드에서 추가한 부분 | 의도와 한계 |
|---|---|---|---|
| 거래 실행 | 인증·시장 통신·ACP/AP2 결제·정산 | 결과를 다음 선택에 연결하는 기억 보정 | 협상 성공만으로 구매 성공을 학습하지 않음 |
| 협상 상태 | 요청을 agent 명령/endpoint에 전달 | Redis task/deal 저장 경로, 버전 검사·TTL | 11/17 운영 seller의 Redis 저장·조회 성공 확인; 재시작 복구·실제 동시 쓰기 충돌 시험 근거 없음 |
| 실패 후 행동 | 주문과 후보 스냅샷 제공 | SKU별 재고 거절 cooldown·대체 상점·시간 예산 | 반복 실패 완화, timeout 후 중복 시도 방지 |
| 가격 근거 | 상점 정보·공개 원장 접근 | 등급·보증별 체결 자료와 정산 이력 | 다른 조건의 가격을 섞지 않으며 표본 부족 시 fallback |
| 재고/광고 | 공급·판매·게시 API | 구매안 재검증, operator pause, 광고 승인·전송 기록 | 가격·재고 일치와 중복 방지; stale 상태의 광고 재개는 시간상 미구현 |

구조도의 상단은 외부 시장과 kit의 책임, 중단은 모델·Buyer·Seller·툴, 하단은 상태·관측 저장소다. Redis는 협상 상태를, SQLite는 분석·광고 이력을, JSON/JSONL은 주문 사이 기억과 운영 증거를 맡는다. 저장소를 나눈 이유는 수명과 검증 기준이 다르기 때문이다. 이 분리는 상태 복구·정산 귀속을 명확히 하지만, 저장소 전체에 걸친 단일 트랜잭션을 제공하지는 않는다.

### 게시판 수집과 한계

`buyer-forum/analyst.py`가 `forum.json`과 공개 ledger를 읽고 SQLite에 보존한다. 후보 보고서 `forum-candidates.json`을 만들고 buyer의 `forumSelection.ts`가 참조한다. SKU별 거래량·게시판 언급과, 등급·보증별 가격 비교 자료를 구분한다. 자료가 오래됐거나 관측 범위가 불충분하면 기존 선택 방식으로 돌아간다.

11월 13일 점검에서는 매 회 한 페이지만 읽는 수집 때문에 과거 ledger를 따라가지 못했다. 현재는 저장한 cursor 다음부터 최대 20페이지를 순서대로 읽고, 페이지 제한에 도달하면 따라잡았다고 표시하지 않는다. 11월 16일 16:16 집계는 `ledger_caught_up=true`이지만 `coverage_ready=false`였다. 이후 [16:49 점검 집계](logs/four-checks-redacted-20261116.json)에서는 `ledger_caught_up=true`, `ledger_pages_fetched=1`, `coverage_ready=true`, 관측 구간 약 202.7분으로 확인됐다. 두 값은 서로 다른 조건을 나타내므로 오전·오후 상태를 혼동하지 않는다. `analyst.py::run_once()`는 poll 간격이 90초를 초과하거나 cursor를 따라잡지 못하면 `coverage_since`를 현재 시각으로 갱신한다. `create_report()`는 해당 시작점으로부터 3시간이 지났는지를 검사한다. 이 조건 충족은 코드가 관리하는 관측 구간의 충족이며, 시장의 모든 사건을 누락 없이 수집했다는 독립 검증 근거는 없다. 후보가 출력됐다는 로그만으로 충분한 관측 기간이나 추천 품질을 주장하지 않는다. 정산의 보증 null도 확정된 보증 0으로 바꾸지 않는다.

### 아키텍처 figure — Redis와 저장소의 책임 분리

[architecture.tex](architecture.tex)는 코드·운영 로그에 근거한 에이전트 보조에 대해 작성한 안이다. 실제 웹앱 서비스 배포를 위한 역할 분리·입출력 검증·상태 보존·결과 피드백을 명한다. 이는 시장 매매 전략이나 배포 완료 선언이 아니다. 실선은 요청·판단·상태 저장 및 조회, 녹색 점선은 근거·기억 피드백이다. 11/17 운영 Redis 저장·조회가 확인되어 이전의 황색 점선과 적용 대기 표현을 제거했다. 구조도의 수치는 11:38까지의 관측값이며, 아래 보고서 집계는 13:57:30까지로 범위가 다르다.

- `storage.py::stores()`는 `REDIS_URL`이 있으면 `RedisTaskStore`와 `RedisDeals`를 생성한다. URL이 없으면 `InMemoryTaskStore`와 `MemoryDeals`를 사용한다. [17:18 실행 프로세스 점검](logs/redis-connection-check-20261116.json)에서 week-08 seller의 `REDIS_URL`이 없는 것을 확인했다. 이후 저장소 루트 `.env`에 REDIS_URL 값이 있는 것을 확인했다. 따라서 원인은 설정 파일의 값 누락이 아니라 판매자 실행 경로의 로딩 누락이었다. 17:28 수정 검증에서 새 진단 프로세스가 Redis 저장소를 선택했고 별도 PING이 성공했다. 이는 11/16 점검 당시 기록이다. 이후 11/17 새 seller 세션에서 Redis 선택과 실제 저장·조회 성공이 기록되어 운영 적용을 확인했다. 접속 비밀번호와 환경변수 전체는 출력하거나 저장하지 않았다.
- `RedisTaskStore`는 owner scope를 해시한 키 공간에 protobuf 작업, 버전, terminal 상태를 저장한다. WATCH/MULTI/EXEC와 이전 버전 비교로 오래된 작업 쓰기를 거부하고, WATCH 충돌은 최대 5회 시도한다. terminal 작업 저장 시 대응 deal 삭제를 같은 Redis 트랜잭션에 포함한다.
- `RedisDeals`는 task id별 협상 JSON을 GET/SET/DEL한다. 자체적인 버전 검사는 없다. 두 저장소의 기본 TTL은 30일이며 `TASK_TTL_SECONDS`로 바꿀 수 있다. Task·deal·결제·재고 전체가 하나의 원자적 트랜잭션이라는 뜻은 아니다.
- 재고 unit 예약은 seller 프로세스의 `holds` 메모리다. Redis를 설정하더라도 예약까지 자동 복구하거나 다중 seller에 공유하는 구조가 아니다. `seller-ads.lock`이 동일 경로의 두 번째 seller 프로세스 실행을 막는다.
- buyer 장기 기억은 JSON/JSONL, 게시판 분석·광고·영수증 연계는 SQLite, 재입고 제어와 운영 증거는 파일에 남긴다. 이를 Redis 저장으로 표시하지 않았다.

#### Redis 설정 로딩과 운영 적용

`storage_env.py`가 현재 작업 디렉터리에 의존하지 않고 소스 위치를 기준으로 설정을 찾는다. 우선순위는 **기존 환경변수 → week-08/.env → Git 저장소 루트 .env**이며, `REDIS_URL`과 `TASK_TTL_SECONDS`만 로드한다. 비밀값을 복사하거나 출력하지 않고, URL의 달러 기호를 변수 치환하지 않는다. 명시적인 기존 값은 빈 문자열도 덮어쓰지 않는다. `python-dotenv` 의존성을 requirements에 명시했다.

`storage.py`는 TTL 계산과 저장소 생성 전에 로더를 호출한다. 11/16에는 [로더 테스트 4건](logs/redis-env-tests-20261116.log), [새 진단 프로세스 저장소 선택](logs/redis-env-selection-20261116.json), [PING 성공](logs/redis-env-ping-20261116.json)까지 확인했다. 11/17에는 다음 운영 로그로 실제 Redis 적용을 추가 확인했다. 기존 메모리 상태를 Redis로 자동 이전하는 기능은 없다.

## 부록 A. 검증 범위와 제출 전 남은 작업

본문 §1은 작업 폴더의 설계·구현과 시점이 명시된 운영 이력을 설명한다. **마지막으로 분리 검증한 커밋(`352360c`, 로그 압축 변경 후 `805d591`)은 최신 작업 폴더와 일치하지 않아 재현성 문제가 남아 있다.** `storage_env.py` 누락으로 import 실패, TypeScript의 `src` 경로 설정 오류와 `tsconfig.tests.json` 누락, Buyer 하네스 경로 오류가 확인됐다. 해당 커밋의 `agent.json`에는 구매 기록 `review` 훅이 없으며, 판매가격·재입고 설정도 본문의 최신 작업 폴더 설명과 다르다.

`weeks/week-08/README.md`와 `scripts/check_week08.py`가 현재 로컬에 없어 week-08 공식 검사를 실행하지 못했다. 존재하지 않는 검사 통과를 주장하지 않는다. 실제 API 모델 평가는 이번 보고서 갱신에서 새로 수행하지 않았다.

### 후속 개선을 평가하는 방법

향후 비교에서는 기간·주문 종류·후보 수를 함께 기록한다. 이번 보고서는 통제 실험을 수행했다고 주장하지 않는다.

| 검증 질문 | 관측 단위/계산 | 주의점 |
|---|---|---|
| 재시도가 정산으로 이어지는가 | 고유 order별 명시적 재고 거절 후 paid ledger 유무 | 시도 수와 주문 수를 섞지 않음; 불확실한 요청 재시도는 제외 |
| 시간이 줄었는가 | 주문 시작부터 종료까지 경과 시간과 timeout 수 | 빠른 실패 증가를 성능 개선으로 오해하지 않음 |
| 가격 근거가 실제 쓰이는가 | 조건별 표본 충족 주문 수와 tie-break 적용 로그 | historical_price_tiebreak가 unavailable이면 가격 효과 귀속 금지 |
| 기억 연결이 정확한가 | 공식 ledger와 로컬 payment/purchase의 일치·충돌·미연결 수 | 미연결을 성공 또는 실패로 임의 분류하지 않음 |
| 순위에 도움이 되는가 | 같은 시점의 Class 구성 점수와 운영 지표 | 상대평가와 정책 효과 분리; 한 건 성공으로 일반화하지 않음 |
