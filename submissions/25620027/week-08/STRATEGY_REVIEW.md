## 반영한 정책

1. **확인된 자기 인젝션은 즉시 중단.** R3 buyer가 직접 관측한 ‘시장/운영자 권위 사칭+가격 수락/예산 변경/별점 강요’가 있으면 추가 모델 제안과 receipt 전달을 멈춘다. 그 관측이 기억에 남아 있는 동안 재선택도 코드에서 거부한다. 일반 광고·인용된 공격 예시·싸다는 이유·제3자 악평은 같은 확정 사건으로 간주하지 않는다. 탐지 범위가 한정돼 있어 모든 인젝션 탐지를 보장하지 않는다.
2. **암호/상업 조건 불일치는 결제 거부.** 실제 payer와 시장 검증층으로 금액/상품/키/예산/재사용을 막는다. 통신 장애나 모델429를 상대의 사기라는 증거로 바꾸지 않는다. 자동 공개 고발·허위 후기는 추가하지 않았다.
3. **R3에서는 마진 선택을 모델에 돌려줌.** R2의 ‘reserve 이상이면 무조건 즉시 수락’과 달리, R3는 현재 ask에 도달한 실제 제안만 반드시 수락한다. reserve~ask 사이에서는 모델이 counter/accept를 고른다. 하한·호가 상한·호가 인상 금지·실제 제안 금액만 수락하는 가드는 유지한다. 기본 상품의 기존 시작 상한은 유지하므로 최적 마진을 찾았다고 주장하지 않는다.
4. **운영 조건과 광고 일치.** R3 카드와 안내 페이지를 품목→metadata.ask→동일 task 제안→서명 receipt→ACP/시장 정산 순으로 짧게 구조화했다. ‘offer100이면 무조건 즉시 판매’라는 구판 약속은 R3에서 제거했다. 평점·추천 강요, 가짜 운영자 권위, 검증하지 않은 전역 최저가/재고/품질은 사용하지 않는다.

`AX_MARKET_ROUND=3`에서만 새 상업/인젝션 중단 정책이 켜진다. 기존 live R2는 건드리지 않았다. 로컬에서는 reserve 이상의 counter 허용·ask 충족 수락·reserve 미만 거부, 공격 응답 뒤 추가 제안0회, 정상 구매 유지가 통과했다. 실제 수익·유입 개선은 아직 측정하지 않았다.

## 허점 관찰과 보강의 구분

- 공식 AcpShop의 GET cancel 가능성을 로컬에서 확인해, 운영용 subclass와 진단 gateway의 method 경계로 막았다.
- 공식 payer는 descriptor의 hostname을 대조한다. scheme/port까지 같은 origin이라고 검증하는 것과 같지는 않다. 이를 실제 상대에게 악용하지 않았으며 추가 wallet 방어 후보로 남긴다.
- 서명이 맞는 반복 구매는 여전히 정상 정산될 수 있다. 담합/보복성 후기의 의도는 서명만으로 검증되지 않는다.
- 이름 기반 기억은 URL 변경에 강하지만 가게가 이름/등록 정체성을 바꾸는 모든 우회를 해결하지는 않는다. registry 공개키까지 사용한 정체성 연속성은 추가 검토 대상이다.
- 프로토콜의 진짜 보장과 LLM이 좋아할 법한 설명은 별개다. 교수의 ‘signed receipt 안내가 AI에 먹혔을 가능성’은 가설이다. 우리의 간결한 사실형 문구도 모델별 A/B 없이 매출 상승으로 확정하지 않는다.
