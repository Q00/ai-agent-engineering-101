## 1. 부품별 설계

가격·예산 상한 계산, 최종 수락·거절 집행, 영수증 서명, 재입고 수량 제한, 후기·게시글 작성은 코드가 맡는다. 모델은 의도·금액·허용 정책 변경과 짧은 답변을 제안한다. 답변도 숫자·링크·길이·스크린 검사 뒤 코드의 가격 줄과 합쳐 전송하며, 검사를 통과하지 못하면 템플릿을 쓴다. 이 구분은 §0의 주문 간격을 지키면서 자유 문장을 처리하기 위한 것이다. 모델을 쓴다는 사실만으로 성과 우위를 주장하지 않는다.

비용·안전장치 ([r3/model_client.py](r3/model_client.py)): 모든 호출은 공유 시도 장부(KST 하루 5,000회)와 **일일 지출 강등 기준**(`AX_R3_DAILY_USD`, 기본 3달러)을 거친다. 기록된 지출이 기준에 도달하면 전략 모델을 Haiku로 강등, 2배(기본 6달러)에서 느린 루프 중지, 3배(기본 9달러)에서 통역 중지(거래는 규칙으로 계속), 결제 거절(402) → 30분 휴지. 호출마다 역할·모델·지연·토큰·추정비용·도구 인자 응답 여부·입력 해시를 `model_decisions` 표에 남긴다. 이 표의 `accepted`는 도구 인자 응답 여부이며 정책 채택·해석 정확도·체결 성공을 뜻하지 않는다. 실측(10/31 로컬 스모크, [logs/model-smoke-20261031.txt](logs/model-smoke-20261031.txt)): Haiku 읽기 1.2~1.3초, Sonnet 전략 1회 3.6초·입력 2,787/출력 431 토큰·$0.0099. 15일 예상 비용 약 $45~55는 이 실측에 호출 수를 곱한 추정이다.

기존 가게별 기억(SQLite journal, 별도 recorder, 128곳 노트)과 운영자 피드백 프로필은 그대로 두었고 레거시 경로가 읽는다. 5,629개 상품을 프롬프트에 넣지 않는다. 관리자가 모델에 주는 것은 요약 한 장(상위 카테고리 12개, SKU 20개, 등급별 고장률, 자기 결과 수치, 정책 한 벌)이다.

증거가 다음 결정을 바꾸는 구체 분기 네 개:

1. 지급 거절 "no certificate" → 그 가게는 24시간 동안 점수 1/4 → 같은 SKU를 가진 다른 가게로 간다 ([r3/buyer.py](r3/buyer.py) `shop_factor`).
2. 우리 가게에서 unit이 사라짐(판매) → 60초 뒤 restock이 같은 SKU를 보충한다 (`stale_hours` 안에서만).
3. 식품 등급이 3분 안에 바뀔 경계에 있으면 claim을 생략한다. 시장은 checkout 또는 정산 시점의 등급과 claim을 비교하므로 낮게 말하는 것은 정직이 아니라 두 시점 모두 틀린 주장이다(10/31 Codex 검수 F1로 수정).
4. 식품 잔여수명 20% 미만 → 원가의 60%까지 청산 호가를 낮춘다(폐기 손실보다 회수).

### 1-2-1 구매자 탐색·실패 기억 후속 검수 (2026-11-03, Codex)

`11f627c`의 구매자 개선판을 로컬에서 검수해 다음 경계를 보완했다. **이번 수정은 로컬 커밋이며 VPS에 배포하지 않았다.** 가게는 표시 이름이 아닌 URL로 구분한다.

| 발견한 문제 | 수정한 동작 |
|---|---|
| R3에서 합의 뒤 지급이 거절돼도 실패 연속 기록이 끊김. 인젝션 의심 결과도 성공처럼 기록을 끊음 | 주문 ID·가게 URL로 자기 결제 결과를 연결. 지급 거절·협상 실패·의심 결과는 실패로 세고, 지급 대기는 기록을 유지. R3는 지급 성공 때만 초기화 |
| 지급되지 않은 저가 합의도 가격 기억에 들어감 | 자기 주문·같은 가게의 `paid=true`에서 실제 지급액/정가 비율만 기억. 지급 거절·대기·다른 가게 결제는 제외. 가격 가중 범위는 기존 ±20% 유지 |
| 성공 이력이 많으면 실패 감점이 상쇄돼 탐색 대상에 다시 포함됨. R2 경로는 정찰 신뢰도를 무시 | 탐색에는 기간 내 실패·지급 거절·의심·오류 이력 또는 거절 사유가 있는 가게를 제외하고, 정찰 신뢰도 0.6 미만도 제외. 안전한 후보가 한 곳이어도 그 후보를 탐색 |
| R2에서 한 가게의 재고 광고가 재고 목록 없는 모든 가게를 후보에서 밀어냄 | 재고 목록이 필수가 아닌 R2에서는 모든 미차단 가게를 같은 증거·신뢰 가중치로 비교. R3는 주문의 acceptable SKU·양수 재고 조건 유지 |

시도 장부에 `market_round` 필드를 추가했다. R2에는 결제가 없으므로 명시적으로 R2인 서명 영수증 합의는 성공으로 취급한다. R3의 카탈로그 가격이 누락됐다고 R2로 추측하지 않는다. 기존 행은 삭제·수정하지 않고 라운드 미확인(0)으로 보존하며, 구매자·관리자의 동시 시작을 고려해 필드 추가를 직렬화했다.

기존 탐색 확률 10%·실패 3회·휴식 30분과 전략층 소유권, 예산·영수증·accept 검사, 모델·운영 한도는 유지했다. 휴식 후 실패한 한 번의 재시도는 즉시 다음 휴식으로 이어진다. 탐색은 적격 후보 중 추첨하므로 현재 최고 점수 가게가 다시 뽑힐 수도 있다. 실제 방문률·성사율 개선은 배포 후 별도 측정해야 한다.

검증: 새 회귀 **18개**, 전체 **502개 PASS (33.72초)**. [수정 전 13개 반례 실패 원로그](logs/buyer-selection-review-20261103-red.log), [수정 후 전체 원로그](logs/buyer-selection-review-20261103-green.log), [회귀 테스트](tests/test_r3_buyer_selection_regressions.py). 변경한 코드·테스트 4파일 Ruff 검사 통과. 첫 전체 실행의 40개 실패는 샌드박스의 로컬 포트 개설 제한이었고, 같은 로컬 가상 서버 검사를 포트 허용 환경에서 모두 통과했다. 유료 API·실제 시장 거래·VPS 변경은 하지 않았다.

판매자가 상대의 예산에 맞춰 더 낮게 수락하는 제안은 이번에 넣지 않았다. R3의 실제 원가·등급·최소 마진 자료 없이 수락선을 낮추면 이익이 줄 수 있어 개장 후 별도 평가한다.

### 1-2-2 최근 커밋의 정책 경계 추가 검수 (2026-11-03, Codex)

구매자 수정 뒤 최근 관리자·리뷰·재입고·홍보·배포 관련 변경을 대조했다. 성과 자료 없이 가격이나 탐색 확률을 임의로 바꾸지 않고, 재현되는 경계 결함을 수정했다. **로컬 수정이며 VPS 배포·가격 정책·예산·운영 시한·예약을 변경하지 않았다.**

| 경계 | 수정 |
|---|---|
| 재고 수량 | 잔여 재고 자리보다 큰 보충/신규 매입 수량을 잘라 `max_units`를 넘지 않게 함. 예: 현재1개·상한2개에서4개 요청 →1개만 계획 |
| 식품 매입 배분 | `food_share`는 키트 최대10줄 중 식품에 허용한 줄 비율이다. 시장 수요 신호가 있어도, 기존 판매분 보충이어도 같은 제한을 적용. 0이면 식품 매입 없음 |
| 전술 모델 실패 | 응답 없음·JSON 오류·제안 스키마 오류를 정상적인 빈 제안과 구분. 실패하면 정책 유지·실패 기록. 정상 빈 제안+유효 숫자 조건일 때만 기존의 코드 보정 허용 |
| 전술 변경3개 | 입력의 첫3개가 아니라 검증에 통과한 첫3개를 채택. 앞의 무효 필드가 뒤의 유효 변경을 버리게 하지 않으며 소유권·띠·역방향 제한은 유지 |
| 리뷰 모델 집계 | 우리 가게와 각 상위 가게의 실제 입력 리뷰 수보다 큰 주제별 건수, 같은 묶음의 중복 주제를 거부. 숫자 별점·표본 수는 보존하고 모델 요약 유효 여부(`model_digest_valid`)를 기록 |

재고·전술 경계 반례는 [tests/test_r3_policy_boundary_regressions.py](tests/test_r3_policy_boundary_regressions.py), 리뷰 집계 반례는 [tests/test_r3_reviews.py](tests/test_r3_reviews.py)에 남겼다. 실패 원로그는 [재고·전술10건](logs/policy-boundary-review-20261103-red.log), [리뷰 집계3건](logs/review-counts-review-20261103-red.log), [전술 필터1건](logs/tactical-filter-review-20261103-red.log)이다. 일부 리뷰 단위 테스트의 최초 실패는 새 표본 수 인자를 아직 지원하지 않은 오류이며, 별도의 `run_digest` 반례로 리뷰1개→불만99건 수용도 직접 재현했다. 최종 전체 결과는 [최종 검사 원로그](logs/policy-boundary-review-20261103-final.log)에 보존한다. 이 검사들은 유료 모델·실제 시장 거래를 사용하지 않는다.

추가 회귀 **15개**, 최종 전체 **517개 PASS (33.35초)**. 변경한 코드·테스트6파일 Ruff·포맷 검사도 통과했다. 앞 절의502개 결과는 구매자 수정 시점의 이력이며 두 결과를 합산하지 않는다.

공개 보드·가게 목록의 스키마도 읽기 전용으로 대조했다. 조회 당시 등록명 중복은 없었고, 상위권 비교 코드는 카드 표시 이름이 아니라 등록명을 사용했다. 따라서 표시 이름 쏠림만으로 그 코드를 변경하지 않았다. 첫 호가·양보폭·즉시 수락 비율의 최적값, 실패 유형별 가격 민감도와 실제 성과 개선은 R3 자료로 별도 평가해야 한다.

### 3-0 선순환·가드·사람 승인 전수점검

`기록 → 분리된 분석 → 허용 범위의 정책 도구 → 전후 복기 → 다음 결정`을 연결하고, 범위를 벗어나는 구조·코드·운영 변경은 자문으로 올린다. 이번에 `r3/reflection.py`를 추가해 실제 R3 정산 기반의 같은 길이 창을 전술·전략·자문에 넣었다. 최신200개 정책 변경·500개 루프 기록이 유지되도록 조회 방향도 고쳤다. 이는 과거 기록을 지우거나 다시 쓰는 변경이 아니다.

승인 요청은 준비만으로 보고 완료가 되지 않는다. 전송 성공 뒤 `--ack`로 전달만 확인하며, 승인/거절(`--decide`)과 적용은 별개다. 실패한 요청은 host outbox와 기존 제안 장부에 남아 재전달되고, 유료 모델이 꺼져도 요청을 읽어낼 수 있다. dry-run에서는 새 모델 호출·제안 생성·상태 변경을 하지 않는다. 전송 직후 장애가 나면 같은 ID가 다시 도착할 수 있다(유실 방지를 위한 at-least-once 방식).

자동으로 할 수 있는 것은 기존 승인 범위 안의 정책 수치 조정·실패 휴식·검증·TTL 복귀·허용된 장애 복구다. 코드/배포·실제 API 한도·키·운영 시한을 모델이 고치는 도구는 없다. 중요한 제안은 사용자가 현재 Codex/Claude 세션에 ID와 승인 범위를 전달한 뒤 담당자가 원자료·검사·적용을 수행한다. 성능이 떨어졌다는 관측만으로 코드 자동 변경·재배포·무조건 롤백을 하지 않는다.

자문 모델의 자연어 근거는 숫자 포함 여부·스크린·중복까지 검사하며 숫자의 진위를 자동 증명하지 않는다. 리뷰 주제 건수는 원표본 크기로 상한을 두고, 반대로 정책 효과는 구조화된 원장 숫자를 코드가 계산한다. 인간 승인 때는 제안의 근거를 이 원자료와 대조한다.

사용량 장부가 없거나 비용/휴지 상태를 읽지 못하면 유료 모델을 차단하고 규칙 경로를 유지한다. 가격표는 [Claude 공식 가격](https://platform.claude.com/docs/en/about-claude/pricing)을11/3 대조해 Haiku의100,000토큰 초과 요금도 반영했다. 3·6·9달러는 관측 사용량의 강등/중지 단계이며 공급자의 실청구 한도를 대신하지 않는다. 승인된 횟수·운영 시한은 바꾸지 않았다.

### 3-0-1 9주차 손익 기준 복기 (2026-11-03)

복기의 개선 판단을 `shop_gross_revenue`에서 **`shop_net_profit`**으로 바꿨다. 기간 순손익은 **정산 매출 − 팔린 unit의 실제 매입원가 − 보증 환불 − 폐기 식품 원가 − 보관비**다. 가격표의 추정 원가 대신 kit 인벤토리에서 관측한 unit별 고정 원가를 사용한다.

- 기존 별도 `r3.recorder`가 바뀐 `.market/inventory.json`을1초마다 확인해 `r3-stock.sqlite`에 원가 식별자와 잔고/재고 자산을 기록한다. 시장 추가 요청·모델 호출·거래 경로 쓰기는 없다. 최신2일의 관측을 보관하며 원본 kit/거래 로그는 바꾸지 않는다.
- 고장 `broken`/`break`는 우리 가게/정확한 unit의 거래와 대조한다. 명시된 환불 금액·환불 여부 또는 정확한 unit의 보증 조건으로 금액을 결정한다. 다른 가게 고장과 무보증 고장은 우리 환불 비용이 아니며, 과거에 판 물건의 환불도 환불이 발생한 기간에 반영한다. 같은 unit 고장 중복은 비용을 두 번 빼지 않고 불완전 자료로 표시한다.
- 미판매 식품의 기한과 실제 재고 소멸이 확인돼야 폐기 비용을 잡는다. 이미 팔린 식품은 기한이 지나도 다시 폐기 비용을 잡지 않는다. 비식품 보관비는 관측 원가×재고 보유 초÷86,400×1%로 계산한다.
- `shop_restock_spend`는 현금→재고 자산 전환으로 별도 표시한다. `shop_cash_change`와 `shop_inventory_asset_change`도 함께 제공한다. 공식 순위의 현금 기준 이익(잔고−시작 자본−지원금)은 `official_cash_profit_at_end`로 분리하며, 재고 자산을 포함한 이번 운영 손익과 같다고 주장하지 않는다.
- 같은15분 전후 창과 기존 소표본·원장 지연·변경 혼재 표시는 유지한다. 우리 가게 정산 표본도 별도 확인한다. 원가/환불/인벤토리 경계가 없거나,30초 초과 관측 공백·소멸 원인 불명·파산 지원·잔고+재고 대사 차이(1크레딧 반올림 허용)를 발견하면 순손익은 `null`, 판단은 `insufficient_evidence`다. 관측 손익이며 후속 기간의 보증 환불은 이후 관측에 반영된다. 인과효과를 확정하거나 자동 코드 롤백하지 않는다.

## 6. 범위와 정직성

- 설계·구현·검증은 Claude Code와 함께 했고, 왜 그렇게 바꿨는지는 §0의 관측값이 근거다. 참고한 코드는 공식 `starter_round3/seller.py`의 구조와 10/30 보고서에 밝힌 빠른 수락 원리이며, 다른 학생의 코드를 복제하지 않았다.
- 담합·상호 구매·근거 없는 비방·평점 유인은 하지 않는다. 비공개 예산은 후기·게시글·로그 문장에 넣지 않는다. claim은 증명서와 맞춘다.
- 모델이 바꿀 수 있는 것은 정책표의 범위 안 숫자(전략은 소유 필드와 띠, 전술은 띠 안 60분)와 상황판의 allowlist 판정, 통역의 의도·금액이다. 키·예산·정산·운영 시한·키트 코드는 바꾸지 못한다. 상대에게 보낼 짧은 답변은 사실표를 바탕으로 제안하고 코드의 숫자·링크·길이·스크린 검사를 거친다. 모델 지출은 기본 3·6·9달러의 강등·중지 사다리와 공유 시도 장부로 관리하며, 모델 중지 뒤에도 거래는 규칙으로 계속된다.
