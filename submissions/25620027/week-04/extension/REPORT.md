# Week 04 확장 실험 — 상태 기반 혼합 프로토콜

성진호 · 25620027

## 1. 왜 이 구조를 추가했는가

기본 실험은 한 에피소드 전체를 `free`, `tagged`, `structured` 중 한 형식으로 고정했다.
확장 실험은 형식마다 잘하는 일이 다르다는 관찰에서 출발했다. 가격이 정해지기 전에는
자유문장이 편하고, 가격을 주고받을 때는 행위 태그가 싸게 읽히며, 실제 거래를 확정할 때는
구조화 메시지와 코드 검사가 필요하다고 보았다. 따라서 세 형식을 경쟁시키는 대신 협상
상태에 따라 배치했다.

![자유형 탐색, 태그형 협상, 구조화 합의 확인과 로컬 guard를 연결한 상태 기반 혼합 프로토콜](../figures/week04-hybrid-protocol.svg)

- `discovery/free`: 첫 유효 가격이 나오기 전이다. 공개 발화를 LLM reader가 읽는다.
- `bargaining/tagged`: 첫 가격이 상태에 기록된 뒤다. 선두 태그로 행위를 읽고, 제안 가격만
  reader가 읽는다.
- `settlement/structured`: 공개 수락은 거래가 아니라 합의 후보를 만든다. Buyer와 Seller가
  자기 한도만 본 채 JSON으로 각각 확인한다.
- `local guard`: `price <= budget`, `price >= reserve`를 코드로 따로 검사한다. 확인 2개와
  guard 2개가 모두 통과할 때만 거래를 커밋한다.

공개 협상 행위는 과제의 네 가지를 그대로 유지했다. `confirm-deal`, `abort-deal`은 상대에게
전달되는 새 협상 행위가 아니라 내부 commit 제어 메시지다. 이는 자유 협상과 엄격한 합의
확정을 분리한 작은 2단계 commit 구조로 볼 수 있다.

## 4. 해석

### 안전성은 좋아졌지만 거래 능력이 좋아진 것은 아니다

Hybrid의 위반 0건은 모델이 더 신중해졌다는 뜻이 아니다. 코드 guard가 위험한 settlement
후보 다섯 건을 거래로 바꾸지 못하게 막았기 때문이다. 시나리오 2의 가격 75를 Seller가
두 번 수락한 경우와 시나리오 3의 가격 80을 수락한 경우도 모두 seller guard에서 멈췄다.
따라서 이것은 **모델 성능 향상**보다 **아키텍처가 만든 안전 보장**으로 해석해야 한다.

반면 거래 가능 상황의 성사율은 2/6으로 tagged의 4/6보다 낮았다. 상태 전환 자체가 reader에
의존했기 때문이다. “Would you accept 90?” 같은 가격 문장을 reader가 제안이 아니라 수락이나
거절로 읽으면 첫 제안 가격이 상태에 기록되지 않고 discovery가 계속된다. 시나리오 2의 첫
두 반복은 이 문제로 settlement에 진입하지 못했다.

### 상태 전환에는 조정 비용이 생겼다

형식 오류는 24건으로 네 조건 중 가장 많았다. discovery에서 tagged로 바뀐 뒤 일부 모델은
이전 자유문장 습관을 이어 가며 `(reject-proposal)` 대신 `Reject-proposal:`처럼 답했다. 또한
settlement가 거부돼 협상으로 돌아와도 에이전트가 거래가 이미 끝난 것처럼 말한 사례가
있었다. 같은 에이전트의 대화 중간에 통신 문법을 바꾸려면 새 문법만 제시하는 것 외에
**전환 사실과 실패 이유를 양쪽 이력에 명시적으로 전달하는 조정 메시지**가 필요하다.

### 비용은 중간값이 아니었다

Hybrid의 reader 호출은 42회로 free의 75회보다 적었지만 tagged의 34회보다 많았다. 여기에
settlement 확인 16회가 추가되어 전체 API 시도는 136회였다. tagged보다 30회 많고 free보다
14회 적다. 긴 상태별 프롬프트와 확인 호출 때문에 토큰은 26,134로 네 조건 중 가장 많았다.
즉 여러 형식을 조합하면 각 형식의 장점이 자동으로 합쳐지는 것이 아니라, 라우팅과 합의
확인의 비용도 함께 생긴다.

### 결정론과 비결정론의 경계

상태 전환 규칙, 태그·JSON parser, 두 로컬 guard, 거래 commit, 채점은 같은 파싱 결과에
대해 같은 값을 내는 결정론적 코드다. 그러나 공개 발화, reader의 행위·가격 분류, 양측
확인 JSON은 모델이 생성하므로 비결정론 영역이다. temperature 0은 출력 다양성을 낮출 뿐
완전한 재현을 보장하지 않는다. 이 구조의 목적은 모델의 모든 판단을 결정론으로 바꾸는
것이 아니라, **잘못된 비결정론적 판단이 최종 거래로 확정되는 지점에 결정론적 경계를
두는 것**이다.

## 5. 다음 설계에서 보완할 점

1. 첫 가격 전환을 reader 한 번에만 맡기지 않고, 숫자 후보 추출과 행위 분류를 분리해
   “가격 질문”과 “수락”을 구별한다.
2. settlement veto 뒤 양쪽 이력에 `미확정·계속 협상` 상태와 실패 범주를 공개하되 상대의
   비공개 한도는 노출하지 않는다.
3. tagged 형식 위반이 반복되면 같은 형식 예시를 다시 주는 제한된 repair 단계를 둔다.
4. 이번 지표에는 포함하지 않은 자기 한도 노출을 별도 privacy violation으로 측정한다.

이 확장판은 random forest처럼 여러 모델의 표를 모으는 방식이 아니다. 현재 협상 상태를
보고 적합한 통신·검사 모듈로 보내는 **상태 기반 router**이며, 각 단계의 실패가 다음 단계로
번지지 않도록 commit 경계를 둔 구조다.
