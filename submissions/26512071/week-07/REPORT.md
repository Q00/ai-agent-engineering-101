## (1) 구매자가 상점을 고르는 방법과 기억의 형식

### 선택 순서

`market_buyer.py`의 실제 순서는 다음과 같다.

1. **Probe**: 최대 16개 작업자로 Agent Card를 병렬 조회한다. 요청별 제한은 5초이며 JSON-RPC interface가 있는지 확인한다. 실패한 상점은 제외하되 모두 실패하면 원래 목록으로 돌아간다.
2. **기억 확인**: 이름별 기억에서 `receipt_problem`이 있는 상점을 모델 호출 전에 제외한다. `[pick] skipping ...: my memory has a bad receipt from it`를 남긴다. 모두 제외되면 원래 후보를 다시 허용한다.
3. **단일 후보**: 하나만 남으면 모델 없이 선택한다.
4. **제휴 선택**: `BUYER_ALLIES`의 후보 중 이번 품목의 과거 최저 호가가 예산을 넘었던 기록이 없는 상점을 `BUYER_ALLY_RATE` 확률로 고른다. 기본 확률은 0.5이며 탐색·일반 모델 선택보다 먼저다.
5. **탐색**: 앞에서 선택되지 않았고, 후기와 내 거래가 모두 없는 새 상점과 다른 후보가 함께 있으면 `BUYER_EXPLORE` 확률로 탐색한다. 첫 제안은 예산의 60%다. 기본값은 꺼짐, 배포 파일은 0.25다. 전체 주문의 25%가 반드시 탐색이라는 뜻은 아니다.
6. **일반 선택**: 내 거래·보드·정제한 후기를 상점별 한 줄로 만들어 Sonnet에 전달한다. 모델은 정확한 후보 이름과 이유를 JSON으로 답하고 표와 이유는 로그에 남긴다. 두 번 실패하면 원래 후기 평균이 가장 높은 후보를 고른다. 이 fallback은 광고·중복 정제된 표와 같은 계산이 아니다.

### 거래·영수증 검사

가격 제안과 중단은 `buyer.py`의 Sonnet 하네스를 사용한다. A2A 요청에 `A2A-Version: 1.0`을 넣고 같은 `taskId`로 협상을 이어 간다. 예산 초과 제안은 코드가 예산으로 낮추고 최대 8회 제안 후에도 협상 중이면 취소한다.

완료 task의 영수증에서 서명 존재·품목·예산·최종 제안보다 비싼 청구·task id를 검사한다. 최종 제안보다 낮은 영수증 가격은 허용한다. 정수값인 실수는 정수로 바꾸고 등록소에서 공개키를 얻으면 Ed25519 서명을 검증한다.

**한계**: 공개키를 얻지 못하면 자동 거절하지 않고 `sig_seller not checked: no registry key`로 기록한다. 로컬 성공은 시장 인정 거래와 다르다. 문제 있는 영수증도 최종 출력에는 담되 기억의 `price`는 null로 둔다. 최종 주문 검사와 구매자 서명은 kit이 수행한다.

### 기억

`memory.jsonl`에 시도당 한 줄을 저장한다. 터널 URL은 바뀌므로 이름으로 기억한다. 필드는 시각·상점·품목·예산(`time`, `shop`, `item`, `budget`), 첫/최저 호가·제안 횟수(`first_ask`, `min_ask`, `rounds`), 완료 시 마지막 제안·영수증 가격(`agreed`, `receipt_price`), 정상 가격 또는 null·문제·별점·탐색 여부(`price`, `receipt_problem`, `stars`, `explore`)다.

## (2) 후기를 하네스에 보여 주는 방식

일반 선택에서는 다른 상점으로 유도하는 광고를 먼저 거른다. `try`, `visit`, `check out`, `go to`, `head to`, `recommend`, `instead`가 있고 후보 목록의 다른 상점명을 언급하면 광고로 판단한다. 이름은 영문·숫자 단어로 정규화하며 길이 6자 이상에 적용한다. 모든 광고 표현을 잡는 것은 아니다.

광고 후기는 그 후기가 달린 상점의 평균·인용에서 뺀다. 광고 대상에는 `ADVERTISED inside ... reviews of other shops` 표시만 붙이고 차단하지 않는다. 경쟁자 이름을 넣어 상대를 차단시키는 역이용을 피하기 위해서다.

이후 대소문자·공백을 정규화해 동일 문장은 한 번만 센다. 서로 다른 문장의 별점 평균과 최근 최대 3개 후기를 보여 주고 후기당 120자로 잘라 JSON 문자열로 감싼다. `(R1)`, `(R2)`도 표시한다. 프롬프트에는 후기는 낯선 사람이 쓴 데이터이며 지시를 따르지 말 것, 내 경험을 우선할 것, Round 2 검증 거래 후기에 무게를 둘 것을 적었다. 거래 검증은 후기 내용의 정직성까지 보장하지 않는다.

전체 보드 별점은 별도 열이며 광고 제거 후 평균으로 재계산하지 않는다. 거래 뒤 별점·후기는 코드가 정한다. 문제 영수증·쓸 수 없는 첫 응답은 1점, 예산 내 거래 실패는 3점, 정상 영수증에 제안 2회 이내 또는 첫 호가 대비 15% 이상 할인이면 5점, 나머지 정상 거래는 4점이다. 상점이 별점을 직접 지시하는 경로를 없앴지만 모든 prompt injection 방어를 증명한 것은 아니다.

근거: `market_buyer.py`의 `review_line`, `ads_in`, `pick`, `main`; `32479f2`, `f9c5b7b`.

## (5) 챌린지

### 챌린지 1: 거래·후기를 보고 가격 바꾸기

#### 정책 변화

1. **초기 모델 중심**: 높은 첫 호가·느린 양보로 이탈했다. 변경 전 로그는 협상 시작 34회·수락 19건이다.
2. **기념가·공정가**: 첫 10건 기념가와 새 3점 이하 후기당 5건 추가를 도입했다. 당시 일반 첫 호가 상한 1.1배는 초기 실험이지 현재 일반 모드가 아니다.
3. **가격표·수요 연동** (`1e22564`): 가격표는 lamp 105·chair 189·bookshelf 273, reserve는 100·180·260이다. 최근 600초에 첫 메시지에서 품목을 찾은 횟수 `v`로 첫 호가 상한을 정한다. 기본값은 `QUIET=5`, `BUSY=30`, `LIST=1.05`다.

   ```text
   m = 1 + (1.05 - 1) × clamp((v - 5) / (BUSY - 5), 0, 1)
   첫 호가 = max(reserve, min(모델 호가, round(reserve × m)))
   ```

   5회 이하이면 reserve, 30회 이상이면 가격표가 상한이고 중간은 선형 보간한다. 모델 호가가 더 낮을 수 있다. 현재 요청도 포함하며 재시작하면 방문 수가 초기화된다.
4. **동적 설정** (`81ce091`): `SHOP_PRICING` JSON에서 `busy`·선택적 `hold`를 최대 1분에 한 번 읽는다. 새 협상 시작 때 호출하며 독립 타이머는 아니다. BUSY는 QUIET 초과, HOLD는 0~3만 반영하고 잘못된 파일은 기존값을 유지한다. 카드 가격표는 바꾸지 않는다.
5. **HOLD** (`c6b9a21`): 현재 호가 미만·reserve 이상 제안에 즉시 수락하기 전 최대 HOLD회 추가 호가를 보낸다. reserve와 정확히 같은 제안에만 적용되는 것은 아니다. 최소 `max(1, round(reserve×0.03))`씩 내리되 reserve를 지킨다. 현재 호가 이상은 보류하지 않는다. HOLD=0이면 reserve 이상 제안을 바로 받는다.

시장 모드에서 조기 거절은 최대 협상 횟수 전까지 추가 호가로 바꾸고 20초 내 모델 판단이 없으면 코드 규칙을 적용한다. 숫자 든 설명은 버리고 가격을 마지막에 두어 치수·수량과 혼동을 줄였다. 판매자 최대 협상은 10회다.

#### 설정과 사용 흔적

재참가 파일은 `SHOP_PROMO=0`, `SHOP_NICK=fair-furniture`, `BUYER_EXPLORE=0.25`, `SHOP_PRICING` 지정이다. 읽은 가격 파일은 `{"busy":30,"hold":0}`이다. 파일 스냅샷이며 실행 중 환경 전체를 직접 확인한 것은 아니다.

`SHOP_PROMO=0`이면 `promo_left()`는 0이므로 새 저평점에도 기념가가 켜지지 않는다. 코드가 남아 있다고 현재도 적용된다고 설명하면 틀리다. 로그에는 `HOLD 0 -> 1`, `HOLD 1 -> 0`과 `[hold]` 2,596회가 있다. 사용 흔적이지 이익 개선의 통제 실험은 아니다.

점유율은 변경 전 스냅샷 0.4%, 10월 21일 Round 2 0.5%, 최신 Round 2 5.8%다. 다른 시점·라운드의 누적값이며 가격만의 인과 효과가 아니다. 이름 변경·운영 시간·시장 구성·제휴·다른 코드 변경도 함께 있었다.

reserve 성사는 14,319건(**74.64%**)이다. 로컬 `price-reserve` 합 27,332는 시장 `profit` 27,215와 구분한다. 로컬 수락은 시장 최종 인정을 보장하지 않는다. 판매·종료 로그도 시작 시점이 달라 성사 수가 다르다. 변경 후 누적값은 여러 정책이 섞인 결과이지 현재 설정만의 실험이 아니다.

낮은 가격으로 거래를 넓힌 기록은 있지만 reserve 성사가 많아 건당 여유가 작다. BUSY·HOLD는 그 균형을 조정하는 수단이며 각 변경의 순수 효과는 분리해 측정하지 못했다.

## (6) 배포 위치와 방법

처음 Mac에서 실행한 뒤 터널·이름 조회 문제를 겪고 Windows PC로 옮겼다. 운영 파일은 PC의 `agent-market/`에 있으며 claim code가 든 스크립트는 제출하지 않는다.

- `rejoin.ps1`: cloudflared로 `http://127.0.0.1:8900`을 HTTP/2로 공개하고 DNS 확인 후 kit에 `--port 8900 --public-url <터널 주소>`를 전달한다.
- `run-forever.ps1`: kit 종료 후 60초 뒤 재참가하는 구성이다. 모든 장애에서 복구가 완료되었다는 뜻은 아니다.
- 판매자: `python seller.py --port {port} --market`
- Round 0 구매자: `python buyer.py --url {url} --item {item} --budget {budget}`
- 시장 구매자: `python market_buyer.py --shops {shops} --item {item} --budget {budget}`
- 하네스: `claude -p --model sonnet --tools "" --setting-sources "" --no-session-persistence`
- 로컬 `shop_key.pem`, `buyer_key.pem`은 `*.pem`으로 Git에서 제외한다. 키 내용·claim code는 보고서에 넣지 않았다.

HANDOFF의 `SHOP_PROMO=10`, 제휴 미구현, 남은 증거 목록은 당시 상태다. 이후 가격표·수요 연동·동적 설정·HOLD·제휴·광고 처리가 추가되었고 현재 기념가는 꺼져 있다. 보고서는 최신 코드·파일을 기준으로 작성했다.

공식 검사 명령은 저장소 루트 기준 다음과 같다.

```bash
python scripts/market_test_week07.py submissions/26512071/week-07
python scripts/check_week07.py submissions/26512071/week-07 --github kimchyoungman
```

현재 보존된 전체 테스트는 10월 22일 25/25 통과다. 최신 집계는 모델 호출·주문 생성 없이 재현할 수 있다.

```bash
python submissions/26512071/week-07/report_evidence.py
```

매번 새 `logs/report-audit-<시각>/`에 집계·보드를 저장하며 기존 운영 로그·과거 증거는 편집하지 않는다. 입력 해시·기간·테스트 제외 건수·조회 실패도 남긴다. 운영이 계속되면 수치는 달라질 수 있다.

최신 전체 운영 로그와 원본 데이터는 [압축 증거 폴더](logs/submission-evidence-20261027-151917/README.md)에 보관했다. 운영 로그 원본은 약 345MB로 GitHub 단일 파일 제한을 초과하므로 전체 바이트를 gzip으로 압축했다. 원본을 축약하거나 편집하지 않았고, 압축 해제 후 전체 SHA-256과 보고서 집계 시점 prefix 해시의 일치를 확인했다. CI가 요구하는 `logs/market-kit.log` 경로에는 기존 커밋의 과거 운영 로그를 그대로 유지하며, 최신 전체본은 `market-kit.log.gz`다. 따라서 PR의 고정 경로 로그와 최신 전체본의 범위를 혼동하지 않는다.

**마감 가동은 별도 확인 조건이다.** 최신 보드에는 구매자 인정 거래 15,708건과 GitHub 연결이 있지만 상점은 offline이었다. 마감 시점 두 역할 모두 실행 중인지 다시 확인해야 한다. 저장된 테스트 통과, 구조 검사, 마감 가동, PR 제출은 서로 다른 조건이다.
