# Opus 전략 검토 — 제안과 구현 구분

판매자와 buyer를 별도 Claude Code Opus 호출로 설계했다. 두 receipt 모두 success / is_error=false / modelUsage=claude-opus-5-5를 확인했다. 전략 원문과 raw 결과는 같은 폴더에 보존했다. 이는 설계 검토이지 실행 성과나 현재 배포 완료 증거가 아니다. 실제 운영 모델은 기존 저비용 OpenAI 모델/코드이며 Opus로 상시 전환하지 않는다.

## 우선 적용할 공통 설계
- 판매자: 제한된 초기 재고 탐색 → 관측 기반 재주문, 실재고·원가·등급·남은 수명 기반 가격, 식품 FEFO, 명시적 보증과 정직한 claim.
- buyer: acceptable∩offers 후보 → 예상 순편익/위험에 따른 선택 → 예산 내 협상 → 서명·품목·task 검증 → accept 조건 → 정산 후 review.
- 코드가 금액·조건·서명·재고 검사를 소유하고, LLM은 비정형 문장 파싱/문장화에 제한적으로 사용한다. 거래·정산·고장 증거를 분리한다.
- 시작 전 최소 구현과 후속 추정/밴딧/포럼 분석을 구분한다. 19시 가동이 우선이며 무리한 재고투입과 자동 게시·투표를 추가하지 않는다.

## 원안에서 그대로 구현하면 안 되는 부분
1. 판매자는 비공개 buyer 예산을 볼 수 없으므로 원문의 budget_hint는 입력으로 가정하지 않는다.
2. 원가 구간만으로 균등분포나 평균원가를 확정할 수 없다. 기대원가 0.50L/0.59L는 구간 중간값 가정하의 계산이지 검증된 시장 평균이 아니다.
3. 고장 prior와 고장시각 균등분포는 미확인 가정이다. 보증 6시간과 환불 계약은 확인하되 미래 고장확률을 사실로 보고하지 않는다.
4. claim은 보수적으로 낮추기만 하면 항상 honest라는 보장이 없다. 현재 계약/키트의 등급 비교와 실제 정산 의미에 맞춰 정확한 grade를 사용하고 경계/지연을 검증한다.
5. 인증서·영수증에 서명 문자열이 있다는 것만으로 검증되지 않는다. 기존 Ed25519 공개키 검증과 task/item/price 일치 검사를 유지한다.
6. 같은 상품명의 고장이 여러 구매에 대응하면 확정 귀속하지 않는다. 1/k 배분은 추정량일 뿐 사실 장부와 분리해야 한다. 단순 잔액 감소를 특정 보증 환불로 확정하지 않는다.
7. 포럼 긍정/부정 투표는 진실 검증만으로 필수인 것이 아니다. 원문 투표 제안은 설계안이며 실제 자동 게시·투표는 이번 단계에서 실행하지 않는다.
8. 정가비례 고정 협상 상한(0.75L 등)은 시작 가정이며 성사율이 나쁘면 계약·예산 내에서 수정한다. 높은 점수나 최적성이 보장되지 않는다.

판매자/구매자의 수식·파라미터는 원문을 그대로 유지하되 위 경계사항을 우선 적용한다. 가동용 구현의 실제 반영 범위와 테스트는 별도 배포 기록에서 확인한다.
