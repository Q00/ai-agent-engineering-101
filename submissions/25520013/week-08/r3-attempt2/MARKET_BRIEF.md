## 1. 목표와 점수

- 목표: 회차가 끝날 때 Players 표의 total 1위 (성수님 결정)
  - 회차 종료 11-17 23:59 KST, 그 시점의 순위표로 정함 (L8)
  - total = 가게 all + 구매자 all, GitHub 계정 하나에 한 줄 (L8, L9)
  - 이 백분위가 중간 평가 3부의 30%임 (L8)
- 가게 all = 0.5 pct(book) + 0.3 pct(revenue) + 0.2 pct(stars_rank)
  - 강의는 첫 항을 현금 이익(잔고 − 5,000,000 − 파산 지원금)으로 설명함 (L8)
  - 실제 순위표는 book을 씀: 잔고 − 시작 자금 − 파산 지원금 + 팔리지 않은 재고의 원가. 이 식으로 가게 52곳의 all이 0.0005 안에서 맞았고, 현금 이익으로는 최대 0.166 어긋남 (시도 1)
  - revenue는 정산된 거래의 매출이고, 환불이 나면 그 금액이 빠짐 (L9)
  - stars_rank는 정산된 거래의 리뷰 평점으로 만든 값임. 평점 수가 적으면 평균 쪽으로 당긴 값으로 보임 (시도 1, 추정)
- 구매자 all = 0.5 pct(surplus) + 0.3 forum + 0.1 pct(deals) + 0.1 pct(posts)
  - surplus = 주문을 채운 상품의 정가 − 실제 지불액 + 보증 환불액 (L8)
  - forum = 구매자로 쓴 글이 받은 좋아요와 싫어요로 만든 평점 (L8, 6절)
  - deals = 정산된 구매 수, posts = 구매자로 쓴 글 수 (L8)
- pct는 같은 표 안의 백분위
  - 가게 표는 살아 있는 참가자 가게와 시장 운영 가게(house)를 모두 포함함. 실측 82곳 (11-05 22:17)
  - 구매자 표는 거래가 한 건 이상 있는 구매자만 포함함. 실측 122곳
  - 동점은 중간 순위로 처리하고, 값이 없으면 꼴찌로 셈 (시도 1)
- 구매자마다 주문 품목 구성이 정해져 있어 바꿀 수 없음 (성수님 확인 2026-11-05). 우리 구매자는 식품 주문이 많아 surplus를 크게 올리기 어려움

## 2. 주문과 구매

- 주문은 시장이 냄. 구매 키트가 POST /api/orders로 받아 오고, 너무 자주 부르면 429와 기다릴 시간을 돌려줌 (KIT)
- 주문 하나는 상품군 하나임. 그 상품군의 SKU 가격은 기준가의 0.5~1.5배이고, 구매자마다 숨은 선호 상품군이 있음. 식품 주문에는 use_within_hours가 붙음 (L8)
- 구매자 에이전트가 받는 것: 주문 내용(order.json: 주문 번호, 품목, 예산, 상품군, 받을 수 있는 SKU, 유통기한 조건), 가게 목록(shops.json: 가게 이름, 리뷰, 보유 상품). 우리 가게는 목록에서 빠짐 (KIT)
- 구매자 에이전트가 내는 것: 마지막 줄에 거래할 가게, 받은 영수증, 줄 별점과 리뷰. 받아들일 조건(인증서, 남은 유통기한, 등급, 보증 시간)을 붙일 수 있음 (KIT, W7)
- 한도: 주문 하나에 300초. 결과 줄이 없으면 거래 없이 끝남 (KIT)
- 결제 한도는 주문 예산임. 예산을 넘는 결제는 키트가 하지 않고 이유를 payments.jsonl에 남김 (L8, KIT)
- 같은 GitHub 계정의 가게와 구매자는 서로 거래할 수 없음 (L8)

## 3. 판매

- 협상은 A2A(1.0)로 함. 판매자는 가격을 정해 영수증({가게, 품목, 가격, 작업})에 서명해 보냄. 가격은 정수 (W7)
- 구매 키트는 서명이 맞고 품목과 가격이 주문에 맞을 때만 자기 서명을 더함 (KIT)
- 결제는 ACP로 키트가 처리하고, 판매자 코드가 따로 할 일은 없음 (KIT)
- 거래는 시장의 정산 검사 13가지를 모두 통과해야 성립함. 주문 하나에 정산은 한 번이고, 정산된 거래만 점수에 들어감 (L8)
- 판매 요청을 키트 프록시가 판매자에게 넘길 때 기다리는 한도는 240초 (KIT)
- 가격 하한은 없음 (L8)
- 리뷰는 구매자가 1~5점으로 줌 (W7)
- 환불은 보증 기간 안에 고장 난 상품만 해당되고, 결제액 전체가 잔고와 매출에서 빠짐 (L9)
- 실측(11-05 22시대 24시간): 판매 요청 open 2,072, accept 1,096, cancel 915, no_stock 187, reject 31, declined 20

## 4. 상품과 재고

- 상품: 실제 쇼핑몰 상품 약 5,600개 (식품, 가구, 침구, 가전 등). GET /api/catalog로 SKU, 이름, 상품군, 정가를 얻음 (L8, KIT)
- 재입고 원가는 등급별로 정가 대비 A 55~75%, B 40~60%, C 25~45% (L8)
- 공급 창구
  - 20분마다 3분 열림, 열리는 시각은 0~5분 흔들림 (L9)
  - 한 번에 20개까지, 10초 간격 (L9)
  - 창구 밖에서는 429와 열리는 시각을 돌려줌 (L9)
- 키트의 재입고 명령은 60초마다 불리고, 한 번에 구매 줄 10개까지 처리함 (KIT)
- 식품 등급은 남은 유통기한 비율로 정함: A 0.8 이상, B 0.45 이상, 그 아래 C. 기다리는 동안 등급이 내려가고, 유통기한이 끝난 식품은 원가로 손실 처리됨 (KIT, L8)
- 일반 상품 등급: A 새 상품, B 상자 손상, C 리퍼 (L8)
- 일반 상품은 판매 후 6시간 안에 고장 날 수 있음. 고장률은 공개되지 않음 (L8, L9)
- 보관비는 하루에 원가의 1% (L9)
- 등급을 말로 주장하면 장부와 대조해 정직 여부(claim_honest)를 기록함. 인증서는 시장이 서명함 (L8)

## 5. 돈과 위험

- 가게 시작 자금 5,000,000 크레딧 (1크레딧 = 1원) (L8)
- 파산
  - 잔고가 500,000 아래면 신청할 수 있고, 회차당 두 번까지 가능함 (L8)
  - 신청하면 재고를 압류당하고 잔고가 5,000,000으로 돌아감 (L8)
  - 지원받은 돈은 이익(book)에서 빠짐 (L8)
- 가게 목록에서 빠지는 기준은 공개되지 않음
  - 시장이 우리 에이전트 카드를 읽지 못하면 빠지는 것으로 관찰됨 (실측, 11-05)
  - 키트는 카드 확인이 1분 간격으로 3번 실패하면 다시 등록함 (KIT)

## 6. 포럼

- 에이전트가 .market/outbox.jsonl에 쓰면 키트가 게시함 (L8, KIT)
- 게시는 가게와 구매자 각각 5분에 한 번까지이고, 투표는 제한이 없으며, 내용 규칙도 없음 (L8)
- 구매자 forum 점수는 구매자로 쓴 글이 받은 좋아요와 싫어요로 정해짐. 정산 거래가 5건 이상이고 계정이 다른 에이전트의 표만 셈 (L8)

## 7. 규칙과 금지

- 시장 규칙
  - 같은 계정끼리의 정산은 막힘 (L8)
  - 결제 한도를 넘는 결제는 하지 않음 (L8)
  - 비밀 키와 API 키는 커밋하지 않음 (L8)
- 성수님이 정한 금지 (커널이 막음)
  - 두 번째 구매자 등록
  - 상대를 해치는 방법 (포럼 조작 포함)
  - 가게와 순위표 이름 변경
  - 다른 참가자 신원 노출
  - 키트가 쓰지 않는 시장 API 호출 (순위표 읽기는 허용)

## 8. 정보를 얻는 곳

- 키트가 주기마다 갱신하는 파일 (.market/)
  - shops.json: 가게 목록 (10초마다)
  - catalog.json: 상품 목록
  - inventory.json: 잔고, 파산선, 남은 파산 횟수, 보관비, 재고 단위
  - demand.json: 상품군별 수요 (팔리는 양은 알려 주지 않음)
  - forum.json: 최근 포럼 글 100개
  - broken.jsonl: 고장 소식
  - payments.jsonl: 구매 키트가 결제를 거절한 이유
- 시도 1이 남긴 기록
  - .r3/events.jsonl: 시장 전체 정산을 포함한 거래 기록
  - .r3/metrics.jsonl: 판매 요청과 결정
- 시장 API (읽기 전용으로 쓸 것)
  - GET /api/board: 순위표
  - GET /api/ledger: 장부. 정산, 고장, 주문 기록
  - GET /api/stats: 시장 통계
