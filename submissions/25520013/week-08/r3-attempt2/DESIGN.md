## 1. 목적과 원칙

- 목적: R3 순위 1위
- 원칙은 bitter lesson(Sutton, 2019)을 따름. 사람이 짠 전략보다 강한 모델이 정확한 정보로 내린 판단이 낫다는 가정임
  - 사람이 주는 것: 목표, 정보, 게임 규칙
  - 모델이 정하는 것: 협상 하나하나의 판단, 재고와 가격 운영, 어느 주문에 힘을 쓸지, 그리고 이 판단을 내리는 하네스 자체(프롬프트, 메모리 쓰는 방식, 하위 에이전트 구성, 스크립트)
  - 수정이 좋았는지도 모델이 결과를 보고 판단함. 사람이 짠 A/B나 채택 절차는 두지 않음
- week-06에서 성수님이 만든 구조를 그대로 넓힘: 판단은 모델이 하고, 한계는 코드가 강제함 (week-06 REPORT.md 2절)

## 4. 전체 구조

세 층으로 나눔

- 고정 커널: 사람이 쓴 코드이고 모델이 고칠 수 없음. 시장 연결, 규칙 강제, 수집, 기록, 안전장치를 맡음 (10절에 전부 나열)
- 하네스: 모델이 읽고 고치는 파일 묶음. 에이전트마다 하나씩 있음
- 모델: gpt-6.1-terra

에이전트는 처음에 셋으로 시작하고, 구성은 운영자가 바꿀 수 있음

| 에이전트 | 깨어나는 때 | 하는 일 |
| --- | --- | --- |
| 운영자 | 주기 점검 (처음 30분, 간격은 운영자가 바꿈), 마지막 수정 뒤 요청이 운영자가 정한 건수만큼 쌓였을 때, 큰 사건 (순위 급변, 가게 목록에서 빠짐, 파산선 접근) | 브리핑과 도구로 상황을 보고, 판매자와 구매자의 하네스를 고침. 하위 에이전트를 추가하거나 지움. 재입고 계획을 씀 |
| 판매자 | 구매자 요청이 올 때 (A2A) | 가격 제시, 수락, 거절. 운영자가 정한 방식대로 모델 호출 또는 모델이 쓴 스크립트로 처리 |
| 구매자 | 주문이 올 때 (구매 명령, 300초) | 주문마다 모델을 한 번 불러 계획을 씀: 시도할 가게와 SKU 순서, 첫 제안가와 이어지는 가격 단계, 받아들일 상한(이 값 이하로 부르면 받음). 협상은 커널이 계획대로 기계적으로 실행하고 라운드마다 모델을 부르지 않음. 모델 시간 초과와 한도 거절은 브리핑에 남고, 운영자가 필요하면 구매자를 모델이 쓴 스크립트로 돌림 (성수님 결정 2026-11-05) |

- 재입고는 60초마다 불리므로 매번 모델을 부르지 않음. 운영자가 쓴 재입고 계획(데이터)을 커널이 실행함
- 운영자가 쓴 스크립트는 격리 실행함: 네트워크 없음, 시간 제한, 출력은 커널의 규칙 강제를 다시 통과함

## 5. 목표와 브리핑

- 목표 문장: 최종 순위표 Everyone 보기의 total 1위 (성수님 결정 2026-11-05). Class 보기(student_total, 학생끼리 다시 매긴 백분위)는 참고로 함께 보여 줌. 점수 공식을 그대로 줌
  - 가게 점수 = 0.5 pct(Book) + 0.3 pct(Revenue) + 0.2 pct(Stars)
  - 구매자 점수 = 0.5 pct(surplus) + 0.3 forum + 0.1 deals + 0.1 posts
- 브리핑: 커널이 주기마다 새로 만들어 운영자에게 줌. 해석 없이 사실만 담음
  - 지금 순위와 1위, 2위와의 점수 차, 항목별 백분위
  - 상위 가게들의 시간당 매출, 거래, 거래당 매출, book 증가([상위 가게]), 상품군별로 우리 제시가 어떻게 끝났는지와 SKU별 우리 제시가 대 시장 체결가([협상 결과]; 판매자가 구매자가 닫거나 응답이 끊긴 협상을 a2_deal_end로 남김). 운영자 지시문 목표에 '순위를 지키는 것이 아니라 total을 올림, 11-06 기준 차이는 가게 쪽'을 넣음 (성수님 결정 2026-11-06 13시: 2위에서 유지로만 판단하고 가게 경쟁력을 올리지 않음)
  - 최근 6시간 우리 가게 리뷰를 판매와 주문 번호로 이어 계정별 평균의 평균(패치 3.4 별점의 셈 단위), 평균이 낮은 계정(해시 id), 등급별과 상품군별 평균([별점]) (성수님 결정 2026-11-06 16시: 별점 순위가 13위에서 18위로 밀렸는데 운영자 브리핑에는 리뷰 전체 평균만 있었음)
  - 동시 비교는 3시간이 지나면 커널이 판정 없이 끝내고 지금 판을 유지함(versions.TRIAL_MAX_H, 운영자가 깨어날 때 확인, 브리핑에 남은 시간 표시). 비교 중에는 판매자를 고칠 수 없어서, 작은 차이 하나가 판매자를 하루 동안 묶지 않게 함 (성수님 결정 2026-11-06 16시 6시간, 16:30 3시간으로; 판마다 약 450건이면 판매/요청 차이 약 0.07 이상이 드러남, 추정)
  - 2026-11-06 17시부터 동시 비교는 꺼져 있음(versions.TRIAL_ENABLED = False, 성수님 결정): 3시간 비교로도 작은 차이는 판정되지 않고 그동안 판매자를 못 고쳐 대응만 늦어짐. 운영자는 판매자를 edits로 바로 고치고 약 1시간 뒤 [판별 성과], [상위 가게], [협상 결과], [별점]으로 유지, 다시 수정, 되돌리기를 정함. trial 요청은 커널이 이유와 함께 거절하고, 장치와 테스트는 남겨 둠
  - 가게 all 0.90 목표(성수님 2026-11-06 17시): 브리핑 [가게 목표]가 공식(0.5 book + 0.3 revenue + 0.2 stars_rank, 전체 가게 중간 순위 백분위; 순위표 all과 오차 최대 0.0005)으로 항목별 순위, 위 가게까지 차이와 그 가게 속도, 그 순위에서의 all을 보여 주고, [이익]이 판 물건 원가를 이어 상품군별 총이익과 시장 몫을 보여 줌. 어느 항목을 어떻게 올릴지는 운영자가 정함

  - 가게와 구매자 항목마다 바로 위 3곳까지의 차이와 한 계단이 all에서 갖는 값(가중치 / (가게 수 − 1), 추정). 항목마다 오르기 쉬운 정도가 다르다는 사실만 주고 어느 항목을 올릴지는 운영자가 정함 (성수님 결정 2026-11-06: 별점 stars_rank는 0.01에 3계단, 매출은 한 계단에 +22%라서)
  - 최근 구간의 장부: 매출, 잔고, 평점, 잉여, 시간당 변화
  - 시장 변화: 가게 수, 시장 전체 정산 수, 가격 분포
  - 우리 재고와 유통기한
  - 지난 브리핑 이후 운영자가 고친 것과 그 뒤의 숫자
  - 게임 규칙과 금지 행동 (10절)
  - 남은 시간, 최근 호출 거절 횟수
- 판매자와 구매자에게는 요청 하나에 필요한 부분만 줌: 주문 내용, 해당 SKU 재고와 시세, 상대 구매자나 가게에 대한 메모리

## 6. 관찰과 도구

- 원본 로그가 큼 (거래 기록 최근분만 12MB를 읽음). 도구는 먼저 요약을 돌려주고, 모델이 원하면 세부로 파고드는 방식
- 관찰 하나는 크기 상한을 둠 (처음 4천 토큰, 추정). 넘으면 잘라 내고 잘린 사실과 세부 조회 방법을 함께 알려 줌

| 도구 | 쓰는 에이전트 | 돌려주는 것 |
| --- | --- | --- |
| board | 운영자 | 순위표 요약 (다른 참가자는 해시 id) |
| ledger | 운영자 | 기간별 장부 요약 |
| events | 운영자 | 조건으로 거른 거래 기록, 처음엔 개수와 표본 |
| shops, catalog, inventory | 전부 | 가게 목록, 상품 목록, 우리 재고 |
| memory_search | 전부 | 빠른 층에서 찾은 사실 |
| trajectory_find | 운영자 | 깊은 층 궤적 파일 검색 (grep과 파일 읽기) |
| harness_read, harness_write | 운영자 | 하네스 파일 읽기와 고치기 (커널이 버전을 남김) |
| script_run | 운영자 | 쓴 스크립트를 지난 기록에 돌려 본 결과 (실제 거래 없음) |
| shadow | 운영자 | 실제 요청에 다른 하네스 판이 어떤 결정을 냈을지 기록만 함 |

- script_run과 shadow는 쓸 수 있는 도구일 뿐 반드시 거쳐야 하는 절차가 아님. 쓸지 말지는 운영자가 정함

## 7. 메모리

| 층 | 쓰는 때 | 방식 | 근거 |
| --- | --- | --- | --- |
| 빠른 층 | 판매자와 구매자의 요청 처리 | mem0에는 코드로 집계할 수 없는 것만 저장하고 몇 개만 찾아옴: 운영자의 회고와 교훈, 하네스 판별 결과 요약, 구매자 쪽에서 본 가게별 협상 버릇 | 요청당 응답 시간이 중요함 |
| 깊은 층 | 운영자의 주기 점검과 하네스 수정 | 궤적 원본을 파일로 두고 운영자가 도구로 찾아봄 | LME-V2에서 이 방식 72.5%, RAG 최고 48.5%. Meta-Harness도 같은 결론 |

- 궤적 파일 한 줄: 시각, 에이전트, 하네스 버전, 받은 입력 요약, 도구 호출과 관찰, 결정, 나중에 붙는 결과 (거래 성사, 가격, 평점)
- mem0의 사실 추출도 모델 호출이라 호출 한도에 들어감. 무엇을 저장할지는 하네스의 memory.json에서 모델이 정함
- 판매자는 요청에서 구매자가 누구인지 볼 수 없음 (요청마다 A2A context_id가 다름). 그래서 구매자 성향 기억은 두지 않음
- SKU별 시세와 성사율 같은 숫자는 정산 기록을 그대로 mem0에 넣지 않고 커널 도구가 집계해 보여 줌. 정산을 그대로 넣으면 하루 5,286건에 terra 약 265번이 들고 (실측 11-05: 20문장 묶음 하나에 21~23초), 코드 집계보다 부정확함 (성수님 결정 2026-11-06)
- 정산 기록의 own_owner는 우리 가게 판매와 우리 구매자 구매 둘 다에 켜짐 (실측 11-05: 24시간 5,286건 중 판매 2,764, 구매 2,522). 어느 쪽인지는 구매자 칸으로 가름
- 메모리 점검: LongMemEval-V2의 다섯 능력으로 우리 시장 질문 세트를 만듦. 6시간마다 한 번 (한 번에 terra 15번), 질문은 mem0에 넣는 내용(교훈, 판별 결과, 가게 버릇)에 맞춤

| LME-V2 능력 | 질문 예 |
| --- | --- |
| 정적 상태 기억 | Book 점수의 가중치는? 이 SKU의 정가는? |
| 동적 상태 추적 | 3시간 전 우리 순위는? 지금 소파 재고는? |
| 작업 흐름 지식 | 협상이 정산까지 가는 단계는? |
| 환경의 함정 | 가게가 목록에서 빠지는 조건은? 특정 구매자의 낮은 평점 패턴은? |
| 전제 확인 | 존재하지 않는 거래를 전제로 한 질문에 그렇지 않다고 답하는가 |

- 시도 1의 evals/memory_eval과 evals/answer.py가 LongMemEval 1판의 능력(정보 추출, 여러 세션 추론, 시간 추론, 지식 갱신, 답 보류)으로 같은 일을 하고 있어 틀을 넓혀 씀
- 점검 결과는 브리핑에 들어가고, 메모리 설정을 고칠지는 운영자가 정함

## 8. 컨텍스트 관리

- 호출마다 컨텍스트를 네 부분으로 채우고, 부분마다 상한을 둠 (처음 값, 추정)

| 부분 | 판매자, 구매자 | 운영자 |
| --- | --- | --- |
| 하네스 (system, skills) | 2천 토큰 | 4천 토큰 |
| 브리핑 또는 요청 내용 | 1천 토큰 | 6천 토큰 |
| 메모리에서 찾은 근거 | 1천 토큰 | 도구로 필요할 때 |
| 도구 관찰 | 해당 없음 | 관찰 하나 4천 토큰, 한 번의 점검에 합계 3만 토큰 |

- 운영자는 긴 기록을 컨텍스트에 쌓지 않음. 지난 점검 내용은 궤적 파일에 있고 필요할 때 도구로 찾아봄
- 상한 값 자체도 하네스 설정이라 운영자가 바꿀 수 있음. 커널은 모델의 최대 입력 크기만 지킴

## 9. 하네스 자기 수정

운영자가 점검 때마다 하네스를 고칠 수 있음. Harness²의 두 겹 재귀를 시장에 맞게 옮김

Harness²가 실제로 하는 일 (논문 2.2절, 2.3절, 부록 H, 저장소 core/recursion.py, core/library.py)

- 제안(Propose)
  - 편집 세션 둘이 하네스 파일을 직접 고침
    - 하나는 절차와 도구 사용을 봄
    - 다른 하나는 해당 분야 지식을 봄
  - 고칠 때마다 궤적의 어느 순간을 보고 고쳤는지 근거를 적음
  - 고치지 않는다(KEEP_BASE)는 답도 허용함
- 탐색(Probe)
  - 고친 판을 같은 작업, 같은 모델, 같은 환경에서 한 번 돌림
  - 별도 채점자나 점수는 없음
- 결합(Compose)
  - 같은 모델이 원래 판과 고친 판의 궤적, 결과물, 차이를 읽고 수정마다 유지, 수정, 폐기를 정함
  - 기준
    - 여러 번 반복된 실패는 강한 근거이고, 한 번만 나온 결함은 잡음으로 봄
    - 나빠질 가능성도 좋아질 가능성만큼 따짐
    - 결과물을 못 낸 수정은 위험으로 봄
- 하네스 단위
  - 작업이 끝나면 회고 세션이 수정별 효과(도움, 해로움, 효과 없음, 판단 불가)와 교훈 한 개를 씀
  - 교훈이 있을 때만 그 판의 하네스 전체와 함께 분야별 라이브러리에 저장함
- 논문에서 탐색과 라이브러리를 빼고 고치기만 하면 오히려 나빠졌음 (WB-Code 73.4 → 63.2, 그림 7). 그래서 우리도 근거를 남기며 고치고 경험을 쌓게 함

시장에 옮길 때 달라지는 점

- 같은 작업을 다시 돌릴 수 없음
  - 시장에서는 같은 구매자의 같은 주문을 재현할 수 없음
  - 그래서 탐색은 shadow 도구로 함: 실제로 들어온 같은 요청에 고친 판이 낸 결정을 기록함
  - 다만 협상이 여러 번 오가면 고친 판의 첫 결정만 관찰되고, 그 뒤 결과는 알 수 없음
  - 재입고 계획이나 스크립트는 script_run으로 지난 기록에 돌려 볼 수 있음
- 되먹임을 빠르게 (성수님 결정 2026-11-06)
  - 순위표 점수는 백분위라 효과가 몇 시간 뒤에 보임. 그래서 커널이 판단 기록의 하네스 판 번호와 정산 기록을 이어 판별 성과(요청 수, 성사율, 정가 대비 가격, 별점)를 브리핑에 바로 보여 줌. 판정은 운영자가 함
  - 판 사이 성사율은 시간대와 요청 구성이 달라 그대로 비교하면 판정이 안 남 (실측 11-06 01~09시: 운영자 효과 판단 75건 중 74건이 판단 불가). 그래서 커널이 상품군 구성을 이전 판에 맞춘 판매/제시, 같은 시간 시장 전체 정산 중 우리 몫(시장 점유), 상품군별 2시간 흐름과 시장 체결가를 함께 보여 줌. 판정은 여전히 운영자가 함
  - 동시 비교(trial, 판매자만): 운영자가 후보 판을 올리면 커널이 라이브러리에 보관만 하고, 새 판매 요청을 task id 해시로 지금 판과 후보 판에 나눔(비율 0.1~0.9). 같은 시간, 같은 종류의 요청을 받으므로 판 차이만 남음. 진행 중에는 판매자 edits와 revert를 막고, 채택(trial_end adopt)하면 후보를 새 판으로 설치함. 후보가 깨져 있으면 그 요청은 지금 판이 답함. 별점은 거래 단위로 이어지지 않아 판별로 나누지 않음 (성수님 결정 2026-11-06)
  - 운영자 지시문에는 목표, 점수 공식, 시장 사실, 커널 규칙만 둠. 처음 지시문의 "고치지 않는 것도 답", "결과를 못 낸 수정은 위험" 같은 사람의 판단 기준은 11-06에 뺌: 운영자가 9시간 반 동안 판매자 수정 1번에 그쳤고, 판단을 모델에 맡긴다는 설계와 맞지 않았음 (성수님 결정 2026-11-06)
  - 요청은 시간당 약 305건, 판매는 약 115건 (실측 11-04~05). 30분이면 요청 약 150건으로 성사율 약 8%p 차이를 가려낼 수 있음 (추정)
  - 운영자는 시계 간격과 함께 마지막 수정 뒤 요청이 정한 건수만큼 쌓이면 바로 깨어남. 건수는 운영자가 정함
  - 적용 전 탐색 도구 replay_probe: 고친 판을 기록된 요청 수십 건에 돌려 결정이 의도대로인지 몇 분 안에 봄. 쓸지는 운영자가 정함
- 결합은 운영자가 직접 함. Harness²처럼 별도 판정자를 두지 않고 같은 모델이 궤적을 읽고 정함
- 회고와 라이브러리
  - 점검마다 운영자가 수정별 효과 표와 교훈 하나를 씀
  - 라이브러리는 library/INDEX.md, library/harnesses/판번호/(하네스 전체), library/harnesses/판번호/EXPERIENCE.md
- 점수를 보여 줌
  - Harness²는 편집 세션에 점수나 채점 기준을 일부러 숨김 (부록 D.2, core/context.py)
  - 이 설계는 성수님 의도대로 목표와 점수를 운영자에게 그대로 보여 줌
  - 대신 점수를 올리는 지름길로 쓰일 수 있는 행동은 커널 규칙으로 막음 (10절)

안전장치

- 커널은 고친 판마다 버전을 남기고, 운영자가 언제든 이전 판으로 돌아갈 수 있게 함
- 고친 판은 적용 전에 형식 검사를 거침 (Harness²의 validate와 같은 수준)
  - 편집 가능한 경로 밖의 파일이면 거절
  - 스킬의 머리말이 빠졌으면 거절
  - 파이썬이 컴파일되지 않으면 거절
  - 부르는 스크립트가 없으면 거절
  - 늘 읽히는 파일이 상한을 넘으면 거절
  - 검사에 걸리면 운영자에게 오류를 돌려주고 한 번 더 고치게 함
- 마지막으로 정상 작동한 판은 커널이 따로 보관함. 하네스가 깨져 요청을 처리하지 못하면(형식 오류, 시간 초과가 이어짐) 커널이 그 판으로 되돌리고 운영자에게 알림. 이는 작동 여부만 보는 안전장치이고 성과 판정은 하지 않음

| 항목 | 내용 | 종류 |

| 시장 연결 | 키트 v4의 A2A 판매, 구매 명령, 재입고 명령, ACP 결제 경로를 그대로 씀 | 규칙 |

## 12. 위험

- 남은 기간이 짧아 운영자가 쌓을 경험이 적음. bitter lesson의 이점은 데이터가 쌓일수록 커짐
