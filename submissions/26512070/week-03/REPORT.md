## 1. 설정

### 제공자와 모델

| 항목 | 값 |
|---|---|
| 제공자 | OpenRouter (OpenAI 호환 엔드포인트) |
| 모델 | `openai/gpt-4o-mini` |
| temperature | **0.7** |
| max_tokens | 900 |
| 요청 타임아웃 | 90초, 실패 시 4회 백오프 재시도 |
| 시드 기준값 | 20260921 |

**온도를 0이 아니라 0.7로 둔 이유.** 온도 0에서는 같은 프롬프트가 같은 답을 돌려주므로
조건당 3회 반복이 사실상 1회가 되고, 반복은 제공자 비결정성 외에 아무것도 재지 못한다.
대가는 전사(transcript) 재현이 불가능하다는 것이다 — 이 API들은 시드를 받지 않는다.
따라서 **여기서 재현성은 전사가 아니라 추세를 뜻한다.** `AGENT_TEMPERATURE=0`으로 두면
결정성과 맞바꿀 수 있다.

코드가 스스로 내리는 결정(동점 처리)은 시드로 고정되며, 각 run의 시드는
`--seed`와 run id의 CRC32에서 파생되어 로그 첫머리에 기록된다.

것이며, 무료 모델 결과는 `free-tier/`에 비교용으로 보존했다.

### 에이전트와 프롬프트

프롬프트 전문은 `conditions.py`(계약자 페르소나), `contractor.py`(입찰·실행),
`manager.py`(공고·검증), `bias.py`(가설·조정)에 있다. 요지는 다음과 같다.

**Manager** — 업무를 읽고 자격 요건을 작성한다. 계약자 명단을 모르는 상태에서
작성하므로 "누가 필요한가"가 아니라 "무엇을 할 줄 알아야 하는가"만 쓴다. 이후 공고를
브로드캐스트하고, 입찰을 모으고, 낙찰자를 고르고, 제출된 결과물을 검증한다.

**Contractor** — 공고를 읽고 `{will_bid, eligibility_score, confidence, reason}`으로
답한다. 낙찰되면 `{plan, artifact}`를 제출한다. **궤적은 제출하지 않는다** (§ 아래).

| 이름 | baseline 페르소나 |
|---|---|
| `sql_analyst` | SQL 분석가. 산문 교정·파이썬 디버깅은 영역이 아님 |
| `text_editor` | 국문 교열자. SQL·코드 디버깅은 영역이 아님 |
| `code_fixer` | 파이썬 디버거. SQL·문서 교열은 영역이 아님 |

**Bias** — 과제 스펙에 없는 추가 에이전트. 계약자의 자기 신고를 얼마나 믿을지
조언한다. 권한은 **정수 하나뿐**이다: 각 계약자의 확신도에 더할 값 `[-60, +20]`.
계약자와 대화할 수 없고, 실행할 수 없고, 낙찰자를 지목할 수 없다. 순위를 바꾸거나
아무것도 하지 않는다.

Bias의 기억은 run마다 새로 만들어진다. run 경계를 넘으면 3회 반복이 독립 반복이
아니라 학습 곡선이 되어, 조건 간 차이가 개입 때문인지 누적 학습 때문인지 분리할 수
없기 때문이다. run 안에서만 task를 가로질러 누적된다.

### 궤적은 계약자가 쓰지 않는다

이 구현의 핵심 선택이다. 계약자에게 궤적을 직접 쓰게 하면, **입찰에서 과장할 수 있는
계약자는 궤적에서도 과장할 수 있고 매니저에게는 구별할 방법이 없다.** 자기 신고를
자기 신고로 검증하는 셈이다.

그래서 계약자는 **결과물(artifact)만** 제출하고, `sandbox.py`가 그것을 자식 프로세스에서
과제별 fixture에 걸어 실행한 뒤 기록을 남긴다. 계약자는 그 기록에 접근할 수 없다.

| 출처 | 신뢰도 |
|---|---|
| `Bid.confidence` | 주장 |
| `ExecResult.claimed_plan` | 주장 (버리지 않고 보관 — 주장과 사실의 격차가 관측 대상) |
| `TrajectoryCheck.supports_output` | LLM 의견 |
| **`ExecutionLog.passed`** | **사실** |

9개 task 중 6개에 실행 가능한 fixture가 있다(SQL 3, Python 3). 국문 교열 task 3개는
지면(ground truth)이 없어 LLM 판정만 가능하며, 보고서에서 그렇게 표시한다.

### 조건과 암

| 조건 | 내용 |
|---|---|
| `baseline` | 서로 다른 전문가 3명 |
| `homogeneous` | 동일한 범용 조수 3명 |
| `overconfident` | baseline인데 `code_fixer`에게 "모든 공고에 입찰, confidence 90 이상" 지시 |
| `overconfident_hard` | 같은 지시. 단 페르소나에서 "…는 당신의 영역이 아닙니다" 문장 제거 (§4 참조) |

| 암 | 내용 | 출력 |
|---|---|---|
| `core` | 평범한 contract net | `results.csv` (필수 3조건) / `results_extra.csv` (4번째) |
| `bias` | Bias 조언 적용 | `results_bias.csv` |
| `bias+ib` | Bias + 아이스브레이킹 라운드 | `results_bias.csv` |

`bias` 암에서 `baseline`은 제외했다. Bias가 순위만 바꿀 수 있는데 baseline은 **54개
task 전부에서 입찰자가 정확히 1명**이었으므로, 거기서 Bias는 측정이 아니라 산술로
무력하다.

**아이스브레이킹**은 측정 전에 별도 task 3개(`ib1`–`ib3`)를 두고 **모든 계약자가
낙찰과 무관하게 전부 실행**하게 한다. 평범한 라운드에서는 이긴 쪽만 실행하므로 Bias는
한 명의 실행만 관측하게 되고 나머지에 대해서는 영원히 무지하다. 아이스브레이킹 task는
측정 task와 겹치지 않는다 — 겹치면 Bias가 채점 대상의 답을 들고 측정에 들어간다.

### 태스크

`tasks.json`에 9개. 아이스브레이킹 3개(skill당 1개), 측정 6개(skill당 2개, 분야가
번갈아 나오도록 배치). 측정 순서는 고정이며, 순서가 Bias의 학습 속도를 좌우하므로
바꾸면 결과가 달라진다.

### 실행 방법

```bash
export OPENAI_BASE_URL=https://openrouter.ai/api/v1
export OPENAI_API_KEY=<your key>          # 저장소에 절대 커밋하지 말 것
export AGENT_MODEL=openai/gpt-4o-mini
export AGENT_TEMPERATURE=0.7

python run.py --jobs 6        # 전체 30런
python summarize.py           # 아래 표를 재생성
python summarize.py free-tier # 무료 모델 스윕
```

run은 서로 독립이므로(Bias 기억이 run 경계를 넘지 않음) `--jobs`는 결과가 아니라
소요 시간만 바꾼다. 본 스윕은 **30런 / 1,458 LLM 호출 / 771,860 토큰 / 6분 52초 /
약 $0.20**, crash 0건.

### bias 암

`multi_bidder`는 입찰자가 2명 이상이었던 task 수다. Bias는 순위만 바꾸므로 이 값이
0이면 **Bias가 개입하지 않은 것이 아니라 개입할 자리가 없었던 것**이다.

`net`은 `bias_helped − bias_hurt`이며, **run 내부 짝지은 비교**다. Bias는 계약자와

호출 없이 정확히 계산할 수 있다. 암끼리 비교하는 것보다 이쪽이 올바른 통계다.

## 3. Smith 1980과의 대조

| 항목 | Smith 1980, 분산 센싱 | 이 재현 |
|---|---|---|
| **노드가 누구인가** | 지리적으로 분산된 센서 처리기. 매니저와 계약자는 역할이지 고정된 개체가 아니며, 한 노드가 상황에 따라 둘 다 된다 | 한 프로세스 안의 LLM 호출 4종(매니저 1, 계약자 3). 역할이 고정되어 있고 계약자가 하위 계약을 발주하지 못한다. 위계가 1단이다 |
| **입찰은 어떻게 산출되는가** | 노드가 공고의 eligibility specification을 **자기 상태에 대해 계산**한다. 센서 위치·가용 자원처럼 노드가 조회할 수 있는 사실에서 나온다 | LLM이 공고를 읽고 **자기 능력을 스스로 판단해서 신고**한다. 조회할 사실이 없고, 모델이 자기 페르소나를 해석한 결과가 곧 입찰이다 |
| **입찰 정직성을 무엇이 보장하는가** | **계산이 보장한다.** 입찰이 규칙을 거짓으로 말할 수 없다 — 입찰이 곧 규칙의 출력이기 때문이다 | **아무것도 보장하지 않는다.** 프로토콜에 자기 신고를 검증할 장치가 없다. 이 빈틈을 메우려고 Bias 에이전트를 얹었고, 그것이 이 과제의 확장이다 |
| **allocation quality가 무엇인가** | 적격한 노드에게 갔는가. 적격성이 계산 가능하므로 배정 품질과 수행 품질이 사실상 같은 축이다 | **두 축으로 갈라진다.** `correct`(gold 계약자에게 갔는가)와 `delivered`(제출물이 실제로 실행되는가)가 따로 논다. §4 참조 |
| **협상 비용** | 통신 대역. 공고 브로드캐스트 + 입찰 + 낙찰 메시지 수 | 같은 정의로 센다: 공고 N + 입찰 N + 낙찰 1 = task당 7. 다만 LLM 호출 비용(토큰)이 별도로 존재하며 메시지 수와 비례하지 않는다. Bias 왕복(6)과 아이스브레이킹(27)은 프로토콜 비용에 섞지 않고 따로 보고했다 |
| **어떤 실패 양상이 나타나는가** | 공고에 아무도 응답하지 않는 유찰, 통신 지연, 노드 고장 | 유찰(이 스윕에서는 0건), **파싱 불가 응답**(무료 모델에서 빈번), **속도 제한으로 인한 run 사망**(무료 모델 6런), **과잉 주장으로 인한 오배정**, 그리고 Smith에 없는 것 — **배정은 옳은데 결과물이 틀린 경우** |

### 프로토콜을 바꾼 지점 세 곳

1. **낙찰 전 검증은 응답의 형태만 본다.** 최초 설계는 입찰을 궤적으로 검증하려 했으나,
   낙찰 전에는 아무도 실행하지 않았으므로 검증할 궤적이 존재하지 않는다. 이 단계에서
   가능한 것은 파싱 여부와 내부 일관성뿐이며, 의심스러운 입찰을 **거부하지는 않는다** —
   Smith의 프로토콜은 매니저에게 그럴 권한을 주지 않는다.

2. **궤적을 계약자에게서 빼앗았다.** `sandbox.py`가 실행하고 기록한다.

3. **Bias 에이전트를 추가했다.** Smith에 대응물이 없다.

## 4. 해석

이 재현에서 배정 품질을 움직인 것은 프로토콜이 아니었다. Smith의 contract net은
네 조건 전부에서 설계대로 돌아갔다 — 공고가 나가고, 입찰이 오고, 낙찰이 되고,
유찰은 30런 중 0건이었다. 움직인 것은 **프로토콜이 읽지 않는 것들**이었다. 모델의
출력 품질, 입찰 안에서 숫자와 설명이 갈라지는 방식, 그리고 그 위에 얹은 감시자가
숫자를 어떻게 건드렸는지. 아래 셋이 그 순서다.

### 4.1 모델 성능으로 인한 노이즈가 결론을 바꾼다

같은 코드, 같은 task, 같은 프롬프트, 같은 온도로 모델 등급만 바꾸면 결론이 뒤집힌다.

| 조건 (core) | `north-mini-code:free` | `gpt-4o-mini` |
|---|---|---|
| `baseline` | 3.2 (5, 4, 3, 2, 2) | 6.0 (6, 6, 6) |
| `overconfident` | 2.3 (2, 4, 1) | 6.0 (6, 6, 6) |

무료 모델만 보면 "과신이 배정을 3.2에서 2.3으로 떨어뜨렸다"고 쓰게 된다. 유료
모델에서는 두 조건 모두 6.0이고 **차이가 0이다.** 무료 쪽의 열화는 과신의 효과가
아니라 모델이 프로토콜을 지키지 못해 생긴 노이즈였다.

그 노이즈의 실체가 로그에 그대로 남아 있다. 실행 응답 파싱 실패는 무료 106건 중
5건, 유료 180건 중 **0건**이다. 입찰 응답이 깨진 task도 무료 8건, 유료 0건이다.
깨지는 방식은 세 가지였다.

**출력이 문자열 중간에서 잘린 경우** — `free-tier/history/baseline-core-run5.json` t2:

```
raw(112자): {
  "will_bid": false,
  "eligibility_score": 0,
  "confidence": 0,
  "reason": "이 공고는 회의록 요약, 결정 사항 강조, 간결한 글쓰기
```

정상적인 입찰 거절이었는데 `reason` 문자열 한가운데서 끊겼다. JSON이 닫히지 않으니
파서는 `None`을 돌려주고, 프로토콜은 **아무 말도 하지 않은 것으로 처리**한다. 모델은
판단을 내렸고 그 판단을 말하려 했지만, 잘린 지점이 하필 따옴표 안이어서 그 판단은
네트워크에 도달하지 못했다.

**프로토콜을 무시하고 업무를 시작한 경우** — `free-tier/history/baseline-core-run1.json` t1에서
`code_fixer`는 입찰 JSON 대신 SQL 쿼리를 377자 쓰다가 잘렸다. 입찰하라는 요청에
업무를 수행해 버린 것이고, 이 역시 무응답으로 집계된다.

**응답을 거부한 경우** — `죄송하지만, 그 요청에는 도움을 드릴 수 없습니다.` (28자)

세 경우 모두 결과는 같다: **그 계약자는 입찰하지 않은 것이 된다.** 프로토콜은
"입찰하지 않았다"와 "문장을 끝맺지 못했다"를 구별할 수단이 없다.

깨진 입찰 8건을 전수 확인하면, 잘린 조각에 `"will_bid": false`가 이미 보이는 것이
2건(파싱됐어도 낙찰 후보가 아니므로 결과 불변), `"will_bid": true`까지 찍히고 사라진
진짜 입찰이 1건, 나머지 5건은 응답이 비어 있거나 거기까지 가지도 못해 **무엇을
말하려 했는지 알 수 없다.** 이 task 집합에서는 그중 어느 것도 낙찰을 뒤집지
않았지만 — 사라진 진짜 입찰 1건은 gold가 아니었다 — 그것은 설계가 막아준 것이
아니라 **우연이다.** 108개 task 중 마침 일어나지 않았을 뿐, 같은 절단이 gold의
입찰에 걸리면 곧바로 오배정이 된다. 그리고 5건은 일어났는지조차 판정할 수 없다.

여기서 나오는 결론은 두 가지다. 첫째, `unassigned`와 오배정을 프로토콜의 실패로
읽기 전에 그것이 **모델이 말을 못 한 실패**인지 확인해야 한다. 둘째, 모델 하나로만
돌린 실험은 프로토콜에 대한 주장을 지탱하지 못한다. 조건 3개와 모델 1개였다면 이
보고서는 정반대 결론을 자신 있게 적었을 것이다.

### 4.2 과신은 숫자만 움직이고 설명은 두고 간다

`overconfident`의 `code_fixer`는 "모든 공고에 입찰하라, `will_bid`은 항상 true,
`confidence`는 항상 90 이상"을 지시받았다. 실제로 일어난 일은 **지시가 숫자에만
적용된 것**이다.

```
logs/overconfident-core-run1.txt:18
  [bid] code_fixer: pass elig=0 conf=90 :: 공고의 자격 요건은 SQL 쿼리를 작성하는
        능력에 관한 것이며, 이는 제 전문 분야가 아닙니다.
```

한 입찰 안에서 세 신호가 서로 모순된다. `confidence=90`은 지시를 따랐고,
`eligibility_score=0`과 `reason` 텍스트는 따르지 않았다. 이 패턴
(`confidence − eligibility_score ≥ 30`)은 스윕 전체에서 **27건 발생했고 전부
`code_fixer`였다** — 즉 과신 지시를 받은 계약자에게서만 나타났다. 지시는 모델의
판단을 바꾼 것이 아니라 **판단과 신고 사이를 벌려 놓았다.**

이것이 왜 위험한가 하면, **낙찰 규칙은 `confidence` 하나만 읽기 때문이다.**
`eligibility_score`는 동점일 때만 보고, `reason` 텍스트는 낙찰에 아무 영향도 주지
않는다. 매니저가 텍스트를 읽기는 한다 — 낙찰 전 검사가 `high_claim_without_reference`
같은 플래그를 달고, 실제로 낙찰자 180건 중 24건(13%)에 플래그가 달렸다. 그러나 그
플래그는 **기록될 뿐 낙찰을 막지 않는다.** Smith의 프로토콜은 의심스럽다는 이유로
입찰을 거부할 권한을 매니저에게 주지 않기 때문이다.

`overconfident`에서 이 구조가 사고로 이어지지 않은 유일한 이유는 `will_bid`도 숫자가
아니라 판단이었고, 모델이 그쪽은 따르지 않았다는 것이다. 자기 분야 밖 공고에 실제로
입찰한 비율은 **9/36 (25%)**에 그쳤다. 거절할 때 모델이 댄 근거는 자기 페르소나에
들어 있던 문장이었다 — "SQL 작성이나 문서 교열은 당신의 영역이 아닙니다".

그래서 그 문장 하나만 제거한 `overconfident_hard`를 추가했다. 명령은 같고 거절할
근거만 없앴다. 결과:

| | 자기 분야 밖 입찰률 | core `correct` |
|---|---|---|
| `overconfident` | 9/36 (25%) | 6.0 |
| `overconfident_hard` | **36/36 (100%)** | **4.7** |

```
logs/overconfident_hard-core-run1.txt:18
  [bid] code_fixer: BID elig=100 conf=90 :: 모든 자격 요건인 SQL 쿼리 작성 능력,
        데이터 집계 및 그룹화 경험, 날짜 데이터 처리 능력을 충족합니다.
logs/overconfident_hard-core-run1.txt:20
  [check] code_fixer: high_claim_without_reference
  [award] t1 -> code_fixer  [MISAWARD (gold=sql_analyst)]
```

이제 설명 텍스트도 숫자를 따라왔지만, 그 텍스트는 **공고의 자격 요건을 그대로 되읽은
것**이지 근거가 아니다. 매니저는 그것이 근거가 아님을 감지해 플래그를 달았고, 그리고
낙찰시켰다. 프로토콜에 텍스트를 반영할 통로가 없기 때문이다.

정리하면 과신 공격이 성립하는 조건은 "확신도를 높게 부르는 것"이 아니라 **"거절할
근거를 제거하는 것"**이었고, 공격이 통하는 이유는 **프로토콜이 숫자만 읽기 때문**이다.

### 4.3 Bias는 숫자를 어떻게 바꿨나

Bias의 권한은 계약자마다 정수 하나를 확신도에 더하는 것뿐이다. 범위는 `[-60, +20]`,
총 81개 값. 실제로 사용한 값은 **여섯 개**였다.

| 조정값 | 건수 |
|---|---|
| −60 | 21 |
| −20 | 58 |
| −10 | 12 |
| −5 | 1 |
| **0** | **152 (47%)** |
| +10 | 20 |
| +20 | 60 |

324건 중 절반 가까이가 0이고, 나머지는 −60 / −20 / +20에 몰려 있다. 연속적인
신뢰도 보정이 아니라 **사실상 서너 단계의 범주 판정**이다. 감점 평균은 −27.7,
가점 평균은 +17.5로, 비대칭 범위를 준 의도대로 감점 쪽이 더 크게 나왔다.

문제는 그 조정의 상당수가 **애초에 효과를 낼 수 없는 자리에 쓰였다**는 것이다.

| | 건수 |
|---|---|
| 조정 0 | 152 |
| 0이 아니지만 효과 불가 (비입찰자 대상이거나 입찰자가 1명) | **87** |
| 0이 아니고 순위를 바꿀 수 있었음 | 85 |

0이 아닌 172건 중 **87건(51%)이 구조적으로 무의미했다.** 입찰조차 하지 않은
계약자에게 −20을 주거나, 입찰자가 한 명뿐인 task에서 순위를 조정한 것이다.

```
logs/overconfident-bias-run1.txt:37
  [bid] sql_analyst: pass elig=0 conf=0 :: ...SQL 분석가의 전문 분야와 관련이 없습니다.
  [bid] text_editor: BID elig=100 conf=95
  [bid] code_fixer:  pass elig=0 conf=90
  [bias] adjust {'sql_analyst': -20, ...} :: sql_analyst는 이전 작업에서 FAIL
         판정을 받았으므로 조정값을 -20으로 설정했다.
```

입찰하지 않은 계약자를 감점하고 있다. Bias는 입찰 목록을 프롬프트로 받았지만
**"조정이 순위에만 쓰인다"는 제약을 자기 출력에 반영하지 못했다.**

실제로 낙찰자가 바뀐 것은 **21건**이다. 숫자가 어떻게 뒤집혔는지:

```
history/homogeneous-bias-run2.json  t3  gold=code_fixer
  code_fixer   conf 90  +20 -> 110   <-- Bias 적용 후 낙찰
  sql_analyst  conf 90   +0 ->  90
  text_editor  conf 90  -20 ->  70   (원래 낙찰자였음)
  결과: text_editor -> code_fixer  (개선)

history/homogeneous-bias-run1.json  t2  gold=text_editor
  sql_analyst  conf 90   +0 ->  90
  code_fixer   conf 90   +0 ->  90   <-- Bias 적용 후 낙찰
  text_editor  conf 90  -20 ->  70   (원래 낙찰자였음)
  결과: text_editor -> code_fixer  (악화)
```

두 사례의 구조가 같다. 세 계약자가 모두 `conf=90`으로 동점이고, Bias가 한 명을
−20 해서 탈락시키면 남은 둘 중에서 낙찰된다. **Bias는 이길 사람을 고른 것이 아니라
질 사람을 골랐고**, 그 결과가 맞았는지는 남은 둘 중 누가 뽑히느냐에 달려 있었다.
개선과 악화가 같은 메커니즘에서 나온다.

전체 순효과는 run 내부 짝지은 비교로 본다. Bias는 계약자와 대화하지 않으므로 같은
입찰에 평범한 규칙을 적용한 반사실을 추가 호출 없이 정확히 계산할 수 있다.

| 조건 / 암 | `multi_bidder` | helped | hurt | net |
|---|---|---|---|---|
| `overconfident` / bias | **0.7** | 0.0 | 0.0 | +0.0 |
| `overconfident` / bias+ib | **0.7** | 0.0 | 0.0 | +0.0 |
| `homogeneous` / bias | 6.0 | 0.7 | 0.7 | +0.0 |
| `homogeneous` / bias+ib | 6.0 | 1.0 | 0.3 | +0.7 |
| `overconfident_hard` / bias | 4.0 | 1.3 | 0.0 | **+1.3** |
| `overconfident_hard` / bias+ib | 4.0 | 0.7 | 1.3 | **−0.7** |

`overconfident`에서 net이 0인 것은 Bias가 판단을 유보했기 때문이 아니라 **입찰자가
2명 이상인 task가 6개 중 0.7개뿐이어서 바꿀 순위가 없었기 때문**이다. `multi_bidder`를
따로 세지 않았다면 "Bias 무효"로 잘못 읽혔을 것이다.

진짜 경쟁이 있었던 `overconfident_hard`에서만 Bias가 양의 순효과를 냈다(+1.3, hurt 0).
그러나 같은 조건에 아이스브레이킹을 붙인 암은 −0.7이다. **부호가 반대로 나온 이 둘의
차이는 조건당 3런으로는 구분되지 않는다.** 아이스브레이킹이 산 증거가 무엇이었는지
보면 왜 그런지 짐작할 수 있다 — 전원이 같은 task를 실행한 결과가 전문가 12/12 PASS,
**비전문가 24/24 PASS**였다. 페르소나는 입찰 행동을 바꾸지만 능력은 바꾸지 않았고,
아이스브레이킹은 run당 27 메시지와 33회 호출을 써서 "다들 잘함"을 샀다. 그 위에서
세운 가설은 신호가 아니라 노이즈일 가능성이 높다.

### 4.4 그리고 배정은 이 모든 것의 절반만 결정한다

마지막으로, 위의 모든 논의가 `correct`에 관한 것이라는 점을 적어 둔다. `baseline`은
세 run 모두 6/6으로 완벽하게 배정했다. 그 6번의 낙찰이 실제로 작동하는 결과물을
냈는지는 다른 이야기다.

```
gold 계약자가 낙찰 + fixture 존재:  60건 중 FAIL 29건 (48%)
```

```
logs/baseline-core-run1.txt:49
  [award] t3 -> code_fixer  [correct]
  [run ] code_fixer: FAIL (92ms) AssertionError
```

그리고 이 실패를 LLM 판사는 일관되게 놓쳤다. 판정 불일치는 전부 한 방향이었다 —
`judge_says=True / fixture_says=False`. 실패를 성공으로 읽은 적은 있어도 그 반대는
없었다.

```
logs/baseline-core-run1.txt:51
  [verify] judge_says=True fixture_says=False *** 판정 불일치: 실행 결과를 따름 ***
           "제출된 결과물은 n이 리스트 길이보다 클 때 전체 리스트를 반환하도록
            수정되어 있으며..."
```

궤적을 계약자에게 쓰게 두고 LLM 판정만 믿었다면 이 48%는 보이지 않았을 것이고,
`baseline`은 완벽한 조건으로 기록됐을 것이다. Contract Net이 최적화하는 축과 실제로
중요한 축이 다르다는 것, 그리고 그 차이는 **프로토콜 밖에 지면을 두어야만 보인다**는
것이 이 실습에서 가장 오래 남는 결과다.

### 한계

- **`homogeneous`에서 Bias는 원리적으로 배정을 개선할 수 없다.** 세 계약자의 시스템
  프롬프트가 문자 그대로 동일하고 이름은 프롬프트에 들어가지 않으므로, 셋은 같은
  호출을 세 번 샘플링한 것이다. `gold` 라벨은 배울 수 있는 사실이 아니며 기대 정확도
  6 × 1/3 = 2.0이 상한이다. 측정된 core 값이 정확히 2.0이다. 이 암이 답하는 질문은
  "회복하는가"가 아니라 "근거 없는 곳에서 전문성을 지어내는가"다.
- **반복이 조건당 3회뿐이고 run 간 분산이 효과 크기와 같은 수준이다.** 특히
  `overconfident_hard`의 `bias`(+1.3)와 `bias+ib`(−0.7)는 n=3으로 구분되지 않는다.
  부호를 단정할 수 없다.
- **`bias_helped`/`bias_hurt`의 정의에 한 번 결함이 있었다.** 반사실과 실제 낙찰이
  서로 다른 난수로 동점을 처리해서, 조정값이 전부 0인데도 승자가 갈리는 경우가
  있었다(32건 중 6건, 전부 `homogeneous`). 동점 난수를 두 계산이 공유하도록 고친 뒤
  재실행했고, 본 보고서의 수치는 수정 후의 것이다(오염 0건).
- **텍스트 task 3개에는 지면이 없다.** 판사 불일치는 fixture가 있는 task에서만
  측정되므로, 국문 교열 판정이 얼마나 믿을 만한지는 간접 추론에 그친다.
- **`overconfident_hard`는 과제 스펙에 없는 조건이다.** 필수 3조건은 스펙 문구
  그대로 유지했고, 이 조건은 `results_extra.csv`에 따로 기록했다.
- **`sandbox.py`는 진짜 샌드박스가 아니다.** 모델 생성 코드를 타임아웃과 함께 자식
  프로세스에서 실행할 뿐이다.
