# buyer 병렬 탐색과 유통기한 사전 확인: 설계와 적용 가능성 (2026-11-04 21:0x, 초안)

상태: **설계만**. 라이브 코드는 바꾸지 않았다. 사용자 요청(11/4 20:5x): v62(식품 55%/68%, 30 s, 12곳)의 효과를
1시간 보는 동안, 여러 가게를 병렬로 찾는 buyer를 설계하고 적용 가능성을 검토한다. 조건: 주문 상태(`ctx.situation`)와
이벤트 기록이 한 흐름 전제인 점, 두 가게가 동시에 영수증을 주는 경우, 바꾸는 범위는 buyer 코드, 테스트와 로컬 확인 후 배포.

## 1. 측정 (최근 6시간, 우리 buyer 기록 `memory/raw/buyer/` + 키트 `payments.jsonl`)

| 식품 | 값 |
|---|---|
| 주문 | 924 |
| 영수증을 받은 주문 | 554 (60%) |
| 가게와의 대화 | 2,123 (주문당 1곳 544건, 5~6곳 177건) |
| 주문 처리 시간 중앙값 | 2.0 s |
| 대화 결과: 거절 | 1,162, 중앙값 1.1 s, 773건은 우리 제안 1번 이하에서 끝 |
| 대화 결과: 응답 시간 초과 | 211, 중앙값 4.4 s (v61의 4 s 제한) |
| 실패 뒤 다른 가게에서 성사 | 197 주문, 성사 전까지 잃은 시간 중앙값 4.6 s |
| **키트가 결제하지 않은 식품 영수증** | **360 / 1,058 (34%)**, 그중 343건 "유통기한 부족" |

가게 한 곳과의 대화는 1~2초에 끝난다. 순서대로 묻느라 잃는 시간은 성사된 주문의 약 1/5에서 4.6초 정도다.
시장은 주문이 끝나고 약 20초 뒤 다음 주문을 준다(11/4 10:4x 측정). 그러니 병렬로 얻는 것은 주문 수 몇 % 수준이다.
**반면 가격까지 합의하고 결제에서 떨어지는 식품 주문이 34%다.** 이것이 장부 성사율 34%와 lee-sungsoo 62% 차이의 대부분이다.

### 유통기한 거절은 영수증의 등급으로 미리 알 수 있다

식품 등급은 남은 유통기한 비율로 정해진다(A 80% 이상, B 45% 이상, C 그 아래; 키트 `FOOD_GRADE_CUTS`).
영수증의 `claim`(가게가 밝힌 등급)과 SKU의 `shelf_hours`로 남은 시간의 범위가 나온다. 결제 기록 약 750건을 맞춰 본 결과:

| 등급 주장 | 주문 사용 기간과 비교 | 결제 | 유통기한 거절 |
|---|---|---|---|
| C | 사용 기간 > 유통기한 45% (확실히 부족) | 8 | **138** |
| B | 45~80% 사이 (불확실) | 65 | 84 |
| C | 0~45% 사이 (불확실) | 149 | 0 |
| A, B | 사용 기간 ≤ 하한 (확실히 충분) | 270 | 25 (A 주장이 거짓) |

C를 밝힌 영수증이 "확실히 부족"으로 나오면 95%가 거절된다. 영수증은 인증서 본문을 담지 않는다(인증서는 buyer가
끝난 뒤 키트가 ACP 결제에서 받음). 그래서 buyer가 볼 수 있는 것은 가게의 등급 주장과 대화 중 언급한 등급뿐이다.

## 2. 결론: 순서를 바꾼다

1. **먼저 유통기한 사전 확인** (설계 1). 효과가 크고(6 h에 결제에서 떨어지던 주문 약 140~190건을 다른 가게로 다시 시도할 수 있음), 코드가 작고, 병렬과 독립적이다.
2. **그다음 2단계 병렬 탐색** (설계 2). v62로 주문당 시간(30 s)과 응답 대기(8 s)가 늘어난 만큼, 느린 가게가 주문을
   잡아먹는 것을 막는다. 효과는 v62와 설계 1을 측정한 뒤 판단한다.

## 3. 설계 1: 유통기한 사전 확인 (shelf guard)

- `bounds(claim, shelf_hours)` → (최소, 최대) 남은 시간. A: 0.8~1.0, B: 0.45~0.8, C: 0~0.45 × `shelf_hours`.
- ~~**대화 중**: 가게 메시지에서 뽑은 등급으로 바로 떠남~~ → 첫 판에서는 빼기로 함(11/4 21:0x, 사용자가 01:47
  사건을 짚음). 메시지에서 뽑은 등급은 검증하지 않은 값이고, 이 경로는 성사 전에 끊으므로 효과를 잴 수 없다.
  영수증 단계만 넣는다.
- **영수증에서**: `check_and_finish()`에서 `act.finish` 전에 `receipt.claim`으로 같은 검사. 걸리면 영수증을 돌려주지 않고
  `finish_none("no deal: shelf ...")`, `run()`의 다음 가게 루프가 이어서 시도한다(지금은 영수증을 받으면 끝).
- **불확실(B 45~80%)** 구간은 건드리지 않는다(결제 65 : 거절 84). 대신 가게별로 유통기한 거절 수를 `reflex`에 남겨
  `rule_pick.expected()`에서 그 가게의 기대값을 낮춘다(거짓 A 주장 25건도 여기서 걸러짐).
- 플레이북 `buyer.shelf_guard: true|false` (기본 false, 켜는 것은 전략판). 스키마에 bool 하나.
- 이 확인은 가게 쪽에 우리 조건을 말하지 않는다. 첫 메시지에 필요 시간을 적었더니 가게가 거절하던 문제(11/4 01:47,
  26건 중 2건 성사)는 생기지 않는다.
- 01:47 사건과의 차이 (`ded892e`): 그때는 첫 메시지에 "N시간 이상 남은 것"을 적어 **가게가** 첫 메시지에서 거절했다
  (118건 중 44건 합의 → 26건 중 2건). 설계 1은 가게에게 아무것도 더 말하지 않고, 이미 합의된 영수증 중 결제가 거의
  확실히 거절될 것만 우리 쪽에서 거른다. 거르는 146건 중 원래 결제되던 것은 8건(6 h에 식품 결제 약 700건의 1%)이다.
- 줄어들 수 있는 것: 그 8건, 그리고 다음 가게를 시도하는 시간(대화당 1~2 s). 라이브에서 1시간 동안 식품 장부 성사
  수가 전 시간보다 줄면 끈다.

## 4. 설계 2: 2단계 병렬 탐색

### 흐름

```
run()
 ├ 후보 정렬 (rule_pick의 expected 순, 지금과 같음)
 ├ 1단계 탐색: 상위 K곳(playbook.buyer.parallel_probe, 기본 1 = 지금과 같음)에
 │   첫 메시지 "I want to buy X (SKU)."를 동시에 보낸다. 가격은 없다 → 이 단계에서 영수증은 나올 수 없다.
 │   각 가게: 첫 응답(호가, 등급 주장, 상태) 또는 시간 초과/거절. 대기는 food_msg_timeout까지.
 ├ 고르기: 살아 있는 대화를 (설계 1 통과) → 호가/정가 낮은 순 → expected 순으로 정렬
 ├ 2단계 흥정: 한 번에 한 곳만 가격을 보낸다(아래 "제안 토큰"). 지금의 rule_turn 그대로.
 │   실패하면 다음 대화로 넘어간다. 이미 첫 응답이 있으므로 첫 메시지를 다시 보내지 않는다.
 │   탐색한 K곳이 다 떨어지면 남은 가게를 지금처럼 순서대로(시간 예산 안에서).
 └ 끝: 성사한 대화 외의 모든 열린 대화를 CancelTask로 닫는다.
```

### 공유 상태를 나누는 법 (한 흐름 전제 풀기)

| 공유되는 것 | 지금 | 병렬에서 |
|---|---|---|
| `ctx.situation` (act.pick/offer/finish가 읽음) | BuyerCore의 Ctx 하나 | 1단계 스레드는 **act 도구를 부르지 않는다**(첫 메시지는 A2A 전송만, `calc.extract`는 상태를 쓰지 않음). act 도구는 2단계에서 메인 스레드만 부른다 → `ctx.situation`은 여전히 한 흐름 |
| `self.events` / `tool_events` (EventWriter) | `seq += 1` 후 append | 1단계 스레드는 이벤트를 쓰지 않고 결과만 돌려준다. 메인 스레드가 모아서 `buyer.probe` 이벤트로 남긴다. 그래도 `EventWriter.emit`에 `threading.Lock` 하나를 넣어 안전장치로 둔다(`atomic.Appender`는 이미 잠금) |
| `reflex.record_outcome` (읽고-고치고-쓰기) | 순차 호출 | 메인 스레드만 호출(탐색 결과를 모은 뒤). 스레드 안에서 호출 금지 |
| A2A 클라이언트(`task_id`) | 가게당 하나 | 가게당 하나(지금과 같음), 스레드 사이 공유 없음 |
| 시계·마감(`deadline`) | `self.clock` | 읽기만 |

핵심은 **병렬은 첫 메시지 왕복만**이라는 점이다. 판단, 도구 호출, 기록은 모두 메인 스레드에 남는다. 그래서
`ctx.situation`과 이벤트 순서를 다시 설계하지 않아도 된다.

### 두 영수증 막기

- 영수증은 가게가 **우리 가격 제안을 받아들일 때** 나온다. 1단계는 가격을 보내지 않으므로 영수증이 나오지 않는다.
- 가게가 첫 메시지에 바로 영수증을 보내도 지금 규칙(`check_and_finish`: 우리 제안 전의 영수증은 합의가 아님,
  결제 안 함)이 막는다. 이 경우 `buyer.extra_receipt` 이벤트만 남긴다.
- 2단계의 **제안 토큰**: 가격이 담긴 메시지는 한 번에 한 대화에서만 나간다(메인 스레드 순차 흥정). 그래서 동시에
  합의되는 두 번째 가게는 구조상 없다. 결과 줄에는 늘 영수증 하나만 담는다.
- 끝날 때 열린 대화는 모두 취소한다. 가게 쪽에서는 지금의 "대화 뒤 떠남"과 같다.

### 가게 쪽 영향

탐색만 하고 취소하는 가게가 주문당 최대 K-1곳 생긴다. 지금도 주문당 평균 2.3곳과 이야기하고 거절·떠남이 흔해서
새로운 행동은 아니지만, K는 3으로 시작한다. 우리 가게도 같은 일을 당하므로 seller 쪽은 바꿀 것이 없다.

## 5. 바꾸는 범위

- `agents/buyer_core.py`: `bounds()`·shelf guard, `probe()`(ThreadPoolExecutor, K개), `run()`의 2단계 흐름, 끝의 취소.
- `core/events.py`: `emit`에 잠금 한 줄(buyer 외에도 무해).
- `core/schema.py`: `playbook.buyer.parallel_probe`(정수 1~6), `playbook.buyer.shelf_guard`(bool). 기본값은 지금 동작.
- 전략판: 켜는 것은 새 버전으로(사용자 승인).

## 6. 테스트와 로컬 확인

- 단위 테스트(`tests/test_buyer_core.py`의 가짜 `Shop`, `connect=` 주입):
  - shelf guard: C 주장 + 긴 사용 기간 → 영수증을 돌려주지 않고 다음 가게에서 성사, `buyer.closed` 사유 확인.
  - 병렬: 느린 가게(지연), 거절 가게, 정상 가게 셋 → 결과 하나, 느린 가게가 주문 시간을 늘리지 않음, 나머지 취소 호출.
  - 첫 메시지에 영수증을 보내는 가게 → 결제 안 되는 영수증으로 처리, 결과는 다른 가게.
  - `parallel_probe = 1` → 지금과 같은 이벤트 순서(회귀).
- 로컬 A2A: 테스트용 가짜 가게 3개(지연 0/3/9 s)를 띄우고 `market_buyer.py`를 실제로 실행, 로그를 `logs/local/`에 남긴다.
- 라이브: 플레이북 값으로 켜고 끈다. 먼저 shelf guard만 1시간, 그다음 `parallel_probe = 3` 1시간.
