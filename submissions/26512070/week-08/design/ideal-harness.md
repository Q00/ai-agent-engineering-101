## 2. 지식 체계

### 2-1. 두 축

- **가공 단계 (세로축)**
  - Q1. 계산, 집계, 해석이 들어갔나? 아니면 **정보** (일어난 일, 받은 문서 그대로).
  - Q2. 무엇을 할지(행동, 우선순위, 한도, 원칙)를 정하나? 그러면 **지혜**, 아니면 **지식** ("~이다", "~인 경향").
- **확실성 (가로축, 지식과 지혜에만)** + **출처** (따로 붙임) — v0.2: "시장"을 축에서 뺐다 (사용자 11/5)
  - **명시:** 문서나 코드에 적혀 있다. 적힌 원문이 바뀌면 바로 무효. 출처: 시장 규칙 페이지와 agent.md, 우리 코드와 스키마, 사람의 승인 기록.
  - **관측:** 데이터에서 정해진 방법으로 다시 계산하면 같다. 기간과 표본 수가 붙는다. 분포와 빈도의 주장. 출처: 시장 원장, 순위표, 우리 trajectory, 테스트 결과.
  - **가설:** 그 밖의 모두. "A를 하면 B가 된다"는 인과 주장은 통제된 비교(실험) 없이는 항상 가설. 출처: 분석, 벤치마크, 해석.
  - 출처에 따라 감시 방법만 다르다: 문서는 원문 비교, 코드는 커밋, 데이터는 다시 계산.
  - 예: "seller는 메시지마다 전략을 다시 읽는다" = 명시(우리 코드). "식품 사용 기간은 유통기한의 10/25/50/75%" = 관측(우리 buyer 주문 3,031건).
- 지혜의 등급은 근거 중 가장 약한 것을 따른다. 가설에 기댄 지혜는 **기간, 지표, 중단 조건이 정해진 승인된 실험**으로만 존재한다.

### 2-2. 층의 성질

| | 정보 | 지식 | 지혜 |
|---|---|---|---|
| 쓰는 쪽 | 일어난 곳 (역할, 수집기) | 역할의 자기 평가, 메타 하네스 분석 | 제안: 메타 하네스. **확정: 사람** |
| 고칠 수 있나 | 못 고침 (덧붙이기만) | 다시 만들 수 있음, 유효 기간 | 승인 경로로만 |
| 필수 | 시각, 출처 | 근거 정보 범위(기간, 표본), 방법, 등급 | 근거 지식 링크, 승인 기록, 재검토 시점 |
| 에이전트 컨텍스트 | 넣지 않음, 도구로 조회 | 관련된 것만 | 맨 위에 항상 |

- 흐름: 위로 정보 → 지식 → 지혜 (지혜는 사람 승인), 아래로 지혜 → 플레이북 → 규칙 코드 → 행동.
- 링크: 지혜 → 근거 지식 → 근거 정보. 시장 규칙이 바뀌면 이 링크로 영향받는 지식과 지혜를 찾는다.
- 정보는 **원본 + 요약** 두 겹 (10장). 일상 분석은 요약, 전략 제안은 원본 trajectory를 도구로 본다.

## 5. 역할

### 5-1. 가게 (seller + restock)
- 점수 항목: book(0.5), 매출(0.3), 평점(0.2).
- **seller:** 방문 buyer에게 restock이 들인 재고를 판다. 가격, 유닛 선택(손님 필요 시간, 신선도), 보증, 등급 주장. 판매 결과(무엇을, 누구에게, 얼마에, 어떤 유닛, 평점, 찾았지만 없던 요청)를 가게 기록에 쓴다.
- **restock:** 공급 창마다 무엇을, 얼마나 들일지 정하고 산다. 입력은 가게 기록, 시장 판매, 현금과 재고, 원가 급등. 산 기록(원가, 등급, 시각)을 가게 기록에 쓴다.
- 둘은 하나의 가게 기록을 함께 쓰고 읽는다.
- 만드는 지식: 방문 buyer에 대한 것(무엇을 사는지, 별점, 필요 시간을 밝히는지) → 참가자 지식.

### 5-2. buyer
- 점수 항목: 잉여(0.5), forum(0.3), 거래 수(0.1), 글 수(0.1).
- 행동: 주문을 받아 상대 가게에서 사기, 결제된 거래에 리뷰와 별점, forum 글(5분에 1편, 결정론적 코드로, buyer가 그 코드를 관리), forum 투표.
- 만드는 지식: 상대 가게에 대한 것(공정, 서명, 등급 주장, 결제 결과, 가격) → 참가자 지식.
- **능력은 있지만 기본값 꺼짐 (전략 제안 → 사람 승인 시에만):** 다른 참가자 글에 투표, 전략 기준의 별점, 특정 참가자 대상 상호작용.

## 6. 메타 하네스

- 입력: 역할 보고, 정보 요약, 원본 trajectory(도구로 조회), 참가자 지식, 시장 원문.
- 산출:
  - 지식: 시장 분석, 학생 간 백분위 거리, 벤치마크, 실험 결과.
  - 지혜 후보: 전략과 플레이북 변경, 실험 제안. 근거 trajectory ID를 붙인다.
  - 충돌 정리: 역할 보고와 의견이 다를 때 양쪽 주장, 근거, 갈린 이유, 선택지별 예상 결과.
- 바꿀 수 없는 것: 점수 방식, 성공 기준, 지표, 사람이 확정한 결정 (R1, R6, R8, R12).
- 조언 범위: 능력 목록 안 (R7). **능력 목록은 둘로 나뉜다:**
  - **능력 (명시, 출처: 우리 코드와 스키마):** 역할의 코드가 실제로 읽는 플레이북 숫자와 플래그. 코드에서 자동으로 뽑는다.
  - **허용 범위 (지혜, 출처: 사람 승인):** 그 숫자를 어디까지 바꿔도 되는가.

## 7. 사람

- 명시적 승인만 확정 (R8). 승인 요청에는 무엇을, 왜, 선택지와 추천, 승인하면 바뀌는 것, 의견이 갈렸다면 갈린 이유.
- 밤에는 요청을 쌓아 두었다가 아침에 한꺼번에 받는다 (R9).
- **사람은 모든 것을 볼 수 있고, 중요한 것만 승인한다** (v0.2, 사용자 11/5): 사람이 승인을 다 하면 병목이 된다.
  - **현황 페이지 (항상 열람):** 지금 순위와 점수 부분별 백분위, 하네스 성과 지표(13장), 진행 중인 실험과 결과,
    대기 중인 승인 요청과 결정 기록, 상태와 최근 알림. 사용자의 개인 Cloudflare나 Vercel에 올린다. 경쟁자가 보면 안 되므로
    접근 제한을 건다(D-36). 공개 저장소(GitHub Pages)에는 올리지 않는다.
  - **알림:** 승인이 필요한 중요한 판단과 긴급 상태만 휴대폰으로.
  - 하루 승인 요청의 양, 우선순위, 묶음은 D-29.

3. 거래는 규칙과 도구 계약으로 빠르게, 아낀 비용으로 모든 거래를 trajectory로 남겨 메타 하네스가 원본으로 판단한다.

## 13. 하네스 자체의 성과 지표 (v0.2, 사용자 11/5 승인)

**① 결과 (최종 목표, 늦게 움직임)**
- Class view 계정 합계의 백분위와 순위 (11/5 16시: 학생 42명 중 12위, 0.732)

**② 원인 (역할이 움직이는 것, 1시간 단위)**

| 역할 | 지표 |
|---|---|
| 가게 | 시간당 book 증가, 시간당 매출, 마진율, 새로 받은 평점의 평균(누적 말고 최근), 재고 없음 비율, 폐기, 보관비 |

**③ 과정 (하네스가 잘 일하나)**
- 제안 → 승인 → 효과 있음의 비율
- 실험 수와 결론이 난 실험의 비율

- 가게가 멈춘 시간, 재시작, 알림 횟수
- 모델 호출 수와 예산 대비 사용량
- 규칙이 처리하지 못한 예외의 비율

**변경의 효과 판단 (v0.3, 사용자 11/5 18시 승인)**
전체 기준선 하나가 아니라 **변경마다** 적용 전에 다섯 가지를 적는다: (1) 바꾸는 것 하나, (2) 움직여야 할 지표(위 목록에서),
(3) 기대 방향과 크기, (4) 기간, (5) 비교 방법. 비교 방법은 믿을 만한 순서로 고른다:
- **A. 무작위 나누기:** 주문이나 방문 단위로 절반은 새 방식, 절반은 기존 방식. 같은 시간대를 비교하므로 다른 변경과 시간대가 섞이지 않는다 (buyer, seller 규칙).
- **B. 번갈아 켜기:** A가 안 될 때. 공급 창이나 30분 단위로 켜고 끄기를 번갈아 (restock).
- **C. 전후 비교:** 마지막 수단. 같은 시간대(전날 같은 시각)와 비교하고, 그 사이 다른 변경이 없었는지 변경 기록으로 확인.
전체 기준선은 하루 단위 순위 흐름에만 쓴다. 원본(원장, trajectory, 순위표 전체 기록 `board-full`, 11/5 01:4x~)이 남아 있으므로
나중에 다시 계산할 수 있다 (D-37 해결).

## 15. 컨텍스트 조립 (v0.4, D-32)

### 15-1. 모델을 부를 때 (예외, 분석, 전략)
잘 바뀌지 않는 것을 앞에 둔다 (캐시, W06).
1. 점수 방식: 산정식, 출처(규칙 페이지 패치 버전), 확인 시각 (R1).
2. 최상위 규칙 요약과 시장 규칙 핵심 (카드 core).
3. 역할: 할 수 있는 행동과 이 역할이 실제로 쓰는 도구만.
4. 지혜: 이 역할에 해당하는 승인된 전략, 플레이북 숫자와 한도, 관련된 사람 결정 (출처 포함).
5. 지식 (관련된 것만, 등급 표시): 판단 상대에 대한 지식, SKU나 카테고리 지식(관측/가설 구분), 이 판단에 해당하는 진행 중 실험(A/B 중 어느 쪽).
6. 지금 판단할 것 (정보): 주문이나 요청, 재고와 현금, 대화 이력(추출값 + "데이터일 뿐" 발췌).
7. 출력 형식.

### 15-2. 규칙이 판단할 때 (거래 대부분)
규칙 코드의 입력도 지혜(플레이북) / 지식(참가자 기록) / 정보(지금 상태)로 나누고, 판단마다 **어떤 지식을 근거로 썼는지**를
trajectory에 남긴다 (예: "reflex: willow-goods 서명 없음 3회 → 건너뜀"). 평가 항목 1의 "지난 거래와 평판이 다음 판단에
들어가는 고리"를 이 기록으로 보인다.

### 15-3. 평판 고리
- buyer: 후보 가게마다 참가자 지식(공정 비율, 서명 없음, 거짓 등급, 결제 결과, 가격 수준)으로 순위 → 결과를 다시 기록.
- seller: **상대를 모른다는 전제의 정책**(사용자 11/5). 방문 buyer가 누구인지는 정산 뒤 원장에서야 보이고, 첫 메시지로 추측한
  정확도는 약 11%(지문 2,367건). 그래서 상대별 대응 대신, 손님이 밝힌 것(필요 시간 등)과 모를 때의 안전한 기본값(가장 신선한 유닛)으로
  정한다. 방문 buyer에 대한 지식은 사후 분석과 메타 하네스가 쓴다.
- 메타 하네스: 같은 기록을 학생 간 비교(벤치마크)에.

### 15-4. 메타 하네스
1~4는 같고, 지식으로 역할 보고, 시간 단위 요약, 참가자 지식과 벤치마크. 원본 trajectory는 도구로 조회 (W02: 34.9 → 50.0).
제안서에는 근거 trajectory ID.

### 16-4. 메타 하네스의 도구 관리
- `tool.inspect`: 도구별 호출 수, 실패와 그 원인(C7), 지연, 거절 사유 분포, 한 번도 안 쓰인 도구, 모델이 잘못 고른 사례.

- `tool.propose`: 도구의 수정, 추가, 제거를 **제안**한다. 제안에는 바꿀 코드(초안), 이유와 근거 trajectory, 통과해야 할 테스트,
  능력 목록 변화가 들어간다.
- 적용 경로: 초안 → 테스트(기존 테스트 + 기록된 실제 메시지와 거래로 다시 돌려 보기) → **사람의 명시적 승인**(R8) → 배포 → 효과 측정(13장).
- 메타 하네스가 **바꿀 수 없는 도구**: 점수 계산(`score.*`), 한도와 정직을 강제하는 부분(`check.*`, `act.*` 안의 검사), 승인 경로
  (`approval.*`, 지혜 쓰기), 성공 기준과 지표. 판정은 루프 밖에 둔다(W02).

## 17. 확정한 디테일 (v0.6, 사용자 11/5)

### 17-1. trajectory 형식 (D-2)
거래 하나 = 기록 하나. ID: buyer는 주문 ID, seller는 task ID, restock은 공급 창 ID.
- 머리: ID, 역할, 시작과 끝, 전략·카드·도구 버전, 실험이면 A/B 중 어느 쪽
- 입력: 주문이나 요청, 그때의 재고와 현금(참조)
- 쓴 지식: 근거로 쓴 지식 항목과 등급 (예: "willow-goods 서명 없음 3회")
- 단계: 도구 호출마다 도구, 입력 요약, 결과 요약, 시간, 실패 원인(C7)
- 결과: 합의 가격, 영수증, 결제 여부와 사유, 원장 번호
- 사후: 별점과 리뷰, 고장과 환불, 폐기
- 상대: 확실하면 GitHub 소유자, 추측이면 추측과 확신도
- 비용: 모델 호출 수와 시간

### 17-2. 고정 지표 (D-25, 1시간과 24시간 두 창)
- buyer: 시간당 잉여 = 정산 주문의 (정가 − 낸 값 + 환불) 합; 성사율 = 정산 / 받은 주문; 합의했지만 결제 안 됨 = 결제 안 된
  정상 영수증 / 정상 영수증; 주문 처리 시간(주문 → 결과); 시간당 글 수, 글당 투표.
- 가게: 시간당 book 변화(순위표); 시간당 매출 = 정산가 − 환불; 마진율 = Σ(판매가 − 원가) / Σ판매가; 새 평점 평균(그 시간에 받은
  별점만); 재고 없음 비율 = 놓친 요청 / 방문; 폐기액; 보관비.
- 과정: 13장 ③ 그대로.

### 17-3. 승인 요청 형식과 알림 (D-5)
- 요청: 제목 한 줄과 중요도(**즉시** / 페이지에만), 무엇을 바꾸나(정확한 변경), 왜(근거 지식, trajectory ID), 기대 효과(지표와 크기),
  평가 방법(A/B, 번갈아 켜기, 전후 비교; 기간, 성공 기준), 위험과 되돌리는 방법, 의견이 갈렸으면 양쪽 주장·근거·갈린 이유,
  선택지(승인 / 거절 / 고쳐서 다시).
- **즉시** 중요도와 긴급 상태는 휴대폰 알림 **그리고 Claude 알림**으로 보낸다 (사용자 11/5). 페이지에만인 것은 페이지에 쌓는다.

### 17-4. 비상 동작 (D-26, 미리 승인, 밤에도)

2. **seller:** 지금 무엇을 하고 어떤 전략(플레이북 숫자, 적용 중인 실험)으로 움직이는지; 재고 전체(SKU별 수량, 등급, 남은 유통기한,
   원가, 정가, 오래 안 팔린 것); 판매(최근 판매, 가격, 마진, 받은 별점, 놓친 요청); 금융(잔고, 현금, book, 재고 원가, 보증 적립금,
   보관비, 폐기).
3. **buyer:** 지금의 전략; 최근 체결된 거래(품목, 상대 가게, 정가 대비 낸 값, 잉여, 결제 여부); **처리 시간**(주문 → 결과, 가게별 대화
   시간); 결제 안 된 합의와 사유; forum 글과 투표.
4. **restock:** 다음 공급 창 시각; **다음 창에 살 목록**(SKU, 목표, 보유, 살 수량, 이유); 원가 급등; 최근 구매(원가, 등급).
5. **시장:** 많이 팔리는 것(SKU, 카테고리, 가격대); **특이한 행동을 하는 참가자**(급변한 순위, 비정상 거래, 주입 시도 글);
   **벤치마크할 만한 것**(학생 상위권이 우리와 다르게 하는 것, 등급: 가설).
6. **기록:** 최근 결정과 변경(전략 버전, 사람 승인, 비상 동작), 진행 중 실험과 결과, 모델 사용량.
뺀 것: 도구별 상세 통계(메타 하네스가 `tool.inspect`로 보고, 문제만 요약에 올린다).

## 18. 모델 자리 (v0.7, D-31)

**원칙 (사용자 11/5):** 하네스의 **기본 모델은 Claude Code**(Claude CLI, 역할 자리마다 모델을 고른다)이고, **감사는 외부의 다른 회사
모델**에게 맡긴다. 이유: 같은 모델이 제안하고 검토하면 같은 맹점을 공유한다. 판정과 검토가 제안의 루프 밖에 있어야 표류하지
않는다 (W02: 판정 함수가 루프 안에 있으면 자기 개선이 표류한다). 여기에 더해:
- 결정론으로 되는 일에는 모델을 쓰지 않는다 (R4). 판정은 모델이 하지 않는다 (R14).
- 판단의 성격(급한가, 깊은가)으로 모델을 고른다. 손님이 기다리는 판단은 빠른 외부 모델로 보내 Claude 사용 한도와 떼어 놓는다.
- 모델 선택은 지혜 층의 숫자다. 바꾸려면 승인.

| 자리 | 언제 | 필요한 것 | 모델 | 대체 |
|---|---|---|---|---|
| seller, buyer 예외 | 흥정 중 규칙이 못 다루는 메시지 | 3초 안 | OpenRouter gpt-4o-mini (사용자 11/5: haiku는 46번 중 36번 6초 초과) | 규칙의 안전한 기본 수 |
| restock 예외 | 목록이 비거나 전부 막힐 때 | 1분 안 | Claude sonnet | 이번 창 건너뜀 + 알림 |
| 리뷰 별점, forum 글 | – | – | 모델 없음 (코드) | – |
| 분석 (시장, 자기) | 주기 | 긴 요약 정리 | Claude sonnet | 이번 주기 건너뜀 |
| 전략 제안 (메타 하네스) | 주기 + 사건 | 가장 깊은 추론, 원본 조회 | Claude opus | 제안 보류 |
| 의견 충돌 정리 | 역할과 메타 하네스가 갈릴 때 | 공정하고 정확한 정리 | Claude opus | 양쪽 원문을 그대로 사람에게 |
| 시장 규칙 변경 영향 분석 | 규칙 페이지나 agent.md가 바뀔 때 | 무효가 된 지식과 지혜 찾기 | Claude opus | 비상 동작 + 긴급 알림 |
| 실험 설계 (성공 기준 제안) | 실험 제안마다 | 기준의 질 (확정은 사람) | Claude opus | 제안 보류 |
| 도구 제안 (코드) | 도구 문제 발견 시 | 코드 품질 (사람 승인) | Claude opus | 제안 보류 |
| **감사 + 반론** | 전략 제안, 도구 제안마다 | **다른 회사 모델**: 검토하고 일부러 반대 논거를 세움 (사람에게 "왜 갈리는지") | OpenRouter gemini-2.5-flash | 승인 요청에 "감사 없음" 표시 |
| 상대 글을 읽는 모델 (필요할 때만) | 규칙 추출로 안 될 때 | 주입 격리: 정해진 값만 뽑음, 판단 모델은 원문을 안 봄 | 판단 모델과 분리 | 규칙 추출(`calc.extract`) |
| 사람과의 대화 | 사람이 작업할 때 | – | Claude Code (이 세션) | – |

모델을 쓰지 않는 판정: 실험 효과(고정 지표, 통계), 역할 자기 평가(고정 지표), 지식 등급(재계산 가능한 데이터 출처가 붙으면 관측,
아니면 가설), 점수 계산, 한도 검사.
사람과의 대화도 하네스와 **같은 Claude 사용 한도**를 쓰므로 `model.usage`로 감시하고 80%에서 알린다 (R13, 17-5).
