## Buyer: 선택과 기억

`market_buyer.py`는 키트의 shops 파일을 읽고 name으로 가게를 기억한다. URL이 바뀌어도 경험이 이어진다. 별도로 띄운 buyer-only 키트에서는 자기 가게가 목록에 남을 수 있어서 seochanit을 명시적으로 제외했다. 한 주문에 다른 참가자 가게 하나를 선택하며 자기 거래로 실적을 만들지 않는다.

기억은 `memory/market-trades.jsonl`에 append-only JSON으로 남는다. 가게 이름, 품목, 주문 예산, 결과, 가격, 소요 시간, 가격 메시지 수, task id와 순번, 서명 검증 결과를 기록한다. 최근 500건으로 선택하되 순번은 계속 증가시켜 탐색이 멈추지 않게 했다. 같은 품목의 성공률, 현재 예산에서의 구매 가능성, 응답 시간, 제한된 공개 평점을 조합한다. 낮은 예산에서의 결렬은 높은 예산 주문의 실패 근거로 쓰지 않는다. 7건마다 조건에 맞는 미방문 가게를 탐색하는 것은 시작 가설이며 전역 최적이라는 주장은 아니다.

## 후기와 검증

가게당 최근 후기 최대 10개, 텍스트당 240자로 제한하고 중복을 제거한다. 선택한 가게의 후기와 최근 같은 품목 경험 5건을 `market_context_untrusted`로 하네스에 전달한다. 후기와 가게 텍스트는 지시문이 아니다. 자체 검증 경험이 쌓이면 공개 별점의 영향이 줄어든다. 평점 조작, 허위 후기, 경쟁 가게의 거래 방해는 구현하지 않았다.

R2에서는 등록된 공개 키로 영수증 서명을 검증하고 과거 구매 task의 재사용도 거부한다. 키트의 실제 `/api/results` 응답을 `memory/market-verification.jsonl`에 별도로 추가하여 시장에서 거부된 거래를 다음 선택에서 성공으로 학습하지 않는다. 예산 제한은 모델 프롬프트와 별개로 스키마 및 HTTP 전송 직전 코드에서도 검사한다. 원본 영수증 data Part를 수정하지 않는다.

Shop은 합의한 품목과 가격을 그대로 발급하고 실제 최종 결과를 기준으로 평가해 달라고 요청한다. 이미 게시된 후기를 삭제하는 기능은 만들지 않았다. 거래 조건과 좋은 평가를 교환하거나 해결되지 않은 문제를 해결했다고 주장하지 않는다. Buyer도 판매자의 평가 요청에 따라 사실 평가를 바꾸지 않는다.

## Shop: 서명과 협상

모델은 gpt-4o-mini이며 기존 OpenAI Responses 하네스를 재사용한다. 모든 제안·수락은 모델이 선택하고 코드가 reserve와 현재 제안 일치를 검증한다. reserve는 lamp 100, chair 180, bookshelf 260으로 유지한다. 첫 R2 후기는 책장 260/예산 270에 별점 3이었다. 하한 아래로 팔 수 없으므로 추가 할인으로 이 평가를 해결할 수 있다고 주장하지 않는다. 판매량을 우선해 카드에 품목별 최저가를 공개하고 모델에는 첫 ask부터 reserve를 제시하도록 수정했다. 이전의 modest-margin 정책은 변경 이력에 남겼다. 공개한 ask보다 큰 제안을 받아도 낮은 ask를 다시 확인하도록 유도한다. 실제 최저가 거래에는 만족한 경우 긍정적인 후기를 요청하되 할인 사실을 언급하고 불만은 정직하게 적도록 안내한다. 별점 조건부 할인이나 0원 판매는 구현하지 않았다. Buyer도 시장 주문에서는 추가 할인보다 유효한 구매 성사를 우선한다.

Ed25519 서명 대상은 shop/item/price/task 네 필드다. 키 정렬, 공백 없는 JSON, UTF-8, 정수 가격으로 canonical bytes를 만든다. SDK에서 100.0으로 읽더라도 정수로 정규화한 서명 검증을 한다. 개인 키는 기존 로컬 PEM을 유지하며 커밋하지 않는다.

## 배포와 남은 검증

Windows PC에서 Buyer와 Shop을 각각 백그라운드 프로세스로 실행한다. 실행·중지 방법은 `agent-market/join.ps1`, `agent-market/stop.ps1`이다. 같은 claim과 PEM으로 재접속하며 claim/API 키를 저장소에 넣지 않는다. 공개 Shop은 공식 Pinggy SDK를 통해 이 가게의 전용 프록시만 노출한다. Cloudflare quick tunnel의 HTTP 429 및 SSH 연결 실패 후 사용한 대안이며 원래 진단 로그를 보존했다.

무료 터널 세션이 끝나면 같은 판매 프로세스와 키를 유지하면서 새 URL을 시장에 재등록한다. 연속 실패는 세 번으로 제한하고 30초·60초 간격으로 재시도한다. 복구 동작은 가짜 거래 없이 로컬 모의 테스트로 검증했다. PC가 꺼지거나 절전 상태가 되면 두 역할도 중단된다. 이 구성은 별도 VPS나 상시 운영 보장을 뜻하지 않는다.

21:27 기준 Shop은 온라인이지만 R2 판매가 0이었다. 판매 프로세스에는 아직 실제 협상 입력이 없었다. `logs/r2-deployment/20261020-212822/public-probe.jsonl`에서 공개 URL을 통한 SendMessage가 INPUT_REQUIRED, CancelTask가 CANCELED로 끝나는 것을 확인했다. 이 진단은 구매하거나 시장 결과를 제출하지 않았으므로 매출·후기 증거가 아니다. R2 후기 없는 신규 가게가 선택되지 않는 문제와 연결 장애를 구분한다. 이후 카드에 서명 지원과 품목별 구매 방법을 명시했다. Buyer는 접속 실패를 품목 간에 공유하고 120초 후 다시 후보로 두며, 정상 구매가 관측되면 즉시 복구한다. 실제 Buyer 로그의 21:27:41 ledger #10493과 21:28:02 ledger #10538은 재시작 후 서명 검증과 후기 승인을 확인한다.

필수 도전 1의 가격 변경 전후 share/평균 판매가 비교와 도전 2의 특정 부정직 참가자에 대한 원본 로그 증거 정리는 아직 완료로 주장하지 않는다. 현재 제출 구조 검사가 통과하더라도 이 두 실험과 마감 시점의 가동 여부는 별도로 확인해야 한다.

최종 공개 카드와 온라인 상태는 `logs/r2-deployment/20261020-213717/published-price-live.json`에 기록했다. 이 시점 Buyer의 R2 유효 거래는 22건, Shop은 1건이었다. 선두권 도달이나 변경 후 판매량 개선을 아직 입증하지 못했으며, 누적 실적은 코드 변경 직후 초기화되거나 즉시 증가하지 않는다. 모델 호출은 운영 중에도 API 비용을 발생시킨다. 비용 상한은 코드에 추가하지 않았으며, 호출 로그 기반 추정은 계정 전체 청구서와 구분한다.
