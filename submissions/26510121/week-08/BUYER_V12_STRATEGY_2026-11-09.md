# Buyer v12 — Saved 개선량과 처리 시간을 함께 결정

## 진단

v11의 Saved·실제 등급·보증별 가격 상한 방향은 유지할 가치가 있다. 하지만 거래 시간 비용을 충분히 반영하지 못했고, 운영 코드에 큰 반복 처리 비용이 있었다. 주문별 과거 결과 재처리와 느린 견적 대기를 함께 고친다. 단순히 고장 위험이나 가격 상한을 느슨하게 만들어 거래 수를 늘리지 않는다.

실제 입력의 읽기 전용 프로파일에서 `Journal.reconcile`은 21.608초를 썼다. 과거 구매를 112번 읽는 전체 프로파일에서 JSON 디코딩이 약 99만 회 발생했고, 결과·모호한 고장 이벤트 7,733건의 중복 추가를 시도했다. 비교 프로파일은 실제 INSERT 비용을 제외하므로 당시 전체 실행 지연을 이 숫자로 단정하지 않는다.

구매 기록을 한 번 읽어 상품명으로 색인하고, 같은 event ID의 결과를 한 트랜잭션에 INSERT OR IGNORE하도록 교정했다. 수정 후 같은 읽기 전용 방식의 reconcile은 0.280초였다. 입력이 시간에 따라 조금 늘어난 운영 스냅샷 비교이며, 실제 시장 처리량 개선율의 인과 추정은 아니다. 모호한 고장 귀속, 늦게 온 고장, 성숙 시간, 결과 중복 방지의 의미는 유지한다.

## 실행 전략

- **시간까지 포함한 목적함수**: Buyer 후보와 가격 행동의 기대 순위/Saved 개선량을 실행 시간 시나리오로 나누어 비교한다. 작은 추가 할인을 위해 유리한 거래를 오래 지연시키는 행동을 줄인다. 실행 시간은 관측 지연과 명시한 사전값이며 보장된 값이 아니다.
- **견적 경쟁**: 처음 두 가게의 견적만 병렬 요청한다. 등급·보증·가격 조건이 알려져 있고 현재 Saved보다 0.04 이상 높은 기여가 가능한 견적을 얻으면 짧은 비교 유예 후 그 견적을 우선 처리한다. 응답하지 않는 가게 때문에 전체 스레드풀 종료까지 기다리지 않는다. 진행 중인 나머지 요청은 취소/종료 대상으로 처리한다. 병렬 작업은 견적만 수행하고 결제하지 않는다.
- **경로 학습**: 실제 결제와 종료된 실패 시도를 order ID·가게·SKU별로 중복 없이 집계한다. 미결제 합의를 바로 실패로 단정하지 않는다. 식품 사용 시간 조건이 다른 실패와 요구 수명을 충족하지 못했던 과거 구매를 현재 경로의 성과로 섞지 않는다. 성공 확률이나 기대 거래 수를 1보다 높게 만들어내지 않는다.
- **총 시간 제한**: 준비 시간을 포함해 식품 22초·공산품 32초를 기본 실행 예산으로 둔다. 가게 경로는 최대 네 곳, 초기 병렬 견적은 최대 두 곳, RPC는 남은 시간과 요청별 제한을 모두 지킨다. 협상은 세 단계이고 이미 결제 가능한 제안을 수락하는 행동과 추가 협상을 시간 비용까지 비교한다.
- **조건 확인**: 사용기한 요청에 기존 30초 결제 여유도 포함해 요구한다. 명시적인 가격이 있는 공산품에는 반복적인 등급·보증 설명 요청 대신 최초 요청과 최종 인증 조건을 사용한다. 가격을 해석할 수 없는 경우만 한 번 확인한다. 불리한 최종 등급·보증 변경과 가격 인상은 기존 검증에서 거절한다.

시장 인증서, 정확한 SKU, 서명, 등급, 보증, 사용 수명, Saved 가격 상한, 중복·불확실 결제 복구 금지는 유지한다. API 모델은 바꾸지 않는다. 게시글·forum 규칙과 유료 투표는 이번 교정의 대상이 아니다.

## Shop 연결과 적용

17:39 장애 때 공개 카드와 registry는 정상이었지만 보드의 own alive가 false였다. 기존 주소·키로 재등록해 복구했고 양쪽 alive=true를 확인했다. 서버 측 장애의 정확한 원인은 이 증거로 확정하지 않는다.

기존 감시는 registry에서 사라진 경우만 복구했기 때문에 이 상태를 놓쳤다. 새 감시는 공개 카드가 정상이고 다른 가게가 활성 상태인 상황에서, own board offline을 60초 간격으로 두 번 확인하면 같은 키·주소로 재등록한다. 복구 재시도에는 간격을 두며, 전체 가게가 offline이거나 registry가 비었을 때는 재등록 폭주를 피한다.

Buyer 자식 프로세스뿐 아니라 결제 뒤 결과 처리와 Shop 감시가 있는 부모 프로세스도 새 코드를 읽어야 한다. 따라서 검증을 마친 후 기존 운영 프로세스를 협조적으로 종료하고 watcher로 다시 실행한다. 키·재고·원장·순위 누적은 보존한다. 터널은 재기동 중 새 공개 주소가 생길 수 있으며 최종 주소의 시장 등록과 실제 거래를 확인한다. Shop 가격·재고 목적함수와 revision은 변경하지 않는다.
