# Buyer·Shop 동시 1위를 목표로 한 전략 설계

2026-10-27, HTML **R3 → WATCH: ROUND 3 → HW ‘값 다시 정하기’**에 대응한다.
이 문서는 다음 정책 후보의 설계다. 운영 중인 memory-v1과 접속 대기는 유지하며,
검증되지 않은 정책을 운영 코드에 자동 반영하지 않는다. 1위 달성이나 전역 최적성을 입증한 결과는 아니다.

## 순위를 정하는 실제 지표

공식 `/board`의 기본 정렬은 Buyer **Saved**, Shop **Profit**이다.
동점이면 두 역할 모두 거래 건수가 많은 참가자가 먼저 나온다.
API 배열 순서와 화면의 정렬 순서는 같다고 가정하면 안 된다.

- Buyer Saved: 유효 거래에서 남긴 `주문 예산 - 지불 가격`의 누적 합.
- Shop Profit: 유효 거래의 `거래 가격 - 품목 floor`의 누적 합.
- 공개 floor는 lamp 100, chair 180, bookshelf 260이다. 이는 시장의 원가 기준이며,
  다른 가게가 그 가격을 반드시 수락한다는 뜻은 아니다.
- 별점, 거래 수, 매출, 평균 지불 비율은 다른 정렬 탭이거나 보조 지표다.
- API 비용은 실제 운영 제한으로 따로 관리한다. 단위가 다른 실제 비용과 시장 크레딧을
  임의의 환율로 섞어 leaderboard 점수처럼 계산하지 않는다.
- Round 3에서는 정산된 거래만 보상으로 기록한다. Round 2 누적 점수나 서명 영수증만으로
  Round 3의 성공을 주장하지 않는다.

원문과 현재 공개 스냅샷은 `logs/ranking-research-20261027T113855Z/`에 보존했다.
조회 당시 현재 시장은 Round 2였다. 그 순위를 Round 3 순위라고 해석하지 않는다.

## Buyer: 신뢰할 수 있는 상대에서 시간당 절약액을 높인다

비교할 목적함수는 다음과 같다.

`정산 성공 확률 × 성공했을 때의 평균 절약액 ÷ 평균 주문 처리 시간`

실패한 주문의 절약 보상은 0이다. 구매를 피해서 예산을 그대로 보유하는 행위는 Saved가 아니다.
이 값들은 고정 예언이 아니라 실제 경험으로 갱신하는 추정치다. 주문 발급 대기와
시장의 속도 제한도 처리 시간에 포함해, 의미 없는 과도한 polling을 성능 개선으로 착각하지 않는다.

1. **상대 모델:** 가게 이름·서명 키, 품목, 내 예산 구간, Round를 구분한다.
   실제 정산 가격, 성공 여부, 협상 횟수, 처리 시간, 결제 실패 사유를 저장한다.
   URL만 바뀌었다고 같은 가게의 이력을 버리지 않는다.
2. **선택:** 공개 후기보다 개인의 검증된 정산 경험을 우선한다. 가장 싼 가격 한 건보다
   반복 가능한 가격·성공·속도의 조합을 본다. 기록이 오래되면 현재 후보를 다시 확인한다.
3. **제안:** 공개 floor와 내가 실제로 산 가격은 협상 참고값이다. 현재 호가가 경쟁력 있으면
   즉시 수락하고, 자신의 유사 정산 가격보다 비싸면 LLM이 근거 있는 반대 제안을 결정한다.
   모든 주문에서 무조건 할인 요구하거나 첫 호가를 무조건 수락하는 고정 규칙은 두지 않는다.
4. **종료:** 추가 절약의 기대값과 실패·지연 위험을 비교한다. 작은 할인을 위해
   성사 가능성이 높은 구매 전체를 놓치지 않는다. 반복된 같은 제안과 이미 확인된 불가 조건은 끊는다.
5. **탐색:** 평소에는 성과가 좋은 상대를 활용하고, 새 가게와 오래 확인하지 않은 가게를
   작은 비중으로 탐색한다. 지금의 고정 7회당 탐색은 기준 정책이며, 최적 빈도라고 가정하지 않는다.
6. **결제:** 품목·합의가·가게 서명·mandate 상한을 확인하고, 같은 주문의 중복 결제를 막는다.
   거래 후 예산 숫자나 예산을 추정하게 하는 예산 비례 별점 기준을 공개하지 않는다.

낮은 가격은 주문을 더 많이 성공시킬 때 누적 절약으로 이어진다. 응답 없는 최저가 가게나
checkout이 없는 가게에 반복 방문하면 이 목표를 달성하지 못한다.

## Shop: 고객 유입과 성사율을 지키며 시간당 정산 마진을 높인다

비교할 목적함수는 다음과 같다.

`시간당 유효 방문 × 방문당 정산 성공률 × 정산 건당 평균 마진`

실측으로는 `해당 시간에 발생한 정산 마진 합 / 운영 시간`을 본다.
높은 호가 한 번의 성공이나 방문당 마진만으로 전체 성과를 판단하지 않는다.

1. **품목별 호가 실험:** 보수적·기준·공격적인 호가 정책을 작은 범위에서 교차 시험한다.
   가격 자체는 LLM이 하한가와 관찰을 보고 선택한다. 구체적인 최적 숫자는 비교 결과로 정한다.
2. **기회 기록:** 팔린 거래뿐 아니라 제안, 취소, 명시적 거절, 합의, 결제 완료를 구분한다.
   침묵과 로컬 API 장애는 buyer의 거절이나 수요 부족으로 단정하지 않는다.
3. **수락:** 하한가를 지키면서 지금 성사시킬 마진과 더 흥정했을 때의 기대 결과를 비교한다.
   이미 제시한 호가보다 높은 금액을 받아내려 가격 약속을 바꾸지 않는다.
4. **재방문:** 명확한 정수 호가, 짧은 협상, 합의와 같은 영수증, 안정된 ACP checkout을 제공한다.
   공개 가격 설명과 실제 정책을 일치시키고, 품목·서명·정산 지원을 카드에 정확히 표시한다.
5. **환경 적응:** 최근 방문량, 정산율, 가격 분포가 바뀌면 새 상황에서 다시 시험한다.
   후기나 소수 고가 거래에 반응해 갑자기 전체 가격을 올리지 않는다.
6. **관찰 범위:** 인증할 수 없는 buyer 이름으로 개인별 가격 모델을 만들지 않는다.
   상대가 직접 한 제안과 해당 task의 행동을 사용하고, 비공개 예산을 안다고 가정하지 않는다.

하한가 판매는 시장 원가 기준 마진이 0이므로 Profit 1위의 장기 정책이 될 수 없다.
반대로 높은 가격 때문에 방문과 정산이 줄어드는 것도 점수를 떨어뜨린다.
두 효과를 함께 재는 것이 이 실험의 핵심이다.

## 두 역할이 공유할 경험과 운영

- 품목별로 자신이 관찰한 실제 정산 가격, 공개 가격, checkout·통신 성공 정보를 요약할 수 있다.
  buyer의 비공개 mandate 예산이나 인증 정보를 shop의 가격 판단에 넘기지 않는다.
- 모델은 가격·협상 판단을, 코드는 제약 검증과 실행을 담당한다. 기존 학습 구조를 유지한다.
- 기억은 ‘사실·추정·시도·검증 결과’를 구분한다. 실제 호출된 정책 버전과 선택 이유를 남긴다.
- 안정적인 연속 운영을 우선한다. 누적 순위에서는 접속하지 않은 시간이 그대로 기회 손실이다.
  다만 단순 누적 점수 차이로 지연의 원인이나 온라인 시간을 역산하지 않는다.
- 협상 횟수, 모델 입력 길이, worker 시작 시간, 상대 응답 시간을 각각 측정한 뒤 병목을 줄인다.
  새 모델이나 더 긴 문맥이 자동으로 더 높은 점수를 만든다고 가정하지 않는다.
- 자기 거래, 거래 중복, 허위 후기 등으로 보상을 부풀리는 정책은 만들지 않는다.

## memory-v1에서 다음 후보로 넘어가는 검증 순서

1. **기준 보존:** 현재 memory-v1을 대조 정책으로 남긴다. 기존 key·원본 로그·실패 커밋을 유지한다.
2. **R3 보상 확인:** HTML LAB에서 실제 paid/settled와 예산 비공개 기록을 먼저 확인한다.
3. **한 요소씩 비교:** Buyer는 상대 선택 또는 제안 정책 하나, Shop은 호가 정책 하나씩 비교한다.
   같은 품목·Round·비슷한 운영 시간대에서 후보를 섞고 정책별 시도와 결과를 남긴다.
4. **평가:** Buyer는 시간당 정산 절약액과 정산율, Shop은 시간당 정산 마진과 유입·정산율을 본다.
   두 역할 모두 제약 위반, 결제 거부, API 비용, 지연을 함께 확인한다.
5. **증거에 따라 확대:** 작은 표본에서 우연히 높은 정책을 승자로 선언하지 않는다.
   성과가 재현되는 후보의 비중을 높이고, 환경이 바뀌면 다시 탐색한다.

장기 목표는 실제 Round 3의 기본 Saved·Profit 순위에서 각각 1위다.
경쟁자의 정책, 수요, 온라인 시간에 따라 결과가 달라지므로 사전에 1위를 보장할 수 없다.
이번에 수립한 것은 그 목표를 직접 겨냥하는 검증 가능한 전략과 선택 절차다.
