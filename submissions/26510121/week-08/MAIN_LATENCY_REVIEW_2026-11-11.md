# Main Shop / Buyer 지연 종합 분석 — 2026-11-11

**현재 주요 병목은 API 모델 추론이 아니라 Main 안에서 반복하는 이력 조회·후보 평가, Shop의 동기식 계산, 주문 실행·정합의 결합이다.** v14의 역할 분리는 도움이 될 수 있지만, 같은 코드를 Agent별로 복제하면 조회·락·자원 경합만 늘어날 수 있다. 먼저 공통 사실 뷰를 만들고 Main의 반복 작업을 줄여야 한다.

## 2. 가장 큰 Shop 병목: 가격·보증 후보마다 같은 원장을 다시 푼다

`r3/economy.py:49`는 가격 후보를 만들고, 각 후보에서 `r3/meta.py:134`의 `quote_completion()`을 호출한다. 이 함수는 호출할 때마다 Shop 정산 최대 10,000건과 견적 최대 10,000건을 읽고 Python/JSON으로 필터링한다. 공산품은 여러 보증 옵션에 대해 같은 후보 계산을 반복한다.

읽기 전용 격리 프로파일의 한 공산품 unit 사례는 다음과 같다.

- `shop_candidates()`가 보증 옵션을 포함해 4회 진입했고, `quote_completion()`은 9회 호출됐다.
- 정산 행 109,538개, 견적 행 90,000개, 기회 행 30,000개를 **중복 포함** 디코딩했다. 이는 그만큼의 고유 거래가 있었다는 뜻이 아니다.
- 계측된 후보 생성은 cold 4.204초, module cache가 일부 남은 재실행 3.612초였다. `quote_completion()`의 누적 시간은 각각 약 2.58초, 2.47초였다.
- 식품 샘플도 5개 가격 평가에서 견적 50,000행, 정산 50,556행을 중복 포함해 읽었다.

이 수치는 단일 입력의 cProfile 계측값이며 실거래 p95가 아니다. 재실행마다 shadow journal의 파생 쓰기는 버리므로 완전히 warm한 운영 worker와 같지 않다. 그래도 같은 이력을 후보마다 반복해서 디코딩하는 구조는 직접 확인됐다.

적합한 수정은 **의사결정 한 번에 과거 자료를 한 번만 읽고**, SKU·등급·보증·가격 구간별 조회 뷰를 재사용하는 것이다. 원래의 ±10% 가격 비교, task 중복 제거, 5분 미체결 성숙 기준, 늦은 정산 반영을 보존해야 한다. 계산을 줄인다는 이유로 이 의미를 바꾸면 다른 정책이 된다.

추가로, 같은 읽기 전용 transaction·고정 시각에서 Shop 식품과 공산품 각각 한 입력을 3쌍씩 실행했다. 비교 순서는 번갈아 배치했다. 제안 알고리즘을 바꾸지 않고 **결정 내부의 동일한 events 조회만 재사용**한 실험이다.

| 단일 입력 사례 | 기존 중앙값 | 조회 재사용 중앙값 | 전체 출력 hash |
|---|---:|---:|---|
| Shop 식품 | 1.370초 | 0.601초 | 6회 모두 동일 |
| Shop 공산품 | 2.533초 | 0.682초 | 6회 모두 동일 |

공산품에서 중복 포함 디코딩은 241,112행→48,426행이었다. cProfile을 켜지 않은 별도 입력 실험이므로 위의 4.204초와 직접 전후 비교하지 않는다. 동시 요청·실제 DB 쓰기·다른 입력·결정 사이 freshness/invalidation은 검증하지 않았다. 따라서 운영 적용 기준을 충족했다고 보지 않는다. 이 실험에서는 order/shops 파일 시각이 맞지 않아 Buyer 사례는 건너뛰었다.

## 3. Shop event loop에서 동기 계산과 DB 정리가 실행된다

`seller_r3.py`의 `_execute()`는 async지만, `select_unit()`, `customer_memory.visit/incoming/summary()`, `shop_candidates()`는 동기식으로 호출한다. `asyncio.to_thread()`에 넘기는 것은 그 뒤의 `Chooser.choose()`뿐이다. 이미 수 초를 소비한 뒤 빠른 판단 부분만 worker로 옮긴 구성이다.

따라서 다른 요청을 처리해야 할 event loop가 후보 생성과 파일·DB 처리 동안 막힐 수 있다. 요청이 겹치면 실제 연산 시간 외에 대기 시간도 생긴다. 단일 worker로 실행되는 seller의 카드·A2A 응답에도 영향을 줄 수 있다. **현재 시장 offline 발생을 이 요인 하나로 확정하지는 않았다.** 동시 카드/협상 요청의 event-loop lag 계측이 추가로 필요하다.

기억 관리 `retain()`은 새 방문과 incoming 메시지 경로에서 실행되며 `BEGIN IMMEDIATE`, 오래된 작업 archive, 삭제/정리를 수행한다. 실제 query plan에서 customer 이력 정리 SELECT는 `SCAN events USING COVERING INDEX event_kind`와 임시 정렬 B-tree를 사용했다. 단일 kind 조회의 indexed SEARCH와 다르다. DB 전체 2.62GB를 매번 모두 읽었다고 해석해서는 안 된다.

적합한 수정은 예약·계약의 원자성은 Main에 남기고, 과거 요약 계산과 정리/보관은 별도 작업으로 이동하는 것이다. 무작정 thread만 늘리면 동일 unit 경합, GIL 및 SQLite writer 경합이 남는다. 동일 task 순서와 unit 예약 배타성 검사가 필요하다.

## 4. Buyer는 수백 경로를 정밀 평가한 뒤 극소수만 접촉한다

공산품 준비의 후보 수는 중앙값 241개, p95 약 426개였다. 그런데 초기 병렬 RFQ는 최대 두 가게이고, 총 접촉 경로의 설정은 4개다. 접촉하지 않을 후보에도 정밀한 과거 조건 평가를 수행한다.

`buyer_candidates()`의 후보 루프는 다음을 반복한다.

- purchase/attempt 배열을 해당 가게·SKU에 대해 다시 필터링.
- `shop_hint()`에서 forum 관측 최대 1,500개를 후보마다 다시 조회.
- 거절 unit 목록을 여러 경로에서 다시 읽음.
- 판매 조건별 `buyer_assessment()`를 수행하면서 동일한 보드/규칙 상태를 재조회.

현재 식품 19개 후보의 격리 프로파일에서도 forum 28,500행, purchase 16,000행, agreement 6,000행을 중복 포함해 디코딩했다. 후보 생성은 cold 1.339초, 일부 cache 재사용 시 0.845초였다. 운영에서는 snapshot 파일 파싱과 연결 생성 비용도 붙는다. 재생은 한 SQL 연결과 이미 읽은 파일 객체를 사용하므로 그 비용을 포함하지 않는다.

해결은 `빠른 적합성 필터 → 다양성을 보존한 shortlist → shortlist만 상세 평가`다. 정확한 SKU·사용 시간·현재 재고, 안정된 상대 identity로 먼저 좁히고, 대체 SKU·등급·보증을 놓치지 않게 경로 다양성을 둔다. 단순히 첫 몇 개만 남기면 중요한 구매 기회를 없앨 수 있다.

## 5. 주문마다 프로세스가 시작되고, 정합이 거래 전후에 반복된다

`agent.json`과 `r3/checkout.py`에 따라 Buyer 실행/재시도마다 `market_buyer.py` 자식 프로세스를 만든다. 가벼운 비거래 측정 3회에서 빈 Python 자식 중앙값은 0.057초, Buyer 모듈 import까지는 0.312초였다. 정상 프로세스 시작 비용은 존재하지만 현재 수 초~10초 준비 시간보다 우선순위는 낮다. 모든 지연을 cold start 탓으로 돌리면 안 된다.

Buyer child는 실행 시작에 `journal.reconcile()`을 호출하고, 부모도 결제 후 정합한다. sync에서도 수행한다. 격리된 쓰기 없는 정합 샘플은 0.477초였으며 purchase 10,000행, outcome 20,000행을 디코딩하고 batch 9,567행의 기록을 시도했다. batch 수는 새 기록/새 보상이 아니라 이미 존재하는 idempotent 행 시도를 포함한다. 실제 DB 쓰기 비용은 이 재생에 포함하지 않았다.

지속 실행 Buyer worker와 watermark 기반 증분 정합이 적합하다. 다만 단일 결제 권한, 불명 결제 재시도 금지, late refund/canonical outcome 개정은 유지해야 한다. CPU 절약을 위해 환불 의무나 실제 결제 상태를 오래 cache하는 것은 대안이 아니다.

## 6. deadline은 협상·결제·취소까지 일관되게 이어지지 않는다

최근 시도에는 `no_agreement` 2,001회, `ReadTimeout` 134회, 부적합 유통기한 70회, ambiguous ask 102회가 있었다. 시도 횟수이지 고유 실패 주문 수가 아니다. ReadTimeout 시도 시간의 p95는 7.827초였다.

Peer의 per-request timeout은 단일 통합 wall-clock 기한이 아니다. 네트워크의 여러 단계, 계산, 후속 RPC와 정리가 연결된다. 선택된 협상 peer의 `finally` 취소는 최대 2초 동기식이고, prepared quote의 취소는 별도로 background에서 처리한다. 정상 종료/취소 방식이 통일돼 있지 않다.

또한 부모의 가게 목록 조회·Buyer child·결제·결과 제출에는 통합 단계별 span이 없다. 시장 결과 제출의 retry/backoff는 다음 주문 요청을 늦출 수 있다. 결제는 불확실한 상태에서 속도를 이유로 재시도할 수 없다.

해결은 하나의 주문 deadline을 준비·견적·협상·checkout·결과 제출의 예산으로 나누고, 다음 왕복이 유리한지 판단하는 것이다. 취소는 자원 상한이 있는 별도 큐로 보내되 task/예약의 유효기간을 명확히 유지한다. timeout을 일괄 단축해 성공률을 떨어뜨리는 방식은 피한다.

## 7. 공통 sync에 여러 역할이 직렬로 묶여 있다

공식 kit는 Buyer 주문 루프와 sync thread를 분리한다. 그러나 sync 안에서 inventory/forum/demand 조회, outbox, control/adaptive/evolution/merchant/forum 작업, broken news와 공개 원장 정합이 순서대로 수행되고 그 후 restock thread를 예약한다. 기본 sleep 10초는 실제 갱신 주기가 10초라는 보장이 아니다. 작업 시간과 외부 요청 시간이 추가된다.

따라서 게시/분석이 길면 최신 재고·원장과 공급 창 대응이 늦어질 수 있다. Shop 보충은 기본 60초 간격 검사 및 공급 창 제한도 받는다. Buyer Main을 직접 같은 thread에서 멈춘다는 뜻은 아니지만, 오래된 입력·DB/CPU 경합으로 간접 영향을 준다.

실제 정합·접속 복구·필수 데이터 수집을 먼저 유지하고, 분석/평가/게시를 낮은 우선순위의 별도 작업으로 나누는 것이 맞다. 공급 창 시작 시각과 품절 사건에 반응하되 공식 호출 한도와 429를 준수한다.

## 8. 컨텍스트 문제는 토큰뿐 아니라 반복 파싱과 기록량이다

최근 6시간 `prediction` 8,867개에 기록한 JSON payload는 약 **126MB**이고, 가장 큰 한 건은 약 268KB였다. 현재 DB 파일은 약 2.62GB다. 이 크기 자체가 병목이라는 증명은 아니지만, 같은 근거를 후보마다 복제·직렬화하는 비용과 장기 성장을 보여 준다.

`Chooser`의 fast return 전에 공통 context 구성과 prediction 저장이 수행된다. 모델 호출이 없어도 이 작업은 남는다. 반면 실제 서명·정산·결제 불명 상태 기록은 생략하면 안 된다.

Main은 `rules/data/policy version + 필요한 현재 사실 + evidence ID`만 사용하고, 재사용 가능한 과거 요약은 별도 immutable view로 유지하는 것이 적합하다. 비필수 상세 telemetry는 제한된 큐로 옮기되 금융 원장과 실패 증거는 보존한다. 기존 로그를 삭제·수정하는 제안이 아니다.

## 9. 실제로 확인한 복구 스레드 종료

원본 콘솔 2705~2734행에서 11월 10일 19:41:34의 사고가 확인됐다.

1. `ShopSupervisor.tick()`의 `shop-health.json` 원자 교체가 `PermissionError [WinError 5]`로 실패.
2. 예외 처리에서도 `monitor.snapshot('retrying')`가 같은 오류로 실패.
3. 그 두 번째 예외를 처리하지 않아 `Thread-5 (<lambda>)`가 종료.
4. 이후 독립적인 양성 건강 확인이 `healthy`를 갱신했지만 `primary_heartbeat_at`은 그대로였다. 상태 확인은 복구 스레드 재시작이 아니었다.

코드는 Windows 교체 오류에 총 최대 70ms의 제한된 retry를 추가하고, 오류 보고 실패가 supervisor를 종료시키지 않게 했다. 기존 supervisor는 이미 종료됐으므로 해당 소스 수정만으로 살아나지 않는다. 거래 프로세스 재시작은 하지 않았고, runtime session에 묶인 독립 `shop_recovery_guard.py`를 실행했다. 이 프로세스는 이상 2회 확인·120초 cooldown·공식 목록/보드/카드/ACP 검사 후 기존 주소만 재등록한다. 전체 시장 장애·불확실한 결과·최근 primary heartbeat·runtime 교체는 각각 보류/종료 조건이다.

대상 기능 회귀 62개와 전체 tests **277개가 통과**했다. 이는 시장이 향후 항상 online이거나 전략 수익이 향상된다는 검증이 아니다. 10:20~10:22에는 online 복귀와 Shop 거래 8,415→8,416이 확인됐으나 이후 시장 목록 변동이 재발했다. 10:49~10:52, 10:56~10:59 연속 확인에서는 카드/ACP 200과 달리 목록 제외·보드 offline이 반복돼 해당 검증이 실패한 기록도 보존했다. 재등록 수락만을 지속 복구 증거로 세지 않는다.

11:01:13의 별도 공개 진단에서는 등록 목록에 우리 주소가 있고 보드 `alive=true`, 외부 카드 200이었다. 독립 guard도 같은 runtime session으로 계속 실행되며 자동 재등록 후 정상 관측을 기록했다. 이 마지막 확인과 지속 안정성은 다르다. 활성 목록은 일부 구간 24~55개로 변동했지만 그 외부 변동의 원인은 확정하지 않았다. 현재 실행 중인 원래 primary 스레드는 재시작하지 않았으며, source 수정과 별도로 fallback 프로세스가 복구 역할을 맡고 있다.

## 10. 개선 우선순위와 검증

| 순서 | 변경 대상 | 확인할 결과 |
|---|---|---|
| P0 | 복구 worker 생존·별도 장애/진행 시각 | 진단 실패 후에도 다음 tick, runtime 교체 시 종료, 실거래 접근 상태 |
| P1 | Shop 원장 1회 조회와 조건별 재사용 | 동일 입력의 후보·가격·보증·선택 일치, 첫 견적/loop lag 개선 |
| P2 | Buyer 공통 MarketView와 두 단계 후보 평가 | 준비 p95/p99 개선, Saved·완결률 유지, 대체 경로 누락 증가 없음 |
| P3 | 증분 정합·지속 worker·단계별 deadline | 늦은 환불/불명 결제 정합 유지, 전체 주문 시간과 성공률 |
| P4 | sync/게시/평가 분리·제한된 기록 큐 | 데이터 age/공급 창 대응, DB writer/CPU 경합, 증거 보존 |

구조 변경은 같은 frozen 입력에 대해 단위·후보·선택과 보호 조건을 비교하고, 반복 부하·동시 요청에서 전체 p50/p95/p99, event-loop lag, DB 대기, 성공률을 측정해야 한다. 정책을 바꾸는 shortlist나 탐색 변경은 별도로 경제적 검증이 필요하다. 모든 단계의 지연을 0으로 만들 수는 없으며, 현재 수치에서 특정 배수의 개선을 보장하지 않는다.

이번 작업에서 **속도 개선 전략 후보 P1~P4는 운영에 적용하지 않았다.** 적용한 것은 실제 장애의 파일 교체/복구 오류 처리와 독립 복구 감시다. v14 전체는 여전히 설계 상태다.
