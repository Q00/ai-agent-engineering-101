# 2026-11-04 offline 및 실행 중단 복구

## 확인한 사실

- 12:22 KST 진단 당시 공개 board의 Shop·Buyer는 모두 alive였다. Shop 공개 agent-card도 HTTP 200이었다. 이 시점 Shop은 204건, Buyer는 414건 정산돼 있었다.
- 실행 로그의 10:37:24에 기존 터널이 응답하지 않아 교체했다. 10:37:42에는 새 주소를 시장이 읽지 못해 재등록이 HTTP 400(agent-card TimeoutError)으로 실패했다. 다음 Shop 등록 성공은 11:40:03이다.
- 기존 키트 watchdog은 교체한 터널이 정상 응답하면 재등록 실패 상태를 재시도하지 않았다. 그 결과 연결 프로세스는 살아 있어도 시장에는 만료된 이전 주소가 남을 수 있었다.
- 별도로 01:43:21부터 `NoneType * int` 오류가 반복됐다. 과거 구매의 `warranty_hours:null` 값을 고장 이력과 대조하면서 발생했으며, Buyer 주문 처리와 동기화의 공통 `reconcile()`을 막았다. 온라인 표시는 정상 거래 처리를 증명하지 않는다.
- 진단 원문은 `logs/offline-incident-20261104T032618306392Z.json`과 수정하지 않은 기존 실행 로그에 보존했다.

Pinggy 공식 [도움말](https://pinggy.io/help/)은 무료 터널의 60분 만료와 재시작 시 주소 변경을 명시한다. 실제 로그에서도 약 62분 간격으로 터널 교체가 반복됐다. 장시간 offline의 직접적인 결함은 새 주소의 등록 실패를 계속 재시도하지 않은 것이다.

## 수정

1. 보증 기간의 null/누락은 명시된 보증 없음으로 정규화한다. 과거 원본 거래 이벤트를 수정하지 않으며, 보증을 임의로 추가하거나 환불을 확정하지 않는다. 신규 후기와 판매 기록도 같은 규칙을 사용한다.
2. Shop 감독기를 제출 폴더 안에 추가했다. 도달 가능 여부와 시장 재등록 성공을 별도 상태로 관리하고, 실패한 재등록은 URL이 정상 응답해도 15초 검사 주기마다 다시 시도한다.
3. 무료 Pinggy는 55분에 대체 연결을 준비한다. 새 주소의 discovery 확인과 시장 등록 성공 전까지 기존 터널을 유지한다. 준비 실패 시 기존 주소를 버리지 않는다. Cloudflare에는 이 만료 시간을 적용하지 않는다.
4. `.market/shop-health.json`에 최근 검사 시각, 등록 대기 여부와 상태를 저장한다. 키트의 프로세스 정리 목록에 교체 중인 연결도 포함한다. 공유 수업 스크립트는 변경하지 않았다.

## 검증

- `logs/verification-20261104T032533950281Z.txt`: null 보증 회귀를 포함한 68개 통과.
- `logs/verification-20261104T032807896735Z.txt`: 등록 실패 뒤 정상 URL에서 재시도, 기존 연결을 유지하는 교체 순서, 실패한 새 연결 폐기, Cloudflare 분기를 포함한 72개 통과.
- 실제 저장 데이터의 `Journal.reconcile()` 성공과 12:29 KST 이후 구매 재개를 확인했다.
- `logs/recovery-join-20261104T032950455325Z.txt`로 양쪽 실행을 재시작했다. 무료 서비스나 네트워크의 무중단을 보장하는 검증은 아니며, 55분 경과의 실제 예약 교체는 추후 로그로 확인해야 한다.

추가 진단 중 Windows에 `tzdata`가 없어 시간대 표시용 조회가 실패했다. 거래 처리와 관계없는 보조 출력이며 UTC+9 고정 오프셋으로 대체했다. 원본 로그의 공백 경고는 정리하지 않고 보존한다.

최종 실제 확인: `logs/recovery-status-20261104T033159662754Z.json`의 12:31:59 KST 상태에서 양쪽 alive, 공개 카드 HTTP 200, 감독기 healthy/등록 대기 false, 재시작 후 Buyer 결제 4건, 신규 TypeError 0건이었다. 누적 정산은 Shop 204건·Buyer 424건이다. Shop 재고는 0개로, 서버가 알린 다음 공급 창은 12:44:13~12:47:13 KST다. 연결 복구와 다음 공급 창에서의 실제 재매입 성공은 구분한다.
