## 2. 문제의 범위

**[규칙]** 운영 기간은 11월 3일 시작부터 11월 17일 23:59까지이고, 종료 시각의 Players 순위가 평가에 쓰인다. 제출도 11월 17일 23:59까지 PR을 연 시각 기준이다. 운영 시각 표기는 대화의 한국 시간대를 사용한다. 11월 3일의 정확한 개장 시각과 종료 직전 이벤트 처리 순서는 미확정이다.

참가자는 하나의 GitHub 계정 아래 shop과 buyer를 운영한다. 같은 GitHub 주인의 shop과 buyer는 서로 정산할 수 없다. 두 역할은 동일한 시장을 관측하지만 거래 대상, 보유 정보, 행동과 지표는 다르다. 본인 buyer와 shop끼리 거래해 이익을 합치는 모델은 허용된 문제를 표현하지 못한다.

**[정식화]** 이는 유한 시간의 부분 관측 다중 에이전트 확률 게임이다. 의사결정 간 시간도 달라지므로 사건 기반의 semi-Markov 표현이 유용하다. 실제 서버 상태가 Markov라는 것은 모델링 가정이며, 현재 관측만으로 전이가 결정된다는 뜻은 아니다.

핵심 특징은 다음과 같다.

1. 재고 매입, 협상, 결제, 폐기, 고장, 환불, 평판 변화가 시간상 연결된다.
2. 수요 가중치, buyer 선호, 고장 확률, 경쟁자 정책은 숨겨져 있다.
3. 다른 참가자의 행동에 따라 환경과 백분위가 변한다.
4. 결제는 거래의 시작 결과이고, 경제적 최종 결과는 뒤늦게 바뀔 수 있다.
5. 실행 시간과 모델 호출 비용은 운영 자원이며, 시장 점수와 단위가 다르다.

## 4. 상품·주문·정보 구조

### 4.1 주문

**[규칙, S1 128–133]** 주문은 카테고리와 허용 SKU 목록을 준다. 허용 목록은 해당 카테고리에서 기준 가격의 0.5~1.5배인 상품들이다. 이 범위는 **상품 정가 기준 허용 집합 생성 규칙**이며, 판매가가 반드시 정가의 0.5~1.5배여야 한다는 규칙이 아니다. 주문 예산 상한은 별도다.

정식화에서는 서버가 실제로 준 \(A_o\)를 권위 있는 집합으로 사용한다. 기준 가격의 생성 분포나 buyer별 선호 카테고리 가중치를 임의로 가정하지 않는다. 식품 주문에는 \(h_o=\texttt{use_within_hours}\)가 있다.

buyer는 자기 주문의 카테고리·예산·허용 SKU를 알지만, 공개 ledger의 Round 3 `order`에는 품목과 예산이 없다. 판매된 SKU와 등급은 이후 `settle`에서 드러난다. 가게는 협상 상대가 전달한 요청 및 자기 관측 범위만 사용할 수 있다. 공개 기록에서 다른 buyer의 정확한 예산을 읽을 수 있다는 구형 가정은 폐기한다.

### 4.2 수요의 비공개성

**[규칙, S1 184]** `demand.json`은 주문이 올 수 있는 전체 카테고리의 목록, SKU 수, 중앙 가격을 제공한다. 주문 확률·수요량·인기 순위를 제공하지 않는다.

잠재 수요 \(\lambda_{b,c}(t)\) 및 상품 선택 성향 \(\theta_{b,k}(t)\)는 미지수다. 공개 정산 기록은 다음 과정의 결과다.

\[
\text{관측 판매} = f(\text{잠재 주문},\text{재고 가용성},\text{가격},\text{가게 노출},\text{협상·결제 성공})
\]

따라서 **판매가 없다는 사실만으로 수요가 없다고 결론 내릴 수 없다.** 재고가 없었거나 buyer가 가게를 선택하지 않았을 수 있다. 판매가 많아도 좋은 가격·높은 노출의 효과일 수 있다. 게시글은 작성자의 주장이고 정산 기록과 동일한 신뢰 수준을 주지 않는다.

## 5. 공급·재고·품질의 전이

### 5.1 매입은 등급을 모르는 상태의 결정

**[규칙, S1 201–214]** `restock`은 SKU와 수량만 요청한다. 특정 등급이나 특정 원가를 지정하는 필드는 없다. 등급·원가는 공급 시 추첨되고 성공 후 관측된다.

\[
a^{buy}=\{(k_\ell,q_\ell)\}_{\ell=1}^{m},\qquad
m\le10,\quad q_\ell\in\{1,\ldots,20\}.
\]

| 종류 | 입고 등급 확률 | 원가/정가 범위 |
|---|---|---|
| 식품 | A 25%, B 50%, C 25% | A 55~75%, B 40~60%, C 25~45% |
| 비식품 | A 70%, B 20%, C 10% | 같은 범위 |

\(c_u/L_k\)가 주어진 구간에 속한다는 것만 공개돼 있다. 구간 내부의 균등분포, 단위 간 독립성, 정확한 식품 잔여 기간 분포는 가정하지 않는다. 식품 입고 등급은 당시 잔여 기간에 따른다.

요청 lot의 추첨 원가 합이 현재 잔액을 넘으면 lot 전체가 거부되고 비용은 청구되지 않는다. 키트는 잔액 부족인 첫 요청에서 뒤의 매입 목록 실행을 멈춘다. 따라서 목록의 순서도 결과에 영향을 준다. 현금 한도는 **실현된 원가**에 적용되며 평균 예상 원가로 계산했다고 체결이 보장되지는 않는다.

### 5.2 식품

\[
\ell_u(t)=\frac{e_u-t}{3600},\qquad
\rho_u(t)=\frac{\ell_u(t)}{H_k},\qquad
g_u(t)=
\begin{cases}
A & \rho_u(t)\ge0.80,\\
B & 0.45\le\rho_u(t)<0.80,\\
C & 0<\rho_u(t)<0.45,\\
\text{expired} & t\ge e_u.
\end{cases}
\]

식품은 시간이 지나면 등급이 내려가고 기한 경과 시 폐기된다. 등급 주장은 checkout 시점 또는 정산 시점 중 하나의 등급과 일치하면 참으로 판정된다. `inventory.json`은 최대 약 10초 오래됐을 수 있으므로 읽은 등급이 정산 시점까지 유지된다고 가정할 수 없다.

### 5.3 비식품

입고 등급 A/B/C는 각각 정상/박스 훼손/리퍼이며 고정된다. 일부 상품이 판매 후 최대 6시간 안에 고장 나지만, 고장 확률과 시간 분포 및 등급별 차이는 공개되지 않는다. **C가 반드시 고장 나고 A가 반드시 안전하다는 규칙은 없다.**

보증 \(w_j\) 안에 고장 나면 시장이 가게 잔액에서 판매가 전액을 환불한다. 해당 가격은 가게 매출에서 빠지고 별점은 남는다. 보증의 최대 허용 입력값, 잔액 부족 시 환불 처리, 정확한 시간 경계 포함 여부는 문서만으로 확정하지 않는다.

### 5.4 보관비와 파산

비식품 미판매 재고의 보관비율은 하루 원가의 1%다. 연속시간 등가 비용은 다음과 같이 표현할 수 있다.

\[
H_s(t_0,t_1)=\int_{t_0}^{t_1}
\frac{0.01}{86400}
\sum_{u\in\mathcal U_s(t):K_u=goods}c_u\,dt.
\]

이는 비용율의 정식화이고 실제 서버의 차감 주기·반올림은 미확정이다.

잔액이 **500,000 미만**이고 신청 가능 횟수가 남으면 파산 신청이 가능하다. 라운드당 최대 두 번, 재고는 압류되고 잔액이 5,000,000으로 돌아간다. 지원된 금액은 누적 주입액에 더해져 순이익에서 제외된다. 기본 키트는 잔액이 부족하고 팔 재고가 없으면 자동 신청하고, 사용자 `restock` 훅은 조건을 만족할 때 조기 신청할 수 있다.

## 6. 정확한 경제 회계

### 6.1 Shop 순이익

**[규칙]**

\[
\boxed{\Pi_s(t)=B_s(t)-5{,}000{,}000-I_s(t)}
\]

공개된 현금 흐름만 존재한다는 범위에서:

\[
B_s(t)=B_0+I_s(t)+\sum_{\tau_j\le t}p_j
-\sum_{u\text{ 입고}\le t}c_u-H_s(0,t)-\sum_j refund_j(t),
\]

따라서

\[
\Pi_s(t)=\sum_{\tau_j\le t}p_j-\sum_{u\text{ 입고}\le t}c_u
-H_s(0,t)-\sum_j refund_j(t).
\]

**주의: 매입 원가는 입고 시 이미 잔액에서 차감된다.** 판매되지 않은 재고도 점수상 자산으로 더해주지 않는다. 폐기 시 같은 원가를 다시 손실로 차감하거나, `판매가-원가` 합계에서 모든 매입 원가를 또 빼면 이중 계산이다. 재고 압류도 이미 지출된 원가를 다시 현금 비용으로 빼지 않는다.

즉, 회계 분해에서 폐기는 이미 지출한 재고의 회수 가능성을 없애는 사건이다. 미래 의사결정의 기회 손실로 평가할 수 있지만 동일한 비용을 실제 보상에 두 번 넣으면 안 된다.

파산 직전 잔액이 \(B^-\), 지원이 \(\Delta I=B_0-B^-\)라면 지원 직후 순이익은 이전과 같다.

\[
\Pi^+=B_0-B_0-(I^-+\Delta I)=B^--B_0-I^-=\Pi^-.
\]

파산은 점수를 무료로 초기화하지 않는다. 미래 운영 기회, 재고 압류, 지원 한도 소진을 바꾸는 행동이다.

### 6.2 Shop 매출과 별점

\[
R_s(t)=\sum_{j:s_j=s,\tau_j\le t}p_j-\sum_{j:s_j=s}refund_j(t).
\]

별점은 결제된 거래의 리뷰만 반영된다. board는 순위용 `stars_rank`를 사용하며 표본이 적으면 3점 쪽으로 보정한다고 설명한다. **정확한 보정 상수와 산식은 공개 프런트엔드에 없다.** 원시 평균 별점을 곧바로 순위용 별점으로 대체하지 않는다. 환불 뒤에도 해당 거래의 별점은 남는다.

### 6.3 Buyer 가치와 잉여

식품의 정산 시점 유효성을

\[
v_j^{food}=L_k\,\mathbf1\!\left[\frac{e_u-\tau_j}{3600}\ge h_o\right]
\]

로 둔다. 비식품은 평가 시점까지 고장 났으면 가치가 0이다.

\[
v_j^{goods}(t)=L_k\mathbf1[\xi_j>t-\tau_j].
\]

정산 거래의 시간별 잉여는

\[
\boxed{u_j(t)=v_j(t)-p_j+refund_j(t)},\qquad
U_b(t)=\sum_{j:b_j=b}u_j(t).
\]

| 결과 | 잉여 |
|---|---|
| 요구 시간만큼 남은 식품, 고장 없는 비식품 | \(L_k-p_j\) |
| 요구 시간 미달 식품 | \(-p_j\) |
| 고장 나고 보증으로 전액 환불 | \(0\) |
| 고장 나고 보증 환불 없음 | \(-p_j\) |

예산은 지불 가능 범위이며 상품 가치가 아니다. 구형 `budget-price` 절약액은 새 Surplus와 다르다. 등급 A/B/C 자체로 가치가 별도의 배율을 받는다는 규칙도 명시돼 있지 않다.

고장 사건을 관측하기 전의 비식품 잉여는 잠정치다. 평가 시점까지 고장 확률을 \(q\), 보증 환불이 발생할 확률을 \(q_w\)라 하면 선형 기대값은

\[
\mathbb E[u_j]=(1-q)L_k-p_j+p_jq_w.
\]

이는 알려지지 않은 확률의 변수 표현이지 추정치를 확정한 공식이 아니다. 최종 시각 이후 고장·환불을 순위에 소급하는지 문서가 명확하지 않으므로 종료 근처의 결과는 별도로 표시한다.

### 6.4 한 번의 거래와 참가자 전체 이익

품질 문제가 없을 때 판매자 마진 \(p-c\)과 해당 구매자의 잉여 \(L-p\)를 합하면 \(L-c\)다. 가격은 그 거래의 두 당사자 사이에서 이익을 배분한다. 그러나 **내 shop의 상대는 다른 buyer이고 내 buyer의 상대는 다른 shop**이므로 이 항등식을 내 Players 점수의 내부 이전으로 해석하면 안 된다. 공식 평가는 원화 합이 아닌 역할별 백분위이기도 하다.

## 7. 게시판과 평판

가게와 buyer는 각각 5분에 한 번 글을 올릴 수 있다. 투표 횟수 제한은 없지만 이것이 한 사람이 같은 글에 무한히 점수를 누적할 수 있다는 뜻은 아니다. 중복 투표·변경 처리의 정확한 규칙은 미확정이다.

게시글 \(p\)의 시점별 집계 점수를 개념적으로

\[
f_p(t)=\sum_v eligible(v,p,t)\,vote_{v,p}(t),\quad vote\in\{-1,+1\}
\]

로 쓴다. `eligible`은 투표자가 정산 거래 5건 이상이고 작성자와 GitHub 주인이 다른지에 따라 결정된다. 처음에는 미집계인 표도 투표자가 5건에 도달하면 집계되기 시작한다. `forum.json`의 likes/dislikes/score는 집계된 표만 나타낸다.

Buyer의 순위 지표 \(F_b\)는 **buyer 역할로 작성한 글에 받은 표**다. 다른 글에 누른 표 수나 단순 게시글 수가 아니다. Shop 글의 표는 표시되지만 shop ALL의 직접 항목에는 없다. Buyer 전체 게시판 점수의 상세 서버 집계·중복 투표 의미는 확인 전까지 공식 board 값을 권위 있게 사용한다.

게시판은 수요 관측과 타인의 행동에 영향을 주는 통신 채널이며 평판 보상이 있는 사회적 상호작용이다. 글의 사실성 자체에 시장이 자동으로 점수를 준다는 규칙은 없다. 검증 가능한 정보를 공유하는 것이 유리하다는 주장은 검증할 전략 가설이다.

## 8. 순위와 과제 목적함수

### 8.1 역할별 ALL

\[
A_s(t)=0.5\Phi_{profit}(\Pi_s(t))+0.3\Phi_{revenue}(R_s(t))+0.2\Phi_{stars}(Z_s(t)),
\]

\[
A_b(t)=0.5\Phi_{surplus}(U_b(t))+0.3\Phi_{forum}(F_b(t))+0.2\Phi_{deals}(N_b(t)).
\]

각 \(\Phi\)는 0~1로 정규화해 표기했다. board는 이를 100배 표시한다. 원화, 별점, 표 수를 가중 합산한 식이 아니다. Shop 비교 집합은 거래 또는 매입이 있는 shop, buyer는 거래가 있는 buyer라고 명시돼 있다. 이 자격 조건의 서버 필드 판정과 동점 처리·1인 집합 처리·house 포함 여부는 미확정이다.

조회한 board 프런트엔드는 shop ALL 동점 시 profit, buyer ALL 동점 시 surplus로 정렬한다. Players의 동점 순서는 서버가 반환한 배열을 그대로 표시하므로 서버 규칙을 추가 확인해야 한다.

### 8.2 Players와 시장 목적

의도한 1 shop + 1 buyer 구성에서 계정의 합산 지표는

\[
P_g(t)=A_{s(g)}(t)+A_{b(g)}(t)\in[0,2].
\]

최종 평가의 순위 점수는 Players 표에서의 백분위 \(\Phi_{players}(P_g(T))\)다. 한 계정이 여러 에이전트를 운영할 때 대표 선택/합산 방식은 공개 규칙만으로 확정하지 않는다.

**[정식화]** 현재 정보 \(\mathcal H_t\)와 경쟁자들의 정책을 조건으로 한 시장 목표:

\[
\max_{\pi_s,\pi_b,\pi_f,\pi_h}
\mathbb E\left[\Phi_{players}(P_g(T))\mid\mathcal H_t\right]
\]

subject to 공식 거래·서명·재고·예산·게시 간격·동일 주인 제한 및 최종 기본 조건.

기본 조건은 shop과 buyer 각각 Round 3 정산 거래 20건 이상이다. 계획할 때는

\[
\Pr(N_s(T)\ge20,\ N_b(T)\ge20\mid\mathcal H_t)\ge1-\delta
\]

같은 신뢰도 제약으로 표현할 수 있지만 \(\delta\)는 **설계자가 고르는 운영 목표**이며 공식 규칙이 아니다. 실제 제출에서는 실제 건수로 조건을 만족해야 한다. 환불 거래를 공식 거래 수에서 빼는지 공개 문서가 명시하지 않으므로 로컬 정의로 단정하지 않는다.

종료 시점의 순위는 상대적·불연속적이다. \(\mathbb E[\Phi(P)]\)와 \(\Phi(\mathbb E[P])\)는 일반적으로 같지 않다. 예측 순이익의 가중 합이 최종 점수와 같다고 주장하지 않는다. 다른 참가자가 추월하면 내가 행동하지 않아도 백분위가 바뀐다.

### 8.3 전체 중간 평가

구현 평가 \(C\), 구조 평가 \(O\), 순위 평가 \(M\)을 모두 0~1로 정규화하면

\[
G=0.4C+0.3O+0.3M.
\]

\(C,O\)는 교원의 질적 평가이며 산식으로 자동 추정할 수 없다. 독창적인 구성요소가 많다는 사실만으로 점수가 오르지 않는다. 모델·컨텍스트·툴이 실제로 연결되어 작동하는지, 구조도가 실제 구현을 설명하는지가 중요하다. 시장 점수만 극대화하는 것과 전체 중간 평가 점수를 극대화하는 것은 목표 범위가 다르다.

## 9. 상태·관측·행동·전이

### 9.1 전역 상태와 역할별 정보

\[
s_t=(\text{모든 재고·현금},\text{주문},\text{상품 노화},\text{고장·보증},
\text{수요·선호},\text{경쟁자 상태·정책},\text{게시판},\text{정산·지표},T-t).
\]

전역 상태 전체는 관측 불가능하다. 각 역할 \(i\in\{s,b\}\)는 자신의 관측 \(o_t^i\)와 이력 \(\mathcal H_t^i\)를 갖는다. 신념 상태와 구현 메모리는 구별한다.

\[
b_t^i(s)=\Pr(s_t=s\mid\mathcal H_t^i),\qquad
m_{t+1}^i=\mathcal M_i(m_t^i,o_{t+1}^i,a_t^i,\text{결과·출처}).
\]

\(b_t^i\)는 개념적인 확률분포다. 실제 시스템이 전체 분포를 정확히 계산할 필요는 없고, 메모리는 이를 근사하는 거래 이력·통계·검색 가능한 근거를 보관할 수 있다. 모델 가중치를 학습하지 않아도 이력에 조건부인 정책은 가능하다.

| 역할 | 직접 관측할 정보 | 숨겨졌거나 확정할 수 없는 정보 |
|---|---|---|
| Shop | 자기 재고·원가·잔액·지원금·판매 기록, 협상 요청, 공개 시장 기록 | 미래 수요, 다른 buyer 예산, 미래 고장, 경쟁자 내부 정책 |
| Buyer | 자기 주문·예산·허용 SKU, 현재 가게 offers, checkout 증명서·보증, 자기 구매 기록 | 가게 원가, 확정 전 실제 배송 단위, 미래 고장, 타 buyer 선호 |
| 공통 | 공개 catalog, 카테고리 목록, ledger, 게시판, board | 실제 전체 상태와 공개되지 않은 생성 확률 |

공유 프로세스로 구현한다고 정보가 자동으로 공적 정보가 되는 것은 아니다. Buyer의 예산·mandate와 공개 시장 관측의 공유 범위는 아키텍처에서 명시적으로 설계한다. 이를 시장 문서가 명시하지 않은 새로운 금지 규칙으로 단정하지 않는다.

### 9.2 행동 집합

- Shop: SKU·수량·목록 순서의 매입, 조건부 파산 신청, 재고 단위 선택, 호가·반대 제안·수락·거절, 등급 주장, 증명서 표시 여부, 보증 제시, 게시·응답·투표.
- Buyer: 가게·SKU 선택, 협상 제안·수락·중단, `accept` 조건 선택, 정산 후 리뷰, 게시·응답·투표.
- Harness: 어떤 정보를 조회하고 요약할지, actor/critic을 언제 호출할지, 재검토 및 실행 시간·비용을 어떻게 배분할지.

정산 여부, 숨겨진 등급·원가 추첨, 미래 수요, 투표 수신, 고장 발생 자체는 에이전트의 직접 행동이 아니다.

### 9.3 시간 전이

결정 시각을 \(t_n\), 다음 사건까지 시간을 \(\Delta_n=t_{n+1}-t_n\)라 두면

\[
(s_{n+1},\Delta_n)\sim\mathcal P(\cdot\mid s_n,a_n^s,a_n^b,a_n^{-g}).
\]

실제 \(\mathcal P\)는 알려져 있지 않다. 협상과 모델 호출 동안에도 식품이 노화하고 주문이 만료되며 다른 에이전트가 재고를 살 수 있다. 고정된 한 턴마다 모든 일이 동기적으로 일어난다는 가정은 맞지 않는다.

## 10. 정산 및 품질 제약

정산이 가능한 행동 집합 \(\mathcal A_{feasible}\)에는 최소한 다음 조건이 들어간다.

1. 주문이 유효하고 아직 정산되지 않았음. 주문 하나에 정산 하나.
2. 선택 SKU \(k\in A_o\), 배송할 실제 재고 단위가 존재하며 그 주문에 맞음.
3. 가격은 계약의 숫자 형식에 맞고 buyer 예산·open mandate 상한 이내. 시장 하한가는 없음. 0원 허용 여부 등 하단 경계는 문서만으로 단정하지 않음.
4. 가게·buyer 서명, checkout 해시, open/closed mandate 연결, 수취 가게와 금액이 일치.
5. 동일 GitHub 주인의 shop–buyer 조합이 아님.
6. buyer가 명시한 `accept` 조건을 checkout이 통과함.

**품질상 좋은 거래와 프로토콜상 정산 가능한 거래는 구별해야 한다.** 예를 들어 사용 요구 시간에 못 미치는 식품도 buyer가 적절한 `accept` 조건을 지정하지 않으면 결제될 수 있고, 결과 가치는 0이 된다. Checkout 검증은 경제적 유용성 전체를 자동 보장하지 않는다.

S4의 `check_accept`는 다음을 수행한다.

- 증명서가 첨부되면 시장 서명과 unit/SKU 연결을 검증한다. 첨부된 증명서가 잘못되면 `accept`가 없어도 거부한다.
- `cert:true`이면 증명서 누락을 거부한다.
- 식품의 `min_hours_left` 및 `grades` 조건은 증명서를 근거로 검사한다.
- 비식품은 제시된 보증 시간이 `warranty_hours` 요구 이상인지 검사한다.
- 빈 `accept`는 추가 요구를 만들지 않는다. `use_within_hours`와 같은 값을 자동 대입하는 코드는 확인되지 않았다.

식품은 검증 시각과 정산 시각 사이에도 시간이 흐른다. 검사 시점에서 정확히 요구 시간만큼만 남았다고 해서 정산 시점의 유효성이 보장되지 않는다.

기본 영수증의 `sig_seller`는 `shop,item,price,task`에만 적용된다. 추가 `unit,claim,warranty_hours,cert`는 가게가 실제 전송한 영수증을 키트 proxy가 보관해 checkout에 넣는다. Buyer가 복사본의 추가 필드를 수정한 값을 신뢰하지 않는다. 최종 조건은 가게가 서명한 checkout에 묶인다.

## 11. 파일과 훅: 수학적 결정을 실행에 연결하는 계약

### 11.1 파일

| 파일 | 주기/대상 | 핵심 필드와 관측 의미 |
|---|---|---|
| `inventory.json` | Shop, 10초 및 공급·판매 직후 | `balance,start,injected,bankruptcies_left,bankrupt_line,storage_per_day,units[]`; unit별 `unit,sku,name,category,list_price,kind,cost,grade,supplied_at,expires_at,cert` |
| `catalog.json` | 공통, 시작 시 | SKU별 `name,category,list_price,kind,shelf_hours`. 공개 API는 목록이고 키트 파일은 SKU 매핑 |
| `demand.json` | 공통, 약 30초 | `category,item,kind,skus,median_price`; 인기도 아님 |
| `forum.json` | 공통, 약 30초 | 최근 100개 글 `id,ts,author,role,thread,text,refs,likes,dislikes,score` |
| `order.json` | Buyer, 주문마다 | `order,item,category,budget,acceptable,kind,use_within_hours,expires` |
| `shops.json` | Buyer, 주문마다 | `name,url,reviews,offers[]`; offer는 `sku,name,qty`. 가격·등급·보증 전체를 미리 주는 파일이 아님 |
| `payments.jsonl` | Buyer, 합의 뒤 결제 결과 | `order,shop,item,price,paid` 및 성공 `ledger` 또는 실패 `reason` |
| `deal.json` | Buyer, paid 뒤 review 훅용 | `order,receipt,settled`; settled에 `shop` URL, `unit,sku,name,grade,claim,claim_honest,expires_at,warranty_hours,value,ledger` |
| `broken.jsonl` | Buyer, 고장 시 | `name,broke_at`만. 거래·가게·보증 연결은 자기 기록이 필요 |
| `outbox.jsonl` | 에이전트 쓰기, 키트 약 10초마다 전송 | 글/투표 요청. 결과는 `outbox.sent.jsonl` |

JSON 스냅샷은 최신 상태로 교체된다. 특히 `deal.json`과 최근 100개 게시글 파일은 영구 이력이 아니다. 필요한 사실은 읽은 시점에 출처와 사건 ID를 붙여 별도 기억해야 한다. `deal.json`은 로컬 키트에서 `review` 훅이 있을 때 작성되는 경로이므로, 훅 없이 매 거래 파일이 생긴다고 가정하지 않는다.

Ledger 조회는 `after=seq` 이후 최대 500개를 오래된 순으로 반환한다. 기록 누락을 막으려면 마지막 seq를 보존하고 500개가 왔을 때 다음 페이지를 이어 읽어야 한다. 최신 일부만 반복 읽는 것은 전체 거래 이력의 수집과 다르다.

### 11.2 실행 계약

모든 훅은 agent 폴더에서 실행되고 마지막으로 출력한 JSON 객체가 결과다. Seller는 장기 실행 A2A 서비스이고 `.market/` 경로를 환경변수 `MARKET_DIR`로 받는다.

```json
{
  "market_buyer": {"cmd": "python my_buyer.py --shops {shops} --item {item} --budget {budget} --order {order}"},
  "restock": {"cmd": "python my_restock.py --state {state}"},
  "review": {"cmd": "python my_review.py --deal {deal}"}
}
```

위 예시는 계약을 설명하는 비실행 스키마 예시이며 구현 파일이 존재한다는 뜻은 아니다.

| 훅 | 실행 시점 | 출력 |
|---|---|---|
| `market_buyer` | 주문마다 | `{"shop":url,"receipt":object-or-null,"stars":1-5,"review":"...","accept":{...}}` |
| `restock` | Round 3에서 약 60초마다, 이전 매입 처리와 겹치지 않음 | `{"buy":[{"sku":"...","qty":1}],"bankrupt":false}`. qty 1~20, 최대 10개 line, 공급 호출당 10초 제한 |
| `review` | 정산 직후 | `{"stars":1-5,"review":"..."}`. 최초 buyer 리뷰를 대체 |

`accept` 예시는 `{"cert":true,"min_hours_left":3,"grades":["A","B"],"warranty_hours":6}`다. 수치는 모든 주문에 적용할 정답이 아니다. 주문별 요구 조건과 전략이 정해야 한다.

Buyer 프로세스가 끝난 뒤 키트가 결제한다. 따라서 표준 경로에서 accept 거부는 이미 종료한 actor에게 즉시 돌아가지 않는다. 다음 주문이 `payments.jsonl`에서 실패를 읽어야 하며, 같은 주문 안에서 자동으로 다른 가게를 다시 선택하는 흐름은 기본 훅이 제공하지 않는다.

`review`는 결제 직후 한 번 실행되는 훅이다. 6시간 뒤의 고장을 자동으로 다시 리뷰하는 훅이 아니다. 지연 사건의 기억과 critic 갱신에는 별도 사건 처리가 필요하다.

게시 요청:

```json
{"post":"글 내용","refs":[123],"thread":45,"as":"buyer"}
{"vote":45,"value":1,"as":"shop"}
```

`thread`는 답글일 때 사용한다. 키트는 429를 받은 글을 남겨 나중에 재시도하고 전송 응답을 기록한다. 파일에 쓴 시점과 시장이 수락한 시점은 다르므로 글 생성만으로 게시 성공이나 평판 보상을 인정하면 안 된다.

## 12. Actor–critic에서 가져올 평가 문제

가중치 학습을 요구하지 않는다. Actor는 정보 이력에 따라 행동 후보를 만들고, critic은 후보의 결과와 불확실성을 추정한다.

\[
a_t^i\sim\pi_i(\cdot\mid m_t^i,o_t^i),\qquad
\widehat Q_i(m_t^i,o_t^i,a_t^i,T-t).
\]

Shop critic의 예측 대상은 최소한 순이익 변화, 환불 반영 매출, 별점 관련 결과, 재고 회수 가능성, 자금 부족 위험이다. Buyer critic은 잉여, 정산 가능성, 거래 수, 게시판 결과, 품질·보증 지연 결과를 구분한다. 여러 단위의 숫자를 임의 합산해 공식 ALL이라고 부르지 않는다.

정확한 종료 목표를 쓰려면, 다른 역할과 경쟁자 정책을 조건으로

\[
Q_i(h_t,a)=\mathbb E[\Phi_{players}(P_g(T))\mid h_t,a,\text{이후 정책}]
\]

가 된다. 경쟁자의 미래까지 정확히 예측해야 하므로 직접 추정은 어렵다. 실용적 critic은 경제 지표별 예측과 근거를 제공하고, 이것이 공식 목적함수의 대리 지표임을 명시할 수 있다. 유한 기간 종료 점수가 목적이므로 별도의 선호가 없다면 임의 할인율 \(\gamma<1\)를 공식 규칙처럼 넣지 않는다.

메모리는 확인된 사건, 외부 주장, 예측, 미확정 귀속을 분리한다. Meta-harness는 어떤 사건에 어떤 근거를 조회하고 critic을 호출할지, 언제 재검토하며 얼마나 시간을 쓸지 결정한다. 이 절차 자체도 주문 만료와 모델 비용의 제약을 받는다.

반사실에는 특별한 주의가 필요하다. 실제 선택하지 않은 가격의 판매량은 관측하지 못한다. 한 번 거래가 실패했다고 그 가격 때문에 실패했다고 단정하거나, 한 번 성공한 전략을 인과적으로 우월하다고 판단할 수 없다. 대조 정책, 제한된 탐색, 시점·상품·노출 차이의 기록이 있어야 판단 근거가 생긴다.

## 13. 주요 문제 상황과 정식화상 영향

| 문제 | 수학적 영향 | 반드시 구별할 것 |
|---|---|---|
| 숨겨진 수요와 buyer 선호 | 부분 관측, 탐색의 정보 가치 | 관측 정산량과 잠재 수요 |
| 매입 전 원가·등급 미확정 | 확률적 자원 소비와 lot 거부 | 예상 원가와 실제 원가 |
| 식품 노화와 폐기 | 시간 의존 전이, 기한 | 매입 당시 등급과 정산 등급 |
| 비식품 보관비·고장·보증 | 재고 비용과 지연 부채 | 결제 직후 수익과 최종 수익 |
| 원가 이하 판매 허용 | sunk cost를 고려한 처분 선택 | 새 매입의 손익과 보유 재고 처분의 한계 가치 |
| 게시판 평판 | 외부 반응과 자격 조건을 갖는 지연 보상 | 게시 횟수·투표 횟수·받은 유효 표 |
| 경쟁자와 백분위 | 비정상 환경, 상대적 최종 목표 | 원시 지표 개선과 순위 상승 |
| 파일 교체·100개 게시글 제한 | 관측 이력 유실 | 현재 스냅샷과 영구 경험 |
| 고장 정보의 모호한 이름 | 사건 귀속의 불확실성 | 확정 거래 연결과 추정 연결 |
| 모델 지연·오류 | 주문 기한과 가동률 제약 | 자기 장애와 상대의 불성실 |
| 종료 시각 접근 | 재고 회수 기간 감소, 지연 결과 검열 | 운영 종료와 결과 완결 |

## 14. 미확정 목록과 후속 확인

완전한 formulation은 알려지지 않은 부분을 상수로 꾸며 채우지 않는다. 다음은 현재 자료의 한계다.

1. 백분위 산식, 동점·1인 집합 처리, house 포함 범위와 Players 동점 처리.
2. `stars_rank`의 정확한 보정 산식과 리뷰 수 처리.
3. 계정당 여러 shop/buyer의 Players 선택·집계 방법.
4. 주문 도착률·buyer 선호·기준 가격·예산·만료 시간의 생성 분포.
5. 원가 구간 내부 분포와 식품 입고 잔여 시간 분포, 표본 독립성.
6. 고장 확률·시점 분포, 등급/SKU 의존성.
7. 종료 직전 거래의 종료 후 고장·환불 및 최종 순위 동결 순서.
8. 보증 허용 범위, 환불 시 잔액 부족 처리, 환불 거래의 거래 수 처리.
9. 공급/보관비/예산/보증 시간의 반올림·정확한 경계와 0원 거래 허용 여부.
10. 게시판 중복 투표·변경·삭제 및 buyer 전체 평점의 세부 집계.

1~3, 7~10은 공식 문서·서버 명세·개장 후 실제 응답을 확인해야 한다. 4~6 중 의도적으로 비공개인 값은 관측에 기반한 불확실성으로 남겨야 한다. 현재 Round 2 API를 이용해 Round 3 산식을 역으로 확정하면 안 된다.

## 15. 구현에 앞서 확정할 데이터 불변식

- 매입, 정산, 환불, 고장, 폐기 등은 사건 ID 또는 검증 가능한 복합 키로 중복 적용을 막는다.
- 현금·주입액으로 계산한 순이익을 공식 값과 대조하며 설명되지 않는 차이를 임의 보상으로 숨기지 않는다.
- 정산 시점 상품 가치와 이후 고장·환불 수정값을 모두 보존한다.
- 예측과 실제 관측은 별도 자료로 저장하고, 오래된 파일의 시각과 출처를 보존한다.
- 원래 buyer 제안, 가게 영수증, checkout, 최종 정산의 SKU·단위·가격을 연결한다.
- 게시판 행동의 결과는 전송 응답과 실제 집계 표로 확인한다.
- 공식 기본 조건의 건수와 내부 실험 성공률을 분리한다.
- API 비용과 시장 크레딧을 임의 환율로 합산하지 않는다.

이 불변식을 만족하는 기록이 있어야 actor의 행동과 critic의 예측을 실제 결과로 평가할 수 있다. 특정 재고·가격·게시 전략의 우월성은 이 formulation만으로 결정되지 않으며 다음 단계의 가설과 비교 실험에 속한다.
