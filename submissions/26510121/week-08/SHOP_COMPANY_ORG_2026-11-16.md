# Shop 조직형 의사결정 구조

목표는 부서 수를 늘리는 게 아니라, 각 기능의 책임과 Main에 전달되는 계약을 고정하는 것이다. 모든 부서는 같은 `market_generation`, `rules_hash`, `inventory_generation`, `observed_at`을 붙인 짧은 데이터 봉투를 읽고 결과를 낸다. 낡거나 서로 다른 세대의 자료가 섞이면 거래를 승인하지 않고 기존 의무 이행과 안전한 기존 재고 판매만 계속한다.

## 조직도와 현 코드의 대응

| 운영통제실 | `control.py`, `recovery.py`, `transport.py`, `lifecycle.py` | 온라인 상태, 원장 최신성, 공급창, 중복 실행을 확인한다. 복구와 거래 실행을 분리하고, 같은 주문·공급을 중복 처리하지 않는다. |
| 연구·자동화실 | `research.py`, `capability.py`, `strategy_lab.py`, `evolution.py` | 현재 실험은 비활성화/Shadow로만 둔다. 충분한 표본의 홀드아웃 비교와 안전 기준을 통과한 변경만 제안한다. 자동 생성 산출물은 Main 권한을 갖지 않는다. |
| 사장실 / Main | `model.py`, `cycle.py`, `worker_bridge.py` | 후보 부서의 짧은 수치 패킷을 받아 최종 제약검사를 하고 거래를 실행한다. 보통 경로는 결정론적 코드이며 LLM은 없어도 동작해야 한다. |

## 의사결정 권한

1. 시장정보실은 기회를 보고하고 주문할 수 없다.
2. 회계실은 Book/현금/준비금 경계를 제공한다. 준비금이나 만료 대사는 조달실 점수로 덮을 수 없다.
3. 품질실은 승인된 서비스 가능 조건과 금액 손실률을 제공한다. 단순 평균 별점으로 매입을 승인하지 않는다.
4. 조달실은 기대 순 Book 변화가 **매입 0개**보다 양수인 후보만 낸다. 보수 시나리오가 손실이면 기본 선택은 대기다. 이미 검증된 SKU는 실현 이익 범위 안에서만 증량한다.
5. 판매실은 보유가치(원가 장부가 - 향후 보관료 - 만료/위험)와 판매 후 기대 Book 변화를 비교한다. 식품의 기한 임박 처분은 폐기 대안과 비교하며, 공산품은 단순히 원가 회수만으로 환불 위험을 정당화하지 않는다.
6. 점수전략실은 실제 코호트 백분위와 인접 문턱을 제공한다. 현금/품질 안전선을 통과한 선택지 안에서만 ALL 개선을 최적화한다.
7. Main은 모든 결과가 최신이며 동일한 규칙/재고 세대인지 확인하고, 충돌 시 더 보수적인 승인을 따른다. 즉시 실행시간 제한 때문에 심층 분석을 기다리지 않고 만료된 패킷은 거부한다.
8. 리스크감사실은 6시간 이후 공산품 품질과 실제 환불을 재집계하고, 식품은 계약별 만료 뒤 폐기를 반영한다. 정책은 고정 창의 성숙 결과로만 갱신한다.

## 승인 봉투

부서간 계약은 자유형 문장 대신 JSON으로 고정한다.

```json
{
  "department": "procurement",
  "market_generation": "...",
  "rules_hash": "...",
  "observed_at": 0,
  "expires_at": 0,
  "sku": "...",
  "units": 1,
  "evidence": {"mature_sales": 0, "mature_refunds": 0, "net_book_delta": 0},
  "baseline_wait_net_book_delta": 0,
  "proposed_net_book_delta": 0,
  "downside_net_book_delta": 0,
  "quality_hold": false,
  "decision": "wait"
}
```

필수 불변조건: `market_generation`/규칙 해시가 맞지 않으면 거절, 만료된 근거는 거절, 값 누락은 승인으로 간주하지 않음, 준비금/현금 제약 위반 거절, `proposed_net_book_delta <= baseline_wait_net_book_delta`면 매입 거절. 모든 외부 행동은 Main 한 곳에서만 실행한다.

## 전환 순서

현재 코드는 조직표에 적힌 기능을 여러 모듈에 나눠 구현하지만, 아직 위 봉투 계약과 부서 권한을 강제하지 않는다. 따라서 바로 모든 코드를 이사하지 않고, 먼저 관측 패킷과 대기 기준선을 기존 모듈에 붙인 뒤 Shadow 결과를 원장과 대조한다. 그 뒤 Main 승인 게이트, 성숙 성과 검증, 마지막으로 파일별 책임 정리를 진행한다. 실행 전 현재 남아 있는 임시 `v29` 변경은 이 구조와 일치하지 않으므로 제외한다.

이 구조도 순위 하락이 절대 없다고 보장하지 않는다. 보장 가능한 범위는 낡은 자료, 음수 검증손익, 준비금 위반, 미성숙 고장률만으로 공격적 매입을 승인하지 않는 것이다.
