# 구매자 구현과 공식 기본 거래 테스트

2026-10-17, 현재 공식 `scripts/trade_test_week06.py`의 **21/21 실행을 통과**했다.
`agent.json`의 판매자·구매자 명령을 그대로 사용했고 원본 테스트 코드는 변경하지 않았다.
최종 공식 결과는 `test-report.json`, 원본 통신 로그는 `logs/trade-test.log`, 전체 콘솔은
`logs/trade-runs/20261017-043240-026/console.log`에 있다.

## 구매자의 구조

- `buyer.py`: 인자·실행 로그·240초 자체 기한과 종료 처리.
- `negotiation/a2a_client.py`: 카드와 skill 확인, JSONRPC 1.0 선택, 모든 요청의 버전 헤더, taskId, 영수증 검증.
- `negotiation/buying.py`: 관찰 → 모델 결정 → 검증된 제안/취소 → 다음 응답의 협상 루프.
- `negotiation/state.py`: task별 마지막 제안·요약·최근 4턴.
- 공통 `harness.py`와 `contracts.py`: 같은 API worker에서 구매자 역할의 JSON 결정을 받고 예산·행동·가격·품목을 검사.

구매자는 상대의 비공개 최저가를 받지 않는다. 제안 가격과 중단 여부는 모델이 선택한다.
코드는 예산을 넘는 결정을 전송하지 않으며, 중복 구매를 피하기 위해 완료 후 종료한다.
가격 제안의 응답이 유실되면 GetTask로 확인하고, 결과가 불확실하면 재전송하지 않는다.
이 유실 경로는 오프라인 모의 시험으로 검증했고, 실제 네트워크 장애를 유발한 것은 아니다.

최종 책장 판매자 시나리오에서는 고정 구매자의 8회 한도까지 260을 반복했고 거래 없이
INPUT_REQUIRED 상태로 끝났다. 최저가 방어 조건은 통과했지만 정체된 협상을 모델이
항상 종료하는 것은 아니라는 한계가 있다. 구매자에는 기한·교환 횟수 제한과 취소 동작을 둔다.

원본 파일을 편집해 성공처럼 바꾸지 않았다. 상세 실패 줄 인용과 해석은 `REPORT.md`에 있다.

구매자와 판매자의 실패 관찰로 진행한 모델 실험은 각각 3회 모두 정책 기대를 충족했지만,
실제 거래와 구분해 `logs/buyer/probe-*`, `logs/seller/probe-*`에 보관했다.
프롬프트와 필드 순서를 함께 수정했으므로 필드 순서 하나의 효과만 입증한 것으로 해석하지 않는다.

## 실행과 남은 과제

Windows에서는 공식 테스트의 shell 프로세스 종료 뒤 실제 Python 판매자가 남아 있었다.
각 실행에서 기록한 포트·명령과 이 제출 폴더의 가상환경 부모 실행 경로를 확인한 뒤
해당 네 프로세스만 종료했다. 정리 후 테스트 포트의 남은 listener는 0개였다.
정리 원본 출력은 최종 실행 폴더의 `cleanup-*.log`에 보관했다. 공식 테스트 소스는 수정하지 않았다.

가상환경을 활성화해 `python`이 실행 가능한 상태에서 제출 폴더를 현재 디렉터리로 두고 실행한다.

```powershell
python ../../../scripts/trade_test_week06.py .
python ../../../scripts/check_week06.py .
```

네트워크 없는 검사는 39개, 현재 공식 제출 구조 검사도 통과했다. 최종 구매자 실행은
각각 약 2.9~8.7초였고 여섯 실행 모두 구매 또는 정상 중단 결과를 출력했다.
실험·통합 테스트의 실패도 각각 커밋했다.
기본 거래 테스트 통과와 별개로 **필수 도전 1·2는 아직 미완료**다. 다음은 대규모 카탈로그,
그다음은 여러 가게와 장보기 목록이다. 최종 보고서의 도전 로그 인용은 해당 실행 뒤 보완한다.
