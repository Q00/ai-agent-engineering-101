# 단계 3 — 행동 도구와 가격 한도

## 구현과 순서

각 도구를 구현·검증한 뒤 별도 커밋했다. stage 2의 get_negotiation과 함께 총 5개 도구를 제공한다.

| 도구 | 검사 | 성공한 뒤 상태 |
|---|---|---|
| propose | 협상 접근, open, 자신의 차례, 0 이상의 정수, 자신의 토큰 한도 | 제안 기록·활성 제안 교체·상대 차례 |
| accept_proposal | 협상 접근, open, 자신의 차례, 상대의 활성 제안, 그 가격에 대한 자신의 토큰 한도 | 가격을 기록하고 deal 종료, turn=null |
| reject_proposal | 협상 접근, open, 자신의 차례, 상대의 활성 제안 | 거절 기록·활성 제안 제거·상대 차례 |
| refuse | 협상 접근, open, 자신의 차례 | no_deal 종료, turn=null |

role과 수락 가격은 에이전트 인자로 받지 않는다. 수락 가격은 서버의 활성 제안에서 가져온다. 거절 기록에는 가격이 없고, 역제안이 필요하면 다음 자신의 차례에 propose를 호출한다. 거절된 제안은 기록에는 남아 있지만 더 이상 수락할 수 없다.

## 한도 검사 원리

buyer는 token limit보다 높은 가격, seller는 token limit보다 낮은 가격을 거부한다. 같은 가격은 허용한다. server / server_inject의 토큰에만 limit이 있으므로 prompt / prompt_inject에서는 가격 한도를 서버가 강제하지 않는다. 신원, 협상 범위, 차례, 종료, 정수 검사 자체는 네 조건에 동일하다.

서버 조건의 제안은 제안자 한도를 통과하고, 수락은 수락자 한도를 통과해야 한다. 두 검사를 거쳐 성립한 거래는 양쪽 한도 안에 있다. 가격 검사 함수에만 의존하고 수락에서 검사를 빼먹으면 상대가 내 예산을 넘는 가격을 제안했을 때 위반 거래가 생기므로 propose와 accept_proposal 양쪽에서 검사한다.

예를 들어 reserve=40, budget=70이라면 buyer의 50 제안 뒤 seller의 71 제안은 seller 한도 안이어서 허용된다. buyer가 71을 수락하면 자신의 예산을 넘으므로 거부된다. buyer 차례와 활성 71 제안은 유지되며 buyer는 같은 차례에 70을 제안할 수 있다. seller가 70을 수락하면 두 한도 안의 거래가 된다.

모든 검사는 상태 변경보다 먼저 수행하고, 검사와 변경 전체를 동일한 RLock으로 감싼다. 실패한 행동은 moves·활성 제안·차례·종료 상태를 바꾸지 않는다. 동시 buyer 호출 두 개 중 하나가 성공하면 차례가 바뀌어 나머지는 거부된다.

## 검증

저장소 루트에서 실행한다. 모델 요청은 없다.

```powershell
& ./submissions/26510121/week-05/.venv/Scripts/python.exe -X utf8 -m unittest discover -s submissions/26510121/week-05/tests -p 'test_stage*.py' -v
```

stage 2의 14개와 stage 3의 18개, 총 32개 검사 통과. 네 조건의 정상 거래, 양쪽 제안/수락 한도 위반, 거부 후 같은 차례의 유효 행동, 한도 경계와 0 가격, 거래 불가능 사례, 역제안 가격 적용, 거절된 제안 무효화, 제안 없는 수락/거절, 차례/협상 위반, 잘못된 가격 자료형, 종료 후 행동, 동시 호출을 검사했다.

첫 통합 실행에서 관리자 인증 검사 한 건에 WinError 10054 연결 끊김이 발생했다. 나머지 행동 검사는 통과했다. 서버 코드 변경 없이 재실행한 전체 32개 검사는 통과했다. 원인은 확정하지 않았으며 실패와 성공 원본을 모두 checks/stage3-*.txt에 보존했다. 에이전트 실행 결과로 세지 않는다.
