# Week 02 — Harness A/B 실험 보고서

## 1. 변형 정의와 실험 조건

두 하네스는 동일한 태스크(`app.log`에서 ERROR가 가장 많은 시간을 `HH:00`으로 답하기), 성공 기준(`14:00` 포함), 모델(OpenRouter `nvidia/nemotron-3.5-lightning:free`), 공용 모델 래퍼와 읽기 전용 도구 `read_file`, `count_pattern`을 사용했다. 다섯 요소 중 **도구 세분성**과 **사람 개입점**은 동일하며, 쓰기 도구가 없어 개입 대상도 없다. **컨텍스트 관리**는 ReAct가 한 대화의 전체 이력을 매 반복에 사용하는 반면 Plan은 별도 planner가 계획을 만들고 executor가 계획과 단계별 누적 이력을 사용한다. **종료 조건**은 ReAct가 도구 호출 없는 최종 응답 또는 `max_steps=8`에서 끝나고, Plan은 계획 실행 후 최종 응답을 생성하되 전체 `max_steps=16`과 단계당 도구 라운드 3회를 적용한다. **오류 복구**는 ReAct가 도구 오류를 Observation으로 돌려 다음 반복에서 복구하고, Plan은 `OFF_PLAN` 시 최대 1회만 재계획한다. 토큰은 API usage의 입력+출력 토큰 합, iterations는 모델 호출 수, interventions는 사람 승인/거절 횟수다. 각 실행의 프롬프트·도구·상한은 `logs/`에 있으며, 실행 명령은 `./.venv/bin/python run_ab.py --runs 3`이다.

## 3. 해석

두 하네스는 유효 실행 3회 모두 성공했고 사람 개입도 0회로 동률이었지만, 이 태스크에서는 ReAct가 평균 토큰과 반복 횟수 및 그 안정성에서 우세했다. ReAct 로그는 세 번 모두 `read_file` 관찰 뒤 두 번째 모델 호출에서 `14:00`을 결정해 2회 반복으로 끝난 반면, Plan 로그는 답을 얻기 전에 계획을 생성하고 각 단계를 누적 대화 이력으로 순차 실행한 뒤 최종 답변을 별도로 생성하여 10~13회 호출을 사용했다. 특히 run 7과 8은 단계당 도구 호출 상한을 넘어 `OFF_PLAN`이 발생하고 재계획 1회가 추가되어, Plan의 평균 토큰이 36,995.67로 ReAct의 4,241.67보다 높고 토큰 분산과 반복 분산도 더 커졌다. 따라서 파일을 한 번 읽은 뒤 바로 집계할 수 있었던 이번 단순 태스크에서는 Plan의 선행 계획·단계 실행·재계획 비용이 성공률 이점으로 이어지지 않아, 성공률과 개입은 동률이지만 토큰 효율·호출 효율·일관성에서는 ReAct가 더 적합했다.

## 4. 리뷰 요청 이후의 재실행 이력

최초 제출 커밋 `820310c`에는 `TASK.md`, 실험 결과와 로그, 이 보고서가 함께 포함되어 있다. 따라서 최초 실험의 성공 기준이 실행 전에 확정되어 있었다는 사실을 Git 이력만으로는 입증할 수 없다. 이 한계를 사후에 커밋 날짜를 바꾸거나 기존 이력을 재작성하는 방식으로 보완하지 않았다. 최초 제출과 남아 있던 과거 실행 자료는 삭제하거나 내용을 수정하지 않고 보존했으며, 과거 자료는 `48fdecb`에서 별도로 추가했다.

리뷰 이후에는 기존 태스크와 성공 기준 `expected: 14:00` 및 재실행 절차를 `cf415e1`에서 실제 재실행 전에 먼저 커밋했다. 이후 run 10~15를 순서대로 수행하고 성공·실패와 관계없이 각 시도를 별도 커밋했다.

| run | harness | 최종 상태 | 분류 | 커밋 |
|---:|---|:---:|---|---|
| 10 | ReAct | X | `APIConnectionError` 연결 실패 | `d94085c` |
| 11 | ReAct | X | `APIConnectionError` 연결 실패 | `89d0630` |
| 12 | ReAct | X | HTTP 401 인증 실패 | `1d726a9` |
| 13 | Plan-then-Execute | X | HTTP 401 인증 실패 | `6e18cee` |
| 14 | Plan-then-Execute | X | planner가 JSON list 대신 도구 호출 형태의 문자열을 반환하여 plan parse 실패 | `13050dd` |
| 15 | Plan-then-Execute | X | 실행 도중 `APITimeoutError` 발생 | `892a660` |

run 12와 13 이후 진단에서 `OPENAI_API_KEY`에 OpenRouter 키가 아닌 다른 credential이 설정되어 있었음을 확인했다. 올바른 OpenRouter API key로 교체한 뒤 같은 모델 `nvidia/nemotron-3.5-lightning:free`의 `/chat/completions` 호출이 정상 응답했으며, run 14와 15는 인증이 정상화된 이후의 실제 모델 실행이다. 키 값은 코드, 로그, 보고서에 기록하지 않았다.

run 14는 API나 네트워크 실패가 아니라 planner 출력 형식 위반으로 종료된 실제 하네스 실패다. run 15에서는 중간 응답에 `Answer: 14:00`이 포함됐지만 실행이 끝나기 전에 timeout이 발생하여 최종 답변이 비어 있었고 judge 결과도 X였다. 따라서 성공으로 재분류하지 않았다. 모든 실패는 당시 결과 그대로 남겼으며 재실행으로 교체하거나 삭제하지 않았다.

재실행 여섯 건에는 정상 완료되어 비교 지표로 사용할 수 있는 실행이 없다. 다섯 건은 연결·인증·timeout 문제이고, run 14는 모델 출력 형식 실패다. 따라서 이 재실행 결과만으로 ReAct와 Plan-then-Execute의 성능을 직접 비교하거나 최초 제출의 수치 분석을 재검증할 수 없다. 위 최초 제출 분석은 원래 결과에 대한 분석으로 유지하되, 리뷰 이후 재실행은 절차와 실패 이력을 입증하는 자료로 구분한다.
