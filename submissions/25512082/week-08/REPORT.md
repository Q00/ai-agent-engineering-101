## 1. 부품별 설계


### 1.1 모델

이 에이전트의 모델은 Codex CLI 0.163.0의 `gpt-6.1-sol`(reasoning effort low)이다. Week 07부터 10월 27일 Round 2 연습까지는 이 모델이 Seller와 Buyer의 흥정을 직접 결정했다. 그 과정에서 모델 호출 실패와 가격 판단 문제가 여러 차례 확인되어, Round 3에서는 모델을 거래 경로에서 빼고 실패해도 거래가 멈추지 않는 재입고 제안 자리로 옮겼다.

**호출 방식 (`harness.py`).** 결정이 필요할 때마다 `codex exec --ephemeral --sandbox read-only --model gpt-6.1-sol -c model_reasoning_effort="low" --output-schema ...`를 한 번 실행한다. 모델이 낸 JSON은 로컬에서 스키마, reserve, 예산 기준으로 다시 검증한다. 제한 시간은 120초이고, 실패하면 오류 종류(인증, 모델 없음, 네트워크, 시간 초과, 분류 불가 등)를 붙여 `HarnessError`를 낸다. Codex는 ChatGPT 계정 로그인으로 사용했으며 API 키는 쓰지 않았다.

**실패 원인.**
- Week 07 Market Test의 14건은 모델 호출 도구인 Codex CLI의 계정 **사용량 한도 소진**이 원인이었다. 코드 결함이 아니었으므로, 사용량을 확보한 뒤 같은 코드로 25개를 모두 통과했다.
- Round 2 연습의 49건 중 48건은 `UNKNOWN_ERROR: Codex failed for an unclassified reason (exit status 1)`, 1건은 `NETWORK_ERROR: Codex could not reach its service`였다. `UNKNOWN_ERROR`는 Codex의 오류 메시지가 하네스가 아는 유형 어디에도 해당하지 않을 때 붙는다. 하네스는 오류 원문을 저장하지 않도록 만들었기 때문에, 48건의 정확한 원인은 기록에 남아 있지 않다. 같은 날 낮에 사용량 한도에 걸린 적은 있지만, 이 48건이 같은 원인인지는 확인할 수 없다.
- Seller 기록(`logs/seller-trades.jsonl`)에는 끝난 거래와 "규칙이 결정했다"는 사실만 남고 오류 종류는 남지 않아, Seller 쪽 실패 원인은 알 수 없다.

**실패에 대응해 바꾼 설계.**
1. Round 2 연습 직전(20:44~20:45)에 모델 호출이 실패하면 규칙이 대신 결정하도록 했다(커밋 `f7c8e02` Buyer, `c4e9f6d` Seller). 그 덕분에 49건이 실패하는 동안에도 Buyer는 가게에 1점 대신 "No rating"을 남겼고, Seller는 규칙으로 3건을 성사시켰다.
2. 첫 호가는 Week 07 Challenge 1에서 시장 예산 기반 규칙으로 바꿨고, Round 3에서는 등급별 목표가와 원가 하한 규칙으로 정했다.
3. Round 3에서는 `seller.py`·`buyer.py`에서 `harness` 호출을 빼고, 거래 판단을 모두 규칙과 원장·순위표 기반 감독에 맡겼다.
4. 대신 모델은 실패해도 거래가 멈추지 않는 **재입고 제안** 자리에 두었다. `restock_model_advisor.py`는 같은 하네스로 모델을 불러, 규칙이 거른 후보 SKU 안에서 순서와 이유만 정하게 한다(스키마 `schemas/restock_advice.json`). 규칙이 수량과 상한을 다시 적용하고(`enforce`), 모델이 실패하면 규칙 순위로 돌아간다. 코드와 테스트 4개를 작성했으나, **Round 3에서 실제 모델 호출과 비교 평가(shadow mode)는 진행하지 않았다.** 실제 운영에서는 운영 감독이 원장 통계로 SKU를 골랐다.

**개발 도구.** 11월 13일 이후 운영 스크립트 작성과 보고서 정리에는 Claude Code(Claude Opus 5.5)를 사용했다. 이 모델은 거래 판단에는 호출하지 않았다.

#### 규칙 기반 정책을 선택한 이유

Round 3에서는 Seller의 가격 결정과 재입고, Buyer의 거래 선택과 결제 검증을 2주 동안 반복해야 했다. 이에 따라 **거래 조건을 일관되게 적용하고 판단 근거를 확인할 수 있는 규칙 기반 정책**을 선택했다. 주요 이유는 다음과 같다.

1. **거래 조건 준수:** 가격 하한, 매입 한도, 상품 등급, 유통기한 등을 코드로 검증하여 승인된 조건 안에서만 거래하도록 했다.
2. **판단의 일관성과 재현성:** 같은 조건에서는 같은 기준으로 판단하도록 설계하여, 판단 로직을 테스트로 재현하고 거래 결과와 오류 원인을 분석하기 쉽게 했다.
3. **모델 호출 실패의 영향 제거:** 모델 호출 가능 여부는 계정 사용량과 외부 서비스 상태에 달려 있어, 모델을 흥정에 직접 쓴 기간에는 호출이 실패하면 그 거래가 바로 실패하거나 규칙으로 대체됐다. Week 07 Market Test에서는 Codex 사용량 한도로 25개 중 14개가 실패했고, Round 2 연습에서는 Buyer의 모델 호출이 주문 55건 중 49건 실패했다. 공식 Week 08 강의 자료(EP 5)에도 다른 참가자의 Buyer가 모델 API 한도 초과(429)로 1점 평가를 6,837회 남긴 사례가 있어, 이 위험이 본 에이전트만의 문제가 아님을 보여준다.

이후 11월 2일 오프라인 시뮬레이션에서 규칙 기반 운영 정책들을 비교해 운영 정책을 골랐다(`experiments/results/FINAL_OPERATION_READINESS.md`).

다만 이 시뮬레이션에서는 규칙 기반 정책들만 비교했으며, LLM 기반 정책과의 직접적인 성능 비교는 수행하지 않았다. 따라서 규칙 기반 정책이 LLM 기반 정책보다 성능이 우수하다고 단정할 수는 없다. 본 에이전트는 성능 비교보다 거래 조건의 일관성, 모델 오류가 나도 거래를 이어 갈 수 있는 구조, 운영 과정의 안정성을 우선하여 규칙 기반 정책을 선택했다.

## 2. 아키텍처와 키트 기본형과의 차이

그림: `architecture.tex` → `architecture.pdf`.

| 항목 | 키트 기본형 (`starter --round3`, 기본 restock) | 이 에이전트 |
|---|---|---|
| 모델 위치 | 하네스(모델)가 흥정의 매 수를 정한다 | 런타임 모델 없음. 사람이 운영 범위를 승인하고, 그 안에서 규칙 감독이 판단한다 |
| 호가 | 원가 이상, 품질·보증 정보 없음 | 등급별 목표 호가(A 0.78, B 0.72, C 0.65 × 정가), (원가+보관비)×1.05 하한, 영수증에 정직한 등급 주장. 실험 기간에는 A·B를 시장 중앙가로 |
| 재입고 | 재고가 적으면 무작위 SKU | 공식 원장 검증(판매율·이익·원가 미만 비율) → 단기 승인 파일 → `safe_restock` 재검사 → 1회 소진 |
| Buyer | 하네스가 가게와 값을 정한다 | 병렬 호가 → 예상 Saved 증가량에 따른 순위 결정 → 결제 전 검사. 100주문 단위 감독과 Saved 하락 위험 감시 기능 추가 |
| 안전 | 키트·시장 프로토콜의 결제 및 정산 검사 외 별도의 운영 성과 기반 중단 감시는 없음 | 손실·환불·파손·만료·중복 정산·평판 하락·정산 정체를 감시해 신규 매입·주문을 중단한다. 승인 없는 자동 재시작은 하지 않는다 |
| 운영 | `join` 한 번 | flock 단일 인스턴스, 가게와 buyer 키트 분리, 시각 기반 종료 감시, 마감 board 기록 |

**실행 흐름:** 시장과 Seller·Buyer 키트가 거래 정보를 주고받는다. 각 키트는 규칙 기반 Seller·Buyer 코드와 상태 파일을 사용한다. 운영 감독은 원장과 리더보드를 확인해 매입 승인 여부 또는 다음 주문 실행 여부를 결정한다. 별도 감시자는 중단 조건을 확인하며, 운영 범위는 사람이 승인한다.

**주요 차이:** 기본 키트에 가격·재입고 판단 규칙과 운영 중단 조건을 추가했다. 돈이 움직이는 모든 지점(공급 매입, 결제)은 규칙 게이트를 지나고, 게이트의 범위는 사람이 승인한다. 운영 감독은 공식 원장 및 리더보드의 결과를 확인한 뒤 다음 매입·주문 실행 여부를 결정한다.

### 3.8 호가 실험 (ops14 대 ops15)

11월 16일 17:06~17일 05:08 동안 A·B등급 시작 호가를 같은 SKU·등급의 최근 3시간 시장 중앙가로 정했다(원가 × 1.05가 더 크면 그 값). 원복 조건(평균 이익 < 800, 결제 리뷰 평균 < 4.3, 6시간 뒤 시간당 정산 < 1.82)에는 걸리지 않았고 12시간 만료로 끝났다(`logs/operations/seller/price_exp.log`, 마지막 기록: 실험 판매 52건, 평균 이익 1,306, 리뷰 53건 평균 4.58).

ops14·ops15 `end` 기록의 실현 거래(`realized`)를 다시 집계했다.

- **집계 차이:** `price_exp.log`의 실험 판매는 52건이지만 위 표에서 해당 구간의 전체 등급 판매는 53건이다. 집계 시점 또는 포함 범위 차이로 추정되며, 거래별 대조는 수행하지 않았다.
- **관찰 결과:** 실험 중 A·B등급은 다른 구간보다 빨리 판매됐지만 거래당 평균 이익은 실험 후 구간의 약 절반이었다. 호가 방식을 바꾸지 않은 C등급의 실험 중 평균 이익은 2,707이었다.

### 3.9 주요 성과와 한계

**주요 성과**
- 규칙 게이트: 가게 환불·파손·원가 미만 판매·중복 정산 0, 정직 주장 215/215, buyer 환불 없는 파손은 정책 변경 후 0.

- 굿즈 A등급 + 보증 6시간 정책: 정책 변경 뒤 파손 29건이 모두 보증 환불로 처리됐다.
- 결과: 10주차 기준 학생 45위(student_pct 0.022) → 최종 33위(student_pct 0.289).

**한계 및 실패 사례**
- 재고 부족: 가게 거절의 약 85%가 `no_verified_inventory`였다. 승인된 매입 범위가 제한적이어서 일부 수요에 대응하지 못했다.

- 가게 평판: `stars_rank`는 서로 다른 평가 계정 수의 영향을 받는다. ops13의 정산 58건은 구매 계정 16개에서 발생했다.
- Saved 감시: 부동소수점 비교 결함이 있었고, 감시 뒤에도 Saved가 내려갔다(3.7).
- 판매 전용 구간 감시가 재등록 직후의 일시적 `stars_rank 3.0` 판독 1회로 STOP했다(19:10). 연속 2회 조건으로 고쳤다.
- ops16은 원장 백필이 계획된 종료 시각보다 길어 한 번도 매입하지 못했다.

## 5. 한계

- 모델 기반 재입고 보조 기능은 구현했으나 실제 거래에서는 사용하지 않았다(1.1절). Seller는 보증을 제공하지 않는다.
- **Buyer 정산률 기준 불일치:** `buyer_ops4~7.py`의 500주문 단위 검사 메시지와 설명에는 `70%`라고 적혀 있지만, 실제 코드의 `MIN_RATE` 값은 `0.65`이므로 **적용된 기준은 65%**다. 11월 15~16일의 검사 6회에서 정산률이 72.4~82.0%여서 이 차이로 판단 결과가 바뀌지는 않았다.
- **Seller 운영 기준:** `ops15.py`는 3시간 판매율 70% 이상, 실현 이익 중앙값 1,000 이상, 원가 미만 비율 15% 이하, 최근 3시간 시장 정산 20건 이상, 표본 15개 이상을 조건으로 사용한다. STOP 조건에는 `stars_rank` 3.93 미만과 2시간 동안 정산이 없는 상황 등이 포함된다. 메시지와 코드 상수는 일치한다.
- **Saved 감시 오류:** 부동소수점 비교 문제를 수정했으나, 중단 후에도 Saved가 하락했다. 원인과 수정 기록은 3.7절에 정리했다. 수정 전 코드는 `saved_guard7.py.pre-roundfix`로 보관했다.
- **로그와 실험의 한계:** 키트 로그에는 날짜 없이 시각(`HH:MM:SS`)만 기록되어 운영 로그 및 원장과 대조했다. 3.8절의 가격 실험은 조건을 통제한 실험이 아니다.
