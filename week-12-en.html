R3

Wallets and the faucet

On its first run the kit makes two Maroo testnet wallets. shop_wallet.key signs as the shop, and buyer_wallet.key pays other agents. Only the buyer sends transactions, so the buyer wallet is the one that needs funds. Round 3 keys were Ed25519 and do not work in Round 4.

The first line of the run log prints the buyer wallet's address. Claim tOKRW for it at faucet.maroo.io: 5,000 per claim, until the wallet holds 10,000, behind a captcha a person has to solve. 1,000 credits = 1 tOKRW. A buyer that is short of funds does not pay, and the kit logs why.

The wallet files are plain hex and testnet only: never put a key that holds real assets in them.

logs/agent-kit.log
[maroo] shop wallet 0x..., buyer wallet 0x.... Fund the buyer wallet at https://faucet.maroo.io

How the mini app is built

The agent always runs on your computer; a phone only shows the app. The kit's --app 8800 serves the mini app, and the agent's ReAct loop and A2A endpoint run in the same process (FIG. 01). M2

miniapp.js

app/ is your front end; change it freely. Keep one line, <script src="/miniapp.js"></script>, which creates window.miniapp on the page.

FunctionWhat it does
miniapp.chat(text, user)Sends the agent a message and resolves to its answer
miniapp.offer(name, description, fn)Gives the agent a tool app_<name>; fn(args) runs in the page
miniapp.onState(fn)The agent's name, the chat, MeshKit calls waiting for consent, recent moves and tools
miniapp.consent(id, approved)Approves or refuses a MeshKit call

Tools the page offers are the only tools the agent gets without forging them. If the app offers the user's cart or location, the agent can use it to choose goods on the market. To keep the app installable on a phone, keep these lines in the starter page's <head>: viewport (with viewport-fit=cover), manifest, theme-color and apple-touch-icon.

app/index.html
<script src="/miniapp.js"></script>
<script>
miniapp.offer("my_budget", "The user's budget for today, in credits",
              () => ({credits: 30000}));
miniapp.onState(s => render(s));
document.querySelector("form").onsubmit = async e => {
  e.preventDefault();
  const answer = await miniapp.chat(input.value, "me");
  show(answer);
};
</script>

This is flow A in FIG. 02. Say "pick something within today's budget" in the app, and the agent calls app_my_budget when it needs it; the function runs inside the phone's page and returns the result.

Once the app is reachable from outside your computer, it asks for an access code. The kit prints each link with the code (?k=...) in the terminal only, never in the logs, so the agent's tools cannot read it. The browser keeps the code in a cookie. The code lives in .kit/app.key; delete it and run again to change it. Anyone with the link can talk to your agent and approve its MeshKit calls, so keep the link to yourself.

DeviceInstall
AndroidOpen the https:// link in Chrome, then Install app from the menu. Chrome installs only from an https:// link
iPhone, SafariOpen the https:// link in Safari, then Share, Add to Home Screen. If it asks for a code, type the part after k=
iPhone, as an appOpen scripts/round4/ios/MiniApp.xcodeproj in Xcode and Run. On a real device, set your Team (a free Apple ID works) and your own bundle identifier in Signing

If macOS asks whether Python may accept incoming connections, allow it. School and cafe Wi-Fi often blocks devices from reaching each other; use --app-tunnel there.

M4

MeshKit

This is how your agent uses features of a mini app someone else built (FIG. 02, B). List that app in meshkit.json and each feature it offers becomes a tool whose name starts with mesh_. When the agent calls one, a sheet asking permission appears on your phone, and the other app runs only after a person taps Allow. The other app returns the result with a receipt it signed, and the kit passes it to the agent only if the signature checks out. The tools the agent builds cannot reach the app's address, so only a person can press Allow.

Try it first with DailyMart, the example app in the MeshKit repository. It offers one feature: ordering household essentials (grocery.purchase_essentials).

To connect your app to someone else's, make your own key instead of the demo one. seed_hex is 32 random bytes, and the other app has to register the public key derived from it before it accepts your calls. The example app takes the public key to trust from the environment variable MESHKIT_CALLER_PUBKEY. meshkit.json holds the key, and .gitignore keeps it out of git.

TERMINAL
python -c "import secrets; print(secrets.token_hex(32))"            # seed_hex
python -c "import base64,sys; from meshkit import ed25519; \
print(base64.b64encode(ed25519.public_key_raw(ed25519.private_key_from_seed(bytes.fromhex(sys.argv[1])))).decode())" <seed_hex>

F2

The first tools the agent forges

At the start of every run the kit hands the agent the market's directory card. All the agent has is forge_tool, read_tool, reply, write_note and sleep, so before it can take an order or restock it has to build a tool. A tool is made of files under tools/<name>/.

FileContent
permission.ymlname, description, permission (network, write, identity, wallet, pay_limit, timeout, handles), version
logic.pydef run(args, kit) -> JSON
test.pydef test(run, kit)
forge.jsonThe kit's record: version, time, hashes of the three files

Below is part of a shop handler that the kit's tests forge in the agent's place. Given the SKUs a customer wants, it looks for stock, buys one unit from the wholesale market if there is none, and returns a checkout_jwt signed by the shop wallet. It never sees the wallet key; it only calls kit.sign_jwt.

tools/shop_handler/logic.py
def run(args, kit):
    data = args.get("data") or {}
    acc = data.get("acceptable") if isinstance(data, dict) else None
    if not acc:
        return {"reply": "어떤 상품을 찾으세요?", "state": "input_required"}
    h = {"authorization": "Bearer " + kit.token("shop")}
    inv = httpx.get(kit.market + "/api/inventory", headers=h, timeout=20).json()
    unit = next((u for u in inv["units"] if u["sku"] in acc and u["grade"] != "expired"), None)
    ...
    return {"reply": f"{price} 크레딧에 드릴게요.",
            "data": {"checkout_jwt": kit.sign_jwt(co, "shop"), "price": price}, "state": "completed"}

The kit runs test.py in its own process and adds the tool only when it passes. Forging the same name again makes the next version, and the old one moves to tools/.deprecated/. A tool whose hashes do not match does not load, so a tool edited by hand cannot be used. What the agent built and how it used it stays in logs/forge.jsonl and logs/react.jsonl; agent_kit.py tools --dir ... lists the tools it has.
