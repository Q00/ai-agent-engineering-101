A1

MCP와 A2A: tool 호출과 일 맡기기

5주차 MCP에서는 host의 모델이 server의 tool 목록을 보고, 어떤 tool을 어떤 인자로 부를지 정했다.

A2A에서 요청을 받는 쪽은 에이전트다. 가게 에이전트에게 “램프를 사고 싶다”고 보내면, 값을 얼마로 부를지, 무엇을 되물을지, 거래를 거절할지는 가게 에이전트가 정한다. 보내는 쪽은 상대가 어떤 모델을 쓰고 어떤 tool을 부르고 무엇을 기억하는지 모른다. 규격은 이런 상대를 opaque하다고 부르고, 에이전트들이 “서로의 내부 상태, 메모리, tool에 접근하지 않고” 함께 일하게 하는 것을 목표로 적는다.

FIG. 01 A2A between agents, MCP inside each agentdelegation crosses the boundary; tool calls stay inside it
MCP (5주차)A2A
요청을 받는 쪽server의 tool. 이름, 설명, 인자 형식이 공개된다원격 에이전트. 할 수 있는 일(skill)을 자연어로 소개한다
보내는 것tool 이름과 인자 (tools/call)메시지 (SendMessage). text, 파일, JSON 데이터

되묻기는 두 규격에 다 있다. 두 규격은 한 시스템 안에서 같이 쓰인다. 가게 에이전트는 A2A로 주문을 받고, 재고를 확인할 때는 자기 MCP server의 tool을 부른다(FIG. 01).

A2A는 서로의 내부를 모르는 에이전트들이 상대를 찾고(Agent Card), 일을 맡기고(task), 결과를 받는(artifact) 규격이다.

Google이 2025년 4월 9일 50곳 넘는 기술 파트너와 함께 공개했고, 2025년 6월 23일 Linux Foundation 프로젝트가 됐다. 현재 버전은 v1.0이다(v1.0.0은 2026년 3월 12일, v1.0.1은 5월 28일). 이 노트의 예시와 실습은 v1.0 규격과 Python SDK a2a-sdk 1.2.2로 확인했다.

A2

Agent Card: 일을 맡길 에이전트 찾기

A2A server는 Agent Card를 반드시 공개해야 한다(MUST). Agent Card는 에이전트의 이름, 설명, 요청을 받는 주소, 지원하는 기능, skill 목록을 담은 JSON 문서이고, 기본 위치는 https://{도메인}/.well-known/agent-card.json이다. 실습에서 띄울 가게 에이전트의 카드다.

GET http://127.0.0.1:9999/.well-known/agent-card.json
{
  "name": "Lamp Shop",
  "description": "Sells desk lamps, chairs and bookshelves. Negotiates the price with the buyer.",
  "supportedInterfaces": [
    { "url": "http://127.0.0.1:9999/", "protocolBinding": "JSONRPC", "protocolVersion": "1.0" }
  ],
  "version": "1.0.0",
  "capabilities": { "streaming": true },
  "defaultInputModes": ["text/plain"],
  "defaultOutputModes": ["application/json", "text/plain"],
  "skills": [
    {
      "id": "negotiate",
      "name": "Negotiate a purchase",
      "description": "Ask for an item, then send a price. The shop answers with a counteroffer or a receipt.",
      "tags": ["shopping", "negotiation"],
      "examples": ["I want to buy a lamp", "90"]
    }
  ]
}

supportedInterfaces는 요청을 받는 주소와 방식이다. v1.0에는 JSON-RPC, gRPC, HTTP+JSON(REST) binding이 정의돼 있고, server는 지원하는 것을 선호하는 순서대로 적는다. client는 이 목록에서 자기가 쓸 수 있는 첫 항목을 고른다. 실습 가게는 JSON-RPC만 지원한다.

skills는 에이전트가 할 수 있는 일을 사람이 읽는 말로 적은 목록이다. 5주차 tool과 달리 인자 형식(JSON Schema)이 없다. client 쪽 모델이 설명과 예시(examples)를 읽고 무엇을 어떻게 보낼지 정한다.

FIG. 02 Discovery, then the first messagethe card is a plain HTTP GET

client는 잘 알려진 주소(well-known URI) 말고도, 카드를 모아 둔 registry에서 찾거나 미리 설정해 둔 카드 주소를 쓸 수 있다.

FIPA에서는 에이전트 플랫폼의 Directory Facilitator(DF)가 이 일을 했다. 에이전트가 자기 서비스를 DF에 등록하고, 다른 에이전트는 서비스 종류로 DF를 검색했다(yellow pages). A2A에서는 에이전트마다 자기 도메인에 카드를 올리고, registry는 필요할 때 쓴다(FIG. 03).

FIG. 03 Directory Facilitator and Agent Cardthe directory became optional

카드의 내용은 에이전트를 만든 쪽이 직접 쓴다. 3주차 Contract Net의 bid, 5주차의 tool 설명도 그랬다. v1.0에서는 카드에 JWS 서명을 붙일 수 있어서, 카드를 누가 냈는지와 중간에 바뀌지 않았는지는 확인할 수 있다. 카드에 적힌 문장이 사실인지 확인하는 절차는 규격에 없다. 과제에서는 카드 문장 하나를 바꿔 그 효과를 잰다.

A3

Task: 맡긴 일의 상태와 결과물

client는 SendMessage로 메시지를 보낸다. server는 바로 답할 수 있는 질문이면 메시지 하나로 답하고, 시간이 걸리거나 말이 오가야 하는 일이면 task를 만들어 돌려준다. 실습 가게에 “I want to buy a lamp”를 보내면 이런 응답이 온다.

SendMessage 응답 (lab/logs/lab-first-response.json)
{
  "result": {
    "task": {
      "id": "d26f7b6c-2b2a-42ab-af06-9830cf278db5",
      "contextId": "0132caae-a7e3-409b-a0ea-4dbd35bfc5a3",
      "status": {
        "state": "TASK_STATE_INPUT_REQUIRED",
        "message": {
          "role": "ROLE_AGENT",
          "parts": [{ "text": "lamp: asking 130. Send your offer as a number." }],
          ...
        },
        "timestamp": "2026-10-11T10:47:11.822276Z"
      },
      "history": [
        { "messageId": "m1", "role": "ROLE_USER", "parts": [{ "text": "I want to buy a lamp" }], ... }
      ]
    }
  },
  "id": 2,
  "jsonrpc": "2.0"
}

id는 server가 만든 task 번호이고, 이 일에 대한 다음 메시지에는 이 번호를 taskId로 붙인다. contextId는 관련된 task와 메시지를 한 대화로 묶는 번호다. status에는 현재 상태와 가게가 한 말이, history에는 지금까지 오간 메시지가 들어 있다. 일이 끝나면 결과물이 artifacts에 붙는다(FIG. 04).

FIG. 04 What a task carriestalk goes in messages, results go in artifacts

가게의 말(“80 is too low”)은 status의 message로 오고, 거래 결과는 artifact로 온다. 규격은 결과물을 메시지에 담지 말고 artifact로 돌려주라고 적는다(SHOULD). 메시지와 artifact는 모두 Part로 이뤄진다. Part 하나에는 text, raw(파일 바이트), url(파일 주소), data(JSON 값) 가운데 하나가 들어가고, 내용의 형식은 mediaType에 적는다. 실습 가게의 영수증은 data Part라서 받는 쪽 코드가 price를 바로 꺼내 쓴다.

task 상태 값은 v0.3까지 input-required처럼 소문자와 하이픈으로 썼고, v1.0에서 TASK_STATE_INPUT_REQUIRED 형태로 바뀌었다. 인터넷의 예제 코드가 소문자 값을 쓰면 v0.3 기준이다.

상태뜻종류
SUBMITTED접수됨active
WORKING처리 중active
INPUT_REQUIREDclient의 입력을 기다리며 멈춤interrupted

interrupted 상태의 task는 client가 같은 taskId로 메시지를 보내면 다시 진행된다. terminal 상태의 task에는 메시지를 더 보낼 수 없고, 보내면 server가 오류를 돌려준다.

A2A는 위임의 조건을 적는 칸도 비워 두었다. 얼마까지 써도 되는지, 누구의 이름으로 사는지, 결과를 무엇으로 확인하는지를 task에 적을 곳이 없다. 실습 buyer의 예산은 buyer 쪽 모델의 system prompt에만 있다. 7주차에는 이 조건을 위임과 함께 넘기고 검증하는 계약을 만든다.

DISCUSSION: Agent Card의 주장을 누가 확인하는가
  1. 과제의 South Shop 카드에는 “lowest prices in town”이라고 적혀 있다. client의 모델, registry, 카드 서명, 거래 뒤에 쌓이는 평판 가운데 이 문장을 확인할 수 있는 것은 무엇인가. 3주차 overconfident contractor의 bid와 무엇이 같고 무엇이 다른가.
  2. A2A에서 “105”를 수락으로 읽을지는 가게 에이전트가 정한다. FIPA처럼 accept-proposal을 붙여 보내는 편이 나은 경우는 언제인가. 4주차 tagged 조건의 결과로 답한다.
  3. 원격 에이전트는 opaque하다. 거래가 잘못됐을 때 client가 증거로 남길 수 있는 것은 task history와 artifact뿐이다. 이것으로 누가 잘못했는지 가릴 수 있는가. 더 필요한 것은 무엇인가.
PART B: LAB

가게 에이전트를 A2A server로 띄운다

GOAL: run a rule-based seller as an A2A server, take one purchase from a message to COMPLETED with curl, and reach REJECTED and CANCELED once each
LAB

Lamp Shop을 띄우고 curl로 거래한다

모델 없이 규칙으로 값을 부르는 가게 에이전트를 a2a-sdk로 띄우고, curl로 카드를 받은 뒤 램프를 산다. 모델을 부르지 않으므로 API 키 없이 돌아간다. 가게는 처음에 하한가(reserve)의 1.3배를 부르고, reserve 이상의 값이 오면 거래를 끝낸다. 낮은 값이 오면 역제안하고, 낮은 값을 세 번 받으면 거래를 거절한다.

  1. SDK를 설치한다. pip install "a2a-sdk[http-server]" uvicorn. 참조 실행은 a2a-sdk 1.2.2, Python 3.12다. 다른 언어의 SDK를 써도 된다.
  2. server를 만든다. seller_agent.py. AgentExecutor의 execute가 메시지 하나를 받을 때마다 불리고, TaskUpdater로 task 상태를 바꾼다. 카드와 JSON-RPC 경로는 SDK의 route 함수가 만든다.
  3. 띄우고 카드를 받는다. python seller_agent.py로 http://127.0.0.1:9999에 띄우고, /.well-known/agent-card.json을 curl로 받는다.
  4. 헤더 없이 보낸다. A2A-Version 헤더를 빼고 SendMessage를 보낸다. 규격상 헤더가 없으면 server는 0.3 요청으로 해석해야 하고, 1.0만 받는 실습 server는 -32009(VersionNotSupportedError)로 거절한다.
  5. 램프를 산다. 헤더를 붙여 “I want to buy a lamp”를 보내고, 응답의 task id를 taskId로 붙여 80, 105를 차례로 보낸다. COMPLETED와 영수증 artifact가 온 뒤 GetTask를 보내면 history에 메시지 5개가 남아 있다.
  6. 끝난 task에 다시 보낸다. 같은 taskId로 110을 보내 -32004를 받는다.
  7. 나머지 terminal 상태를 만든다. 가게에 없는 sofa를 찾으면 REJECTED, chair에 100을 세 번 부르면 REJECTED, 거래 중인 bookshelf task에 CancelTask를 보내면 CANCELED가 된다.

class Seller(AgentExecutor):
    async def execute(self, context, event_queue):
        task = context.current_task
        if task is None:                                   # 첫 메시지: task를 만든다
            task = new_task_from_user_message(context.message)
            await event_queue.enqueue_event(task)
        up = TaskUpdater(event_queue=event_queue, task_id=task.id, context_id=task.context_id)
        say = lambda text: up.new_agent_message(parts=[new_text_part(text)])
        text = get_message_text(context.message) or ""
        deal = self.open.get(task.id)

        if deal is None:                                   # 어떤 물건인가
            item = next((k for k in self.cfg["reserve"] if k in text.lower()), None)
            if item is None:
                await up.reject(say("We only sell: ..."))        # REJECTED
                return
            ask = math.ceil(self.cfg["reserve"][item] * 1.3)
            self.open[task.id] = {"item": item, "ask": ask, "rounds": 0}
            await up.requires_input(say(f"{item}: asking {ask}. Send your offer as a number."))
            return

        offer = int(re.search(r"\d+", text).group())
        if offer >= self.cfg["reserve"][deal["item"]]:
            await up.add_artifact(parts=[new_data_part({"seller": ..., "item": ..., "price": offer})],
                                  name="receipt")
            await up.complete(say(f"Deal: {deal['item']} at {offer}."))   # COMPLETED
            return
        ...                                                   # 역제안(INPUT_REQUIRED) 또는 거절(REJECTED)

    async def cancel(self, context, event_queue):         # CancelTask
        task = context.current_task
        await TaskUpdater(event_queue=event_queue, task_id=task.id, context_id=task.context_id).cancel()
