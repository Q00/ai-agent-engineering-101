Modern Protocols 1: Model Context Protocol 현대 프로토콜 1: MCP

Who plugs in an agent's tools, and where? The week-01 agent kept its tool list and its tool code inside the agent. The Model Context Protocol (MCP) moves tools out into a separate server and lets any application use that server through messages in one fixed format. We turn the week-04 negotiation market into an MCP server and measure how limit violations change when the price limit lives only in the system prompt and when the token (a permission string sent with every request) carries it too.

A1

The structure of MCP: host, client, server

The week-01 agent kept both the tool descriptions and argument formats handed to the model (TOOLS) and the functions that actually run (TOOLS_IMPL) in its own code, so adding a tool means editing the agent, and using the same read_file from Claude Code or Codex means building it again for that application. With M applications and N tools, you need M×N pieces of glue code.

Anthropic released the Model Context Protocol on November 25, 2024. It moves tools out into a separate program, the server, and fixes the format of the messages an application and a server exchange. Whoever builds a tool writes a server once in that format, and whoever builds an application writes client code once in that format. The code needed drops to M+N.

FIG. 01 M × N adapters become M + N implementationsthe protocol sits between hosts and tools

The host is the application the user works in: Claude Code, Codex, Cursor, and the week-01 loop we modify in the lab are hosts. The host calls the model, and when the model asks for a tool, the host runs that tool on its behalf. The client is the code inside the host that holds the connection to one server. A host that uses three servers has three clients. The server is the program that offers tools and data in the fixed format. Because every connection has its own client, how it connects, which API key it uses, and whether an error happened are all kept per connection.

FIG. 02 Host, client, serverthe host runs the model; each client talks to one server

What a server offers (primitives) is tools, resources, and prompts. The specification separates them by who decides to use each one.

primitiveWhat it isWho chooses
toolsFunctions the model calls. They may change things outside, like writing a filemodel-controlled
resourcesData put into the model's input (the context): file contents, recordsapplication-controlled
promptsTemplates the user picksuser-controlled

MCP is a JSON-RPC specification through which a host discovers and uses the tools, resources, and prompts of external servers.

Model Context Protocol Specification, current revision 2026-07-28. On December 9, 2025 the specification moved from Anthropic to the Agentic AI Foundation (AAIF) under the Linux Foundation, co-founded by Anthropic, Block, and OpenAI.

A tool has a name, a natural-language description of what it does, and a JSON Schema saying which arguments it takes. The host hands the tool lists of its connected servers to the model, and the model reads the descriptions and decides which tool to call with which arguments. Set against week 03's Contract Net, a description plays the part of a contractor's bid, and the host's model plays the manager that decides the award. But a bid was made fresh for each task, while a description is written once by the server and used unchanged for every request. The counterpart of week 03's overconfident contractor is a server with an inflated description, and the specification has no step that filters such descriptions out.

A2

JSON-RPC messages, transports, the stateless revision

The messages host and server exchange are JSON, and which field holds what is fixed by a format called JSON-RPC 2.0. A request holds a request number (id), the function to call (method), and the values to pass (params). A response holds the same number (id) and a result (result) or an error (error). Start the lab's server over HTTP and you can send it requests yourself with the curl command in a terminal. Below are a tools/list request and its response, with the tool list cut to its first entry.

In the server code, the type on a function argument (expression: str) becomes inputSchema, and the explanation string on the function's first line (the docstring) becomes description. It is the same content as the TOOLS entries written by hand in week 01. When the model decides to call calculator, the host sends tools/call.

The way host and server exchange messages is called the transport. With stdio, the host runs the server program itself, writes requests to that program's standard input, and reads responses from its standard output. Standard input and standard output are the channels through which a program takes in and prints out text in a terminal. It is the way to go when host and server are on the same computer, and secrets such as API keys come in through environment variables, as in week 01.

MCP-METHOD, MCP-NAMEOver HTTP, every request carries an Mcp-Method header, and a tools/call also puts the tool's name in Mcp-Name. If a header is missing or disagrees with the body, the server rejects the request with 400 (HeaderMismatch). The rule lets the equipment in front of a server that routes or filters requests (a load balancer or gateway) see which tool is being called without opening the JSON.

With Streamable HTTP, the server opens one address like a web server (usually /mcp), and the host sends a POST to it for every request. The response comes back as one JSON body, or in pieces over SSE. This is the way to go when the server is on another computer or shared by many users. The specification's login and permission procedure (authorization) also exists only for HTTP. The meaning of tools/list is the same either way.

FIG. 03 Two transportssame messages, different path

In the current revision (2026-07-28), the server does not remember earlier requests. So each request carries everything needed to handle it. The protocol version and the client's feature list in the _meta of the tools/list request above are that information. Work that spans several calls, like one negotiation, gets a number (a handle) from the server, and the client sends that number along as a tool argument on every later call. The negotiation_id in the assignment is that number.

FIG. 04 From sessions to self-contained requestsstate rides in the arguments
BEFORE 2026-07-28Up to the 2025-11-25 revision, a client first sent initialize to open a session before it could send requests such as tools/list. The server remembered the client for the length of the session. The 2026-07-28 revision removed that step and the session.

A3

Elicitation and sampling: when the server needs to ask

A server running a tool sometimes needs more information. A calendar server adding an event may need to ask which calendar to use, or may need permission to reach the user's Google account. In the 2026-07-28 revision, the server then returns a result saying more input is needed (resultType: "input_required") instead of a final result. The client gets what was asked for and sends the original request again. The "resultType": "complete" in the earlier tools/list response marks a final result. The specification calls this pattern Multi Round-Trip Requests.

Elicitation is how a server asks the user. In form mode, the server sends the fields it wants and the client draws an input window from them. The window must show which server is asking, and the user must be able to edit the answer or decline before it is sent. Form mode must never ask for passwords, API keys, tokens, or payment details.

For those, the server uses URL mode. The server sends an address; the client shows where it leads, as in “calendar-server wants to open accounts.google.com”, asks for consent, and opens the browser. The user signs in to Google in the browser and grants the permission. What the user types there never passes through the client. All the client learns is the user's choice: accept (open), decline, or cancel (just closed). URL mode arrived in the 2025-11-25 revision.

FIG. 05 Elicitation: form mode and URL modethe user can always decline

The client's own permission to reach the MCP server comes from OAuth (A4). URL mode is for when the server needs permission from another service, such as Google Calendar, on the user's behalf.

Sampling runs the other way. It let a server borrow the client's model: the server sends a request such as “summarize this text”, and the client answers it with its own model. The server can use a model without an API key of its own. The price was a lot of work on the client side. A person had to be able to see and deny each request, and the client had to build a screen for reviewing and editing the prompt, logic for choosing a model, and handling for tools used inside sampling.

The specification scaled the feature back in steps. The 2025-11-25 revision told servers not to use the values that ask the client to add its conversation to the prompt ("thisServer" and "allServers" for includeContext). The 2026-07-28 revision deprecated sampling itself. The proposal (SEP-2577) gives its reasons: it is complex for clients to implement, few clients support it, and a server can call an LLM API directly. Roots and Logging were deprecated in the same revision. A deprecated feature stays in the specification and keeps working for at least twelve months, and may be removed after that.

FIPA-ACL arrived before there were agents to exchange messages with it. MCP came in the other order: hosts with tool calling existed first, and usage grew as those hosts added MCP. Monthly npm downloads of the TypeScript SDK (@modelcontextprotocol/sdk) went from 102,851 in December 2024, just after the release, to 204,541,524 in the 30 days from August 28 to September 26, 2026.

FIPA-ACL defined the meaning of a message through the sender's beliefs and intentions, and those intentions could not be checked from outside. In MCP, too, what the model intended when it called a tool cannot be checked. What a server can check is whether a call was authorized, and the specification has set out that procedure with OAuth 2.1 since 2025-03-26. It is the direction Singh (1998) proposed: move the meaning of a message from beliefs and intentions to commitments that can be checked from outside.

Click ‘Sign in with Google’ on a website and you are taken to a Google page where you sign in and agree to what the site may do. The site then receives a token issued by Google and attaches it to every later request. OAuth is the standard for this procedure. The side that takes consent and issues tokens is the authorization server; the side that checks tokens and hands out data is the resource server. In MCP, the MCP server is the resource server, and the client in the host obtains and uses the token.

The flow is FIG. 07. When a client sends a request without a token, the server returns a 401 error and, in the WWW-Authenticate header, the address of a document saying where to get a token (Protected Resource Metadata). The client finds the authorization server in that document and gets the user's consent. After consent it receives a one-time authorization code and trades it for a token. On the way it writes the server's address in the resource parameter, so the token works only for this server. From then on the token goes in the Authorization: Bearer header of every request.

Every token has a permitted range (scope). A request outside it gets 403 insufficient_scope and the scopes needed, and the client asks the user again for a wider scope (step-up).

2026-07-28 AUTHORIZATION RULESThe 2026-07-28 revision adds rules to this flow. If the authorization server's response carries iss (the authorization server's name), the client checks, before exchanging the authorization code for a token, that it matches the authorization server found through the Protected Resource Metadata (RFC 9207). Client credentials obtained from one authorization server are never used with another. For client registration, Client ID Metadata Documents are recommended over Dynamic Client Registration.
FIG. 07 Authorization in MCP, 2025-06-18 onwardthe server checks every request; the model never sees the token

An MCP server is an OAuth 2.1 resource server that checks the token on every request. The server decides whether the token was issued for it and whether its scope is enough.

“MCP servers MUST validate that access tokens were issued specifically for them as the intended audience.” MCP Specification 2026-07-28, Authorization, Token Handling.

The week-01 discussion asked, with the Bitter Lesson in mind (Sutton's claim that knowledge built in by hand keeps losing to general methods that scale with computation and data), whether protocols are ‘hand-built knowledge’ that larger models will absorb. In MCP the answer differs by task. Reading tool descriptions and choosing which tool to call with which arguments gets better as models improve. Checking the token is done by server code, so its result is the same whatever the model's ability.

The assignment compares leaving the price limit to the model with leaving it to the server. With the limit only in the system prompt, the model has to keep it on its own; with the limit also in the token, the server refuses moves outside it.

A5

Running MCP: context, descriptions, traffic

CONTEXTSub-agents and disposable context

A model sees only its context, the text it takes in as input at one time. When a host connects a server, every tool name, description, and JSON Schema of that server goes into this context. The more servers you attach, the less room is left for the actual work. That is why Claude Code does not load every tool definition up front and instead searches for and loads them when needed (tool search).

A sub-agent is an agent the main agent starts to hand off a piece of work. The sub-agent starts from an empty context, reads files, runs commands, and checks the results. When it finishes, it returns only the result to the main agent and throws its own context away. Because the context is used and then thrown away (a disposable context), only the sub-agent's result stays in the main context. Since only the result comes back, a result in a broken format leaves the main agent unable to see what went wrong. Give the sub-agent a result format, and have the main agent check it.

An MCP server can do the same. The server's tool runs another agent inside (for example codex exec) and returns only the finished result. To the main agent it is one tool call, and the context that other agent used never enters the main context. Handing work to another company's model (model orchestration) works this way too. Claude Code itself can become an MCP server with claude mcp serve. Because the server sits outside the session, it can also relay messages between sessions or keep a record of the path the main session took (its trajectory).

FIG. 08 Keeping work out of the main contextonly results come back

DESCRIPTIONImproving tool descriptions from trajectories

The model reads a tool's description to decide which tool to call, so writing good descriptions falls to the server author. A description can be revised by looking at run records. A tracing tool such as Langfuse records, for every run, which tool the agent called with which arguments and what came back, and success is attached as a score. The whole record of one run is called a trajectory.

GEPA (Agrawal et al., 2025) has a model read trajectories and write down in natural language why they failed, revises the prompt from that, and tests again. Meta-Harness (Lee et al., 2026) goes wider than prompts and revises the harness code itself, looking at earlier candidates' code, scores, and run records. Tool descriptions can be revised the same way: collect the calls that ended in failure across tens of thousands of runs, find how the model misread the description, and rewrite it.

What the revision aims at decides the outcome. If the aim is task success, the description moves toward what the tool really does. If the aim is how often the tool gets chosen, the description inflates into “this is a silver bullet”, and week 03's overconfident contractor is back. You could add a tool such as get_feedback and have agents rate tools, but those ratings are the model's own words and, like week 03's confidence scores, hard to trust.

FIG. 09 Improving a tool description from trajectoriesthe target shapes the description

TRAFFICclientInfo and traffic control

The 2026-07-28 revision recommends that the client write its name and version (clientInfo) in _meta on every request. It is a value much like the User-Agent a web browser sends with every request. You might want to use it to find and block an agent that floods the server. But the specification says clientInfo is written by the sender itself and never verified, so it must not be used for security decisions. clientInfo is for logs and debugging only.

What to block on is the token. Put a proxy, a server that receives requests and passes them on, in front of the MCP server: it counts requests per token and limits them, and it holds the overflow in a queue and passes it on at the pace the server can handle. The queue can be a message queue such as Kafka, and checking tokens is left to the authorization server. The Mcp-Method and Mcp-Name headers in the A2 note exist for proxies like this. The setup lies outside the MCP specification: it puts the ordinary methods of web services in front of an MCP server.

DISCUSSION: The Bitter Lesson and running MCP
  1. Reading descriptions to pick a tool, sending tools/call as JSON-RPC, checking the token: which of these would a larger model make unnecessary, and which would remain?
  2. Who should filter out a server with an inflated description, like week 03's overconfident contractor: the host, a registry (a place that collects lists of servers), or the user? Is it the same problem as week 04's sincerity (never being able to check that a sender believes what it says)?
  3. In a week-04 FIPA message, :sender was a field the sender filled in. In MCP the caller is determined by the token. If one person put the same token into both Claude Code and Codex, could the server tell the two agents apart? If it should, what else is needed?
  4. If you add a tool such as get_feedback that lets agents rate tools, may you revise descriptions from those ratings? What is the same as week 03's confidence scores, and what is different?
  5. If clientInfo cannot be used to block, what should a server block on when one person starts ten thousand agents that send it requests?

HW

The negotiation market as an MCP server: where the limit lives

Move the week-04 negotiation onto an MCP server. The market is the server, and the buyer and the seller each connect to it through a host. The four week-04 acts become the tools propose(negotiation_id, price), accept_proposal, reject_proposal, and refuse. The tool name carries the kind of act and an integer argument carries the price, so the week-04 reader (the model that read free-text messages into an act and a price) is not needed. get_negotiation, which reads the state of the negotiation, is added.

The server decides the following itself, before any model is involved.

IdentityWhether the caller is the buyer or the seller is decided by the token in the request header (the bearer token). No tool has a sender argument. Without a token, HTTP 401.
NegotiationA token is bound to one negotiation. A call with any other negotiation_id is a tool error. The specification's security document (Security Best Practices) also says not to allow a call just because the caller knows a handle like negotiation_id, and to bind the handle to the token's owner (State Handle Hijacking).
TurnA move out of turn is a tool error.

The runner (the script that drives the negotiation) opens negotiations. When the runner sends a scenario and a condition to POST /admin/open, the server returns a negotiation_id and a pair of tokens, one for the buyer and one for the seller. This route is not in the MCP tool list, so agents cannot call it. One server holds many negotiations at once, and the two hosts of each negotiation call the same server's tools with their own tokens. Turns alternate, starting with the buyer.

An attack that changes the model's decision through a sentence mixed into a tool result is called indirect prompt injection. The specification's Security Best Practices document does not cover this attack. The attacks it does cover, confused deputy, token passthrough, SSRF, and state handle hijacking, are ones that server and client code can stop.

The system prompts of the four conditions are identical. The only signal an agent has about its condition is the server's refusal message.

One turn is one host run. The runner starts the host for the side whose turn it is, with that side's token; the agent reads the negotiation with get_negotiation and makes one move. When the host ends without a valid move, the runner passes the turn. The runner opens the negotiation and mints the tokens through an admin HTTP route that is not an MCP tool. The host is your choice: the lab's week-01 host with an Authorization header, or claude -p or codex exec run headless (from a single command, with no interface) with the server attached.

class PartyTokens:                       # TokenVerifier: only tokens the runner minted pass
    async def verify_token(self, token):
        grant = TOKENS.get(token)            # {role, negotiation_id, limit}
        return AccessToken(token=token, client_id=grant["role"], scopes=["negotiate"],
                           resource=f"{BASE}/mcp", claims=grant) if grant else None

mcp = MCPServer("market", token_verifier=PartyTokens(),

                                  required_scopes=["negotiate"], validate_token_resource=True))
